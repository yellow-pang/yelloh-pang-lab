## 한 줄 요약

ComfyUI는 이미지·영상·음성 등의 생성 과정을 노드 그래프로 구성하고 실행하는 AI 작업 엔진이다.
노드는 모델 불러오기나 텍스트 변환처럼 한 단계의 일을 맡는 블록이며, 선은 단계 사이에 전달되는 자료를 나타낸다.
자체 이미지 모델 하나를 뜻하는 이름이 아니라 여러 모델과 처리 단계를 연결하는 UI·API·백엔드다.[1]

## 프롬프트 한 줄 뒤의 과정을 드러내기

이미지를 만들 때도 텍스트를 읽는 모델, 생성 모델, 해상도, 무작위 시작값, 저장 방식이 함께 필요하다.
한 개 버튼 뒤에 숨기면 간단하지만, 어느 부분을 바꿔 결과가 달라졌는지 추적하기 어렵다.
ComfyUI는 이 단계를 연결 관계로 표현하고 워크플로를 다시 저장·불러오는 방식을 제공한다.
같은 절차를 반복하거나 한 부분만 바꾸어 비교하려는 상황을 위한 구성이다.[1]

README는 부분 그래프 재실행, 비동기 큐, 모델 메모리 관리, 사용자 노드 확장을 소개한다.
큐는 작업을 실행 순서에 맞게 대기시키는 장치다.
다만 이런 기능이 있다는 설명과 모든 모델을 같은 하드웨어에서 빠르게 실행한다는 주장은 다르다.
특히 README의 최적화·메모리 관련 강한 표현은 저자의 소개이며 이번 조사에서 측정한 성능은 아니다.[1]

## 기본 이미지 흐름을 구성하는 블록

공식 `basic_api_example.py`에는 기본 워크플로의 API 표현이 들어 있다. `CheckpointLoaderSimple`은 모델 파일을 선택하고 `CLIPTextEncode` 두 개는 긍정·부정 텍스트 조건을 만든다. `EmptyLatentImage`는 생성할 잠재 이미지의 크기와 묶음 수를 정한다.
잠재 표현은 바로 보이는 픽셀이 아니라 모델이 처리하는 중간 자료로 이해하면 된다.[2]

`KSampler`는 모델과 텍스트 조건, 잠재 입력을 받아 생성 처리를 진행하는 블록으로 연결되어 있다.
예제에는 seed·steps·sampler·scheduler 등의 값이 들어간다.
seed는 무작위 시작 상태를 정하는 값이며, 값을 기록하는 것은 결과 조건을 비교하는 데 도움이 된다.
그러나 seed만 같으면 어떤 환경에서도 파일이 완전히 같아진다는 보증은 이 예제에 없다.[2]

그다음 `VAEDecode`가 잠재 자료를 이미지 쪽으로 바꾸고 `SaveImage`가 저장 단계로 이어진다.
연결은 노드 번호와 출력 위치의 쌍으로 표현된다.
화면의 선이 API에서는 참조 값으로 바뀌는 셈이다.
따라서 API의 prompt는 자연어 문장 하나가 아니라 노드 종류·입력·연결을 담은 전체 작업 정의를 가리킨다는 점이 중요하다.[2]

`nodes.py`의 `CLIPTextEncode`는 text와 clip을 필수 입력으로 선언하고 CONDITIONING을 출력한다.
실제 함수는 텍스트를 토큰으로 바꾼 뒤 인코더에 전달하며 clip 입력이 없으면 명확한 오류를 낸다.
토큰은 모델이 처리하도록 나눈 텍스트 단위이고 conditioning은 생성 방향을 안내하는 조건 자료다.
노드의 화면 이름만이 아니라 입출력 계약이 코드에 있는 구조다.[3]

## 예시로 따라가는 흐름

공식 API 예제를 실행하지 않고 읽어보면, 먼저 기본 워크플로 JSON을 Python 객체로 바꾼다.
그 안에는 모델 파일명, 512×512 잠재 이미지, 텍스트 인코더, 샘플러, 디코더와 저장 노드가 이미 연결되어 있다.
이후 예제는 긍정 텍스트를 다른 문장으로 바꾸고 샘플러의 seed를 5로 지정한다.
이 값들은 예제에 적힌 설정이지 이번에 생성한 이미지의 조건 보고가 아니다.[2]

`queue_prompt`는 워크플로를 `{"prompt": ...}` 형태로 싸서 UTF-8 JSON으로 만들고 로컬 서버의 `/prompt`에 보낸다.
UI에서 File → Export (API)로 특정 작업의 API 형식을 얻을 수 있다는 주석도 있다.
즉 화면에서 만든 연결을 매번 프로그램으로 다시 손으로 구성할 필요 없이 실행 요청 자료로 옮길 수 있다는 안내다.[2]

이 스크립트의 끝은 큐에 요청을 보내는 호출이다.
작업의 최종 완료를 기다리거나 생성 파일을 검사하는 코드는 이 예제에는 없다.
따라서 요청이 보내졌다는 사실과 원하는 이미지가 만들어졌다는 확인을 구분해야 한다.
사람이 검토할 것은 모델 파일의 존재와 호환성, 노드 연결, 생성 결과와 저장 위치다.
이 글에는 실행하지 않은 이미지나 임의의 생성 시간을 결과로 제시하지 않는다.[2]

## 코어·화면·모델 파일은 별개다

README는 ComfyUI Core, Desktop, Frontend를 서로 연결된 별도 저장소로 설명한다.
이 저장소의 Python 노드 구현을 읽었다고 데스크톱 패키지의 모든 설치 동작이나 프런트엔드 전체를 검증한 것은 아니다.
모델도 별도 파일이며 큰 모델은 여러 구성 파일을 알맞은 하위 폴더에 배치해야 할 수 있다.
같은 워크플로 파일만 받아도 모든 실행 준비가 끝나는 것은 아니다.[1]

오프라인 실행은 코어가 요청하지 않은 다운로드를 하지 않는다는 안내와 함께 제공된다.
선택적 유료 API 노드는 별도이며 이를 끄는 옵션도 README에 있다.
공식 API 예제 역시 API 노드를 포함한 작업에는 추가 데이터에 키를 전달할 수 있다고 주석으로 안내한다.
그러므로 로컬 UI를 사용한다는 사실만으로 모든 노드가 무료·오프라인이라고 판단하면 안 된다.[1][2]

사용자 노드는 확장성을 주지만 추가 코드와 의존성이기도 하다.
README는 안정 릴리스 태그 밖의 커밋이 불안정하거나 사용자 노드를 깨뜨릴 수 있다고 경고한다.
모델·워크플로·노드·코어 버전의 조합을 함께 확인해야 하며, 생성한 콘텐츠의 이용 조건도 선택 모델의 라이선스와 원본 자료 권리에 따라 따로 검토해야 한다.[1]

## 정리

ComfyUI는 생성 과정을 블록과 연결로 드러내고 같은 정의를 UI와 API로 다루게 한다.
작업 정의, 모델 파일, 실제 실행 결과는 서로 다른 산출물이다.
노드 연결이 준비되었거나 요청이 큐에 들어갔다는 것만으로 결과 품질과 호환성이 확정되지는 않는다.
