## 한 줄 요약

turbovec는 TurboQuant 계열 압축을 사용하는 Rust 벡터 인덱스이며 Python에서도 호출할 수 있다.
벡터는 글이나 이미지의 특징을 숫자 배열로 표현한 자료이고, 인덱스는 질의와 가까운 벡터를 찾도록 저장·검색하는 구성이다.
이 프로젝트가 문서를 스스로 이해해 임베딩을 만들거나 답변을 생성하는 것은 아니다.
이미 만든 벡터를 로컬에 보관하고 유사도 검색하는 단계에 해당한다.[1]

## 많은 숫자를 저장하면서 검색하기

문서 검색에 임베딩을 사용하면 문장마다 긴 숫자 배열을 보관해야 한다.
원래 정밀도의 숫자를 모두 유지하는 대신 작은 코드로 바꾸면 메모리 부담을 줄일 수 있지만, 정보가 일부 사라져 검색 순위가 달라질 수 있다.
이처럼 값을 제한된 대표 값으로 바꾸는 처리를 양자화라고 한다.
turbovec는 이 압축과 검색의 균형을 다루며, README의 메모리·속도 비교는 프로젝트가 제시한 측정 조건에 따른 주장이다.[1]

기본 사용 흐름은 인덱스 생성, 벡터 추가, 질의 검색, 저장과 다시 읽기다.
별도 학습 단계를 필수로 요구하지 않는 TurboQuant와, 표본으로 좌표별 보정을 하는 선택형 TQ+를 구별한다.
API 문서는 `calibrate`를 호출하지 않은 인덱스도 동작하며 자동으로 보정을 학습하지 않는다고 명시한다.
따라서 학습 단계가 없다는 소개와 표본 보정 기능이 있다는 설명은 서로 모순이라기보다 기본 경로와 선택 경로의 차이다.[1][2]

## 회전과 작은 코드, 검색 점수의 관계

README의 개념 설명은 먼저 벡터의 길이와 방향을 구별하고, 같은 변환을 적용한 좌표들을 대표 값 구간에 배정한 뒤 비트 단위로 묶어 저장하는 흐름이다.
검색할 때 질의도 대응하는 좌표계로 옮기고, 모든 원본 벡터를 복구하는 대신 압축된 코드와 코드북을 이용해 점수를 계산한다.
코드북은 작은 코드가 어떤 대표 값을 뜻하는지 정한 표다.[1]

대표 구현 `encode.rs`에서도 `encode`가 회전된 작업 자료를 만들고 `encode_prerotated`로 넘기는 구성을 확인할 수 있다.
보정이 없으면 이동량과 배율을 항등 변환으로 준비하고, 비트 폭에 따라 양자화·패킹 경로를 선택한다.
별도 크기 정보와 점수 보정용 값을 함께 보관하므로 압축 코드를 원본 숫자의 단순 축약본으로만 이해하면 부족하다.
이 파일의 구현을 읽은 것이 수학적 성능 보장 전체를 독립 증명한 것은 아니다.[3]

검색에는 SIMD라는 CPU 기능을 사용한다.
같은 종류의 연산을 여러 숫자에 동시에 적용하는 방식이며, README는 ARM과 x86의 여러 구현 및 대체 경로를 설명한다.
특정 커널의 존재가 모든 장치에서 같은 검색 속도를 뜻하지는 않는다.
데이터 차원, 비트 폭, CPU, 스레드 설정과 반환 개수를 맞춰 비교해야 한다.[1]

## ID를 유지하는 방법과 필터의 의미

`TurboQuantIndex`는 벡터의 내부 위치를 식별자로 사용한다. `swap_remove`로 삭제하면 마지막 벡터가 빈 위치로 이동하므로 위치 번호를 외부 문서 ID처럼 영구 보관하면 어긋날 수 있다. `IdMapIndex`는 외부 `uint64` ID와 내부 위치 사이의 대응표를 유지하여 삭제 뒤에도 문서 식별자를 안정적으로 쓸 수 있게 한다.[2]

검색 대상 제한도 두 형식이 다르다.
기본 인덱스는 위치별 참·거짓 마스크를, ID 인덱스는 허용할 ID 목록을 받는다.
마스크는 자료 변경 뒤 다시 만들어야 한다.
삭제와 추가로 길이가 원래와 같아져도 같은 위치가 다른 벡터를 가리킬 수 있기 때문이다.
허용 목록은 외부 ID를 사용하며, 없는 ID나 빈 목록에는 문서에 명시된 오류 조건이 있다.
검색 후 결과를 버리는 방식과 검색 과정에서 허용 후보만 넣는 방식도 구별한다.[2]

## 예시로 따라가는 흐름

공식 API 예제는 문서 벡터에 `1001`, `1002`, `1003` 같은 외부 ID를 붙이고 `IdMapIndex`에 추가하는 흐름을 보여준다.
이를 개인 공개 문서 검색에 대응시키면, 입력은 같은 임베딩 모델로 만든 문서 배열과 질의 배열이다.
이 설명의 문서 검색 상황은 이해를 위한 가상 예시이며 직접 실행한 결과가 아니다.
벡터 값이나 검색 점수를 만들어 제시하지 않는다.[1][2]

먼저 배열의 자료형이 `float32`인지, 차원이 인덱스와 같은지 확인한다.
ID는 벡터 행 수와 맞는 `uint64` 배열이어야 하고 중복될 수 없다.
이후 추가한 자료를 질의하면 점수와 외부 ID가 돌아온다.
공개 여부나 주제로 후보를 좁히고 싶으면 별도 목록에서 허용 ID를 정한 뒤 검색에 전달한다.
이때 허용 조건의 판단 자체는 호출자가 맡고, 인덱스는 전달된 후보 범위 안에서 검색한다.
반환 ID로 원문을 다시 찾는 연결도 바깥 애플리케이션의 책임이다.[2]

문서 하나를 지운 뒤에는 그 ID가 허용 목록에 남아 있는지 확인해야 한다.
내부 위치 기반 마스크였다면 변경 후 다시 구성해야 하지만 ID 목록에서는 사라진 ID를 정리하는 문제가 된다.
마지막에 `write`로 전체 파일을 저장하거나 `sync`로 변경분 저장 경로를 사용하고, 다시 읽은 인덱스와 문서 ID 대응이 맞는지 확인하는 순서가 된다.
저장 성공만으로 원문 저장소와의 일관성이 자동 보장되는 것은 아니다.[1][2]

## 압축을 선택할 때 남는 확인 사항

API 기준 지원 비트 폭은 2·3·4이고 차원은 양의 8의 배수이며 상한이 있다.
입력에 NaN·무한대나 지나치게 큰 값이 있으면 거부하며 다른 자료형을 조용히 변환하지 않는다.
이런 조건을 무시하고 임베딩 배열을 넘기면 검색 품질 이전에 입력 검증에서 막힐 수 있다.[1][2]

TQ+ 보정에서는 대표성 있는 무작위 표본이 중요하다.
API 문서는 한쪽에 치우친 표본으로 보정하면 재현율이 악화될 수 있고, 이미 잘려 사라진 좌표 정보는 나중 보정만으로 복원하지 못한다고 경고한다.
가능하면 벡터를 넣기 전에 보정하라는 안내도 있다.
재현율은 정확한 검색이 찾을 결과를 얼마나 다시 찾는지 보는 지표이며, 압축률과 함께 확인할 대상이지 높은 값이 모든 검색 과제에서 유지되는 보장은 아니다.[2]

로컬 인덱스라는 점은 임베딩 생성이나 상위 프레임워크까지 자동으로 오프라인이라는 의미가 아니다.
실제 데이터 경계는 결합한 모델과 호출 경로까지 따져야 한다.
저장 내구성 옵션, 자료 복구와 성능 비교도 이번에 실행 시험하지 않았다.

## 정리

turbovec는 벡터를 압축해 로컬에서 검색하는 라이브러리다.
선택의 중심은 원본 대비 정보 손실, 안정적인 문서 ID, 후보 필터와 저장의 의미이며, 임베딩 생성과 답변 품질은 별도의 구성에서 결정된다.
