## 한 줄 요약

Cline은 프로젝트 파일을 읽고 수정하며 명령을 실행하는 코딩 에이전트다.
편집기의 자동 완성 기능만을 뜻하지 않으며, 공통 에이전트 엔진을 IDE 확장·터미널·데스크톱 앱·SDK에서 사용하도록 구성한다.
SDK는 개발자가 같은 엔진을 자신의 프로그램에서 호출하기 위한 인터페이스다.[1]

## 제안한 코드와 실제 작업 사이

개발 요청은 대개 코드 한 조각을 받는 것으로 끝나지 않는다.
어느 파일을 바꿔야 하는지 찾고, 다른 파일과의 관계를 확인하고, 빌드나 테스트 결과를 읽어야 한다.
Cline은 이런 작업에서 모델의 판단과 파일·터미널 도구를 연결한다.
README는 여러 파일의 협조된 수정, 컴파일러·린터 오류 관측, 변경 차이와 체크포인트를 통한 검토를 소개한다.[1]

린터는 정해진 코드 규칙을 검사하는 도구이며, diff는 수정 전후의 차이를 보여주는 표현이다.
에이전트가 오류를 고치겠다고 답한 사실과 실제 파일이 바뀌고 검사가 통과한 사실은 별도다.
Cline의 작업을 이해할 때는 최종 자연어 설명뿐 아니라 도구 출력과 변경 내용을 함께 보는 흐름이 중요하다.[1]

## Plan과 Act, 승인 정책은 다른 축이다

Plan 모드는 코드 조사와 질문, 전략 수립을 위한 경로이고 Act 모드는 계획을 실행하는 경로다.
README는 파일 편집과 명령 실행에 승인 절차를 제공하면서 자동 승인도 선택할 수 있다고 설명한다.
따라서 Cline이 언제나 매 행동마다 사람을 기다린다고 일반화하면 안 된다.[1]

CLI 문서에서는 대화형 TUI, 한 번 요청하고 종료하는 one-shot, NDJSON 이벤트를 출력하는 JSON 모드, 승인을 생략하는 yolo, 배경 작업으로 넘기는 zen을 구분한다.
NDJSON은 한 줄에 JSON 이벤트 하나씩 내보내는 형식이라 다른 프로그램이 순서대로 소비하기 좋다.
인터페이스 모양뿐 아니라 종료 시점과 승인 방식이 달라지므로 실행 목적에 맞는 모드를 명시해야 한다.[2]

대화형 화면에서 계획을 읽는 사용법과 CI에서 사람이 없는 상태로 실행하는 사용법은 같은 안전 조건을 갖지 않는다.
조회한 CLI는 기본 설정부터 도구 호출을 자동 승인한다.
도구 실행 전에 사람이 검토하려면 `--auto-approve false`를 명시해야 한다. `--yolo`는 승인 프롬프트를 생략하고 턴이 끝나면 종료하는 모드로 안내된다.
따라서 `--yolo`를 쓰지 않았다는 사실만으로 매번 승인을 기다릴 것이라고 생각하면 안 된다.
예시 명령을 복사하기 전에 무엇을 허용하는지 읽어야 하는 이유다.[2]

## 규칙과 외부 도구의 확장

`.clinerules`는 프로젝트의 코딩 관례나 테스트 요구사항 같은 지침을 전달한다.
Skill은 필요할 때 특정 지침을 읽도록 하는 경로이고, SDK 플러그인은 도구와 실행 수명 주기의 hook을 등록하는 코드 확장이다.
MCP 서버는 데이터베이스나 API 등 별도의 외부 기능을 연결한다.
네 가지 모두 “확장”이라 불리지만 문서 지침과 실제 실행 권한은 다르다.[1]

README의 배포 도구 예제는 `createTool`로 이름, 설명, 입력 스키마, 실행 함수를 만들고 Agent에 넘긴다.
예제 안의 실제 배포 로직은 주석으로 남겨져 있으므로 그 짧은 코드가 곧 작동하는 배포 시스템은 아니다.
도구의 입력 형식을 정의하는 부분과 외부 시스템을 변경하는 구현을 분리해서 읽어야 한다.[1]

## 예시로 따라가는 흐름

공식 SDK Quickstart는 에이전트 하나에 프롬프트 하나를 보내 응답을 표준 출력으로 흘려보내는 최소 예제다.
시작점은 공급자와 모델을 지정한 `Agent` 생성이고, 다음으로 `assistant-text-delta` 이벤트를 구독한다.
delta는 완성된 응답이 아니라 새로 들어오는 텍스트 조각을 뜻한다. `agent.run()`을 호출하면 이 이벤트를 통해 답변이 순차적으로 출력되고, 끝나면 토큰 사용량을 표시하도록 설명되어 있다.[3]

이 예시를 읽으면 SDK의 중심이 “최종 문자열을 한 번 받기”에만 있지 않다는 것을 알 수 있다.
호출을 시작하는 부분, 진행 중 이벤트를 보여주는 부분, 종료 후 사용량을 확인하는 부분이 나뉜다.
예제는 대화형 CLI나 사용자 정의 도구의 전체 구현을 보여주지는 않고, 해당 목적은 다른 예제로 안내한다.
사람은 공급자 인증과 모델 설정이 맞는지, 출력 이벤트와 종료가 구분되는지, 실제 도구 행동이 있었는지를 별도로 확인해야 한다.
이 글에서는 Quickstart를 실행하지 않았으며 응답 내용이나 토큰 수를 만들어 제시하지 않는다.[3]

일반 코딩 작업으로 확장할 때도 같은 구분이 적용된다.
“테스트를 실행하고 실패를 수정하라”는 README의 요청은 테스트 결과를 실제로 읽는 과정이 필요하다.
답변이 스트리밍되었다는 사실만으로 검증이 수행되었다고 판단하면 안 된다.
파일 변경·명령 출력·체크포인트는 사용자가 작업 결과를 검토하는 서로 다른 자료다.[1]

## 실행 권한과 공개 범위

Cline의 터미널 기능은 설치, 빌드, 테스트뿐 아니라 배포나 데이터베이스 관리에도 사용될 수 있다고 소개된다.
자동 승인이나 예약 작업을 켜면 영향 범위가 커지므로 작업 폴더, 비밀정보, 외부 서비스 접근, 유료 모델 한도를 구분해야 한다.
다른 모델을 연결할 수 있다는 사실은 모든 모델이 같은 도구 수행 능력과 비용을 가진다는 뜻이 아니다.[1]

저장소의 공개 소스 범위에도 차이가 있다.
README는 Apache 2.0을 안내하면서 JetBrains 플러그인 소스는 현재 공개하지 않는다고 명시한다.
공통 엔진을 사용한다는 설명과 모든 클라이언트 구현을 여기서 검토할 수 있다는 주장은 같지 않다.[1]

CLI 문서상 비대화형 OAuth 실행에서 저장된 인증이 없으면 숨은 브라우저 인증을 시작하지 않고 실패를 반환한다.
자동 실행 전에 인증을 준비해야 한다는 실제 제약이다.
Quickstart의 소스 실행 요구사항과 배포된 CLI 바이너리의 요구사항도 같은 것으로 섞어 적지 않아야 한다.[2][3]

## 정리

Cline은 언어 모델을 프로젝트의 실제 도구 작업과 연결하고 여러 인터페이스로 제공한다.
계획과 실행을 나누되 승인 정책은 별도로 설정할 수 있으며, 코드 변경과 검증 근거를 확인하는 책임은 여전히 중요하다.
