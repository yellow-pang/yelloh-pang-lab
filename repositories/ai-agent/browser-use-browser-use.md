## 한 줄 요약

Browser Use는 언어 모델이 브라우저의 상태를 읽고 다음 조작을 선택하도록 연결하는 에이전트 프로젝트다.
Python 라이브러리로 자기 코드 안에서 실행하는 경로와 기존 에이전트에 브라우저를 붙이는 CLI, 에이전트까지 맡기는 호스팅 API를 README에서 구분한다.
이 글의 중심은 공개 Python 라이브러리와 대표 브라우저 연결 예제다.[1]

## 자연어 요청을 브라우저 조작으로 연결한다

웹에서 정보를 찾는 일은 질문을 한 번 보내는 것으로 끝나지 않는다.
페이지를 열고 검색 결과를 살핀 뒤 다시 다른 화면으로 이동해야 할 수 있다.
Browser Use의 라이브러리 예제는 이 작업 목표를 `task`로, 판단을 맡을 모델을 `llm`으로 지정하고 `Agent.run()`을 호출하는 형태다.
모델의 텍스트 답변과 실제 브라우저 조작 사이를 에이전트 실행기가 연결한다.[1]

여기서 브라우저와 모델은 서로 다른 구성 요소다.
브라우저는 페이지와 로그인 상태를 제공하고, 모델은 받은 상태와 목표를 바탕으로 행동을 고른다.
클라우드 브라우저를 선택한다고 에이전트 실행까지 자동으로 같은 호스팅 서비스에 맡기는 것은 아니다.
README는 로컬 실행 코드가 클라우드 브라우저에 연결되는 경우와 완전 호스팅 API를 명시적으로 나눈다.[1]

## 상태 관측·행동 선택·결과 기록의 반복

대표 구현 `browser_use/agent/service.py`의 `step`은 한 단계에서 문맥 준비, 모델 출력 획득, 행동 실행, 후처리를 순서대로 호출한다.
문맥은 모델이 다음 결정을 위해 받는 정보 묶음이다. `_prepare_context`에서는 현재 브라우저 상태 요약을 요청하고 이전 행동 결과, 페이지별 사용 가능한 행동, 관련 파일 정보 등을 메시지 구성 단계에 전달한다.[2]

상태를 받은 모델의 출력은 `_get_next_action`에서 다루고, `_execute_actions`는 그 출력에 들어 있는 행동 목록을 실행한 뒤 결과를 저장한다.
다음 단계의 준비가 이전 결과를 필요로 하므로, 구현은 문맥 준비를 끝낸 후 지난 모델 출력과 결과를 비운다.
이런 순서는 타임아웃이 나더라도 오래된 결과를 새 단계의 결과처럼 취급하지 않도록 하려는 코드상의 경계다.[2]

후처리는 다운로드 확인, 계획 상태 갱신, 반복 행동 감지용 기록, 실패 횟수 처리와 최종 결과 표시를 포함한다.
모델 호출에 제한 시간을 두고 중단 상태를 확인하는 부분도 보인다.
따라서 브라우저 자동화는 한 번의 거대한 프롬프트가 아니라, 상태를 갱신하며 여러 번 판단하고 실패를 처리하는 실행 흐름으로 읽어야 한다.[2]

인증된 화면에 접근하는 예제도 있다. `real_browser.py`는 시스템 Chrome 프로필 목록을 보여 주고 사용자가 고른 프로필 디렉터리를 `Browser.from_system_chrome`에 넘긴다.
이어 그 브라우저 객체를 `Agent`에 전달한다.
새 브라우저를 열기만 하는 것과 기존 로그인 환경을 사용하는 것은 다르며, 이 예제는 후자의 연결 지점을 보여 준다.[3]

## 예시로 따라가는 흐름

README의 최소 예제는 browser-use 저장소의 Star 수를 찾아 달라는 요청이다.
입력은 자연어 목표와 선택한 모델이며, 필요하면 브라우저 구성도 전달한다.
코드가 `Agent.run()`을 기다린 뒤 `history.final_result()`를 출력하는 것으로 이어진다.
여기서 설명하는 것은 공식 예제의 흐름이며 직접 실행한 결과가 아니다.
실제 Star 수나 걸린 시간을 이 글에서 결과로 제시하지 않는다.[1]

구현을 함께 읽으면 이 짧은 코드 뒤의 중간 과정이 보인다.
에이전트는 페이지 상태를 받고, 모델이 고른 행동을 실행한 뒤 그 결과를 다음 판단에 반영한다.
목표 저장소로 이동했는지, 표시된 수치가 원하는 항목인지, 페이지가 아직 로딩 중인지 같은 구분은 최신 상태를 보며 진행해야 한다.
완료 시 반환되는 답은 실행 이력에서 꺼내지만, 사람이 해당 페이지와 관측 시점을 확인해야 값의 의미를 검토할 수 있다.[2]

로그인이 필요한 개인 허가 범위의 작업이라면 별도 연결 예제의 프로필 선택이 앞단에 추가될 수 있다.
이때는 어떤 프로필을 골랐는지와 자동화에 허용한 범위부터 확인해야 한다.
단순한 정보 조회 목표를 장바구니 변경, 결제, 게시 같은 행동의 승인으로 확대하면 안 된다.
이 예시는 관측에서 응답까지의 흐름을 이해하기 위한 것이며 그러한 외부 변경을 수행한 기록은 아니다.[3]

## 로컬 라이브러리와 외부 서비스의 경계

README는 Python 라이브러리가 MIT로 제공되더라도 모델 추론과 호스팅 브라우저 이용은 별도라고 설명한다.
모델 제공자와 클라우드 서비스의 API 사용에는 비용이 생길 수 있다.
로컬 모델을 연결하는 선택지도 안내하지만, 그때는 모델과 하드웨어 요구 조건이 별도로 남는다.
라이브러리의 공개 라이선스와 실행 비용을 같은 뜻으로 읽으면 안 된다.[1]

프로필 동기화에도 범위가 있다.
README는 클라우드 프로필 동기화가 쿠키를 옮기며 로컬 저장소, IndexedDB, 확장 프로그램까지 옮기는 것은 아니라고 명시한다.
따라서 로컬에서 로그인된 사이트가 클라우드에서도 동일하게 열릴 것이라고 가정해서는 안 된다.
추가 로그인이 필요한 사이트가 있을 수 있다.[1]

자동화 탐지나 CAPTCHA에 관한 소개도 모든 사이트에서의 성공 보장은 아니라고 적혀 있다.
접근 권한과 사이트 규칙을 준수해야 하며, 차단을 만났다는 이유만으로 우회 권한이 생기지 않는다.
로그인된 브라우저를 연결하면 접근 가능한 정보가 달라지므로, 프로필을 고르는 일은 편의 설정인 동시에 데이터 접근 범위를 정하는 결정이다.[1][3]

이번에 살핀 상태 준비 코드에는 스크린샷을 요청하고 메시지 설정에 따라 사용하는 흐름도 보인다.
그러므로 외부 모델에 어떤 페이지 정보가 전달되는지는 실제 모델·브라우저·기록 설정에서 확인해야 한다.
소스 한 파일을 읽은 것만으로 모든 데이터 전송과 보안 경계를 검증했다고 주장할 수 없다.[2]

## 정리

Browser Use는 목표와 모델 판단을 실제 브라우저 상태·행동의 반복으로 연결한다.
실행 위치, 모델 비용, 로그인 프로필, 외부 변경 권한을 나누어 정해야 하며, 에이전트가 완료했다고 보고한 내용도 원 페이지와 결과 상태로 확인해야 한다.
