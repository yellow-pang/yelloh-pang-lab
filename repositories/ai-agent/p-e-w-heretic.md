## 한 줄 요약

Heretic은 Transformer 기반 언어 모델의 응답 거절 행동을 줄이도록 모델 내부 가중치를 바꾸는 도구다.
README는 이를 censorship removal 또는 safety alignment 제거라고 표현한다.
이 표현은 프로젝트의 목적 설명이며, 거절이 적을수록 더 정확하거나 안전한 모델이라는 뜻은 아니다.
프롬프트 모음이나 대화 서비스가 아니라 모델을 수정하고 평가하는 연구 도구로 구별할 필요가 있다.[1]

## 거절 빈도와 능력 보존은 같은 목표가 아니다

모델의 답변 방식을 바꾸면 원하는 행동뿐 아니라 다른 능력도 달라질 수 있다.
README가 설명하는 핵심 문제는 거절 수를 줄이는 동시에 원래 모델의 응답 분포에서 너무 멀어지지 않도록 조정하는 것이다.
문서는 방향성 제거 기법과 자동 매개변수 탐색을 결합한다고 소개한다.
여기서 자동화는 정해진 평가 목표에 맞는 후보를 찾는다는 의미이지, 변경의 사회적 적절성까지 판단한다는 의미는 아니다.[1]

방향성 제거는 모델 내부 표현에서 특정 행동과 연관된 방향의 영향을 약하게 만드는 접근이다.
README는 거절 관련 방향을 두 종류의 예시 입력에 대한 내부 상태 차이로 구하고, 지원되는 Transformer 구성요소에 적용한다고 설명한다.
이 글은 원리 이해에 초점을 두며 안전장치를 약화시키는 실행 명령이나 구체적인 조정 절차는 제공하지 않는다.[1]

## 내부 표현, 탐색, 평가기의 역할

Transformer는 문장 안의 관계를 계산하는 신경망 구조이며, 내부 상태는 입력을 읽는 과정에서 만들어지는 수치 표현이다.
Heretic 문서는 첫 출력 토큰에 대응하는 내부 상태를 층별로 비교한다고 설명한다.
층은 모델이 정보를 여러 단계로 변환하는 계산 단위다.
내부 방향과 실제 인간 개념 사이에 완벽한 일대일 대응이 있다는 주장으로 확대해서는 안 된다.[1]

자동 탐색에는 Optuna 기반 최적화가 사용된다고 소개된다.
목적 중 하나인 KL divergence는 두 확률분포가 얼마나 다른지 나타내는 지표다.
이 경우 원본 모델과 수정 모델의 반응 분포 차이를 보는 데 사용되지만, 낮은 수치가 모든 주제에서 지식과 추론이 보존되었다는 증거는 아니다.
README 자체도 수학적 지표와 자동 벤치마크가 인간 평가를 대체하지 않는다고 말한다.[1]

대표 구현 `evaluator.py`에서는 평가기를 플러그인 단위로 관리하는 구조를 확인할 수 있다.
프로그램은 설정된 scorer를 불러와 계약과 설정을 확인하고, 초기화한 뒤 원본 기준 점수를 얻는다.
scorer는 특정 방식으로 모델에 점수를 매기는 평가 구성요소다.
설정이 없거나 같은 인스턴스 이름이 중복되면 오류를 내는 부분이 있어, 평가 목록도 실험 구성의 일부로 다룬다.[2]

같은 파일은 일반 점수와 최적화에 쓰는 목적 점수를 구분한다.
모든 평가기가 반드시 최적화 목표에 들어가는 것은 아니며, 목적의 이름·값·최대화 또는 최소화 방향을 같은 순서로 맞추는 함수가 따로 있다.
주석은 이 순서가 어긋나면 잘못된 목표를 최적화할 수 있다고 설명한다.
어떤 숫자가 나왔는지뿐 아니라 그 숫자가 어느 기준의 점수인지 보존하는 일이 중요하다는 구조다.[2]

연구용 시각화 기능도 소개된다.
여러 층의 내부 상태를 2차원으로 줄여 그림이나 애니메이션으로 보는 방식이다.
차원 축소란 많은 수치로 된 자료를 사람이 볼 수 있는 작은 공간에 표현하는 과정이다.
그림에서 두 무리가 갈라져 보인다는 사실만으로 모든 거절 행동의 원인을 설명했다고 결론 낼 수는 없으며, 문서는 이 과정의 CPU 계산 비용도 언급한다.[1]

## 예시로 따라가는 흐름

공식 평가기 소스를 이용해 비교 기록이 만들어지는 과정을 읽어보자.
입력은 모델 객체, 설정된 평가기 목록과 각 평가기의 설정이다.
생성자는 평가기를 불러오고 초기화한 뒤 기준 점수를 수집한다.
이후 현재 모델의 점수를 얻는 호출은 같은 평가기 목록을 사용한다.
이 단계에서 비교하려는 기준이 원본과 후보에서 동일하게 식별되어야 한다.[2]

`get_paired_score_records`는 현재 점수와 기준 점수를 하나의 기록으로 묶으며, 두 이름이 같은지 확인한 뒤 `name`, `score`, `baseline`을 담는다.
이어 최적화에 사용할 값은 목적 평가기 목록에서 따로 추출된다.
사람이 읽을 때는 좋은 숫자 하나를 고르는 대신 어떤 평가가 단순 관찰용이고 어떤 평가가 실제 탐색 목표인지 확인할 수 있다.
이 글에서는 평가기를 실행하거나 모델을 변형하지 않았으며 점수 값도 만들어 넣지 않았다.[2]

안전한 이해용 상황으로, 이미 공개된 모델 비교 보고서에서 원본과 후보의 일반적인 문장 요약 품질을 검토하는 경우를 생각할 수 있다.
이는 가상 독해 사례다.
기록이 올바르게 짝지어졌더라도 사람이 요약의 사실성, 빠진 내용과 예상치 못한 출력 변화를 확인하는 단계는 남는다.
특히 거절 감소 지표가 좋다는 이유만으로 정확도나 개인정보 보호까지 좋아졌다고 해석할 수 없다.
수정 모델의 공개·사용 여부는 별도의 안전 평가와 권한 검토 대상이다.

## 자동 수정의 바깥에 남는 책임

README는 여러 dense 모델과 일부 MoE·혼합 구조 지원을 설명하지만 순수 state-space 모델 등 일부 구조는 기본 지원 밖이라고 명시한다.
dense와 MoE는 모델 계산에 쓰는 구성 방식의 차이이며, 이름에 언어 모델이 붙었다고 내부 구조가 모두 같지 않다는 점이 중요하다.
지원 여부와 필요한 메모리·의존성은 모델마다 달라진다.[1]

공식 성능 표는 특정 모델과 소프트웨어·하드웨어 조건에서 저자가 제시한 결과다.
문서는 정확한 값이 플랫폼과 하드웨어에 따라 달라질 수 있다고 밝힌다.
이번 조사에서는 그 표를 재현하지 않았고 다른 모델에 대한 성능 보존 비율로 일반화하지 않았다.
사용자 반응을 인용한 문구도 독립적인 안전성 검증으로 사용할 수 없다.[1]

이 도구는 안전 관련 행동을 의도적으로 바꾸므로 허가된 모델과 격리된 연구 범위에서 다루는 전제가 중요하다.
기반 모델의 사용·배포 조건은 도구의 소스 라이선스와 별개이며, 생성물을 공개할 권리가 자동으로 생기지 않는다.
실제 유해 출력 위험, 사실성 저하와 재배포 책임은 자동 최적화가 해결하지 못한다.
연구 목적을 설명하는 것과 제한 없이 사용을 권하는 것은 구별해야 한다.

도구 자체의 README는 GNU AGPL v3 또는 이후 버전을 명시하며 무보증 조건을 함께 적는다.
공개 코드라는 이유로 수정본의 배포나 서비스 제공 조건을 MIT와 같다고 생각해서는 안 된다.
도구의 이 조건과 사용하는 모델 가중치의 조건을 각각 확인해야 한다.[1]

## 정리

Heretic은 모델 내부를 수정하고 여러 평가 목표를 따라 후보를 비교하는 도구다.
자동 탐색의 목표가 거절 감소를 포함한다는 사실을 숨기지 않되, 그 결과를 정확성·안전성·사용 허가의 개선으로 바꾸어 해석해서는 안 된다.
