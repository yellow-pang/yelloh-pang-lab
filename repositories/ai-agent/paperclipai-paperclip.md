## 한 줄 요약

Paperclip은 여러 AI 에이전트에게 과제를 배정하고 진행 상태·승인·비용을 추적하는 조정 플랫폼이다.
Node.js 서버와 React 화면으로 이루어지며, 에이전트가 사용하는 모델이나 실행기는 외부에서 가져오는 구조다.
공식 README도 챗봇, 프롬프트 관리자, 에이전트를 만드는 프레임워크와는 다르다고 선을 긋는다.[1]

## 여러 실행 창보다 먼저 필요한 작업 기록

공개 개인 프로젝트에서 문서 작성, 코드 수정과 검증을 서로 다른 에이전트에게 맡기면 누가 어느 일을 하고 있는지, 결과는 어디에 있는지 추적해야 한다.
터미널 창이 열려 있다는 사실만으로 과제의 소유자나 다음 승인자를 알 수는 없다.
Paperclip은 실행 자체를 새로운 모델로 바꾸는 대신 과제·목표·담당자·비용·기록을 연결해 이 조정 문제를 다룬다.[1]

README의 조직도 비유는 역할과 보고 관계를 모델링한다는 뜻이다.
실제 사람 조직의 판단과 책임을 AI가 자동으로 대체한다는 증거가 아니다.
이 글에서는 공개 프로젝트의 작은 작업 묶음을 예로 삼아, 목표를 어떻게 실행 가능한 과제로 나누고 검토로 넘기는지에 초점을 둔다.

## 목표, 작업 점유, 짧은 실행 주기

과제에는 프로젝트와 상위 목표, 부모 과제와 차단 의존성을 연결할 수 있다.
중요한 것은 제목 하나보다 “왜 필요한 일인지”와 “무엇이 끝나야 시작할 수 있는지”를 함께 전달하는 구조다.
README는 작업 체크아웃과 실행 잠금으로 중복 작업을 조정한다고 설명한다.
여기서 체크아웃은 Git 브랜치를 바꾸는 명령이 아니라 특정 과제의 실행을 맡는 절차다.[1]

대표 공식 스킬은 에이전트가 heartbeat라는 짧은 실행 구간에서 깨어나 과제를 확인하고 일한 뒤 종료한다고 설명한다.
README의 FAQ도 기본적으로 일정과 과제 배정·언급 같은 사건을 통해 실행된다고 한다.
따라서 상시 운영을 소개하는 문구가 개별 에이전트 프로세스가 언제나 계속 돌아간다는 뜻은 아니다.
지속 실행형 외부 에이전트와의 연결 가능성은 또 다른 경로다.[1][2]

일반 heartbeat 절차는 신원·배정된 과제·새 맥락을 확인하고 작업을 점유한 뒤 실행하는 순서다.
대표 스킬은 다른 에이전트가 이미 점유한 과제에서 `409 Conflict`를 받으면 다시 시도하지 말고 멈추라고 명시한다.
할 일을 찾았다는 것과 그 일을 맡을 권한을 확보했다는 것을 구별하는 지침이다.
다만 서버가 이미 확인한 일부 대화 실행과 특정 과제가 명시된 호출에는 축약 경로가 따로 있다.[2]

비용과 승인은 별도 관리 축이다.
README는 에이전트별 예산과 경고·중단 정책, 검토·승인 단계, 일시정지와 취소를 제공한다고 설명한다.
이는 사용량을 보고 통제할 수 있는 기능이지 모든 외부 제공자의 과금이 어떠한 상황에서도 완벽히 같은 시점에 멈춘다는 독립 검증은 아니다.
이 글에서는 비용 집계나 경계 상황을 실제 측정하지 않았다.[1]

## 예시로 따라가는 흐름

개인 오픈소스 라이브러리의 사용 예제를 보강하는 과제를 두 에이전트가 나누는 상황을 가정해 보자.
이해를 위한 가상 예시이며 직접 실행한 결과가 아니다.
한 에이전트는 문서 수정, 다른 에이전트는 예제와 설명의 일치 확인을 맡는다고 정한다.
입력에는 과제 설명뿐 아니라 공개 저장소 위치, 기대 산출물과 검토 조건이 있어야 한다.
Paperclip의 역할은 이 작업을 기록하고 실행 주기를 연결하는 것이다.[1]

수정 담당이 깨어나면 일반 절차에 따라 배정과 맥락을 확인하고 과제를 체크아웃한다.
다른 실행이 이미 소유한다면 충돌 응답에서 멈추는 것이 지침상 맞는 처리다.
작업을 수행한 후에는 바뀐 내용을 말로만 남기는 대신 사용자가 열어볼 수 있는 파일이나 work product를 연결하도록 공식 스킬이 요구한다.
work product는 PR, 미리보기 또는 산출물처럼 결과에 접근할 수 있는 기록이다.
에이전트의 로컬 파일 경로만 전달하면 검토자가 접근하지 못할 수 있기 때문이다.[2]

검토 대기와 완료도 다르다.
공식 상태 안내에서 `in_review`는 검토·승인·사용자 응답을 기다리는 상태이며 `done`은 더 이상 후속 작업이 없는 완료다.
검토 담당에게 넘겼다는 이유만으로 원래 요구가 검증되었다고 기록하면 안 된다.
사람이 확인할 것은 실제 수정 내용, 검증 자료, 남은 의존성과 다음 담당자가 명확한지다.
이 사례에서는 플랫폼에 과제를 만들거나 에이전트를 실행하지 않았으므로 결과 파일·댓글·비용 숫자를 실제 기록처럼 제시하지 않는다.[2]

## 기록과 실제 재개 조건을 구별하기

대표 스킬의 모니터 안내는 특징적인 경계를 보여준다.
실행이 끝난 뒤에도 “계속 확인하겠다”는 댓글만 남기는 것으로 감시가 생기지 않는다.
별도의 지속적인 모니터 상태와 다음 확인 시각, 담당자 및 허용 상태가 있어야 서버가 다시 깨울 수 있다고 설명한다.
시간 기반 재확인은 외부 검사가 끝나는 즉시 전달되는 사건 구독과도 다르다.[2]

이 때문에 산출물·설명·상태는 서로 맞아야 한다.
완료라고 표시한 과제에서 계속 기다리는 모니터가 있다고 말하거나, 차단 원인을 본문에만 쓰고 실제 재개 경로를 남기지 않으면 관리 화면의 의미가 흐려진다.
Paperclip의 공식 지침은 이런 상태 일관성을 다루지만, 지침 파일을 읽었다는 사실로 모든 어댑터가 모든 상황에서 이를 지킨다고 보장하지는 않는다.[2]

자체 호스팅도 외부 연결 조건을 없애지는 않는다.
README의 빠른 시작은 신뢰한 로컬 loopback 모드를 기본으로 소개하고 별도의 인증된 연결 모드를 구별한다.
연결한 에이전트·모델 제공자의 권한과 비용, 프로젝트 데이터 저장은 사용자가 구성해야 한다.
사용 분석은 기본 활성화이며 끌 수 있다고 명시되고, 선택적 추적·오류 수집과도 구분된다.[1]

또한 README의 로드맵에는 아직 예정인 항목이 있다.
기능 표의 조직·예산·과제 관리와 향후 메모리·지식 기능을 같은 완성 범위로 읽지 않는 것이 필요하다.
에이전트의 전문 작업 품질이나 최종 결과의 사실성을 플랫폼이 자동으로 보증하는 것은 아니므로, 사람의 검토 기준과 실제 검증 자료가 남아야 한다.[1]

## 정리

Paperclip은 여러 에이전트의 작업을 과제와 실행 상태, 승인 및 결과 기록으로 연결한다.
새 모델을 제공하기보다 누가 무엇을 맡았고 무엇이 실제 완료되었는지 추적하는 계층이며, 검증된 산출물과 정확한 상태 전이가 그 중심이다.

## 자료 확인 범위

2026-09-27의 공식 README, 루트 구성과 Paperclip 스킬의 heartbeat·상태·모니터·산출물 안내를 읽었다.
플랫폼 설치, 과제 등록, 에이전트 실행 및 예산 제한 시험은 하지 않았으며 서버 구현 전체를 감사한 것은 아니다.
