## 이미지에서 3D 메시를 만드는 로컬 데스크톱 앱

Modly는 사진을 입력받아 로컬 AI 모델로 3D 메시를 생성하는 데스크톱 애플리케이션이다.
메시(mesh)는 점과 면을 연결해 물체의 표면을 표현한 3차원 데이터다.
README는 Windows, Linux, Apple Silicon macOS를 대상으로 소개하고, 모델 실행을 GPU에서 수행한다고 설명한다.
이 저장소 자체가 하나의 3D 생성 모델은 아니며, 모델 확장과 작업 흐름을 관리하고 결과를 장면에 보여주는 앱 역할을 한다.[1]

이미지를 모델에 넣는 코드가 있더라도 일반 사용자가 매번 모델 파일, 실행 환경, 후처리와 내보내기를 직접 연결하기는 어렵다.
Modly는 이 흐름을 노드로 연결하는 작업 화면과 설치 가능한 확장으로 나눈다.
예를 들어 이미지를 입력으로 받는 단계와 메시를 생성하는 단계, 완성된 데이터를 장면에 추가하는 단계가 각각 존재한다.
화면을 통한 조작뿐 아니라 실행 중인 앱을 외부 Agent가 호출하는 CLI도 같은 흐름에 접근하도록 제공한다.[1][2]

## 확장, 워크플로, 자동화 인터페이스

확장은 `manifest.json`과 종류에 맞는 실행 파일을 갖춘 별도 저장소로 설명된다.
모델을 제공하는 확장과 처리 단계를 제공하는 확장은 설치 뒤의 준비가 다르다.
모델 노드가 있는 확장에서는 실제 모델이나 변형을 추가로 내려받아야 하며, 처리 확장은 설치와 설정이 끝난 뒤 사용할 수 있다고 README가 안내한다.
앱 설치와 모델 준비를 한 번의 완료 상태로 합치면 생성 실패의 원인을 놓치기 쉽다.[1]

워크플로는 입력에서 결과까지의 처리 단계를 선으로 연결한 그래프다.
공식 기본 예는 `Image → Generate Mesh → Add to Scene`이다.
README는 각 노드가 연결되어 있어야 하며, 실행 전에 연결의 유효성을 검사한다고 설명한다.
잘못된 그래프는 그대로 남고 경고가 표시되도록 설계되어 있다.
이는 사용자가 만든 작업 구성을 보존하면서 어디가 연결되지 않았는지 고칠 수 있도록 한 동작이다.[1]

추가로 읽은 `tools/modly-cli/SKILL.md`는 자동화의 기준을 명확히 한다.
CLI는 실행 중인 공식 데스크톱 앱의 로컬 API를 호출하며, 최종 기계 판독용 JSON은 표준 출력에, 선택적인 진행 정보는 표준 오류에 쓴다.
표준 출력은 결과를 다른 프로그램에 전달하는 통로이므로 진행 문구와 섞이지 않는 것이 중요하다.
대표 명령은 준비 상태, 모델, 워크플로 실행, 기능 목록과 처리 실행으로 구분된다.[2]

친숙한 `generate` 명령은 내부적으로 `/workflow-runs/from-image` 요청을 보내고 실행 상태를 조회한 다음 최종 메시를 내보낸다.
문서는 실행 ID, 작업 공간 경로와 내보내기 경로뿐 아니라 상태 확인·취소를 위한 복구 정보도 결과에 포함한다고 설명한다.
오래 걸리는 생성 작업을 한 번의 텍스트 응답이 아니라 나중에 다시 추적 가능한 작업으로 다루는 구조다.[2]

## 예시로 따라가는 흐름

공식 README의 기본 워크플로와 CLI 예제는 `input.png`에서 `export.glb`로 이어지는 경로를 보여준다.
이 글은 그 문서상의 사용 순서를 해설하며 직접 실행한 결과가 아니다.
먼저 공식 데스크톱 앱이 실행되어 있어야 하고, 사용할 모델 확장과 모델 파일이 준비되어야 한다.
화면에서는 이미지 입력, 메시 생성, 장면 추가 노드를 연결하고 해당 워크플로를 선택한다.
이 연결이 잘못되어 있다면 생성 버튼을 누르기 전에 그래프 경고부터 확인할 대상이다.[1][2]

Agent가 같은 작업을 요청할 경우에는 먼저 `health`와 모델 목록을 확인하고 이미지와 내보낼 경로를 넘긴다.
자동 모델 선택은 현재 활성 모델을 읽고 실제 모델 목록에 존재하는지 검증하는 방식이며, 이름에 특정 단어가 있다고 숨은 기능을 추측하지 않도록 되어 있다.
작업이 시작되면 실행 ID로 상태를 다시 조회할 수 있고, 완료 후에는 생성된 메시의 작업 공간 위치와 외부 파일 위치를 구분해 받는다.[2]

사람이 마지막으로 확인할 것은 응답의 성공 표기만이 아니다.
공식 체크리스트는 `export_path`의 파일이 존재하고 크기가 0이 아닌지도 요구한다.
여기에 원하는 물체의 형태가 생성되었는지, 이후 사용할 3D 프로그램에서 열리는지 확인하는 과정은 별도로 남는다.
문서가 보여주는 JSON 예시는 출력 계약의 설명이지 이 조사에서 실제 만들어진 파일의 증거가 아니다.
원본 사진에 없는 뒷면까지 정확히 복원되었다고 보장할 근거도 이 자료만으로는 없다.[2]

## 백엔드 응답과 데스크톱 준비 상태는 다르다

CLI 문서는 개발용 `dev` 명령이 FastAPI 백엔드만 시작하거나 검사할 수 있으며, 이것이 Electron 데스크톱 연결이나 장면 조작·전체 워크플로 준비를 증명하지는 않는다고 경고한다.
과거 `/generate/*` 경로는 명시적인 호환 명령으로 분리되어 있고, 현재 생성 경로가 실패할 때 몰래 옛 경로로 바뀌지 않는다.
따라서 서버가 켜졌다는 한 가지 신호만으로 자동화 전체가 준비되었다고 할 수 없다.[2]

프롬프트 기반 ComfyUI 연결도 문서상 `experimental` 영역이며 기본 Modly 계약 밖의 보조 기능이다.
글 입력에서 바로 3D가 나온다는 설명만 읽으면 이미지 생성 단계나 외부 워크플로가 숨겨질 수 있다.
사용하는 모델 확장에 따라 계산 자원과 모델 이용 조건이 달라지므로, GPU 요구량이나 상업 이용 가능성을 앱의 소개만으로 단정하지 않는 편이 정확하다.[1][2]

라이선스 역시 직접 읽을 필요가 있다.
README는 MIT로 소개하지만 실제 `LICENSE`에는 통상적인 MIT 문구 뒤에 파생 앱의 UI 또는 문서에서 원래 프로젝트와 제작자를 표시하라는 추가 문장이 붙어 있다.
따라서 '표준 MIT 문구만 있다'고 요약하면 이 요구를 놓친다.
앱 코드의 조건과 별도 모델·확장의 라이선스도 같은 권한으로 합쳐 판단해서는 안 된다.[3]

## 정리

Modly는 모델을 직접 새로 만드는 저장소가 아니라 이미지에서 3D 결과물까지의 로컬 생성 과정을 다루는 앱이다.
확장의 준비 상태, 워크플로 연결, 추적 가능한 실행과 실제 파일 검증이 서로 이어진다.
CLI 자동화까지 살필 때는 백엔드 생존 여부와 데스크톱 작업 가능 상태를 구별하는 것이 중요하다.

## 자료 확인 범위

2026-09-27 README와 루트 구조, CLI Skill, LICENSE를 확인했다.

플랫폼별 작동이나 결과 메시 품질은 이 문서에서 검증한 사항이 아니다.
