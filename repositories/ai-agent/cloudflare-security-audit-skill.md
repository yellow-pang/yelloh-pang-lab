## 한 줄 요약

security-audit-skill은 코딩 에이전트가 소스 기반 보안 검토를 수행하도록 역할, 근거, 판정과 보고 절차를 제공하는 Skill이다.
독립 실행형 취약점 스캐너나 보안 인증 서비스가 아니다.
언어 모델과 도구 사용·하위 에이전트 기능을 가진 실행 환경에 읽혀 동작하는 지침이며, 공식 README는 단일 저장소 감사의 출발점으로 설명한다.[1]

## 의심스러운 코드와 확정된 문제 사이

보안 검토에서 “입력 검증이 약해 보인다”는 말만으로 실제 취약점을 확정하기는 어렵다.
누가 어떤 입력을 제어할 수 있는지, 앞단의 다른 통제가 있는지, 어떤 사용자나 자원에 결과가 미치는지를 이어서 확인해야 한다.
이 Skill은 권한이 다른 주체 사이의 선인 신뢰 경계를 실제로 넘는 결과를 근거로 요구한다.[2]

이미 다른 계층이 막고 있는 경로에 추가 방어가 없다는 이유만으로 취약점이라고 부르지 않는다는 원칙도 있다.
좋은 관행의 누락, 아직 확인하지 못한 배포 설정, 실제 관측한 경계 위반을 서로 구분하려는 것이다.
이런 판정 기준이 없으면 AI가 많은 후보를 생성해도 소유자가 무엇부터 확인해야 할지 알기 어렵다.[1][2]

## 조사 범위를 기록하고 역할을 나눈다

전체 감사는 구조·입력·신뢰 경계 파악에서 출발해 coverage ledger를 만든다.
ledger는 어디를 조사할지와 어떤 근거가 남았는지 기록하는 장부다.
조정 에이전트는 이 단위로 조사자를 배정하고, 별도 비평 역할이 빠진 범위를 찾도록 한다.
파일이 몇 개 있다는 목록과 실제 점검한 범위는 다른 자료다.[1]

발견한 후보는 그 후보를 만든 에이전트와 다른 검증자가 반증을 시도한다.
이후 구조화된 결과를 만들고 최종 소스 주장도 독립적으로 다시 검토한다.
여러 번 실행하는 경우 이전 근거를 참조하되 바뀐 소스나 미해결 부분을 자동으로 “이미 점검함”으로 처리하지 않도록 지침이 있다.[1][2]

공유 파일은 조정자만 쓰고 조사자별 임시 영역을 분리한다.
여러 에이전트가 같은 결과 파일을 덮어쓰거나 검증되지 않은 대상 코드가 보관할 증거 파일을 바꾸지 못하도록 쓰기 소유권을 구분하는 것이다.
역할 분리는 다양한 답변을 모으는 것뿐 아니라 근거의 출처와 수정 책임을 추적하는 장치다.[2]

## 세 가지 판정과 구조 검증

`confirmed`는 소스 흐름과 제한된 관측 결과가 갖춰진 항목이다. `needs_validation`은 정확히 무엇이 아직 확인되지 않았는지 기록하며 심각도를 붙이지 않는다. `rejected`는 반증된 후보를 남긴다.
미확정은 낮은 등급의 확정 취약점이 아니며, 불확실성을 숨긴 점수로 바꾸지 않는 것이 이 구분의 목적이다.[1][2]

대표 구현 `validate-findings.cjs`는 결과 JSON을 스키마와 대조하고 추가 의미 규칙을 검사한다.
중복 fingerprint, 소스 상대 경로, 양수 줄 번호, trace의 시작·전파·도착 순서 등을 확인하는 코드가 있다.
확정 항목에는 실제 관측 결과를 적은 필드와 수정 전략을 요구한다.
JSON이 문법에 맞는 것만으로 충분하지 않다는 점을 반영한 검사다.[3]

그렇다고 검증기가 취약점의 존재를 자동 증명하는 것은 아니다.
기록의 구조와 요구 필드를 검사하는 일, 그 필드의 소스 주장이 실제로 맞는지 검토하는 일, 안전한 재현에서 관측한 결과를 해석하는 일은 구별된다.
이 Skill이 독립 검증과 보고서 생성을 별도 단계로 둔 이유를 여기에서 이해할 수 있다.[1][3]

## 예시로 따라가는 흐름

본인이 관리하거나 명시적으로 검토 권한을 받은 공개 개인 프로젝트의 접근 제어 코드를 살피는 이해용 가상 예시다.
직접 감사를 실행한 결과가 아니다.
먼저 대상 경로와 출력 위치, 검토할 소스 상태, 허용한 실행 범위를 정한다.
조정자는 입력을 받는 부분과 권한 검사, 자원 접근 부분을 지도처럼 정리하고 ledger에 조사 단위를 만든다.
조사자는 어떤 요청이 어떤 검사 뒤에 어떤 자원으로 가는지 소스 경로를 제시한다.[2]

만약 결정적인 조건이 저장소 밖의 배포 설정에 달려 있다면 그 조건을 추측해 결함을 확정하지 않는다. `needs_validation`에 확인해야 할 정확한 사실과 소유자가 안전하게 확인할 계획을 남긴다.
다른 검증자는 기존 통제로 가설이 막히는지 검토하고, 반증되면 `rejected`로 기록한다.
확정하려면 요구한 경계와 제한된 결과가 실제 근거로 연결되어야 한다.
마지막에 구조 검증을 통과한 기록과 조사 범위를 바탕으로 보고서를 만든다.
사람은 결과 개수보다 빠진 범위, 미해결 조건, 검토한 소스 버전을 함께 읽어야 한다.[1][2][3]

## 문서를 읽었다고 실행 허가가 생기지 않는다

중심 Skill은 기본 모드를 guidance로 정한다.
보안 질문이나 특정 후보 검토에는 관련 부분만 사용하며, 명시적 전체 감사나 보고 산출물 요청이 있을 때 전체 절차와 파일 생성을 수행한다.
모호하면 시작 전에 질문하도록 되어 있다.
Skill을 로드하는 행위 자체가 대상 실행이나 출력 디렉터리 생성을 허가하지 않는다.[2]

대상 코드의 빌드·테스트·브라우저·fixture 처리는 OS가 강제하는 격리 환경 안에서만 수행하도록 규정한다.
외부 네트워크 차단, 허용 목록 기반의 빈 환경, 읽기 전용 대상과 제한된 임시 쓰기 경로, 자원 한도가 모두 필요하다.
조건을 제공할 수 없으면 실행하지 않고 검증 차단 사유로 남긴다.
실제 서비스, 다른 사용자의 데이터, 실제 인증정보와 유료 API를 시험 대상으로 삼지 않는 방어적 경계도 명시한다.[2]

한 번의 실행은 전체 안전성의 증명이 아니다.
quick 또는 범위를 좁힌 검토는 부분 점검으로 보고해야 하고, 예산이 부족하면 남은 후보를 임의로 확정·미확정 결과로 포장하지 말고 불완전한 실행으로 표시하는 지침이 있다.
조사 폭을 줄이는 선택과 근거 기준을 낮추는 선택은 다르다.[2]

## 직접 읽어볼 자료

1. [README의 여섯 단계](https://github.com/cloudflare/security-audit-skill/blob/main/README.md)
   후보 발견부터 최종 기록 검증까지 어떤 역할이 새로 투입되는지 따라간다.
   세 판정의 의미와 결과 보고서가 어느 자료에서 파생되는지도 확인한다.
2. [중심 Skill](https://github.com/cloudflare/security-audit-skill/blob/main/skills/security-audit/SKILL.md)
   Operating modes와 Universal execution safety를 먼저 읽고, 그 다음 coverage와 실행 profile을 살핀다.
   어떤 조건에서 멈춰야 하는지가 기능 목록보다 중요한 자료다.
3. [결과 검증기](https://github.com/cloudflare/security-audit-skill/blob/main/skills/security-audit/validate-findings.cjs)
   `collectFindingSemanticErrors`와 `validateDocument`를 통해 요구하는 기록 구조를 확인한다.
   필드 검증의 성공을 소스 주장 자체의 참으로 혼동하지 않도록 구분해 읽는다.

## 정리

이 프로젝트는 보안 검토를 근거와 범위, 독립 검증의 절차로 정리한다.
의심을 확정으로 부풀리지 않고, 실행 조건이 부족하면 그 부족함을 기록하며, 보고서의 구조와 실제 결함 검증을 분리하는 데 의미가 있다.
