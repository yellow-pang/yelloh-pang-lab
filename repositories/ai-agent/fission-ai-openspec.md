## 한 줄 요약

OpenSpec은 AI 코딩 도우미와 사람이 구현 전에 요구사항과 설계, 작업 목록을 문서로 맞추도록 돕는 명세 중심 개발 도구다.
명세는 프로그램이 어떤 조건에서 어떻게 동작해야 하는지 적은 문서다.
OpenSpec은 이를 대화 기록 밖의 Markdown 산출물로 남기며 기존 코드의 변경에도 사용할 수 있도록 설계한다.[1]

## 대화가 길어져도 남아 있어야 할 약속

“로그아웃 버튼을 추가해 달라”는 요청에는 세션을 어디서 지울지, 확인 화면이 필요한지, 완료 후 어디로 이동할지 같은 판단이 숨어 있다.
AI가 바로 코드를 쓰면 잘못된 가정이 여러 파일에 들어간 뒤 발견될 수 있다.
공식 예제는 제안과 변경 명세를 먼저 열어 한 문단 수준에서 잘못된 가정을 고치는 순간을 강조한다.[2]

OpenSpec은 요구와 코드를 자동으로 일치시키는 증명 도구가 아니다.
무엇을 만들지 적어 검토 가능한 상태로 만들고, 그 문서를 읽으며 구현하고, 완료한 변경을 다음 작업의 기준에 반영하는 흐름이다.
모델이 문서를 작성해도 사람이 목표와 범위를 검토해야 한다는 전제가 있다.[1][2]

## 제안, 명세, 설계, 작업은 다른 질문에 답한다

변경 폴더의 `proposal.md`는 왜 바꾸는지와 바뀌는 범위를, `specs/`는 요구와 구체적인 시나리오를, `design.md`는 기술적 접근을, `tasks.md`는 구현할 항목을 담는다.
하나의 문서를 여러 이름으로 복제하는 것이 아니라 이유·동작·구현 방법·진행을 분리하는 구조다.[1]

시나리오는 “어떤 상황에서 어떤 행동을 하면 무엇이 되어야 하는가”를 표현한다.
README의 테마 예시는 사용자가 토글을 누르면 다크 모드로 바뀌고 선택을 보관해야 한다고 적는다.
구현 파일명이 아니라 관찰 가능한 행동을 적으므로 코드가 바뀌어도 의도를 다시 읽을 수 있다.[1]

현재 기준 명세와 진행 중 변경의 명세도 다르다.
변경 폴더의 delta spec은 추가·수정할 요구를 담고, 보관 단계에서 이를 기준 명세에 반영하는 흐름을 보여준다.
완료 기록을 옮기는 일만이 아니라 다음 세션이 읽을 현재 동작 설명을 갱신하는 일이다.[2]

## CLI와 대화 명령의 역할

`openspec init` 같은 명령은 터미널의 CLI가 프로젝트와 도구 연결을 준비하는 경로다. `/opsx:propose` 같은 작업 명령은 AI 도우미의 대화에서 사용한다.
선택한 도구에 따라 표기가 달라지므로 슬래시 명령을 그대로 셸에 붙여 넣는 방식으로 이해하면 안 된다.[1][2]

`explore`는 아직 정하지 못한 문제와 선택지를 조사하는 단계이고 `apply`는 선택한 변경을 구현한다.
README는 문서를 언제든 수정할 수 있는 반복 흐름을 강조한다.
하지만 “유연하다”는 말이 필요한 자료가 없는데도 구현을 진행하거나 완료 표시를 임의로 하는 뜻은 아니다.
실제 apply Skill에는 상태를 읽고 차단 조건이면 멈추라는 규칙이 있다.[1][3]

## apply가 실제로 확인하는 것

대표 Skill은 먼저 대상 변경을 고르고 CLI의 상태와 스키마를 확인한다.
스키마는 이 작업 흐름에서 어떤 문서와 관계를 요구하는지 정한 구조다.
이후 `instructions apply`가 돌려준 실제 파일 경로, 작업 상태, 남은 항목과 동적 안내를 읽는다.
항상 특정 파일명일 것이라고 추측하지 말고 반환된 `contextFiles`를 읽도록 한다.[3]

프로젝트에 OpenSpec 루트가 없는 경우에도 임의로 만들지 않는다.
사용자가 명시적으로 요청한 경우 설정할지·Store를 쓸지·이번에는 없이 진행할지 확인하고, 자동 선택한 경우에는 OpenSpec 절차를 강요하지 않는 분기가 있다.
Store를 지정했다면 이후 관련 명령에서 같은 저장 범위를 유지하도록 한다.[3]

구현 중 모호함이나 설계 문제가 드러나면 문서를 수정할지 묻고, 명세에 없는 일을 흡수하거나 요구를 줄여 완료 처리하지 말라고 한다.
체크박스는 해당 행동이 온전히 구현되었을 때만 표시하는 기록이다.
계획 문구나 부가 안내 자체는 작업 완료의 증거가 아니라고 파일이 명시한다.[3]

## 예시로 따라가는 흐름

공식 Examples의 로그아웃 버튼 추가 사례는 `add-logout-button`이라는 변경을 제안하는 것으로 시작한다.
AI가 변경 폴더와 제안·명세·설계·작업 목록을 만들면 사용자는 먼저 제안과 delta spec을 읽는다.
이때 확인 화면이 실제로 필요한지, 세션 종료가 어떤 의미인지 같은 가정을 검토하고 틀린 부분을 문서에서 바로잡을 수 있다.[2]

이후 apply는 작업별로 헤더 버튼, 세션 정리, 확인 대화상자 같은 구현을 진행하는 예시를 보여준다.
실제 Skill의 관점에서는 먼저 현재 상태와 문맥 파일을 읽고, 각 요구를 구현한 뒤 해당 작업만 완료로 바꿔야 한다.
마지막 archive는 변경 명세를 인증 영역의 기준 명세에 합치고 변경 폴더를 보관하는 흐름이다.
사람은 체크박스가 모두 표시됐는지만 볼 것이 아니라 로그아웃 뒤 보호된 경로 접근이 어떻게 되는지, 실제 테스트가 요구를 확인했는지, 구현 중 결정이 문서에도 반영됐는지 살펴야 한다.
문서의 예시 대화는 이 원고에서 실행한 로그가 아니며, 코드를 만들거나 archive를 수행하지 않았다.[2][3]

## 문서가 늘어나는 것과 정확해지는 것은 다르다

기능이 아니라 내부 구조만 바꾸는 리팩터링에서는 외부 동작 명세를 억지로 바꾸지 않고 설계와 작업에 초점을 둔다는 예시도 있다.
반대로 버그 수정은 “고친다”는 문장 대신 올바른 동작과 재발 조건을 시나리오로 적는다.
문서 분량보다 변경의 성격에 맞는 계약을 남기는 것이 중요하다.[2]

Stores는 여러 저장소에서 계획을 공유하는 경로지만 README에서는 베타로 구분한다.
지역 프로젝트와 별도 Store의 파일 위치를 혼동하면 다른 범위의 명세를 수정할 수 있다.
또 apply 지침은 일부 문맥 규칙이 프롬프트 수준의 계약이지 강제 검사가 아니라고 밝힌다.
지침 파일이 있다는 사실만으로 에이전트의 준수를 보장하지 않는다.[1][3]

Node.js 요구사항과 MIT 라이선스 외에 익명 명령명·버전 통계 수집도 안내되어 있다.
통계는 설정이나 환경 변수로 끌 수 있고 CI에서는 자동으로 꺼진다고 한다.
패키지 갱신과 프로젝트 안의 지침 갱신이 나뉘어 있다는 점도 사용 시 확인해야 한다.[1]

   테마 변경 사례에서 네 산출물의 역할을 구분한다.

2. [Examples & Recipes](https://github.com/Fission-AI/OpenSpec/blob/main/docs/examples.md)

   같은 절차에서도 명세에 남길 내용이 어떻게 달라지는지 확인한다.
3. [실제 apply Skill](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-apply-change/SKILL.md)
   루트 확인, 변경 선택, 상태·문맥 파일 읽기, 중단과 완료 규칙을 따라간다.
   예쁜 예시 대화 뒤에서 어떤 조건을 지켜야 구현으로 진행할 수 있는지 보여준다.

## 정리

OpenSpec은 요구와 구현 사이의 약속을 변경별 문서로 남긴다.
문서 생성과 실제 구현·검증은 서로 다른 단계이며, 범위가 바뀌면 명세를 함께 수정하고 완전한 동작에만 완료 표시를 해야 한다.

## 자료 확인 범위

2026-09-27 공식 README의 흐름·요구사항·통계 안내, Examples의 기능·버그·리팩터링 사례와 apply Skill의 상태·문맥·중단·완료 규칙을 읽었다.
설치, 프로젝트 초기화, 코드 구현이나 명세 보관 명령은 실행하지 않았다.
