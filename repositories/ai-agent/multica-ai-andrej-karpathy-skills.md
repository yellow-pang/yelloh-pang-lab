## 한 줄 요약

이 저장소는 AI 코딩 도구의 흔한 실수를 줄이기 위한 행동 지침 모음이다.
중심 자료는 `CLAUDE.md`이며, README는 Andrej Karpathy의 LLM 코딩 관련 관찰에서 영감을 얻었다고 설명한다.
새 코딩 모델이나 자동 테스트 엔진이 아니라 기존 도구가 참고하도록 주는 규칙 문서다.[1]

## 작동하는 코드만으로는 충분하지 않은 경우

AI가 요청한 기능을 만들면서 묻지 않은 옵션을 추가하거나 주변 코드까지 다시 정리하면 변경 범위가 커진다.
또한 ‘사용자 데이터 내보내기’ 같은 짧은 말에서 모든 사용자를 대상으로 할지, 어떤 필드를 포함할지, 어디로 내보낼지를 임의로 정할 수 있다.
이 저장소는 그런 잘못된 가정, 과도한 추상화, 요청과 무관한 수정에 초점을 맞춘다.[1]

여기서 추상화는 반복되는 동작을 공통 구조로 묶는 설계 방식이다.
필요한 순간에는 유용하지만 한 번 쓸 작은 기능에 큰 설정 체계를 미리 붙이면 이해와 검증에 드는 일이 늘어난다.
지침은 짧은 코드 자체를 만능으로 내세우기보다, 요청과 성공 조건을 먼저 정하고 그 범위 안에서 최소한으로 구현하라고 요구한다.[2]

## 네 원칙이 맡는 서로 다른 역할

Think Before Coding은 구현 전에 가정과 불확실성을 드러내라는 원칙이다.
해석이 여러 개라면 조용히 하나를 고르지 말고 차이를 제시하며, 더 단순한 길이 보이면 설명하라고 한다.
이는 모든 질문에 매번 확인을 받으라는 형식 규칙보다, 결과를 바꿀 중요한 가정을 숨기지 말라는 취지로 읽을 수 있다.[2]

Simplicity First는 요청하지 않은 기능, 한 번만 쓰는 추상화, 예상만으로 넣은 설정을 경계한다.
Surgical Changes는 이미 있는 코드를 수정할 때의 경계다.
주변 주석이나 스타일을 마음대로 고치지 않고, 기존 관례를 따르며, 자신의 변경으로 쓸모없어진 부분과 원래 존재하던 미사용 코드를 구분한다.
‘정리’라는 이유로 무관한 삭제를 합치지 않는 것이 핵심이다.[2]

Goal-Driven Execution은 동작 지시를 검증 가능한 목표로 바꾼다.
‘버그 수정’은 재현 테스트를 만들고 통과시키는 목표로, ‘리팩터링’은 수정 전후 테스트가 통과하는지 확인하는 목표로 바꾼다.
계획에도 각 단계의 확인 방법을 붙이게 하므로 완료 판단이 모델의 자신감이 아니라 관찰 가능한 결과에 연결된다.[2]

## 예시로 따라가는 흐름

공식 `EXAMPLES.md`의 사용자 데이터 내보내기 사례를 따라가 보자.
입력 요청은 데이터 export 기능을 추가해 달라는 짧은 문장이다.
잘못된 예시는 모든 사용자를 조회하고 JSON 또는 CSV로 저장하면서 파일 위치와 필드까지 스스로 정한다.
예제는 이를 완성도 높은 구현으로 칭찬하지 않고, 대상 범위와 개인정보, 출력 방식, 데이터 구조를 확인하지 않았다는 문제로 표시한다.
여기의 코드는 설명용 대비 사례이며 이 조사에서 실행한 프로그램이 아니다.[3]

바람직한 흐름으로 제시된 것은 먼저 전체 사용자와 일부 사용자 중 어떤 범위인지, 브라우저 다운로드와 API 반환 중 무엇인지, 민감할 수 있는 필드는 무엇인지, 데이터 규모가 어느 정도인지 확인하는 것이다.
그 뒤 가장 단순한 접근 후보를 제시하되 필요한 정보를 모른다는 점을 남긴다.
결과물은 첫 단계부터 임의의 완성 코드가 아니라 구현 계약을 좁힐 수 있는 질문과 선택지다.
사람은 그 질문이 실제 결과와 권한에 영향을 주는지 확인하고, 범위가 정해진 뒤 변경된 각 줄이 요청에 필요한지 검토할 수 있다.[3]

같은 예제 문서에는 빈 이메일 처리 수정에서 사용자명 검증과 주석 변경을 끼워 넣지 않는 대비도 있다.
이는 작은 수정이 덜 성의 있다는 뜻이 아니라, 재현한 문제와 관련 없는 변경을 분리해야 무엇을 확인했는지 명확해진다는 설명이다.
가정 공개와 변경 최소화는 서로 다른 단계지만 함께 쓰일 때 검토 범위를 좁힌다.[3]

## 지침이 보장하지 않는 것

`CLAUDE.md`는 자연어 지침이다.
테스트를 실제 실행하게 만드는 독립 강제 장치나 파일 권한 제한 기능이 들어 있는 것은 아니다.
모델이 문서를 읽을 수 있는 위치에 놓여야 하며, 기존 프로젝트 규칙과 충돌하지 않게 통합해야 한다.
README도 프로젝트별 지침과 합치는 용도를 설명하므로 기존 파일을 통째로 대체하는 행위를 기본 사용법으로 받아들일 필요는 없다.[1][2]

README는 속도보다 신중함에 무게를 두며 단순 오타 수정에는 판단을 적용하라고 명시한다.
따라서 작은 일을 과도한 질문과 계획으로 지연시키는 것이 목표가 아니다.
반대로 ‘간결하게’라는 원칙을 핑계로 필요한 보안 검증이나 입력 검사를 빼는 것도 요청 범위를 정확히 이해한 결과라고 볼 수 없다.
예제는 설계 판단을 보여 주는 자료이지 모든 환경의 완전한 생산 코드가 아니다.[1][3]

자료의 출처 경로도 유의할 부분이다.
현재 분석 대상은 `multica-ai/andrej-karpathy-skills`인데 README의 일부 설치 예시는 `forrestchang/andrej-karpathy-skills` 경로를 사용한다.
이 글에서는 그 경로를 임의로 고쳐 쓰거나 두 이름의 현재 관계를 단정하지 않는다.
실행 전에 실제 설치 대상과 현재 공식 파일을 확인해야 할 문서상의 차이로 남긴다.[1]

## 정리

이 프로젝트의 산출물은 더 많은 코드를 만드는 기능이 아니라, 무엇을 만들고 어디까지만 바꾸며 무엇으로 완료를 확인할지 정하는 행동 규칙이다.
