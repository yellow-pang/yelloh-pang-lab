## Mac 안에서 모델을 서비스하는 서버

oMLX는 Apple Silicon Mac에서 언어 모델을 실행하고 다른 프로그램에 API로 제공하는 추론 서버다.
추론은 이미 학습된 모델에 질문을 넣어 답을 만드는 과정이며, 이 저장소 자체가 새 언어 모델의 가중치를 제공하는 것은 아니다.
메뉴 막대 앱과 웹 관리 화면은 서버 시작, 모델 선택, 메모리와 캐시 설정을 다루는 입구다.
README는 텍스트 생성뿐 아니라 이미지와 글을 함께 읽는 모델, 문장을 수치로 바꾸는 임베딩 모델, 검색 결과 순서를 조정하는 재순위화 모델도 구분한다.[1]

로컬 모델을 하나 띄우는 것과 여러 도구가 계속 이용하는 서비스를 유지하는 일은 다르다.
긴 대화를 매번 처음부터 처리하면 중복 계산이 생기고, 여러 모델을 모두 메모리에 올려두면 다른 프로그램이 사용할 공간이 줄어든다.
oMLX의 설명은 이 두 문제를 캐시 재사용과 모델 생명주기 관리로 나누어 다룬다.
모델 답변의 품질을 바꾸는 학습 도구라기보다, 이미 선택한 모델을 어떤 자원 배분으로 제공할지 관리하는 계층이다.[1]

## 중복 계산과 모델 메모리를 따로 관리한다

KV 캐시는 모델이 앞서 읽은 입력에서 계산한 중간 상태를 보관하는 장치다.
oMLX는 이를 블록 단위로 나누고 같은 앞부분을 공유하는 요청이 재사용하도록 설명한다.
자주 쓰는 블록은 RAM의 hot tier에, 나머지는 SSD의 cold tier에 둔다.
SSD에 저장된 블록은 동일한 입력 접두부가 다시 등장할 때 읽을 수 있으며, README는 서버 재시작 뒤의 재사용도 안내한다.
이는 과거 대화의 의미를 자유롭게 검색하는 지식 저장소가 아니라, 일치하는 계산 상태를 다시 이용하는 캐시다.[1]

대표 구현인 `omlx/cache/paged_ssd_cache.py`의 `load_block_with_metadata`를 보면 먼저 메모리 캐시를 보고, 없으면 SSD 기록을 기다리는 버퍼를 확인한 뒤 디스크 파일로 내려간다.
읽을 파일이 없거나 형식 버전이 맞지 않을 때는 실패를 캐시 미스로 처리한다.
파일 이름만 남아 있다고 재사용이 보장되는 것은 아니다.
캐시 적중 통계와 모델·블록 정보를 함께 관리하는 코드를 통해 README의 계층 구조가 실제 조회 경로와 연결됨을 확인할 수 있다.[2]

동시 요청에는 continuous batching을 사용한다.
여러 요청의 생성 작업을 묶어 처리하는 방식이며 README는 `mlx-lm`의 `BatchGenerator`와 연결한다.
별도로 모델 관리에서는 최근 사용하지 않은 모델을 내리는 LRU, 자주 쓰는 모델의 고정, 유휴 시간이 지나면 내리는 TTL을 제공한다.
캐시 블록의 보관 여부와 모델 전체의 적재 여부를 같은 설정으로 생각하면 안 된다.
오래 보관할 문맥과 항상 준비할 모델은 서로 다른 자원을 사용한다.[1]

API는 OpenAI 및 Anthropic 형식의 엔드포인트를 제공하지만, 같은 요청 모양을 받아준다는 사실이 원격 모델과 동일한 응답 품질이나 모든 기능의 동등함을 뜻하지는 않는다.
예를 들어 도구 호출은 모델의 채팅 템플릿이 `tools` 매개변수를 지원해야 한다.
관리 화면의 모델별 별칭·샘플링 설정도 클라이언트 연결과 실제 모델 동작을 분리해 이해할 때 읽기 쉽다.[1]

## 예시로 따라가는 흐름

긴 공개 소스 파일을 설명한 뒤 같은 파일의 오류 처리 부분만 다시 질문하는 상황을 생각해 보자.
이해를 위한 가상 예시이며 직접 실행한 결과가 아니다.
먼저 클라이언트는 로컬 서버의 `/v1/chat/completions`로 모델 이름과 메시지를 보낸다.
서버는 모델을 준비하고 입력을 처리한 다음 답변을 반환한다.
다음 요청에도 동일한 코드와 대화 앞부분이 들어 있다면 그 앞부분에 해당하는 KV 블록의 재사용 가능성이 생긴다.
단순히 주제가 비슷한 새 문장을 보냈다고 같은 캐시를 쓴다고 해석해서는 안 된다.[1]

필요한 블록이 hot cache에 없을 때 대표 구현은 기록 대기 버퍼와 SSD 색인을 차례로 확인한다.
디스크에서 유효한 캐시를 읽으면 계산에 필요한 배열과 메타데이터를 복원하고, 파일이 없거나 읽을 수 없는 형식이면 캐시 미스로 돌아간다.
따라서 사람이 비교할 대상은 최종 답변만이 아니다.
선택된 모델이 맞는지, 캐시 적중이 실제로 있었는지, 메모리와 SSD 사용량이 설정한 범위인지도 확인해야 한다.
모델 교체나 입력 앞부분 변경이 있는 경우를 분리해야 캐시의 효과를 이해할 수 있다.[2]

마지막으로 답변 속도가 달라지더라도 이를 이 문서의 측정 결과로 볼 수는 없다.
모델 크기, 입력 길이, 동시 요청, 저장장치 상태가 달라지면 조건이 바뀐다.
README의 벤치마크 기능은 이런 조건을 확인할 입구이며, 여기서는 특정 처리량이나 우열을 재현했다고 주장하지 않는다.[1]

## 플랫폼과 노출 범위를 먼저 확인한다

README의 기본 요구사항은 Apple Silicon과 macOS 15 이상이며 소스 설치에는 지정된 Python 범위가 있다.
모델 파일도 MLX 형식과 해당 실행 라이브러리의 지원 범위를 확인해야 한다.
SSD 캐시는 추가 저장 공간을 사용하고, 일부 모델 계열의 네이티브 커널 빌드는 전체 Xcode를 요구한다.
여러 Mac에 나누어 실행하는 기능은 문서가 실험적 기능으로 구분하므로 일반 단일 Mac 사용과 동일한 준비 수준으로 소개할 수 없다.[1]

네트워크 노출도 독립적인 판단이다.
현재 README는 loopback 이외 주소로 서버를 열 때 주 API 키가 필요하며, 키 없는 추론 허용은 기본적으로 꺼져 있다고 설명한다.
이를 수동으로 켜면 접근 가능한 사용자가 추론뿐 아니라 연결된 MCP 도구와 웹 검색도 이용할 수 있다는 경고가 있다.
로컬 API 주소를 바꾸는 일이 단순한 편의 설정이 아니라 접근 권한의 확대임을 기억해야 한다.[1]

## 정리

oMLX는 Mac을 모델 API 서버로 쓰면서 모델 적재와 문맥 계산 재사용을 관리하는 프로젝트다.
RAM·SSD 계층은 반복 계산을 줄이는 설계이고, 답변 품질과 도구 수행 능력은 여전히 선택한 모델에 달려 있다.
캐시, 모델 메모리, 서버 접근 권한을 각각 구분하면 기능 목록이 실제 운영 흐름으로 이어진다.
