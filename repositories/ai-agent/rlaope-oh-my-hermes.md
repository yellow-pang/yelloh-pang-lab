## 한 줄 요약

Oh My Hermes, 줄여서 OMH는 Hermes Agent 위에서 요청을 분류하고 Skill·모델·작업 흐름을 연결하는 확장 계층이다.
Hermes를 대체하는 새 모델이나 숨겨진 코딩 실행기가 아니라, 무엇을 맡기고 어떤 근거가 있어야 완료로 볼지 정하는 운영 규칙과 플러그인 묶음으로 소개된다.[1]

## 실행했다는 말과 확인했다는 말을 분리하기

에이전트에게 코드 검토를 부탁하면 요청을 이해한 상태, 검토 도구를 실행한 상태, 수정했다고 보고한 상태, 검사가 통과한 상태가 생긴다.
이 상태들을 모두 “완료”라고 부르면 실제로 무엇이 남았는지 알기 어렵다.
OMH의 README는 `Plan · not run`, `Code · running`, `Code · reported done`, `Test · verified`를 구분한다.
계획의 존재와 실행 근거를 같은 것으로 취급하지 않는 것이 핵심이다.[1]

Skill은 특정 작업의 지침이고 workflow는 그 지침을 적용하는 단계적 절차다.
OMH는 자연어 요청에서 관련 Skill을 고르고, 모델 및 추론 노력 설정을 적용하고, 필요한 경우 독립 작업을 나누며, 검사 근거를 통해 상태를 보고하는 구조를 설명한다.
UI의 진행 표시보다 그 표시가 어떤 관찰을 의미하는지가 먼저다.[1]

## 점수가 높아도 바로 실행하지 않는 라우팅

대표 구현인 `dispatch_evidence.py`는 이미 점수를 받은 최상위 후보에 실행 결정을 내릴 만큼 강한 근거가 있는지 분류한다.
라우팅은 여기서 “요청을 어느 Skill로 보낼 것인가”를 고르는 과정이다.
이 모듈은 점수나 순위를 바꾸지 않고, 후보가 왜 점수를 받았는지 기록한 label을 읽는다.[2]

명시적인 Skill 호출, 직접 조건, 해당 Skill의 고유한 구문은 강한 근거로 취급할 수 있다.
반대로 우연히 공통 단어가 많이 등장한 경우는 약한 근거로 남겨 후보 목록을 제시하고 선택을 명확히 하는 경로로 보낸다.
코드 주석은 `before`와 `merge` 같은 일상 단어가 겹쳐 높은 점수가 된 사례를 설명한다.
“관련 단어가 있다”와 “이 작업을 요청했다”를 구분하려는 설계다.[2]

특히 시간 표현은 의도와 함께 읽는다.
“매일 아침”에 대응하는 영어 구문은 무엇을 하라는 요청 없이 습관을 보고하는 문장에도 나타날 수 있다.
구현은 요청 형태가 아닌 경우 cadence 구문의 기여를 제외하고, 다른 Skill도 비슷한 구문 근거를 가진 경우 우위를 확인한다.
비ASCII 입력은 영어 단어 기반 판정으로 잘못 걸러내지 않도록 별도 분기를 둔다.
이 분기의 존재가 한국어 전체 정확도를 증명하는 것은 아니다.[2]

## 모델 선택, 병렬 작업, 기억은 다른 결정

README의 모델 설정은 작업 범주별로 모델과 노력 수준의 순서 있는 후보 체인을 둔다.
제공자가 모델을 거절하면 다음 후보를 적용하는 구조이며, 모델 추천 목록 자체가 인증 성공이나 실제 호출 가능성의 증거는 아니다.
어떤 모델을 고를지와 어느 실행자가 코드를 변경할지는 별개로 읽어야 한다.[1]

병렬 작업에서는 파일이 겹치지 않는 작업 단위와 독립 검토를 강조한다.
또한 검증 기록 재사용은 수정본·명령·환경이 모두 맞을 때에만 한다고 설명한다.
이전에 검사가 성공했다는 사실이 새 코드에서도 유효한지 따지는 조건이다.
상태 화면에 비용을 알 수 없을 때는 0으로 표현하지 않고 unknown으로 남기는 설명도 같은 증거 경계에 속한다.[1]

장기 기억은 Hermes 자체 기억과 별도인 파일 기반 저장소로 소개된다.
후보를 검토 카드에 올려 승인·거절·보류를 기록하고, 승인된 기억에는 출처와 재검토 기한을 붙인다.
다음 작업에는 관련성과 입력 예산에 맞춘 회상 묶음을 전달한다.
모든 대화를 자동으로 사실화해 저장하는 방식과는 구별해야 한다.[1]

## 예시로 따라가는 흐름

이해를 위한 가상 예시이며 직접 실행한 결과가 아니다.
사용자가 영어로 병합 전에 검토를 요청했다고 하자.
먼저 라우터가 여러 Skill에 점수를 주더라도 `dispatch_evidence`는 최고 점수의 이유를 다시 본다.
명시적으로 코드 검토 Skill을 부른 경우와 `before`, `merge` 단어만 겹친 경우는 같은 실행 근거가 아니다.
약한 경우에는 최상위 후보를 곧바로 수행하기보다 후보 목록을 유지해 Hermes가 의도를 더 분명히 선택할 수 있도록 한다.[2]

검토 경로가 정해지면 계획이 생겼다는 표시와 실제 실행자 프로세스가 있다는 표시가 구분된다.
실행자가 변경을 마쳤다고 답하면 아직 reported done이다.
해당 수정본에 대해 필요한 검사가 돌아와야 verified로 표현할 수 있다.
사람이 확인할 부분은 어떤 Skill을 골랐는지, 선택 근거가 실제 요청과 맞는지, 검사 명령과 환경이 현재 수정본에 대응하는지다.[1]

작업 뒤 얻은 교훈도 곧바로 영구 기억이 되는 것은 아니다.
README의 기억 흐름에서는 검토를 거친 후보만 승인 기록으로 남는다.
따라서 이 사례의 최종 산출물은 수정 파일 하나뿐 아니라 선택 이유, 실행 상태, 검사 근거와 승인된 교훈의 구별이다.
이 구분이 실제 세션에서 지켜지는지는 실행 기록을 통해 따로 확인해야 한다.[1]

## 설명된 효과와 측정된 효과의 경계

README에는 모델별 조정 및 특정 코딩 과제에 대한 측정 설명이 있다.
그러나 제품 전체의 Hermes 단독 대비 비교 절은 아직 측정 실행이 공개되지 않았다고 명시한다.
부분 실험의 숫자를 전체 제품의 일반적인 비용 절감이나 품질 향상으로 확장해서는 안 된다.
이번 글은 그런 성능 수치를 재현하거나 인용해 우열을 판정하지 않는다.[1]

설치와 setup도 구별된다.
패키지를 받았다고 호스트 등록, 제공자 설정과 모델 체인이 준비되었다는 뜻은 아니다.
기존 Hermes 설정을 바꾸는 과정이 포함될 수 있으므로 실제 적용 시에는 문서의 관리 범위와 승인 조건을 확인해야 한다.
이 조사는 설정을 실행하거나 현재 사용 환경을 바꾸지 않았다.[1]

## 정리

OMH는 Hermes의 작업 선택과 실행·검증 보고를 조정하는 계층이다.
기능 수보다 라우팅 근거, 완료 상태, 검토된 기억의 경계를 읽어야 실제로 무엇을 추가하는지 드러난다.
