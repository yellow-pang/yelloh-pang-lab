## 한 줄 요약

Ponytail은 코딩 에이전트가 불필요한 코드를 늘리지 않도록 판단 순서와 경계를 제공하는 Skill·플러그인 모음이다.
새 컴파일러나 자동 코드 압축기가 아니라, 기존 코드와 표준 기능을 먼저 살피게 하는 작업 지침이다.
“적게 작성하기”는 문제 이해와 안전 장치를 생략하라는 뜻이 아니라고 중심 Skill이 명시한다.[1][2]

## 요청보다 큰 설계를 만드는 문제

날짜를 입력받는 화면 하나가 필요한데 새 라이브러리와 감싸는 컴포넌트, 별도의 스타일 체계까지 추가될 수 있다.
Ponytail의 README는 이런 상황과 브라우저의 `<input type="date">`를 대비한다.
이는 모든 날짜 UI를 한 줄로 해결하라는 보편 법칙보다, 플랫폼에 이미 있는 기능을 먼저 검토하라는 대표 예시다.[1]

프로젝트는 YAGNI, 즉 아직 필요하지 않은 기능을 미리 만들지 않는 원칙에서 출발한다.
미래를 대비한다는 이유로 추상화와 설정을 추가하기 전에 실제 요구를 만족하는지 묻는다.
줄 수 자체를 최소화하는 코드 골프와도 구별하며, 읽기 어려운 기교보다 평범한 코드를 택하도록 한다.[1][2]

## 사다리는 읽기를 대신하지 않는다

판단 순서는 필요성 확인, 저장소 안의 기존 기능 재사용, 표준 라이브러리, 플랫폼 내장 기능, 이미 설치된 의존성, 작은 표현, 필요한 최소 구현으로 이어진다.
처음 성립하는 단계에서 멈추도록 하지만, 먼저 관련 코드와 실제 흐름을 읽으라는 조건이 붙는다.
재사용할 함수가 있는지 조사하지 않고 새로운 짧은 함수를 쓰는 것은 이 지침의 목적과 다르다.[2]

버그 수정에서도 증상만 막지 않고 바꿀 함수의 호출 경로를 살펴 공통 원인을 고치도록 한다.
한 화면의 오류를 가리는 작은 수정이 다른 호출자에 같은 문제를 남긴다면 좋은 최소 변경이 아니다.
코드가 짧다는 결과보다 어디를 바꿔야 하는지 제대로 찾는 판단이 앞선다.[2]

알려진 한계가 있는 단순화에는 `ponytail:` 주석으로 한계와 확장 조건을 적도록 한다.
예를 들어 전역 잠금이나 단순 탐색처럼 현재는 충분해도 특정 조건에서 교체해야 할 선택을 드러낸다.
이렇게 해야 “나중에”라는 말이 근거 없는 추측이 아니라 확인 가능한 전환 조건이 된다.[2]

## 강도와 안전 경계

lite는 요청대로 구현하되 더 간단한 대안을 알리고, full은 기본 사다리를 적용하며, ultra는 필요성을 더 강하게 재검토하는 모드다.
그러나 명시적으로 요구한 기능, 신뢰 경계의 입력 검증, 데이터 손실을 막는 오류 처리, 보안과 접근성은 줄이지 말아야 할 대상으로 명시한다.
사용자가 전체 구현을 요구하면 반복해서 반박하지 않고 수행하도록 한다.[2]

간단하지 않은 분기·반복·파서·보안 관련 로직에는 깨졌을 때 실패하는 최소 실행 검사를 남기라는 규칙도 있다.
“테스트 코드가 늘어나니 모두 생략한다”는 방식이 아니다.
설명 역시 사용자가 보고서나 상세 해설을 요청하면 충분히 제공하도록 예외가 있으므로, 모든 응답을 무조건 짧게 만드는 문체 도구와도 다르다.[2]

## 예시로 따라가는 흐름

공식 README의 날짜 선택기 요청을 읽는 예시다.
입력은 날짜 선택 기능을 추가하라는 요구다.
에이전트는 먼저 기존 프로젝트의 해당 화면과 데이터 흐름을 확인하고 이미 쓰는 컴포넌트가 있는지 살핀다.
요구가 브라우저의 내장 날짜 입력으로 충족된다면 새 패키지와 감싸는 계층을 만드는 대신 내장 요소를 선택하는 방향이 Ponytail의 사다리에 해당한다.[1][2]

출력 예시의 한 줄 HTML은 그 선택을 압축해서 보여주는 설명이며, 실제 앱 전체 수정이 한 줄이라는 측정값은 아니다.
화면의 라벨, 입력값 검증, 저장 경로와 기존 접근성 조건까지 사라지는 것도 아니다.
사람은 특수한 날짜 범위나 표시 요구가 있었는지, 내장 UI가 실제 지원 환경에서 요구를 만족하는지, 불필요하다고 제외한 기능이 명시된 요구는 아닌지 확인해야 한다.
조건이 충족되지 않으면 사다리의 다음 단계에서 필요한 구현을 해야 한다.
이 글에서는 날짜 입력 화면을 만들거나 브라우저로 확인하지 않았고, 공식 예시를 동작 원리 설명에만 사용했다.[1][2]

## 수치보다 실험 조건을 먼저 읽는다

README는 코드량·비용·시간 감소 결과를 소개한다.
추가 확인한 벤치마크 문서는 Haiku 4.5와 특정 공개 프로젝트, 제한된 과제와 반복 횟수를 사용했다고 명시한다.
과거의 단일 응답 줄 수 측정은 설명문까지 세어 차이를 부풀렸다는 비판을 받아, 실제 에이전트가 남긴 코드 변경을 세는 방식으로 바꾸었다고 설명한다.[3]

이 보고서의 보안 과제는 알려진 방어 조건을 유지하는지 보는 결정적 검사다.
보고서도 이를 코드가 안전하다는 증명으로 보지 말라고 경고한다.
일부 기능 과제에서는 서버나 브라우저를 실행하지 않고 작성된 코드를 측정했다고 밝힌다.
따라서 README의 강한 안전성 문구를 모든 프로젝트에 대한 보증으로 옮기면 안 된다.
여기에 적힌 결과는 저자의 측정이며 이 글에서 재현한 수치가 아니다.[3]

## 같은 규칙도 호스트마다 들어가는 방식이 다르다

지침 파일을 읽는 방식과 생명주기 Hook으로 매번 규칙을 넣는 방식은 다르다.
README는 일부 플러그인에서 Node.js가 비대화형 셸의 PATH에 있어야 자동 활성화 Hook이 동작한다고 설명한다.
명령을 제공하는 Skill 호스트와 규칙만 읽는 어댑터도 구분한다.[1]

Cursor의 하위 에이전트나 클라우드 실행에 대한 제약처럼 호스트별 예외도 있다.
설치 해제 후 모드 상태나 설정이 남을 수 있다는 안내 역시 확인할 부분이다.
여러 제품 이름이 호환 목록에 있다는 사실만으로 동일한 모드 전환과 주입 기능을 제공한다고 판단해서는 안 된다.[1]

## 정리

Ponytail은 코드 작성 전에 재사용과 내장 기능을 검토하도록 요구한다.
줄어든 코드가 목적을 만족하고 안전 경계를 보존해야 하며, 벤치마크의 제한된 결과와 실제 프로젝트 검증은 별개다.
