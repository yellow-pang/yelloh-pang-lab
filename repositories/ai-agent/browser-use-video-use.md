## 한 줄 요약

video-use는 코딩 에이전트에게 원본 영상을 읽고 편집안을 만들며 렌더링 도구를 실행하게 하는 Skill과 Python 보조 스크립트 모음이다.
사용자가 타임라인을 직접 조작하는 완성형 GUI 편집기보다는, 대화로 편집 방향을 정하고 파일 산출물을 만드는 작업 절차에 가깝다.
README는 원본 폴더를 입력으로 받고 그 아래 `edit/final.mp4`를 만드는 흐름을 안내한다.[1]

## 영상을 매 프레임 읽는 대신 발화를 기준으로 고른다

여러 번 촬영한 설명 영상에는 같은 문장의 다른 테이크, 말실수, 긴 침묵이 섞일 수 있다.
이 프로젝트는 전체 영상을 프레임마다 모델에 보내기보다 발화의 시간 정보를 기본 읽기 자료로 삼는다.
README는 단어별 시각과 화자·음성 이벤트가 있는 전사 결과를 모으고, 필요할 때만 영상 프레임과 파형을 확인하는 두 층을 설명한다.[1]

전사란 소리를 텍스트로 바꾸는 작업이다.
여기서는 “무슨 말을 했는가”뿐 아니라 “그 단어가 원본의 언제 나왔는가”가 중요하다. `takes_packed.md`는 여러 소스의 전사를 구절 단위로 묶어 에이전트가 읽는 자료이며, 애매한 침묵이나 테이크 비교에서는 `timeline_view`로 프레임·파형·단어 표기가 함께 있는 이미지를 확인하도록 한다.[1][2]

따라서 README의 영상 전체를 보지 않는다는 설명은 시각 정보를 전혀 쓰지 않는다는 뜻이 아니다.
텍스트를 중심으로 편집 후보를 고르고, 판단이 필요한 구간에서 시각 자료를 보충하는 방식이다.
자료량 절감에 관한 README의 수치는 프로젝트가 설명하는 예시이며 이번 조사에서 측정한 성능 결과는 아니다.[1]

## 편집 결정을 파일로 남기는 구조

Skill의 순서는 원본 조사, 문제 구간 메모, 사용자와 대화, 전략 제안, 승인, 실행, 미리보기 검토, 기록이다.
목표 길이나 화면 비율을 무조건 같은 값으로 정하지 않고 실제 재료와 요구에 맞춰 질문하도록 한다.
코드 실행 권한이 있어도 컷 편집을 시작하기 전에 사용자가 전략을 확인해야 한다는 규칙이 반복해서 나온다.[2]

승인한 편집 결정은 `edl.json`에 기록한다.
EDL은 사용할 원본과 시작·끝 시각, 순서 등을 담는 편집 결정 목록이다.
여기에 색 보정, 합성할 애니메이션, 자막 파일 같은 정보가 이어진다.
최종 영상을 한 번에 설명하는 모호한 지시와 달리 어떤 원본 구간이 어떤 이유로 선택되었는지 파일로 추적할 수 있는 구조다.[2]

원본 시각과 완성본 시각도 구분한다.
여러 원본의 일부만 이어 붙이면 원본에서의 단어 위치가 그대로 완성본 자막 시각이 될 수 없다.
Skill은 구간 시작과 완성본 누적 위치를 반영해 자막 시각을 변환하는 규칙을 제시한다.
또 자막은 합성 요소 뒤에 적용해야 겹치는 그림 아래 가려지지 않는다고 설명한다.[2]

## 예시로 따라가는 흐름

개인 공개 튜토리얼을 여러 테이크로 촬영하고, 말실수와 긴 침묵을 줄인 영상으로 만들려는 상황을 생각해 보자.
이해를 위한 가상 예시이며 직접 실행한 결과가 아니다.
입력은 원본 영상 폴더와 남겨야 할 설명, 목표 길이·화면 비율 같은 요구다.
문서의 흐름에서는 먼저 파일 정보를 확인하고 전사를 만든 뒤 `takes_packed.md`에서 구절과 시간 범위를 읽는다.[2]

에이전트는 어떤 테이크의 설명이 이어지는지, 잘못 말한 부분이 있는지 정리하고 컷 방향·자막·색 보정 계획을 제안한다.
사용자가 확인하면 선택한 원본 범위를 EDL에 기록하고, 애매한 지점은 타임라인 이미지로 살핀다.
렌더 단계는 구간을 추출하고 이어 붙인 다음 필요한 합성과 자막을 적용한다.
원본 파일은 유지하고 전사, EDL, 검토 이미지, 미리보기와 최종 영상은 원본 폴더의 `edit/` 아래에 모으도록 되어 있다.[2]

미리보기가 생기면 원본이 아니라 렌더된 결과의 각 컷 경계에서 프레임과 파형을 다시 확인한다.
말이 중간에 잘리지 않았는지, 자막이 가려지지 않았는지, 합성 영상이 알맞은 시점에 나오는지 살피는 단계다.
사용자는 그 결과를 실제로 재생해 발화 의미와 리듬, 자막 오탈자, 듣기 편한 음량을 확인해야 한다.
여기서 기대 산출물의 경로를 설명한 것은 파일을 생성했다는 뜻이 아니며, 전사 정확도나 최종 영상의 품질을 확인한 실행 기록도 아니다.[1][2]

## 자동 검토가 사람의 시청을 대신하지는 않는다

Skill은 컷을 단어 중간에 두지 않기, 경계에 여유를 두기, 소리의 갑작스러운 끊김을 줄이는 페이드, 전사 캐시 재사용 등을 고정 규칙으로 둔다.
원본이 바뀌지 않았다면 다시 전사하지 않게 하는 규칙은 외부 호출을 반복하지 않고 같은 입력을 재사용하는 경계다.
반면 폰트나 색상, 구체적인 연출값은 대부분 특정 영상의 예시라고 명시한다.[2]

자체 검토에서는 음량과 피크를 측정하되 실제로 소리를 듣지 못한다는 한계를 밝히도록 한다.
문제가 있으면 수정 후 다시 렌더하고, 반복 검토 횟수에 한도를 두어 남은 문제를 사용자에게 알리게 한다.
따라서 README의 “self-eval”은 자동으로 좋은 영상을 보증한다는 뜻이 아니라, 확인할 항목과 재시도 절차를 지침으로 제공한다는 의미로 읽어야 한다.[2]

실행에는 셸을 사용할 수 있는 에이전트와 ffmpeg·ffprobe, Python 의존성이 필요하며, 전사 경로는 ElevenLabs Scribe API를 전제로 한다.
선택한 애니메이션 도구에 따라 Node.js나 추가 도구가 필요할 수 있다.
전체가 로컬 오프라인으로만 처리된다고 생각하면 안 되고, 전사할 음성의 외부 전달 조건과 비용·사용 권한을 먼저 확인해야 한다.[1][2]

병렬 하위 에이전트를 쓰는 지침도 실행 환경에 의존한다.
Markdown 지침을 읽을 수 있다는 사실과 해당 환경이 같은 하위 에이전트 도구를 제공한다는 사실은 다르다.
공개할 영상이라면 소재·음악·이미지의 권리, 출연자의 동의와 원본 보존도 편집 성능과 별도로 확인할 사항이다.

## 정리

video-use는 발화 시간표를 중심으로 편집 결정을 만들고, 렌더와 검토 결과를 파일로 남기는 대화형 편집 절차다.
승인된 전략과 원본을 보존하면서 작업하지만, 외부 전사와 실행 도구가 필요하고 최종 시청 판단은 별도로 남는다.
