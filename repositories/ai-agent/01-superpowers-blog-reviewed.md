# Superpowers는 왜 바로 코딩하지 않을까? 쓰던 개발 절차를 다시 살펴봤다

AI Agent로 개발하면서 어느 순간부터 익숙해진 순서가 있다.

바로 코드를 수정하는 대신 먼저 분석을 하고, 계획을 세우고, 테스트와 구현을 진행한 뒤 다시 검증하는 흐름이다. 나는 이 과정을 `Analysis → Plan → 구현 → 검증 → Steps`처럼 정리해서 사용해왔다.

그동안은 Agent가 제안하는 순서를 따라가는 쪽에 가까웠다. 그런데 작업이 이어지면서 궁금해졌다. 왜 구현 전에 이렇게 많은 단계를 거쳐야 할까. 이미 테스트를 통과했는데 왜 또 리뷰를 하고, 마지막에 검증 명령을 다시 실행할까.

한편으로는 과정이 길게 느껴지기도 했다. 작은 수정에도 여러 절차가 붙고, 기능을 만들수록 테스트와 코드가 함께 쌓였다. 안전하게 개발하는 방법이라고 생각해서 사용했는데, 나중에는 무엇을 남기고 무엇을 지워야 하는지 판단하기가 어려웠다.

그래서 이번에는 새로운 도구를 찾기 전에, 이미 사용하고 있던 **Superpowers가 어떤 원리로 Agent의 행동을 바꾸는지**부터 다시 정리해봤다.

## 1. Superpowers를 한 줄로 설명하면

> Superpowers는 Coding Agent에게 소프트웨어 개발의 순서와 판단 기준을 제공하는 개발 방법론 패키지다.

여기서 **Coding Agent**는 코드를 설명하는 데서 끝나지 않고, 파일을 읽거나 수정하고 명령을 실행하며 개발 작업을 수행하는 AI를 말한다. **방법론**은 그 일을 어떤 원칙과 순서로 진행할지 정해둔 체계다.

Superpowers의 공식 소개도 단순한 Skill 목록보다 전체 개발 방법론이라는 점을 강조한다. 요구사항을 이해하는 단계부터 설계, 계획, 구현, 리뷰, 검증, 브랜치 마무리까지 여러 Skill이 연결되어 있다.[1]

처음에는 개발에 도움이 되는 매뉴얼을 모아둔 정도로 생각하기 쉬웠다. 하지만 내용을 따라가 보면 핵심은 지식의 양보다 **Agent가 언제 멈추고, 무엇을 확인한 뒤 다음 단계로 넘어갈 것인가**에 있다.

더 좋은 코드를 한 번에 뽑아내는 비법이라기보다는, 잘못된 방향으로 빠르게 달려가는 일을 줄이려는 장치에 가깝다고 이해했다.

## 2. Agent가 바로 구현하지 않는 데는 이유가 있었다

단순하게 개발을 요청했을 때의 흐름은 다음처럼 생각할 수 있다.

```text
요청을 받는다
→ 관련 파일을 읽는다
→ 코드를 수정한다
→ 테스트한다
→ 완료했다고 알려준다
```

이 방식이 항상 나쁜 것은 아니다. 문제는 첫 단계에서 요청을 잘못 이해했을 때다. 잘못 이해한 요구사항을 기준으로 코드를 만들고, 그 코드에 맞는 테스트까지 작성하면 테스트가 통과해도 내가 원한 기능과는 다를 수 있다.

Superpowers는 이 사이에 확인 단계를 넣는다.[1][2]

```text
요청과 관련된 Skill 확인
→ 작업 규모와 요구사항 파악
→ 설계 확인과 사용자 승인
→ 필요한 경우 구현 계획 작성
→ 작업 공간과 테스트 기준선 확인
→ 작은 단위로 테스트와 구현
→ 별도 리뷰와 최종 검증
→ 브랜치를 어떻게 처리할지 결정
```

여기서 인상적이었던 것은, 조사한 버전이 모든 작업에 똑같이 긴 문서를 요구하지는 않는다는 점이다.

`brainstorming`은 가능성만 확인하는 임시 실험인 **Spike**, 기존 코드 흐름 안에서 범위가 분명한 작은 변경인 **Bounded**, 새 기능 체계나 구성 요소 사이의 연결 방식에 영향을 주는 **Architectural**로 나눈다. Bounded는 짧은 설계와 승인을 채팅에서 확인하고 별도 명세·계획 문서를 만들지 않는다. 반면 Architectural은 명세와 구현 계획을 거친다. 작업 규모에 따라 절차는 달라져도, 진행 방향을 사용자에게 승인받는 원칙은 남아 있다.[2]

이 부분을 보면서, 내가 과정이 무겁다고 느낀 경험과 Superpowers가 의도한 사용법을 구분해야겠다고 생각했다. 절차가 있다는 것과 모든 작업에 가장 큰 절차를 적용한다는 것은 같은 이야기가 아니었다.

## 3. 자주 보던 단계는 서로 다른 문제를 막고 있었다

### 분석과 계획은 같은 일을 두 번 하는 것이 아니었다

`brainstorming`은 무엇을 만들지부터 확인한다. 요청이 모호하다면 질문을 하고, 가능한 접근을 비교하고, 구현 전에 설계를 보여준다.[2]

반면 `writing-plans`는 합의한 설계를 실제 작업 순서로 바꾼다. 어떤 파일을 수정할지, 어떤 테스트로 확인할지, 어떤 명령을 실행할지처럼 구현자가 바로 따라갈 수 있는 내용으로 나눈다.[3]

내가 이해한 차이는 이렇다.

> 분석은 “무엇을 왜 해야 하는가”를 정하는 일이고, 계획은 “그 일을 어디에서 어떤 순서로 할 것인가”를 정하는 일이다.

내가 쓰는 `Analysis → Plan → 구현 → 검증 → Steps`라는 이름 자체가 Superpowers의 공식 고정 단계는 아니다. 특히 내가 완료 후 기록으로 사용하는 Steps와 Superpowers의 계획 안에 있는 작업 단계는 구분할 필요가 있었다.

그래도 구현 전에 목적을 확인하고, 그것을 실행 가능한 순서로 바꾼다는 방향은 연결되어 있었다.

### TDD는 테스트를 먼저 적는 데서 끝나지 않는다

**TDD(Test-Driven Development)**는 원하는 동작을 테스트로 먼저 표현하고, 그 테스트를 통과시키며 개발하는 방식이다.

Superpowers의 TDD Skill은 다음 반복을 강조한다.[4]

```text
RED: 원하는 동작이 아직 없어서 테스트가 실패하는지 확인
→ GREEN: 그 테스트를 통과시키는 최소한의 코드 작성
→ REFACTOR: 동작을 유지하면서 중복과 불필요한 복잡성 정리
```

새로 추가하거나 고칠 동작을 확인하는 테스트가 변경 전부터 통과한다면, 정말 그 문제를 잡는지 먼저 점검해야 한다. 여기서 RED는 단순한 문법 오류나 환경 설정 오류가 아니라, 원하는 동작이 없거나 잘못되어 실패하는 상태를 뜻한다.[4]

하지만 이번에 더 눈에 들어온 것은 마지막 단계였다. 테스트를 만들고 통과시키는 것만 반복하면 코드와 테스트가 계속 늘어날 수 있다. **REFACTOR는 다음 기능을 추가하기 위한 대기 시간이 아니라, 지금 생긴 중복과 복잡성을 줄이는 단계**였다.

내가 앞으로 더 의식해서 봐야 할 부분도 여기에 있다고 느꼈다.

### 디버깅은 떠오르는 수정부터 적용하지 않도록 한다

`systematic-debugging`은 원인을 확인하기 전에 코드를 바꾸는 행동을 경계한다. 오류를 재현하고, 최근 변경과 데이터 흐름을 확인하고, 가설 하나를 세워 작은 변경으로 검증하는 순서를 제시한다.[5]

오류가 났을 때 Agent가 몇 가지 수정을 연달아 적용하면 무언가 진행되는 것처럼 보이기 쉽다. 하지만 여러 곳을 한꺼번에 바꾸면 무엇이 원인이었는지, 어떤 수정이 효과가 있었는지 더 알기 어려워질 수 있다.

그래서 이 Skill은 빨리 수정하는 기술보다 **수정을 시작할 근거를 먼저 찾는 방법**으로 이해하는 편이 맞았다.

### 리뷰와 검증도 서로 다른 일을 한다

**Code Review**는 변경이 요구사항에 맞는지, 설계나 코드에 놓친 문제가 없는지 검토하는 일이다. **Verification**은 테스트, 빌드, 검사 명령 같은 실제 결과로 특정 주장을 확인하는 일이다.

Superpowers에는 리뷰를 요청하는 Skill과 받은 리뷰를 검토하는 Skill이 따로 있다. 리뷰 의견이라고 무조건 반영하지 말고, 현재 코드에서 맞는 지적인지 확인한 뒤 적용하도록 한다.[7]

`verification-before-completion`은 더 직접적이다. “완료됐다”거나 “테스트가 통과한다”고 말하려면, 그 주장을 뒷받침하는 명령을 새로 실행하고 결과를 읽어야 한다.[8]

생각해보면 테스트 통과, 요구사항 충족, 코드 품질은 서로 다른 이야기다. 테스트가 통과했다는 이유로 세 가지를 한꺼번에 확인한 것처럼 받아들이지 말아야겠다고 느꼈다.

## 4. Skill은 결국 Markdown 아닌가?

이 부분도 궁금했다. 파일을 열어보면 자연어로 된 지침이 나오는데, 긴 프롬프트를 저장해둔 것과 얼마나 다를까.

가장 단순한 Skill이 Markdown 지침에서 시작한다는 이해는 맞다. Agent Skills 형식은 `SKILL.md`를 중심으로 이름과 설명, 작업 지침을 담고, 필요한 경우 스크립트나 참고 자료를 함께 둘 수 있게 한다.[10]

```text
skill-name/
├── SKILL.md       이름, 설명, 작업 지침
├── scripts/       선택: 필요한 실행 코드
├── references/    선택: 자세한 참고 자료
└── assets/        선택: 템플릿 같은 자료
```

Agent Skills 형식은 모든 내용을 매번 한꺼번에 불러오기보다, 이름과 짧은 설명을 먼저 보고 관련 Skill이 필요할 때 본문과 추가 자료를 읽는 **단계적 공개** 방식을 안내한다. 실제로 언제 어떤 파일을 불러오는지는 사용하는 Agent 환경에도 달려 있다.[10]

용어를 구분하면 관계가 조금 더 선명해진다.

| 구분 | 내가 이해한 역할 |
| --- | --- |
| Prompt | 지금 무엇을 원하는지 전달하는 요청 |
| Skill | 특정 종류의 작업을 처리하는 재사용 가능한 지침과 자료 |
| Tool | 파일 수정이나 명령 실행처럼 실제 행동을 수행하는 기능 |
| Agent | 요청과 결과를 보고 다음 행동을 결정하는 실행 주체 |
| Agent Harness | 모델, 도구, 권한, 대화 상태 등을 연결하는 실행 환경 |

즉 Skill 파일 혼자 코드를 수정하거나 테스트를 실행하는 것은 아니다. **Harness가 지침을 읽을 수 있게 연결하고, Agent가 그 지침을 따라 Tool을 사용해야 실제 작업이 된다.**

Superpowers에는 이 연결의 출발점으로 `using-superpowers`가 있다. 관련 Skill이 있는지 먼저 확인하게 하는 초기 지침이며, 플러그인과 환경별 연결 방식이 이 지침을 Agent에 전달한다. 파일을 모아두는 것과 Agent가 필요한 순간에 찾아 읽도록 만드는 것은 다른 일이었다.[1][14]

또 하나 구분할 점은 강한 문구와 실제 강제력이다. Skill에 “반드시 확인하라”거나 “승인 전 구현 금지”라고 적혀 있어도, Markdown 자체가 운영체제의 파일 수정을 막는 것은 아니다. Agent가 지침을 이해하고 따라야 한다.[1][10]

이 때문에 Superpowers를 설치했다는 사실만으로 모든 절차가 정확히 지켜졌다고 믿기는 어렵다. 중요한 것은 실제로 무엇을 읽고 어떤 검증을 했는지였다.

## 5. Worktree와 Subagent는 단순히 빨라지기 위한 기능이 아니었다

**Git Worktree**는 같은 저장소의 다른 브랜치를 별도 폴더에서 열어 작업할 수 있게 하는 기능이다. Superpowers는 작업 공간을 분리하고 시작 시 테스트 상태를 확인하는 절차를 둔다.[6]

이렇게 하면 현재 작업 중인 변경을 건드릴 위험을 줄일 수 있다. 시작부터 실패하던 테스트와 이번 변경 때문에 실패한 테스트를 구분하는 데도 도움이 된다.

다만 Worktree는 작업 파일을 나누는 기능이지, 명령의 권한이나 네트워크 접근까지 막는 보안 격리 환경은 아니다. Git의 일부 정보도 공유하므로, 안전한 실행 권한은 별도로 관리해야 한다.[15]

**Subagent**는 큰 작업의 일부를 위임받아 별도 Context에서 수행하는 보조 Agent다. 여기서 **Context**는 AI가 지금 판단할 때 실제로 참고하는 대화와 자료의 범위다.

Superpowers의 `subagent-driven-development`는 작업별 구현자와 별도 리뷰어를 두고, 필요한 자료를 전달해 좁은 문제에 집중하도록 한다. 구현한 Agent의 완료 보고를 그대로 믿기보다, 다른 Context에서 요구사항 준수와 코드 품질을 다시 확인하려는 목적이다.[7]

그렇다고 Agent 수를 늘리면 무조건 좋아지는 것은 아니다. 배경을 충분히 전달하지 않으면 잘못된 전제로 작업할 수 있고, 호출 비용과 검토 시간도 늘어난다. 같은 모델이 비슷한 오해를 공유할 가능성도 남는다.

내가 받아들인 핵심은 병렬 실행 자체보다 **작업과 판단을 적절히 분리하는 것**이었다. 작은 수정 하나까지 무조건 여러 Agent로 쪼개는 것은 별개의 판단이 필요하다.

마지막 브랜치 처리도 같은 맥락이었다. `finishing-a-development-branch`는 검증 이후 병합할지, **PR(Pull Request, 변경 사항의 병합을 요청하는 절차)**을 만들지, 브랜치를 유지할지 사용자에게 선택을 돌려준다. 작업 폐기는 사용자가 명시적으로 요청하고 확인한 경우에만 진행한다. **코드 작업이 끝났다는 것과 저장소에 통합하거나 삭제해도 된다는 것은 구분하는 셈이다.**[9]

## 6. 그런데 왜 코드와 테스트는 계속 쌓였을까

이 글을 정리하면서 가장 다시 보고 싶었던 질문이다.

Superpowers를 쓰면서 코드와 테스트가 많아졌다고 해서, 그 원인을 도구 하나로만 설명하기는 어렵다. TDD를 어떤 방식으로 적용했는지, Agent에게 어떤 보존 기준을 줬는지, 요구사항이 얼마나 바뀌었는지가 함께 영향을 줄 수 있다.

특히 “기존 코드를 건드리지 말고 테스트를 모두 통과시켜라”는 요청만 반복하면, Agent 입장에서는 오래된 코드와 테스트도 계속 지켜야 하는 기준으로 받아들이기 쉽다. 기존 구조를 정리하는 대신 새로운 분기나 호환 코드를 옆에 붙이는 쪽으로 갈 수 있다.

내가 구분해야 할 것은 변경 방법과 보존할 기능의 범위였다. TDD 지침은 변경을 검증하는 데 도움을 주지만, 과거에 만들었던 기능을 지금도 유지해야 하는지는 현재 요구사항을 보고 별도로 판단해야 한다.

이번 자료를 읽으며 가장 중요하게 남긴 문장은 이것이다.

> 테스트가 존재한다는 사실과 그 테스트가 보호하는 기능이 지금도 필요하다는 사실은 다르다.

테스트는 특정 동작을 지켜야 한다는 주장이다. 하지만 제품의 요구사항이 바뀌면 그 주장도 다시 확인해야 한다. Google의 코드 삭제 사례에서도 사용하지 않는 코드의 테스트가 계속 실행될 수 있다는 문제를 다룬다. 테스트 실행 자체를 서비스에서 실제로 쓰인다는 증거로 볼 수는 없다.[12]

그렇다고 의미를 바로 이해하지 못한 테스트를 지워도 된다는 뜻은 아니다.

| 테스트가 보호하는 내용 | 먼저 생각할 방향 |
| --- | --- |
| 현재 필요한 사용자 동작이나 외부 약속 | 유지해야 하는 안전망인지 확인 |
| 과거의 실제 버그와 재발 가능성 | 같은 위험을 다른 테스트가 보호하는지 확인 |
| 이미 다른 테스트가 확인하는 같은 동작 | 중복을 줄일 수 있는지 검토 |
| 내부 함수 호출 순서 같은 구현 세부사항 | 실제 동작 중심으로 바꿀 수 있는지 검토 |
| 제거된 요구사항이나 폐기된 기능 | 관련 코드와 함께 삭제 가능한지 조사 |

여기서 외부 약속은 다른 코드나 사용자가 기대하는 API, 데이터 형식, 동작 같은 것을 뜻한다. 내부에서 호출되지 않는 것처럼 보여도 외부 사용자가 있다면 함부로 제거할 수 없다.

테스트도 작성하고 실행하고 고치는 데 비용이 든다. 실제 버그가 아니라 무관한 내부 변경 때문에 계속 깨진다면 안전망의 품질을 다시 봐야 한다.[11]

앞으로 Agent에게 정리를 맡길 때는 단순히 테스트 수를 줄이라고 하기보다, **현재 필요한 동작과 실제 호출부를 먼저 확인하고, 각 테스트가 무엇을 보호하는지 설명하게 하는 것**이 더 중요하겠다고 생각했다.

## 7. 장점이 분명해도 모든 작업에 같은 절차가 필요한 것은 아니다

Superpowers의 장점은 각 단계의 이유를 따라갈 수 있다는 점이다. 성급한 구현을 멈추고, 합의를 계획으로 남기고, 실패 테스트와 리뷰를 거쳐 실행 결과로 완료를 확인한다.

반대로 작은 작업에 모든 절차를 크게 적용하면 부담이 된다. 문구만 바꾸는 일과 새로운 시스템을 추가하는 일을 같은 규모로 다룰 필요는 없다. 버릴 실험에 완성된 제품 수준의 문서와 테스트를 붙이는 것도 맞지 않을 수 있다.[2][4]

초보자인 입장에서 더 주의하고 싶은 부분도 있다. Agent가 긴 계획과 통과한 테스트 수를 보여준다고 해서 내가 그 변경을 이해한 것은 아니다. 승인 버튼을 누를 수 있다는 것과 올바르게 판단할 수 있다는 것은 다르다.

그래서 앞으로는 결과 숫자보다 이런 설명을 더 확인하려 한다.

“이번 변경에서 반드시 지켜야 할 동작은 무엇인가?”

“새 테스트는 어떤 실제 실패를 잡는가?”

“남긴 코드와 삭제한 코드의 기준은 무엇인가?”

## 8. Hermes나 ECC와는 어떤 관계일까

다른 Agent 관련 저장소를 보다 보면 비슷한 용어가 계속 나와서 같은 종류의 도구처럼 느껴진다. 하지만 역할을 나누어 보는 편이 이해하기 쉬웠다.[1][13]

| 도구 | 중심 역할 |
| --- | --- |
| Hermes Agent | 모델, 도구, 기억, 대화 상태를 연결해 실제 작업을 수행하는 Agent 실행 환경 |
| Superpowers | 그 Agent가 개발을 어떤 순서와 기준으로 진행할지 정하는 방법론 |
| ECC | 기존 Agent 환경 위에 전문 역할, 규칙, 자동화, 기억과 여러 Skill을 구성하는 도구 묶음 |

조사한 Superpowers README에는 Hermes 지원과 함께, 긴 대화가 압축되면 초기 지침을 잃을 수 있다는 주의점도 적혀 있다. 이는 해당 버전 문서의 안내이며, 모든 Hermes 버전에서 같은 문제가 재현된다고 확인한 것은 아니다. 설치 지원과 실제 환경에서의 동작은 구분해서 봐야 한다.[1]

ECC 역시 기능이 더 많다는 이유만으로 Superpowers의 상위호환이라고 보기 어렵다. 개발 순서를 제공하는 것과 개발 환경을 폭넓게 구성하는 것은 중심에 둔 문제가 다르기 때문이다.

이 글에서는 Superpowers가 맡는 역할을 이해하는 데까지만 비교하고 싶었다. 어떤 도구를 고를지는 이름이나 기능 수보다 내가 해결하려는 문제가 무엇인지부터 봐야 할 것 같다.

## 9. 다음에는 이렇게 사용해보고 싶다

다음에 작은 기능을 만들 때는 처음부터 작업 범위를 분명히 전달하고, 그 범위에 맞는 절차가 선택되는지 확인해보고 싶다. 짧은 변경에도 불필요한 문서나 검토가 반복되는지, 반대로 꼭 필요한 확인을 건너뛰지는 않는지 보는 것이다.

테스트를 추가할 때는 RED와 GREEN 뒤에 무엇을 정리했는지도 확인하려 한다. 새 코드가 늘어난 이유만큼, 중복된 테스트나 더 이상 필요 없는 경로를 남긴 이유도 설명할 수 있어야 한다.

리뷰도 “문제가 없다”는 결과보다 실제로 어떤 요구사항과 변경을 확인했는지를 보고 싶다. 같은 작업을 구현자의 재검토와 별도 리뷰어에게 맡겼을 때 차이가 있는지도 작은 범위에서 비교해볼 수 있을 것 같다.

아직 이런 비교를 모두 해본 것은 아니다. 이번 글은 성능을 입증한 사용 후기가 아니라, 이미 쓰던 도구의 원리를 이해하고 다음 확인 기준을 정리한 기록이다.

## 마무리

Superpowers를 다시 보면서, Agent가 바로 코딩하지 않았던 이유를 조금 더 이해하게 됐다. 분석, 계획, 테스트, 리뷰, 검증은 같은 일을 이름만 바꿔 반복하는 것이 아니라 서로 다른 실패를 막으려는 절차였다.

동시에 그 절차가 개발자의 판단을 대신해주는 것은 아니라는 점도 분명해졌다. 테스트가 많다고 좋은 설계가 되는 것은 아니고, 모든 검사를 통과했다고 현재 필요 없는 코드까지 남겨야 하는 것도 아니다.

Superpowers는 계속 살펴볼 가치가 있다. 다만 앞으로는 “도구가 시키는 과정을 따라간다”에서 조금 더 나아가, **이번 작업에는 왜 이 단계가 필요한지 이해하고 사용하는 쪽**으로 가보고 싶다.
