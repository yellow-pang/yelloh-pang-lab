## 한 줄 요약

OpenViking은 AI 에이전트가 사용하는 지식, 기억과 Skill을 함께 관리하는 문맥 데이터베이스다.
문맥은 모델이 지금의 판단에 참고하는 자료를 뜻한다.
에이전트 실행기 자체와는 구별되며 README는 그 위에 구축한 VikingBot을 별도 에이전트 프레임워크로 소개한다.
중심 아이디어는 기억을 보이지 않는 저장 공간에 넣는 대신 `viking://` 경로로 탐색하고 읽을 수 있게 하는 것이다.[1]

## 기억을 저장한 다음 어떻게 찾아볼 것인가

대화에서 선호를 기억하고 공개 문서를 검색하도록 만들면 서로 다른 종류의 자료가 쌓인다.
문서 원본, 대화의 경험, 일을 수행하는 지침은 같은 텍스트라 해도 용도가 다르다.
OpenViking은 자료를 디렉터리 구조에 놓고 자원, 사용자 기억, Skill 같은 영역을 구분한다.
에이전트는 파일을 찾듯 목록과 트리를 보고 내용을 읽을 수 있고 사람도 저장된 정보를 살펴보도록 설계되어 있다.[1]

이 방식은 의미 검색을 포기한다는 뜻이 아니다.
의미 검색은 문구가 정확히 같지 않아도 내용상 가까운 자료를 찾는 방법이다.
README는 검색 범위를 특정 프로젝트나 기억 하위 경로로 제한할 수 있다고 설명한다. `find`는 질의를 직접 검색하고 `search`는 세션 문맥을 바탕으로 검색을 계획하는 것으로 구별한다.
‘무엇을 찾는가’와 ‘어디에서 찾는가’를 함께 제어하는 구조다.[1]

## 요약을 보고 원문을 여는 세 단계

자료를 다 읽기 전에 관련성을 판단하도록 L0, L1, L2라는 층이 있다.
L0는 빠른 확인을 위한 짧은 초록, L1은 핵심 정보와 사용 맥락을 담은 개요, L2는 상세 원문이다.
의미 처리가 된 디렉터리에 `.abstract.md`와 `.overview.md`가 놓이는 예제가 제시된다.
긴 문서 전체를 매번 모델 입력에 넣기보다 먼저 좁은 요약에서 읽을 대상을 선택하려는 구성이다.[1]

모든 가져오기가 요약을 만드는 것은 아니다.
Python SDK 안내의 `vectors_only` 모드는 자원 트리를 기록하고 현재 파일을 벡터화하되 초록과 개요를 생성하거나 갱신하지 않는다고 명시한다.
벡터화는 검색을 위해 내용을 숫자 표현으로 바꾸는 과정이다.
비용이나 처리 방법 때문에 모드를 바꿨다면 검색용 데이터와 사람이 읽을 요약의 준비 상태를 별도로 확인해야 한다.[2]

서버와 클라이언트도 구별된다. `openviking-sdk`는 이미 실행 중인 서버를 HTTP로 호출하는 작은 Python 패키지이며 서버와 로컬 실행 의존성을 포함한 주요 `openviking` 패키지와 역할이 다르다.
SDK의 Python 요구사항만 충족한다고 서버를 운영할 준비가 된 것은 아니다.
README의 서버 시작 안내는 임베딩 모델과 VLM 접근을 요구하며 로컬 또는 클라우드 구성을 선택하게 한다.[1][2]

## 예시로 따라가는 흐름

공식 SDK의 로컬 파일 가져오기 예제는 `/path/to/notes.md`를 `viking://resources/demo-notes`에 추가한다.
입력은 파일 경로, 목적지 URI와 가져오는 이유 같은 옵션이다.
클라이언트는 서버 주소와 API 키로 초기화하고 로컬 경로의 파일 업로드를 처리한다.
기본 반환값은 완성된 검색 결과가 아니라 `task_id`다.
따라서 `get_task`로 상태를 확인하고 `completed`가 된 뒤 처리 산출물을 이용하라는 것이 문서의 명시적 순서다.[2]

그 다음에는 자원 목록을 살펴보고 필요한 경로를 읽거나 질의로 관련 정보를 찾는다.
사람이 확인할 부분은 요청이 접수됐는지와 처리가 완료됐는지를 나누는 것, 예상한 URI에 자료가 들어갔는지, 요약이 생성되는 모드를 사용했는지다.
같은 파일도 `vectors_only`로 추가하면 개요가 새로 작성되지 않으므로 기존 개요만 보고 새 파일의 모든 내용이 반영됐다고 판단하면 안 된다.
이 설명은 공식 예제의 입력과 비동기 처리 계약을 읽은 것이며 직접 서버에서 실행한 결과가 아니다.
반환된 식별자나 검색 문장은 만들어 제시하지 않는다.[2]

## 대화 보관과 사용자 경계

README는 세션을 커밋하면 대화를 보관하고 읽고 편집할 수 있는 Markdown 기억을 추출한다고 설명한다.
여기서 커밋은 Git 변경 기록이 아니라 세션 내용을 기억으로 정리하는 API 작업이다.
SDK는 자동 커밋 설정에서 인자를 생략하는 것과 `None`으로 끄는 것을 구별한다.
기본값을 그대로 두는 것과 자동 저장을 명시적으로 중단하는 것은 다르므로 수집 정책을 의도대로 정하는 데 중요하다.[1][2]

SDK 문서는 API 키가 사용자 소유권을 정한다고 밝힌다.
요청별 `actor_peer`는 동시 작업에서 어떤 행위자 관점으로 볼지를 선택하지만 인증이나 사용자 소유권을 바꾸지 않는다.
사용자마다 별도의 자격증명에 묶인 클라이언트를 사용하고 행위자 값도 인증된 애플리케이션 상태에서 가져오도록 한다.
기억 저장소가 여러 사용자를 다룰수록 경로 이름만 바꾸면 접근이 분리된다고 가정해서는 안 된다.[2]

데이터를 모델로 처리하는 만큼 원문·대화가 어떤 서버와 모델 제공자에 전달되는지도 확인해야 한다.
공개 README의 벤치마크는 지정된 모델과 평가 과제에서 나온 저자 측 결과다.
이 글은 이를 모든 에이전트에 대한 정확도 보장으로 확대하지 않는다.
README는 AGPLv3를 표시하므로 수정·배포 방식은 해당 라이선스 조건을 별도로 검토해야 한다.[1]
