# 좋은 모델과 좋은 Agent는 무엇이 다를까? Hermes Agent와 기억 구조 살펴보기

처음에는 좋은 AI를 쓴다는 말을 성능이 좋은 모델을 고르는 일과 거의 같게 생각했다. 새로운 모델이 나오면 어떤 것이 더 똑똑한지, 코드를 더 잘 작성하는지부터 궁금했다.

그러다 먼저 개발을 해오던 사람에게 좋은 모델만 찾는 것이 아니라 Agent를 만들거나 좋은 Agent 환경을 활용한다는 이야기를 들었다. 그때부터 같은 모델을 써도 그것이 어떤 도구와 실행 환경 안에서 움직이는지에 따라 경험이 달라질 수 있다는 점이 궁금해졌다.

이후 Hermes Agent가 괜찮다는 추천도 받았다. 관련 저장소를 살펴보니 여러 모델을 연결할 수 있고, 파일과 브라우저를 다루며, Skill과 Memory를 사용할 수 있다는 설명이 눈에 들어왔다.

그중에서 가장 관심이 갔던 것은 **새 대화를 시작해도 이전 작업을 이어갈 수 있는가**였다.

나는 작업이 길어지면 새 대화를 만드는 편이다. 그러면 이전에 정했던 기준이나 배경을 다시 설명해야 하는 일이 생긴다. 이 과정을 조금이라도 줄일 수 있다면 단순히 모델 성능을 올리는 것과는 다른 도움이 될 것 같았다.

그래서 Hermes Agent를 Star했고, 실제로 저장소를 조사해 Markdown 학습 기록을 만드는 작업에 사용하기 시작했다. 이번 글에서는 그 과정에서 궁금했던 모델과 Agent의 차이, 그리고 Hermes가 말하는 기억의 구조를 정리해보려 한다.

## 1. Hermes Agent는 Hermes 모델과 같은 것일까

이름부터 구분할 필요가 있었다. **Nous Research**, **Hermes 모델**, **Hermes Agent**는 서로 관련되어 있지만 같은 대상을 가리키지는 않는다.[1][2]

| 이름 | 무엇을 가리키는가 |
| --- | --- |
| Nous Research | AI 모델과 Agent 관련 기술을 연구·개발하는 조직 |
| Hermes 모델 | Nous Research가 공개한 언어 모델 계열 |
| Hermes Agent | 모델에 도구, 기억, 대화 관리와 실행 흐름을 연결하는 소프트웨어 |

즉 Hermes Agent라는 이름 때문에 반드시 Hermes 모델만 사용하는 프로그램이라고 생각하면 안 된다.

조사한 자료에서 Hermes Agent는 여러 **Provider**, 즉 모델에 접속하는 서비스나 API 경로를 지원한다. 모델을 바꾸더라도 도구와 Skill, 기록을 관리하는 Agent 환경은 유지할 수 있는 구조다.[2]

내가 이해한 한 줄 설명은 다음과 같다.

> Hermes Agent는 여러 AI 모델을 연결해 도구를 사용하고, 작업 기록과 기억을 이어가며 목표를 수행하는 오픈소스 Agent 실행 환경이다.

특정 모델 하나의 다른 이름이 아니라, 그 모델이 실제 일을 할 수 있도록 주변을 구성하는 소프트웨어라는 점이 출발점이었다.

## 2. 모델과 Agent의 차이는 답변 뒤에 무엇을 하느냐에 있었다

**모델**은 입력을 해석하고 다음 답변이나 행동 후보를 생성한다. **Agent**는 모델의 판단을 실제 도구 실행과 결과 확인으로 연결한다. **Agent Harness**는 이 반복을 운영하는 실행 환경을 뜻한다.

처음에는 모델을 두뇌, Agent를 일을 하는 사람에 비유하니 이해하기 쉬웠다. 다만 Agent 안에도 모델이 들어가므로, 서로 완전히 분리된 대체재처럼 생각할 필요는 없다.

도구 없이 모델을 한 번 호출하는 상황은 대략 다음과 같다.

```text
질문을 전달한다
→ 모델이 답변을 만든다
→ 끝난다
```

Agent는 중간에 외부 상태를 확인하고 실제 행동을 할 수 있다.[3]

```text
목표를 전달한다
→ 모델이 다음 행동을 고른다
→ 도구가 파일을 읽거나 명령을 실행한다
→ 실행 결과를 모델에게 다시 전달한다
→ 결과를 보고 다음 행동을 고른다
→ 필요한 만큼 반복한 뒤 결과를 정리한다
```

이 반복을 **Agent Loop**라고 한다. 생각하고, 행동하고, 결과를 확인하는 흐름이다.

예를 들어 저장소를 분석해서 문서로 남겨달라고 요청했다고 하자. 답변만 생성하는 상황이라면 설명문을 받는 데서 끝날 수 있다. 도구가 연결된 Agent라면 저장소 구조를 읽고, 관련 파일을 찾아보고, Markdown 파일을 작성하고, 변경 내용까지 확인하는 흐름으로 이어질 수 있다.[3]

중요한 것은 화면이 채팅창인지 터미널인지보다, 모델의 판단이 어떤 도구와 반복 실행 구조에 연결되어 있는지였다.

물론 Agent 환경이 좋아도 모델의 판단이 중요하지 않은 것은 아니다. 같은 도구를 제공해도 모델의 추론 능력이나 도구 호출 정확도에 따라 결과가 달라질 수 있다.[2]

좋은 모델을 고르는 일과 좋은 Agent 환경을 고르는 일은 서로를 대신하는 선택이 아니라, 함께 봐야 하는 문제라고 이해했다.

## 3. Hermes는 모델 주변에 무엇을 붙여두었을까

Hermes의 구조를 크게 보면 요청을 받는 화면과 실제 작업을 수행하는 중심부, 그리고 도구와 저장소로 나눌 수 있다.[3]

```text
사용자 요청
  ↓
CLI·화면·메신저 같은 입력 경로
  ↓
AIAgent
├── 모델 접속과 요청 구성
├── Agent Loop
├── 현재 대화와 Context 관리
└── 도구 호출과 실행 결과 처리
  ↓
파일·터미널·웹·브라우저·Skill·Memory·Subagent
  ↓
대화 기록과 기억 파일, 작업 결과물
```

**Context**는 모델이 지금 판단할 때 실제로 보고 있는 지시, 대화, 도구 결과와 자료의 범위다. 기록이 디스크에 저장되어 있다고 해서 그 모든 내용이 현재 Context에 들어가 있는 것은 아니다.

도구 실행도 모델이 직접 운영체제를 조작하는 방식으로 이해하면 부정확하다. 모델이 어떤 도구를 어떤 입력으로 호출할지 요청하면, Hermes의 실행 환경이 등록된 도구를 찾아 필요한 확인을 거쳐 실행하고 결과를 다시 전달한다.[3]

파일 읽기와 수정, 터미널 명령, 웹 검색, 브라우저 조작 같은 기능이 이 흐름 안에 들어간다. 실제로 사용할 수 있는 기능은 켜둔 Toolset, 즉 도구 묶음과 실행 환경 설정에 영향을 받는다.[4]

### Skill은 반복해서 쓸 작업 방법을 남기는 곳이다

Hermes의 **Skill**은 특정 작업을 어떻게 처리할지 정리한 재사용 가능한 지침과 자료다. `SKILL.md`를 중심으로 참고 문서나 스크립트를 함께 둘 수 있다.[5]

처음부터 모든 본문을 불러오기보다 이름과 설명을 먼저 보고, 관련 작업에서 필요한 Skill과 추가 자료를 읽는 방식이다.[5]

내가 하는 저장소 조사라면 어떤 자료를 먼저 볼지, 출처를 어떻게 남길지, 결과 문서를 어떤 형태로 작성할지 같은 기준을 Skill로 정리할 수 있다.

Hermes는 작업 방법을 Skill로 저장하거나 수정하는 기능도 제공한다. 여기서 말하는 학습은 절차를 파일에 남겨 재사용하는 것이지, 그 과정에서 모델 자체를 다시 학습시킨다는 뜻은 아니다. 잘못된 방법도 저장할 수 있으므로 만들어진 Skill을 검토하는 일은 필요하다.[5]

### Subagent는 작업 일부를 다른 Context로 나눈다

**Subagent**는 일부 작업을 위임받는 보조 Agent다. Hermes에서는 별도 Context를 가진 Agent에게 목표와 필요한 배경을 전달할 수 있다.[6]

저장소 구조 조사와 기억 기능 조사가 독립적이라면 나눠서 진행해볼 수 있다. 긴 자료가 중심 대화를 모두 채우는 것을 줄이는 데도 도움이 된다.

대신 보조 Agent가 부모의 전체 대화를 자동으로 아는 것은 아니다. 필요한 배경을 빠뜨리면 잘못된 전제로 작업할 수 있고, 여러 Agent를 실행하면 모델 호출도 늘어난다.

그래서 병렬로 많이 돌리는 것보다 무엇을 나눌 수 있고 무엇을 함께 봐야 하는지부터 판단해야 한다고 느꼈다.

### MCP와 예약 실행은 작업 범위를 넓힌다

**MCP(Model Context Protocol)**는 외부 도구를 Agent에 연결하는 규격이다. Hermes는 외부 서버가 제공하는 기능을 도구로 등록해 사용할 수 있다.[7]

**Cron**은 정해진 시점에 작업을 실행하는 예약 기능이다. Agent를 쓰는 예약 작업은 새로운 Session에서 조사를 수행하고 결과를 파일이나 설정한 전달 경로로 남길 수 있다. 모델을 호출하지 않고 스크립트만 실행하는 모드도 있다.[8]

예약을 등록하는 것과 실행을 유지하는 것은 다르다. 정기 실행을 맡는 Gateway 서비스나 별도로 구성한 스케줄러가 돌아가야 하며, 인증과 결과 전달 설정도 필요하다. 예약 작업에 특정 저장소의 지침과 작업 경로를 적용하려면 `workdir`도 지정해야 한다. 기본 예약 작업이 현재 채팅의 프로젝트 지침까지 그대로 물려받는 것은 아니다.[8]

이런 기능들을 보면서 Hermes가 코드 작성에만 범위를 제한한 도구는 아니라는 점이 더 잘 보였다.

## 4. 가장 궁금했던 Memory는 하나가 아니었다

Hermes를 찾아본 가장 큰 이유는 기억이었다. 처음에는 “이전 대화를 기억한다”는 설명을 하나의 기능으로 받아들였는데, 실제 구조는 여러 층으로 나뉘어 있었다.[9][10][11]

| 구분 | 무엇을 담는가 | 다시 사용할 때 |
| --- | --- | --- |
| 현재 Context | 지금 대화에서 모델이 실제로 참고하는 내용 | 현재 작업의 판단에 사용 |
| Session history | 대화와 도구 실행의 상세 기록 | 기존 대화를 이어 열거나 검색 |
| Persistent memory | 오래 유지할 환경 정보와 사용자 선호 | 새 대화의 기본 정보로 제공 |
| 과거 대화 검색 | 저장된 대화에서 필요한 메시지 | 검색해 현재 Context로 가져옴 |
| 프로젝트 지침 파일 | 저장소의 규칙과 작업 기준 | 해당 작업 경로에서 불러옴 |
| 작업 공간 Snapshot | 시작 시점의 경로와 Git·프로젝트 상태 | 시작 상황을 이해하는 참고 자료 |

이 표를 정리하고 나서야 “저장한다”와 “지금 알고 있다”가 다른 말이라는 점이 조금 더 분명해졌다.

기록이 창고라면 Context는 지금 책상 위에 펼쳐놓은 자료에 가깝다. 창고에 있어도 꺼내오지 않았다면 현재 판단에 사용되지 않을 수 있다.

### 같은 대화를 이어가는 것과 새 대화가 기억하는 것은 다르다

**Session**은 하나의 대화와 작업 흐름을 구분하는 단위다. Hermes는 대화 내용과 도구 호출·결과 같은 정보를 SQLite라는 로컬 데이터베이스의 `state.db`에 저장한다.[9]

같은 작업을 이어가고 싶다면 기존 Session을 다시 여는 방식이 있다. 이것은 이전 대화의 상세 기록을 이어받는 일이다.

반면 새 대화에서도 반복해서 알아야 할 핵심을 넣어두는 것이 **Persistent memory**, 즉 대화를 넘어 유지되는 기억이다.

두 기능을 구분하지 않으면 “전에 이야기했는데 왜 모르지?”라는 질문에 답하기 어려웠다. 그 내용이 이전 대화에만 있는지, 항상 불러올 기억으로 정리되어 있는지부터 봐야 했기 때문이다.

### 오래 남길 기억은 MEMORY.md와 USER.md로 나뉜다

기본 기억 파일은 다음 두 가지다.[10]

```text
MEMORY.md
→ 환경 정보, 오래 유효한 규칙과 학습 내용

USER.md
→ 사용자 성향, 설명 방식과 선호
```

기본 위치는 `~/.hermes/memories/` 아래이며, 사용하는 Profile에 따라 기억의 범위가 나뉜다.

두 파일에는 저장 크기 제한이 있고, Session 시작 시점의 내용이 초기 지시에 들어간다. 기억 도구로 바꾼 내용은 즉시 파일에 저장되지만, 그 쓰기 때문에 기존 초기 지시가 바로 바뀌지는 않는다. 다만 **기억 도구의 응답에는 바뀐 상태가 표시되므로, 현재 대화에서 새 기억을 전혀 알 수 없다는 뜻은 아니다.** 새 Session은 저장된 내용을 다시 불러온다.[10]

여기에 모든 대화를 복사해 넣는 것은 아니다. 여러 대화에서 유효한 내용을 골라 담는 작은 메모에 가깝다.

### 모든 대화가 자동으로 영구 기억이 되는 것은 아니다

Hermes는 대화를 기록하지만, 오래 남길 기억은 선별한다. Agent가 기억 도구를 사용하거나 별도의 검토 기능이 유용한 정보를 골라 저장할 수 있다.[10]

그래서 “기억해달라고 명시한 것만 저장된다”는 이해도, “말한 모든 것이 다음 대화에 항상 들어간다”는 이해도 정확하지 않았다.

기본 설정은 Agent의 기억 저장을 허용하지만, `memory.write_approval`로 승인을 요구할 수 있다. 대화형 CLI에서는 바로 확인을 요청하고, 백그라운드 검토나 다른 입력 경로에서는 승인 대기 항목으로 남기는 방식이다. 중요한 기준은 무엇이 저장됐는지 직접 확인하고 싶다.[10]

기억 기능이 있다는 것보다, 필요한 내용을 정확히 선택하고 관리할 수 있는지가 더 중요해 보였다.

## 5. 작은 기억에 없는 내용은 과거 대화에서 찾는다

그렇다면 상세한 과거 내용은 어떻게 가져올까.

Hermes의 `session_search`는 저장된 대화에서 관련 메시지를 찾는 기능이다. 조사한 자료에서는 SQLite의 **FTS5**, 즉 메시지의 텍스트 전체를 대상으로 검색하는 기능을 사용한다고 설명한다. 과거 대화가 모두 기본 Context에 들어가는 대신, 필요한 기록을 찾아 가져오는 방식이다.[9][10]

```text
새 대화에서 과거 작업이 필요해진다
→ session_search로 관련 표현을 검색한다
→ 해당 대화와 메시지를 찾는다
→ 필요한 앞뒤 내용을 확인한다
→ 현재 작업의 Context에 가져온다
```

이 구조라면 모든 기록을 항상 모델에게 전달할 필요는 없다. 평소 필요한 선호와 환경은 작은 기억으로 두고, 세부 내용은 필요할 때 찾을 수 있다.

반대로 어떤 기록을 찾아야 할지 모르면 검색도 어려워질 수 있다. 저장소 이름, 파일명, 오류 문구처럼 구체적인 단서가 있으면 이전 작업을 찾기 더 좋겠다는 생각이 들었다.

나에게 인상적이었던 것은 기억의 용량 하나가 아니었다. **항상 필요한 작은 기억, 상세한 대화 기록, 필요한 순간의 검색을 나눠둔 방식**이었다.

## 6. 프로젝트마다 기억이 자동으로 분리될까

여기에는 주의할 점이 있었다.

기본 `MEMORY.md`와 `USER.md`는 저장소별이 아니라 **Profile별**이다. Profile은 설정과 대화, Skill, 기억 등을 묶어 관리하는 단위다. 같은 Profile로 여러 저장소에서 작업하면 그 기억을 함께 참고할 수 있다.[10]

따라서 특정 프로젝트에서만 맞는 규칙을 전역 기억에 넣으면 다른 프로젝트에도 영향을 줄 수 있다.

프로젝트와 함께 관리할 규칙은 `.hermes.md`, `AGENTS.md`, `CLAUDE.md` 같은 지침 파일이 더 적합하다. 여기에는 저장소의 구조, 빌드 명령, 작업 기준을 둘 수 있다. 단, **여러 종류의 지침 파일을 만들었다고 전부 합쳐 읽는 것은 아니다.** 시작 시 `.hermes.md`, `AGENTS.override.md`, `AGENTS.md`, `CLAUDE.md` 등의 우선순위에 따라 지침 종류를 선택한다. 선택된 `AGENTS.md`는 디렉터리 단계에 따라 이어 읽을 수 있으므로, 파일 종류의 우선순위와 같은 종류 파일의 계층 적용을 구분해야 한다.[11]

기억을 분리하려면 별도의 Profile을 사용할 수 있다. 공식 문서는 독립적인 Hermes 프로세스 두 개가 같은 홈 디렉터리의 기억을 함께 수정하지 않도록 주의하라고도 안내한다. 여러 Agent 사이의 공유가 목적이라면 단순히 같은 폴더를 쓰게 하기보다 외부 기억 제공자 같은 별도 연결 방식을 검토해야 한다.[10]

작업 시작 시점에 확인한 Git 상태나 프로젝트 정보도 영구히 최신 상태라고 볼 수는 없다. Snapshot은 이름 그대로 그 시점의 모습이다. 실제 파일을 수정하기 전에는 현재 상태를 다시 확인해야 한다.[3]

내가 앞으로 구분해서 남기고 싶은 기준은 이렇다.

> 설명 방식 같은 공통 선호는 사용자 기억에, 프로젝트 규칙은 저장소 파일에, 정확한 진행 상태는 작업 문서와 Git 기록에 남긴다.

## 7. 대화가 길어져 압축되면 기억은 어떻게 될까

Context는 무한하지 않다. 대화와 도구 결과가 길어지면 현재 요청에 담을 수 있는 범위를 관리해야 한다.

Hermes의 Context 관리 자료는 오래된 도구 결과를 줄이고, 대화 일부를 요약하고, 최근 내용을 남기는 압축 방식을 설명한다. 조사한 기본 방식에서는 같은 Session 안에서 활성 Context를 다시 구성하면서 원래 메시지는 검색할 수 있도록 데이터베이스에 남긴다.[12]

이것은 오래된 내용이 전부 완벽한 장기 기억으로 바뀐다는 뜻이 아니다.

요약에서 중요한 파일명이나 결정의 이유가 빠질 수 있고, 이전 메시지가 저장되어 있어도 다시 찾아오지 않으면 현재 판단에 반영되지 않을 수 있다.

그래서 긴 대화를 무한히 이어가는 것보다, 작업 단위로 결과를 Markdown에 남기고 다음 대화에서 이어가는 방식도 계속 필요해 보였다. Memory가 문서와 Git 기록을 없애주는 것은 아니었다.

## 8. Coding Agent로 쓸 수 있을까

Hermes는 코드 읽기와 수정, 터미널 실행, Git 작업, 테스트 실행, 브라우저 확인에 필요한 도구를 갖추고 있다. 이런 구성을 보면 Coding Agent로 사용할 수 있다.[2][4]

다만 Hermes 전체를 설계부터 브랜치 통합까지 하나의 절차로 묶는 도구는 아니다. 제공되는 도구와 Skill을 바탕으로, 요구사항 확인·TDD·리뷰의 순서를 프로젝트 기준에 맞춰 조정하거나 다른 방법론을 추가할 수 있다.[2][5]

이 지점에서 Superpowers와의 관계도 이해됐다.

**Hermes가 일을 수행하는 환경이라면, Superpowers는 개발 작업의 순서와 기준을 추가하는 방법론**이다. 조사한 Superpowers README에는 Hermes용 연결과 긴 대화 압축 이후 초기 지침에 관한 주의점이 함께 적혀 있다. 이 안내를 모든 Hermes 버전의 확정된 동작으로 일반화하기보다, 실제 설치 버전에서 확인할 항목으로 보는 편이 맞다.[14]

Codex나 Claude Code와 비교할 때도 “어느 쪽만 Agent인가”를 묻기보다는 중심 용도와 구성 방식을 보는 편이 맞았다.[2][15]

| 비교할 대상 | 이 글에서 본 중심 역할 |
| --- | --- |
| Codex | 소프트웨어 개발 작업을 중심으로 하는 Coding Agent 환경 |
| Claude Code | 코드 탐색·수정·검증을 중심으로 하는 Coding Agent 환경 |
| Hermes Agent | 개발뿐 아니라 조사, 브라우저, 파일, 기억과 예약 작업까지 연결하는 범용 환경 |

Memory가 Hermes에만 있는 기능인 것은 아니다. Codex도 로컬 기억 기능을 제공하며, 공식 문서상 기본 설정에서는 꺼져 있다. Claude Code에도 자동 기억과 `CLAUDE.md` 기반 지침이 있다. 같은 기억이라는 이름을 써도 활성화 조건과 저장 범위는 다르므로, 기능의 유무만 비교해서는 부족하다.[15]

내가 Hermes에서 보고 싶었던 차이는 기능 이름의 유무보다, **모델을 바꾸면서도 도구와 기억, 조사 절차를 같은 환경 안에서 이어갈 수 있는가**였다.

다양한 것을 바꿀 수 있다는 점은 장점이다. 반대로 코딩에만 집중하고 싶고 별도 환경 설정을 줄이고 싶다면, 그 자유도가 오히려 관리할 일로 느껴질 수도 있겠다.

## 9. 내가 저장소 조사에 연결해 본 이유

현재 내가 시작한 활용은 GitHub 저장소를 조사해서 학습 기록으로 남기는 일이다.

```text
저장소 URL 전달
→ README와 공식 문서 확인
→ 파일 구조와 관련 구현 확인
→ 관심을 가진 이유와 실제 역할 비교
→ 출처가 있는 Markdown 기록 작성
→ 문서와 변경 범위 확인
```

이 작업에는 답변 생성만 필요한 것이 아니다. 웹 자료를 읽고, 파일을 확인하고, 비교 기준을 유지하고, 결과를 실제 문서로 남기는 일이 이어진다.

Hermes는 웹과 파일 도구, Skill, 과거 대화 검색을 이 흐름에 연결할 수 있다는 점에서 관심이 갔다.[3][4][5][10]

그렇다고 작성된 분석이 자동으로 정확하다는 뜻은 아니다. 큰 저장소에서 일부 파일만 확인했을 수 있고, 보조 Agent의 요약이 원문을 잘못 전달했을 수도 있다. 출처가 붙어 있어도 그 문서가 실제 주장을 뒷받침하는지는 따로 봐야 한다.

특히 왜 Star했는지 같은 개인적인 이유는 Agent가 추측해서 쓰게 두면 안 된다. 내가 관심을 가진 배경을 전달하고, 자료에서 확인한 사실과 내 판단을 나눠 남겨야 한다.

이 작업에서 기대하는 가치는 한 번의 그럴듯한 답변보다 **조사하고, 근거를 확인하고, 기록하는 방식을 다음 작업에서도 다시 사용하는 것**이다.

## 10. 기억과 도구가 많아질수록 조심해야 할 점

가장 먼저 볼 것은 권한이다. 로컬 터미널과 파일, 로그인된 브라우저를 사용할 수 있다는 것은 실제 환경을 바꿀 수 있다는 뜻이다. 삭제, 배포, 외부 전송처럼 되돌리기 어려운 일은 별도의 확인과 좁은 권한이 필요하다.[13]

Docker 같은 격리 환경을 선택할 수 있어도 모든 기능이 자동으로 안전해지는 것은 아니다. 도구를 어떤 환경에서 실행하는지, 연결한 MCP가 무엇에 접근하는지 알아야 한다.

기억도 관리가 필요하다. 잘못된 선호나 오래된 환경 정보가 저장되면 다음 대화에서도 같은 오해가 이어질 수 있다. 프로젝트 전용 정보가 공통 기억에 섞이지 않았는지, 더 이상 맞지 않는 항목은 없는지 확인하고 수정할 수 있어야 한다.[10]

대화 기록에는 도구 결과와 작업 정보가 함께 남을 수 있다. Memory에서 항목 하나를 지웠다고 과거 대화와 다른 저장소에서도 모두 삭제됐다고 가정해서는 안 된다. 기억 파일, 대화 데이터베이스, 외부 기억 서비스를 구분해서 봐야 한다.[9][13]

로컬에 남는 기록도 민감한 데이터로 다룰 필요가 있다. Hermes 홈 디렉터리를 백업하거나 공유할 때는 어떤 대화·기억·인증 정보가 포함되고 누구에게 노출되는지 먼저 확인하려 한다.

비용과 설정도 남는다. 모델 연결뿐 아니라 웹 검색, 브라우저, 보조 Agent, 압축과 기억 검토 같은 기능이 추가 호출이나 설정을 요구할 수 있다. 문제가 생겼을 때 모델 때문인지, 인증 때문인지, 도구 설정 때문인지 구분하는 일이 필요하다.[2]

## 11. 계속 사용하면서 확인해보고 싶은 것

가장 먼저는 새 대화에서 기억을 어떻게 사용하는지다. 한 대화에서 선호를 저장한 뒤 다음 대화에서 자동으로 반영되는지, 상세 기록은 필요할 때 검색하는지 나눠 보고 싶다.

같은 저장소와 같은 조사 기준으로 모델을 바꾸는 비교도 해보고 싶다. 문장이 자연스러운지뿐 아니라 실제 파일을 확인했는지, 출처가 맞는지, 문서 수정이 얼마나 필요했는지를 보는 것이다.

Skill을 추가하기 전후에도 차이가 있을 것 같다. 단순한 요청만 했을 때와 조사 순서·인용·검증 기준을 명시한 Skill을 사용했을 때, 결과뿐 아니라 작업 과정이 얼마나 일정해지는지 확인해보고 싶다.

마지막으로 여러 대화에 걸쳐 하나의 조사를 이어갈 때 Memory, 과거 대화 검색, Markdown 문서 중 무엇이 어떤 역할을 하는지도 보고 싶다.

아직 이런 비교를 모두 끝낸 것은 아니다. 기억의 품질과 모델별 안정성은 기능 설명만으로 결론 내리기보다 직접 확인할 부분으로 남겨두었다.

## 마무리

Hermes Agent를 찾아보면서 좋은 모델과 좋은 Agent 환경이 왜 다른 문제인지 조금 더 구체적으로 이해하게 됐다.

모델은 판단을 담당하는 중요한 부분이다. 하지만 파일을 읽고, 도구 결과를 확인하고, 다음 행동을 고르고, 이전 작업을 다시 찾는 과정은 실행 환경이 함께 만들어낸다.

특히 기억은 모든 것을 자동으로 아는 하나의 기능이 아니었다. 작은 공통 기억과 상세한 대화 기록, 필요한 순간의 검색, 반복 절차를 담은 Skill이 서로 다른 역할을 맡고 있었다.

그래서 Hermes를 모든 개발 도구의 대체재로 보기보다는, **모델과 도구, 기억을 어떻게 연결해야 내 작업이 이어지는지 직접 이해해볼 수 있는 Agent**로 사용해보려 한다. 지금 맡기고 있는 저장소 조사와 학습 기록부터, 잘 이어지는 부분과 내가 여전히 확인해야 하는 부분을 하나씩 살펴보고 싶다.
