## 한 줄 요약

PI-Desktop은 프로젝트, 대화 세션, AI 모델과 플러그인을 한곳에 모으는 데스크톱 작업 환경이다.
특정 모델 하나를 감싼 채팅창이나 IDE 확장만을 뜻하지 않는다.
README는 로컬 중심 저장, 모델 교체, 플러그인 확장을 핵심으로 설명하며 macOS·Windows·Linux를 대상으로 제시한다.
확인한 문서의 릴리스 계열은 Early Preview로 표시되어 있다.[1]

## 대화가 끝난 뒤에도 남아야 하는 작업

코딩을 요청하면 답변만 남는 것이 아니라 파일 변경, 명령 출력, 검토할 차이와 후속 작업이 생긴다.
여러 프로젝트에서 이런 기록을 섞지 않고 이어가려면 대화를 작업 단위로 관리해야 한다.
PI-Desktop은 `Project → Session → Agent → Work`라는 구조를 제시한다.
세션은 프로젝트에서 진행하는 작업의 지속적인 기록이고, 앱을 다시 시작해도 이어갈 수 있는 대상으로 설명된다.[1]

에이전트는 여기서 요청을 해석하고 도구를 호출하는 실행 주체다.
그 주체가 쓸 모델과 도구, 사람이 보는 패널을 데스크톱이 묶는다.
README에 나타나는 세션 분기·검색, 파일 참조, 변경 차이 검토와 명령 출력 확인은 ‘좋은 답변’만 평가하는 대신 실제 무엇이 바뀌었는지 살피도록 하는 구성이다.
중단된 작업의 복구는 가능할 때 수행한다고 표현되어 있으므로 무조건적인 복구 보장으로 읽으면 안 된다.[1]

## 실행 방식과 확장 방식 나누어 보기

README는 Agent, Plan, Goal이라는 작업 모드를 구분한다.
Agent는 읽기·편집·명령·검사를 반복하는 일반 실행, Plan은 실행 전에 프로젝트를 조사하고 접근 방법을 검토하는 흐름, Goal은 목표와 수락 기준을 정한 뒤 경로를 선택하는 흐름으로 소개된다.
이름은 자동화 정도를 설명하지만 권한이 필요한 작업은 여전히 별도 권한 층을 통과한다고 명시한다.[1]

병렬 작업에도 두 단위가 있다.
Subagent는 독립된 문맥으로 분리된 조사를 수행하고 상위 에이전트에게 결과를 돌려준다.
Worker Session은 직접 들여다보고 재사용할 수 있는 온전한 세션이며 전체 기록을 가진다.
문맥이란 모델에게 주어지는 대화와 자료의 묶음이다.
여러 작업을 분리하는 것은 이 묶음이 뒤엉키는 문제를 줄이지만, 여러 결과를 통합하고 서로 충돌하는 변경을 검토하는 책임까지 없애지는 않는다.[1]

확장은 모델에게 도구를 더하는 데 그치지 않는다.
공식 플러그인 개발 가이드는 명령, 독립 패널, 오른쪽 작업 패널 뷰, 에이전트 도구, 필요할 때 읽는 Skill, MCP 서버, 상주 서비스를 구분한다.
예를 들어 패널은 사람이 보는 HTML 화면이고 에이전트 도구는 모델이 호출할 함수다.
하나의 플러그인이 양쪽을 제공할 수 있지만, 화면을 표시할 권한과 도구를 등록할 권한은 같은 개념이 아니다.[2]

## 예시로 따라가는 흐름

공식 가이드의 `panel-basic` 예제로 확장이 실제 어떤 순서로 연결되는지 읽어볼 수 있다.
사용자가 플러그인 화면에서 새 템플릿을 선택하고 빈 폴더를 지정하면, 가이드상 앱은 시작 파일을 만들고 개발 플러그인으로 읽는다.
빈 폴더 조건은 기존 프로젝트를 덮어쓰지 않도록 하는 장치다.
생성되는 핵심 파일은 식별자와 권한을 선언하는 `manifest.json`, 실행 진입점인 `main.js`, 패널 화면인 `renderer/index.html`이다.[2]

예제의 입력은 ‘My First Plugin: Open Panel’ 명령 선택이다.
호스트가 제공한 `pi` API로 등록된 명령은 `pi.ui.openPanel`을 호출하고 인사 토스트를 표시한다.
플러그인이 내려갈 때에는 `onUnload`에서 명령을 해제한다.
이 작은 흐름만으로도 선언 파일, 실행 프로세스, 사용자 화면이 서로 다른 역할임을 알 수 있다.
이것은 문서의 예제 경로를 설명한 것이며 직접 실행한 결과가 아니다.
사람이 확인할 부분은 명령이 등록됐는지, 필요한 `ui.panel` 권한만 요청하는지, 종료 시 등록을 정리하는지다.
AI 모델이 답하는 과정 없이도 성립하는 예제라는 점이 데스크톱 확장 플랫폼의 성격을 잘 드러낸다.[2]

## 권한 게이트가 운영체제 샌드박스는 아니다

개발 가이드는 플러그인 진입 코드가 별도 Node 프로세스에서 동작하고, 패널은 Node 통합이 없는 격리된 Electron 창에서 실행된다고 설명한다.
양쪽의 호스트 API 호출은 권한 게이트를 거친다.
그러나 동일한 문서는 플러그인 프로세스의 원시 Node API까지 운영체제 수준으로 격리한 것은 아니라고 경고한다.
권한 목록이 있다는 사실만으로 신뢰할 수 없는 플러그인을 안전하게 실행할 수 있다고 결론 내리면 안 된다.[2]

배포 패키지에도 경계가 있다.
플러그인을 읽을 때 TypeScript를 컴파일하거나 의존성을 대신 설치하지 않으므로, 실행 가능한 JavaScript와 HTML 및 필요한 자산을 미리 담아야 한다.
가이드의 devkit과 SDK는 당시 비공개 워크스페이스 패키지로 설명되며 일반 npm 설치가 가능하다고 가정하지 말라고 한다.
앱에서 템플릿을 만드는 경로와 저장소에서 개발 도구를 빌드하는 경로를 분리해서 읽어야 한다.[2]

로컬 중심이라는 표현 역시 선택한 모델의 추론까지 무조건 로컬이라는 뜻은 아니다.
README는 클라우드 모델, 로컬 모델, 사용자 게이트웨이와 호환 API를 모두 열어둔다.
어떤 데이터를 어느 모델에 보내는지와 비용은 사용자가 선택한 연결에 달린 문제다.
세션과 프로젝트 관리의 저장 위치, 모델 요청의 목적지, 플러그인의 접근 권한을 각각 확인해야 한다.[1]

## 정리

PI-Desktop은 AI 모델을 새로 만드는 프로젝트가 아니라 장기 작업을 관리하고 기능을 조립하는 데스크톱 플랫폼이다.
지속 세션과 확장이 중심이지만, 미리보기 상태와 플러그인 신뢰 경계를 전제로 읽어야 한다.
