## 한 줄 요약

portless는 로컬 개발 서버의 숫자 포트를 기억하기 쉬운 이름의 URL로 연결하는 도구다.
웹 애플리케이션을 대신 구현하거나 인터넷에 정식 배포하는 서비스가 아니다.
README의 기본 예시는 `localhost:3000` 같은 주소 대신 `https://myapp.localhost`로 앱에 접근하는 것이다.
사람이 여러 개발 서버를 오갈 때뿐 아니라 에이전트가 어느 앱을 열어야 하는지 지정할 때도 같은 주소 체계를 사용한다.[1]

## 포트 충돌보다 먼저 생기는 주소 혼동

개인 프로젝트의 화면과 API, 문서 사이트를 함께 켜면 각 프로그램은 다른 포트에서 기다린다.
다른 실행이 먼저 포트를 사용하면 주소가 달라질 수 있고, 별도 작업 사본을 켜면 어느 화면이 어느 코드인지 혼동하기 쉽다.
portless는 실제 프로그램이 사용하는 포트와 사람이 기억하는 호스트 이름을 분리한다.
포트가 없어지는 것이 아니라 프록시 뒤로 옮겨지는 셈이다.[1]

프록시는 요청을 받아 다른 서버에 전달하는 중간 프로그램이다.
README에 따르면 앱 실행 시 프록시가 자동으로 시작하고 자식 프로세스에 `PORT` 환경변수로 포트를 전달한다.
프레임워크가 이 변수를 읽지 않는 경우 알려진 서버 명령에 포트와 필요한 호스트 옵션을 주입한다.
이름 붙이기와 실제 서버가 그 포트에서 대기하도록 맞추는 일은 서로 다른 단계다.[1]

## 이름에 따라 요청을 나누는 원리

대표 구현인 `proxy.ts`에는 요청에서 호스트를 읽는 함수가 있다.
HTTP/1.1에서는 `Host`, HTTP/2에서는 `:authority`를 우선 사용한다.
주소창의 이름이 프록시의 경로 선택 근거가 된다는 뜻이다.
원래 요청의 프로토콜·호스트·포트를 전달하는 `X-Forwarded-*` 헤더 구성과 HTTP/2 응답에 허용되지 않는 연결 단위 헤더 처리도 분리되어 있다.
주소를 예쁘게 출력하는 기능만으로 이루어진 프로젝트가 아니다.[2]

README는 HTTPS와 HTTP/2가 기본이며 첫 실행에서 로컬 인증기관을 생성하고 신뢰하도록 설정한다고 설명한다.
인증기관은 브라우저가 개발용 인증서를 신뢰하도록 하는 기준이다.
macOS와 Linux에서 기본 HTTPS 포트를 사용하기 위한 권한 상승도 발생할 수 있다.
이런 시스템 변경이 부담스럽다면 문서의 일반 HTTP 선택지를 검토해야 하며, 자동이라는 표현을 권한 변경이 없다는 의미로 읽어서는 안 된다.[1]

여러 패키지가 한 저장소에 있는 모노레포에서는 워크스페이스 구성을 읽고 개발 스크립트가 있는 패키지를 발견한다.
이름을 명시할 수도 있고 패키지와 프로젝트 이름에서 추론할 수도 있다.
별도의 Git 작업 사본에서는 브랜치 이름을 앞에 붙이는 규칙도 제시한다.
이름의 계층이 서비스와 작업 사본을 구별하지만, 어떤 이름으로든 자동 접근이 되는 것은 아니다.
기본 하위 도메인 라우팅은 등록된 이름만 받는 엄격 모드다.[1]

## 예시로 따라가는 흐름

README의 `myapp`과 `api.myapp` 구성을 기준으로 보면 입력은 앱 이름과 실제 서버 시작 명령이다.
프록시는 이름을 등록하고 앱에는 내부에서 쓸 포트를 전달한다.
브라우저에서 `https://myapp.localhost`로 요청하면 프록시가 호스트를 읽어 해당 개발 서버로 넘긴다.
화면이 API를 호출할 때에는 API용 이름과 서버가 서로 맞아야 한다.
이는 공식 예제의 처리 관계를 풀어쓴 것이며 직접 실행한 결과가 아니다.[1][2]

사람은 첫 화면이 열렸다는 사실 외에도 요청한 이름이 올바른 작업 사본인지, 앱이 주입된 포트에서 실제로 대기하는지, API 요청이 다시 프록시로 돌아와 순환하지 않는지 확인해야 한다.
구현에는 요청이 portless를 통과한 횟수를 추적해 전달 루프를 감지하는 처리가 있다.
프런트엔드 서버의 프록시 설정이 원래 호스트를 잘못 유지하면 이름 매핑을 만들었다는 사실만으로 연결이 완성되지 않는다.
또 `&&`나 환경변수 접두사 등으로 복잡하게 묶인 스크립트는 자동 포트 주입 대상에서 제외될 수 있으므로 시작 로그와 실제 리스닝 주소를 비교해야 한다.[1][2]

## 편의성과 시스템 설정의 경계

README는 프로젝트가 pre-1.0 상태이며 버전 사이에 상태 디렉터리 형식이 바뀔 수 있다고 밝힌다.
기여자마다 로컬 설치 버전이 다르면 인증서 신뢰 설정을 다시 수행해야 할 수도 있다.
비대화형 실행에서는 필요한 확인을 조용히 넘기지 않고 오류로 종료하도록 설명하므로 일반 터미널에서 된 실행을 그대로 CI에 옮겨도 된다고 가정하면 안 된다.[1]

사용자 상태는 `~/.portless`에 저장하며 sudo 실행에서도 호출한 사용자의 홈을 기준으로 삼도록 설명한다.
사용자 앱과 높은 권한으로 실행된 프록시가 서로 다른 등록 목록을 보는 문제를 피하기 위한 구성이다.
대표 코드의 hosts 동기화 경로에는 로컬 접속 여부와 토큰 검사도 나타난다.
다만 이러한 검사를 읽었다는 사실은 전체 네트워크 보안 감사를 수행했다는 뜻이 아니다.[1][2]

사용자 정의 도메인 접미사는 로컬 이름 해석 설정까지 관련된다.
README는 `.local`의 mDNS 충돌과 `.dev`의 HTTPS 강제 특성을 주의점으로 들며 `.test`를 권한다.
로컬 개발 주소와 외부 공개 주소를 구분하고 인증서 신뢰와 hosts 변경을 이해한 뒤 선택해야 한다.[1]

## 정리

portless는 로컬 서버 앞에 이름 기반 라우팅을 두는 도구다.
서버의 포트와 설정을 없애지 않으며 안정된 이름 뒤에서 앱 실행·인증서·프록시 경로가 올바르게 맞아야 한다.
