## 한 줄 요약

OpenClaw는 사용자의 컴퓨터에서 실행하며 메신저와 기기 기능을 연결하는 오픈소스 AI 비서다.
대답을 생성하는 단일 모델이 아니라 대화 세션, 모델 연결, 도구 실행과 채널을 함께 관리하는 시스템이다.
README는 하나의 Gateway를 중심으로 개인 비서나 공유 배포를 구성할 수 있다고 설명한다.[1]

## 채팅 화면 뒤에 필요한 연결부

메신저에서 질문하고 답을 받는 것만으로는 파일·브라우저·기기 기능을 다루는 비서가 완성되지 않는다.
어느 대화의 요청인지 기억하고, 사용할 모델과 도구를 고르고, 실행 결과를 다시 적절한 화면으로 보내야 한다.
OpenClaw는 이 연결을 Gateway에 모은다.
Gateway는 대화·도구·사건·채널 연결을 조정하는 로컬 제어부이며, Control UI와 명령줄 화면은 여기에 연결되는 입구다.[1]

채널은 Telegram이나 Discord 같은 대화 서비스와 비서를 잇는 통로다.
컴패니언 앱과 노드는 지원 기기에서 음성, 화면, 카메라 및 기기 내부 행동을 추가한다.
따라서 여러 플랫폼 이름을 지원 목록에서 보았다고 모든 기능이 모든 운영체제에서 같다고 이해해서는 안 된다.
README도 기기 기능을 지원 플랫폼에 한정해 설명한다.[1]

## 모델, 상태, 실행 위치를 분리한다

첫 번째 구분은 비서와 모델이다.
OpenClaw는 호스팅 모델과 로컬 모델 제공자를 연결하며, 도구·스킬·플러그인으로 행동 범위를 확장한다.
모델을 바꾸는 것과 대화가 들어오는 채널을 바꾸는 것, 기기에서 실행할 도구를 바꾸는 것은 서로 다른 설정이다.
이 구조를 알면 채팅 서비스가 모델을 직접 포함하고 있다고 오해하지 않게 된다.[1]

두 번째는 로컬 보관과 외부 전송이다.
README는 상태·메모리·자격 증명이 사용자 하드웨어에 있다고 설명하지만, 설정한 모델 제공자와 채팅 플랫폼에는 프롬프트가 전달될 수 있다고 함께 밝힌다.
기본 버전 확인 통신과 선택적 진단 전송에 관한 설명도 있다.
따라서 “자기 컴퓨터에서 실행한다”를 “네트워크로 어떤 자료도 보내지 않는다”로 바꾸어 말할 수 없다.[1]

세 번째는 Gateway와 도구 실행의 위치다.
샌드박스는 도구가 접근할 파일과 프로세스의 범위를 좁히는 실행 환경이다.
공식 문서에 따르면 기본값은 꺼짐이며, 켜더라도 Gateway 자체는 호스트에 남고 도구 실행만 샌드박스 백엔드로 이동한다.
문서도 이를 완벽한 보안 경계라고 부르지 않는다.
이 차이는 비서가 사용자 파일을 읽거나 명령을 실행할 때 핵심이다.[2]

샌드박스의 mode, scope, backend는 별개 설정이다.
mode는 언제 적용할지, scope는 에이전트별·세션별·공유 중 어떤 단위로 환경을 나눌지, backend는 어느 실행 기반을 쓸지를 정한다.
공식 설명의 `non-main`은 주 세션을 제외하고 적용하며 `all`은 모든 세션에 적용한다.
여러 설정이 독립적이므로 “샌드박스를 켰다”는 한 문장만으로 실제 분리 수준을 알 수 없다.[3]

## 예시로 따라가는 흐름

공개 개인 프로젝트의 문서를 요약해 달라는 요청을 연결된 메신저에서 보낸다고 생각해 보자.
이해를 위한 가상 예시이며 직접 실행한 결과가 아니다.
요청은 채널을 통해 Gateway에 도착하고, 해당 대화 세션에서 선택한 모델과 필요한 도구로 이어진다.
모델이 문서를 읽기 위해 파일 도구를 사용해야 한다면 도구 정책과 실행 환경 설정이 결과에 영향을 준다.
사람은 답변의 문장뿐 아니라 실제로 읽을 수 있었던 파일이 무엇인지 확인해야 한다.[1][2]

샌드박스 문서의 최소 설정 예는 `mode: non-main`, `scope: session`, `workspaceAccess: none`을 제시한다.
이 예를 읽을 때 주 세션까지 격리한다고 생각하면 안 된다.
모드 문서는 그룹·채널 세션이 별도 키를 쓰므로 non-main에 포함된다고 설명한다.
파일을 읽지 못했다면 모델의 이해력 문제로 바로 판단할 것이 아니라, 어떤 세션이었고 작업공간 접근과 도구 허용이 어떻게 설정되었는지 먼저 확인하는 순서가 된다.[2][3]

또한 문서는 생성자 역할에 샌드박스 필수가 지정된 세션에는 일반 모드보다 강한 요구가 적용되고, 해당 백엔드를 사용할 수 없으면 호스트 실행으로 우회하지 않는다고 설명한다.
기대하는 결과는 무조건 요청을 완수하는 것이 아니라 허용된 경계 안에서 얻은 답 또는 접근할 수 없다는 명확한 상태다.
이 글에서는 실제 메시지를 보내지 않았으므로 어느 세션에서 어떤 파일 접근이 허용되었는지에 관한 실행 로그는 없다.[3]

## 들어오는 메시지와 도구 권한의 경계

README는 수신 메시지를 신뢰할 수 없는 입력으로 취급하라고 안내하며, DM 채널의 모르는 발신자는 기본적으로 페어링 절차를 거친다고 설명한다.
페어링은 누구와 연결할지 확인하는 단계이지 그 사람이 보낸 모든 내용이 안전하다는 보장은 아니다.
외부 사용자를 연결하거나 Gateway를 원격에 노출하기 전에는 보안과 격리 안내가 필요하다고 명시되어 있다.[1]

샌드박스 역시 도구 정책을 대체하지 않는다.
문서는 전역이나 에이전트별로 금지한 도구는 샌드박스를 켠다고 다시 허용되지 않는다고 설명한다.
반대로 elevated 도구 실행처럼 경계를 벗어나는 명시적 경로도 문서화되어 있으므로, 도구 허용·격리·예외 권한을 따로 점검해야 한다.
README의 기본 상태에서는 주 세션의 도구가 호스트에서 실행될 수 있다는 점을 놓치면 안 된다.[1][2]

자기 기기에서 데이터를 관리하는 선택은 운영 책임도 가져온다.
모델 제공자와 메신저의 계정, 비용, 보낼 자료와 실행 가능한 행동 범위는 사용자가 구성한 조합에 달려 있다.
이번 조사는 문서의 연결 방식과 경계 확인이며, 특정 배포가 안전하다거나 모든 채널에서 동일한 동작을 한다는 평가가 아니다.

## 정리

OpenClaw의 역할은 여러 채팅 입구와 모델·도구·기기를 하나의 비서 흐름으로 연결하는 데 있다.
로컬 실행 여부만이 아니라 외부 전송 경로, 세션 분리와 실제 도구 권한을 함께 봐야 시스템의 범위를 이해할 수 있다.
