# Superpowers를 대체할 수 있을까? ECC를 Star하고 다시 살펴본 이유

나는 GitHub의 인기 저장소를 살펴보다가 개발에 도움이 될 것 같은 프로젝트를 발견하면 Star를 해두는 편이다. 바로 설치하는 경우도 있지만, 대부분은 나중에 어떤 문제를 해결하는 도구인지 다시 확인하기 위한 표시다.

ECC도 그렇게 발견했다.

당시에는 Superpowers를 사용하면서 다른 선택지도 궁금해진 상태였다. **Superpowers는 Coding Agent가 설계, 계획, 테스트, 리뷰, 검증 순서로 개발하도록 돕는 방법론 패키지**다. Agent에게 일을 맡길 때 이런 흐름이 있다는 것은 좋았지만, 작은 수정에도 과정이 길어지거나 코드와 테스트가 계속 쌓이는 점은 고민이었다.

그러다 ECC를 보니 Skills, Agents, Hooks, Rules, Memory처럼 이름부터 익숙하면서도 낯선 기능이 많이 나왔다. 처음에는 Superpowers보다 더 많은 기능을 갖춘 개발 환경처럼 보였다.

“이쪽으로 바꾸면 지금보다 유연하게 개발할 수 있을까?”

그 질문이 ECC를 Star한 가장 큰 이유였다. 이번에는 기능 목록을 훑는 데서 끝내지 않고, **ECC가 무엇을 대체하고 무엇을 새로 추가하는 도구인지**를 중심으로 정리해봤다.

## 1. ECC는 무엇인가

ECC는 **Everything Claude Code**의 약자다. 이름에서 짐작할 수 있듯 Claude Code를 사용하며 정리한 설정과 개발 방식에서 출발했지만, 조사한 자료에서는 여러 Coding Agent 환경을 지원하는 방향으로 범위가 넓어져 있었다.[1][2]

내가 이해한 한 줄 설명은 다음과 같다.

> ECC는 기존 Coding Agent 위에 전문 역할, 작업 지침, 규칙, 자동화와 기억 기능을 선택해서 구성하는 도구 묶음이다.

여기서 **Coding Agent**는 AI 모델을 이용해 코드를 읽고 수정하며, 도구를 실행해 개발 작업을 수행하는 소프트웨어를 말한다.

ECC 자료에는 **Agent Harness**라는 표현도 자주 나온다. Harness는 모델이 실제 일을 할 수 있도록 도구, 권한, 대화 상태, 기억 등을 연결한 실행 환경이다.

다만 ECC가 모델 실행과 도구 호출을 모두 담당하는 독립 Agent라는 뜻은 아니다. Claude Code나 Codex 같은 기존 환경이 실제 실행을 맡고, ECC는 그 위에 필요한 역할과 절차를 얹는다.[1]

따라서 ECC를 새로운 Coding Agent 하나로 이해하는 것보다, **지금 사용하는 Agent 환경을 더 세밀하게 구성하는 확장 도구**로 보는 편이 정확했다.

## 2. 이름이 많은 이유는 역할이 다르기 때문이다

처음에는 Skill도 지침 같고 Rule도 지침 같아서 무엇이 다른지 헷갈렸다. 정리해보니 각 요소는 작업에 개입하는 방식이 달랐다.[1][3]

| 구성 요소 | 쉬운 뜻 | 맡는 역할 |
| --- | --- | --- |
| Skill | 특정 작업용 매뉴얼 | 테스트나 보안 검토를 어떤 절차로 할지 안내 |
| Agent | 전문 역할을 맡은 작업자 | 계획, 리뷰, 오류 해결처럼 관점을 나눠 작업 |
| Rule | 계속 지켜야 할 공통 기준 | 보안 원칙, 코드 스타일, 테스트 기준 적용 |
| Hook | 특정 사건에 반응하는 자동 동작 | 파일 수정이나 도구 실행 시 검사·기록 수행 |
| Command | 작업을 시작하는 명령 | 사용자가 원하는 작업 흐름을 명시적으로 호출 |
| Memory | 다음 작업에 남길 기록 | 결정, 환경 정보, 반복해서 얻은 교훈 보존 |
| MCP(Model Context Protocol) | 외부 도구와 연결하는 규격 | GitHub, 브라우저, 외부 서비스의 기능 연결 |

이 중에서 먼저 구분하고 싶었던 것은 Skill, Rule, Hook이었다.

### Skill은 방법이고 Rule은 기준이다

Rule이 “무엇을 지켜야 하는가”라면 Skill은 “그 일을 어떻게 할 것인가”에 가깝다. 예를 들어 테스트에 관한 공통 원칙은 Rule에 두고, 실제로 테스트부터 작성해 구현하는 구체적 순서는 Skill에서 안내할 수 있다.[3][4]

조사한 ECC는 `skills/`를 작업 지침의 중심으로 두고 있었다. `commands/`의 일부 명령은 이전 호출 방식이나 환경별 호환성을 연결하는 역할도 한다. 그래서 Command와 Skill의 개수를 모두 더해서 독립 기능 수라고 생각하면 같은 흐름을 중복해서 셀 수 있다.[1]

이 부분을 보면서, 목록이 길다는 인상보다 실제로 서로 다른 역할을 하는 기능이 무엇인지 보는 편이 낫겠다고 느꼈다.

### Hook은 안내를 넘어 실제 동작에 개입할 수 있다

**Hook**은 정해진 이벤트가 발생했을 때 실행되는 동작이다. ECC에는 도구 실행 전 명령을 검사하거나, 파일 수정 뒤 형식을 정리하고 타입을 검사하거나, 대화 시작과 종료 시 상태를 기록하는 예가 있다.[3]

Skill이 “작업 후 검사를 해라”라고 알려주는 매뉴얼이라면, Hook은 설정된 시점에 검사 명령을 실제로 실행하는 연결 장치다. 일부 Hook은 조건에 따라 도구 실행을 막을 수도 있다.

이 차이는 꽤 중요해 보였다. 매번 요청하지 않아도 반복 검사를 수행할 수 있기 때문이다. 동시에 잘못 설정하면 정상 작업을 막거나 수정할 때마다 대기 시간이 붙을 수 있다.

자동화가 많아지는 만큼, 어떤 시점에 무엇이 실행되는지 알아야 한다는 부담도 함께 생기는 셈이다.

## 3. ECC의 개발 흐름은 하나의 고정된 절차일까

ECC도 계획, 테스트, 구현, 리뷰, 검증을 중요하게 다룬다. 큰 흐름만 보면 Superpowers와 비슷하게 느껴질 수 있다.[1][4][5]

```text
사용자 요청
→ 프로젝트 규칙과 현재 상태 확인
→ 계획 또는 전문 Agent의 분석
→ 실패하는 테스트와 최소 구현
→ 설정된 Hook의 자동 검사
→ 별도 리뷰
→ 빌드·타입·테스트 등 최종 검증
→ 다음 작업에 필요한 기록 저장
```

하지만 기능이 저장소에 존재한다는 이유만으로 이 모든 단계가 항상 실행되는 것은 아니다.

Rule은 사용하는 환경의 로딩 방식에 영향을 받고, Skill과 Agent는 실제로 선택되거나 호출되어야 한다. Hook은 이벤트에 연결되어 있어야 자동 실행되고, 기억과 학습 기능도 별도의 설정이 필요할 수 있다.[1][3]

**어떤 기능을 설치하고 어떻게 연결했는지에 따라 실제 경험이 달라진다**는 점이 중요했다.

ECC는 정해진 코스 하나를 그대로 따라가는 방식보다, 필요한 역할과 자동화를 조합해 나만의 개발 흐름을 구성하는 쪽에 가까웠다. 자유롭게 고를 수 있다는 장점과 그 선택을 관리해야 한다는 부담이 함께 있었다.

## 4. Superpowers와 가장 다른 점

처음 가졌던 질문은 “ECC가 Superpowers보다 더 좋은가?”였다. 그런데 자료를 읽을수록 질문을 조금 바꿔야겠다고 생각했다.

두 도구가 책임지려는 범위가 달랐기 때문이다.[1][11]

> Superpowers는 개발을 어떤 순서로 진행할지에 중심을 두고, ECC는 개발 환경에 어떤 역할과 기능을 배치할지까지 다룬다.

| 비교 기준 | Superpowers | ECC |
| --- | --- | --- |
| 중심 관심사 | 설계부터 검증까지 이어지는 개발 순서 | 역할·규칙·자동화·기억을 포함한 환경 구성 |
| 작업 지침 | 여러 Skill을 일관된 흐름으로 연결 | 다양한 Skill과 전문 Agent를 선택해 조합 |
| 리뷰 | 개발 과정 속 독립 검토의 순서 강조 | 공통 리뷰와 언어·분야별 전문 리뷰 제공 |
| 테스트 | 실패 확인, 최소 구현, 정리의 반복 강조 | TDD와 공통 테스트 기준을 함께 제공 |
| 자동화와 기억 | 핵심 개발 절차와는 구분되는 영역 | Hook, 대화 기록, 학습, 기억 공유까지 포함 |
| 사용자 부담 | 작업에 맞게 절차의 크기 조절 | 기능 선택, 중복 규칙, 권한과 설정까지 관리 |

그래서 ECC를 Superpowers의 상위호환이라고 단정하기는 어려웠다.

ECC로도 계획, TDD, 리뷰, 검증 흐름을 구성할 수 있다. 그렇다고 Superpowers의 설계 승인이나 작업별 리뷰 순서, 브랜치 마무리까지 같은 의미로 자동 재현되는 것은 아니다. 그 연결은 다시 정해야 한다.

반대로 여러 Agent 환경 사이에서 기억을 공유하거나, 도구 실행 시점에 자동 검사를 넣거나, 분야별 리뷰어를 고르는 일은 ECC가 더 넓게 다루는 영역이었다.

내가 찾고 있던 것이 개발 절차의 대안인지, 아니면 기존 절차에 부족한 기능인지 먼저 구분해야겠다고 느꼈다.

## 5. 기대했던 대체 도구와 실제로 필요했던 기능은 달랐다

### 코드 정리: refactor-clean

가장 먼저 눈에 들어온 것은 정리 절차를 담은 `refactor-clean`과 정리 역할을 맡는 Agent 지침인 `refactor-cleaner`였다. 사용하지 않는 코드와 의존성을 탐지하고, 위험도를 나눠 작은 단위로 삭제·검증하도록 안내한다. 이름이 분석 프로그램처럼 보일 수 있지만, `refactor-clean` 자체는 **Agent가 따라야 할 작업 지침**이다. 실제 탐지는 프로젝트에 맞는 분석 도구나 코드 검색으로 수행한다. 문서에는 JavaScript·TypeScript용 `knip`, Python용 `vulture` 등이 예시로 나온다.[6]

여기서 **의존성**은 프로젝트가 다른 라이브러리나 코드에 기대어 동작하는 관계를 뜻한다.

코드가 계속 쌓일 때 필요한 것은 새 코드를 더 잘 만드는 기능만이 아니었다. 지금 남아 있는 코드가 무엇을 위해 존재하는지 확인하는 절차도 필요했다. 그래서 이 기능은 처음 가졌던 “전체를 바꿔볼까”라는 생각보다 더 구체적으로 다가왔다.

이 지침도 확실하지 않으면 보존하도록 한다. 이름에 clean이 들어간다고 불필요한 코드를 자동으로 정확하게 판정해주는 것은 아니다.[6]

실제로 사용하려면 현재 지켜야 할 동작, 외부에서 사용하는 API, 삭제하면 안 되는 경로를 먼저 전달해야 한다. 탐지 결과는 삭제 승인 목록이 아니라 확인할 후보로 봐야 한다는 뜻이다.

### 전문 리뷰어: 같은 코드도 다른 관점으로 보기

ECC에는 계획자, 코드 리뷰어, 언어별 리뷰어처럼 역할이 나뉘어 있다. 공통 리뷰어는 변경 내용뿐 아니라 주변 코드와 호출부를 확인하고, 근거가 충분한 문제를 보고하도록 지시한다.[5]

이 기능은 리뷰 횟수를 늘리는 것보다 **무엇을 다른 관점에서 확인할지 정하는 데** 가치가 있어 보였다.

예를 들어 기능 요구사항을 확인하는 검토와 언어별 관습이나 오류 가능성을 확인하는 검토는 관심사가 다를 수 있다. 반대로 같은 질문을 여러 리뷰어에게 반복해서 던지면 비슷한 지적만 늘어날 수도 있다.

내가 먼저 확인하고 싶은 것은 리뷰어의 수가 아니라, 실제로 놓쳤던 문제를 추가로 찾는지다.

### Context 점검: 기능이 많아질수록 무엇이 들어가는지 보기

**Context**는 모델이 현재 판단에 사용하는 지시, 대화, 도구 결과 같은 정보다. ECC의 `context-budget`은 **Claude Code의 설정과 지침 파일을 살펴보고 토큰 사용량을 추정하는 Skill**이다. 토큰은 모델이 글을 처리하는 단위다. 이 지침은 글 길이와 도구 수 같은 간접 지표를 사용하므로, 현재 요청의 정확한 사용량이나 요금을 실시간으로 측정하는 프로그램은 아니다. Codex 같은 다른 환경에 적용하려면 설정 위치와 지침이 불러와지는 방식부터 맞춰야 한다.[9]

필요한 기능을 잘 고르면 도움이 되지만, 항상 읽히는 규칙과 도구 설명이 계속 늘면 지금 작업과 무관한 정보도 함께 들어갈 수 있다. 그래서 새 기능을 켜는 일만큼 무엇을 꺼둘지도 중요해 보였다.

`verification-loop`도 관심이 갔다. 빌드, 타입 검사, 코드 규칙 검사, 테스트, 보안과 변경 내역을 순서대로 확인하는 흐름이다.[7] 다만 예시 명령을 그대로 붙이는 것이 아니라, 내 프로젝트에서 실제로 사용하는 검증 명령으로 바꿔야 의미가 있다.

## 6. ECC에도 TDD가 있다면 테스트가 쌓이는 문제는 해결될까

도구를 바꾸는 것만으로 해결될 문제는 아니었다.

ECC의 TDD 자료도 테스트를 먼저 작성하는 흐름과 **80% 이상의 Coverage**를 요구한다. Coverage는 테스트가 코드의 문장이나 분기 등을 얼마나 실행했는지 나타내는 비율이다. 단위 테스트, 구성 요소 사이의 연결을 보는 통합 테스트, 사용자 흐름을 처음부터 끝까지 확인하는 E2E 테스트도 다룬다.[4]

이 수치는 ECC 지침의 기준이지, 모든 프로젝트에 그대로 적용해야 하는 품질 보증선은 아니다. 절차와 테스트가 이미 부담인 상황에서 비슷한 규칙을 중복해서 켜면 같은 고민이 더 커질 수 있겠다.

그래서 내 관심은 TDD 규칙을 하나 더 추가하는 것보다, **현재 지켜야 할 동작과 실제 사용 경로를 기준으로 코드·테스트를 정리하는 일**에 있다. 테스트가 있다는 이유만으로 영구 보존해서도 안 되고, 중복처럼 보인다는 이유만으로 바로 지워서도 안 된다.

`refactor-clean`은 탐지와 삭제 후 검증을 안내하지만, 사라진 요구사항까지 대신 판정하지는 않는다. 실제 호출부와 외부 사용자를 확인한 다음 삭제 범위를 정해야 한다.[6]

이 점에서 “Superpowers가 무거우니 ECC로 바꾸자”는 결론은 너무 빨랐다. 먼저 필요한 것은 교체보다 보존 기준의 정리였다.

## 7. Memory는 편리해 보였지만 또 다른 관리 대상이었다

ECC의 기억 기능도 하나로 묶어 생각하면 이해하기 어려웠다. 자료에서는 대화의 작업 상태를 저장하는 기능, 반복 패턴을 학습하는 기능, 여러 Agent 환경에서 기록을 공유하는 기능이 구분되어 있었다.[3][8]

`continuous-learning-v2`는 반복해서 관찰한 수정이나 작업 방식을 **Instinct**, 즉 작은 행동 규칙과 신뢰도를 가진 기록으로 만든다.

`unified-memory`는 여러 환경이 함께 참고할 수 있는 로컬 Markdown 기억 저장소를 다룬다. 다만 **Skill 파일만 추가한다고 기억 저장 기능까지 설치되는 것은 아니다.** 문서는 CLI나 MCP로 저장소를 사용하려면 `ecc-universal` 실행 프로그램을 별도로 준비해야 한다고 명시한다. 함께 사용할 Agent들이 같은 저장소 위치를 보도록 설정하는 것도 필요하다. 모든 대화를 자동으로 모아 클라우드에 동기화하는 기능으로 이해하면 안 된다.[8]

다만 이 기록은 검증된 정책이 아니라 아직 검토하지 않은 참고 정보로 취급하도록 되어 있었다. 중요한 결정은 코드, 테스트, 이슈나 공식 문서에서 다시 확인해야 한다.

이 제한이 오히려 현실적으로 느껴졌다. 기억을 남기는 것 자체보다 **틀린 기억을 언제 확인하고 고칠 수 있는지**가 중요하기 때문이다.

일시적인 환경 정보가 오래 남거나, 다른 프로젝트에서 맞았던 규칙이 현재 작업에 섞이면 일관되게 잘못된 판단을 반복할 수도 있다. 그래서 기억 저장소를 설계 문서나 작업 관리 도구의 완전한 대체물로 사용하고 싶지는 않았다.

## 8. 설치 전에 확인해야 할 것

기능 목록만 읽을 때는 지나치기 쉬웠지만, 설치 전에는 따로 확인할 점이 있었다.

먼저 규칙이 중복될 수 있다. 기존 프로젝트의 `AGENTS.md`, 테스트 규칙, 코드 검사 설정이 있는데 ECC의 공통 규칙까지 그대로 넣으면 같은 내용을 여러 번 요구하거나 서로 다른 기준을 적용할 수 있다.[3]

지원 환경이 많다고 기능이 모두 같다는 뜻도 아니다. 조사한 ECC는 Claude Code를 중심으로 구성되어 있고, Codex나 Hermes에서는 Skill·Agent·Hook 연결 방식에 차이가 있다. 그렇다고 Codex에 Hook 지원이 없다는 뜻은 아니다. ECC의 Codex용 문서에는 별도의 lifecycle Hook, 즉 세션 시작 같은 이벤트에 연결되는 Hook이 있으며, 설치 후 정의를 검토하고 신뢰를 승인하는 절차도 명시되어 있다.[10]

이제 “지원한다”는 말을 보면 세 가지를 나눠 보고 싶다. 파일을 설치할 수 있는지, Agent가 그 파일을 실제로 발견하는지, 자동 실행이나 차단까지 같은 방식으로 동작하는지다.

MCP와 Hook도 필요한 범위만 확인하고 켜는 편이 좋겠다. 외부 프로그램이나 서비스가 연결되면 권한과 인증 정보를 관리해야 하고, 자동 명령은 실제 파일과 실행 상태에 영향을 줄 수 있다.[1][3]

업데이트도 같은 맥락이다. 구성 요소가 많으면 문서, 설치 설정, 환경별 연결 방식이 바뀌는 지점도 많아진다. 지금 잘 동작하는 설정이 새 버전에서도 같은지 확인할 책임이 생긴다.

작은 프로젝트에서는 개발보다 도구 설정에 더 많은 시간을 쓰게 될 수도 있겠다는 생각이 들었다. 기능의 폭은 장점이지만, 그 폭이 지금 필요한지는 별개의 문제였다.

## 9. 그래서 어떻게 써볼 생각인가

지금 내 판단은 전체 교체보다 **필요한 기능을 좁게 시험하는 쪽**이다.

먼저 `refactor-clean`과 리뷰 지침을 읽고 작은 작업에 적용해보고 싶다. 그다음 Context 점검과 검증 흐름이 실제로 도움이 되는지 확인할 수 있을 것 같다. 기억 공유나 자동 Hook은 반복되는 문제가 분명해졌을 때 검토하려 한다.

Superpowers와 ECC의 계획·TDD·리뷰 규칙을 모두 동시에 켜는 방식은 첫 시도로 선택하고 싶지 않다. 더 안전해졌는지 알기 전에 중복 절차부터 늘어날 수 있기 때문이다.

비교한다면 같은 시작 상태와 같은 요구사항으로 작업을 나눠보는 편이 낫겠다. 다른 작업을 시켜놓고 걸린 시간만 비교하면 도구 차이인지 작업 차이인지 알기 어렵다.

| 시험해볼 작업 | 보고 싶은 차이 |
| --- | --- |
| 작은 버그 수정 | 원인을 확인한 뒤 고치는지, 불필요한 변경이 생기는지 |
| 범위가 작은 기능 추가 | 요구사항을 빠뜨리지 않으면서 계획과 테스트가 적절한지 |
| 기존 코드 정리 | 함수 이름이나 파일만 나뉘는 것이 아니라 복잡성이 줄어드는지 |
| 불필요한 코드·테스트 삭제 | 현재 동작을 지키면서 실제 유지 비용을 줄이는지 |
| 실패하는 테스트 조사 | 반복 실행이나 테스트 약화로 문제를 덮지 않는지 |

아직 이 비교 결과를 얻은 것은 아니다. 확인하고 싶은 것은 기능 수나 작업 단계 수가 아니라, 내가 변경 이유를 이해할 수 있고 결과를 유지하기 쉬워지는지다.

## 마무리

ECC는 Superpowers를 대체할 수 있을지 궁금해서 Star한 저장소였다. 살펴보고 나니, 더 큰 개발 방법론 하나라기보다 **여러 Agent 환경을 구성할 수 있는 넓은 도구 상자**라는 쪽으로 이해가 바뀌었다.

현재 쓰는 흐름을 완전히 바꾸려면 ECC의 기능을 어떻게 연결할지도 다시 정해야 한다. 반대로 부족한 기능만 보완하려면 정리 도구나 전문 리뷰처럼 작은 부분부터 가져와볼 수 있다.

그래서 ECC는 당장 전부 켜둘 도구가 아니라, **필요한 기능을 하나씩 골라 검증해볼 저장소**로 남겨두려 한다. 첫 기준은 기능 수가 아니라, 작은 정리 작업에서 실제로 유지 비용을 줄여주는지다.
