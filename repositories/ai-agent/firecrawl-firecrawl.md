## 한 줄 요약

Firecrawl은 웹에서 자료를 검색하고 페이지 내용을 추출해 Markdown·HTML·구조화 데이터 등으로 전달하는 API 프로젝트다.
웹 정보를 사용하는 에이전트와 프로그램의 자료 수집 층에 해당하며, 호스팅 서비스와 공개 소스를 제공한다.
페이지 내용을 얻는 일과 그 내용의 사실성을 검증하는 일은 같은 기능이 아니다.[1]

## URL을 알아도 바로 읽을 수 있는 것은 아니다

웹페이지에는 본문 외에 메뉴·광고·스크립트와 반복 요소가 섞인다.
어떤 페이지는 JavaScript 실행 뒤 내용이 나타나고, 사이트 전체에서 필요한 주소를 먼저 찾아야 할 때도 있다.
Firecrawl은 이런 수집 단계를 호출 표면으로 나누고 후속 프로그램이 소비하기 쉬운 결과를 제공하는 것을 목표로 한다.[1]

Markdown은 제목·목록·링크를 텍스트로 표현하는 형식이고 JSON은 필드와 값으로 데이터를 전달하는 형식이다.
둘 중 어느 쪽이 적절한지는 목적에 따라 다르다.
원문을 읽고 인용하려면 본문과 출처를 유지하는 것이 중요하고, 반복 항목을 비교하려면 필드 구조가 필요할 수 있다.
구조가 생겼다고 추출 내용이 자동으로 완전해지는 것은 아니다.[1]

## 검색, 단일 추출, 주소 발견을 나눈다

Search는 검색어로 자료를 찾고 결과 내용을 받는 경로, Scrape는 특정 URL의 내용을 얻는 경로다.
Map은 사이트 안의 주소를 발견하는 데 초점을 둔다.
여러 URL의 본문이 필요하면 Crawl이나 Batch Scrape를 사용하며, 이미 대상 목록을 갖고 있는 경우와 링크를 따라 범위를 넓히는 경우를 구분할 수 있다.[1]

Interact는 먼저 추출한 페이지의 식별자를 사용해 추가 상호작용을 하는 경로다.
클릭·입력·스크롤이 들어가므로 읽기와 상태 변경이 섞일 수 있다.
Agent 기능은 자연어로 원하는 자료를 설명해 수집을 맡기는 별도 입구로 소개된다.
이 글은 각 기능의 존재와 예시를 읽은 것이며 모든 사이트에서 성공하는지 시험한 것은 아니다.[1]

README의 높은 수집 범위나 짧은 지연시간은 프로젝트가 소개하는 성능 주장이다.
대상 사이트, 요청 조건과 배포 환경을 확인하지 않고 개인 환경에서도 같은 수치가 나온다고 일반화하지 않는다.
특히 클라우드에 추가 기능이 있다고 명시하므로 공개 소스 배포와 호스팅 서비스가 완전히 같다고 볼 수 없다.[1]

## 비동기 작업과 결과 페이지는 다른 개념이다

여러 페이지를 수집하는 작업은 바로 모든 본문을 반환하기보다 작업 ID를 먼저 주고 상태를 확인하는 경로가 있다.
비동기는 요청을 시작한 뒤 완료를 기다리거나 나중에 조회하는 방식이다.
README는 Crawl의 시작 응답과 상태 응답을 분리하고 SDK가 반복 상태 확인을 처리한다고 설명한다.[1]

추가 확인한 JavaScript SDK 예제는 `crawl()`로 완료와 결과 수집을 맡기는 방식과 `startCrawl()` 후 `getCrawlStatus()`로 조회하는 방식을 비교한다.
결과가 많으면 응답도 여러 페이지로 나뉠 수 있다.
이때 “페이지”는 수집 대상 웹페이지와 API 결과 묶음을 각각 뜻할 수 있으므로 구분해야 한다.[2]

`autoPaginate`, `maxPages`, `maxResults`, `maxWaitTime`은 결과를 더 가져오는 범위를 제어한다.
수집 시작의 `limit`과 결과 조회의 제한은 같은 설정이 아니다.
일부 결과를 받은 것을 전체 사이트를 다 읽은 것으로 표시하지 않으려면 상태와 반환 항목 수, 다음 결과의 존재를 함께 봐야 한다.[2]

## 예시로 따라가는 흐름

공식 `example_pagination.ts`는 Firecrawl 문서 사이트를 대상으로 제한된 Crawl을 시작하는 예제를 제공한다.
API 키로 클라이언트를 만들고, 첫 경로에서는 `crawl()`을 기다린 뒤 상태·문서 수·다음 결과 정보를 출력한다.
두 번째 경로에서는 `startCrawl()`에서 작업 ID를 받고 자동 페이지 넘김을 끈 상태 조회로 첫 묶음을 읽는다.[2]

이후 자동 페이지 넘김을 켜되 최대 응답 페이지와 결과 수, 추가 조회 시간을 제한하는 호출을 보여준다.
같은 파일은 이미 알고 있는 URL 목록을 Batch Scrape로 처리하는 자동·수동 경로도 비교한다.
입력 URL에서 수집 작업이 생기고, 작업 상태를 통해 결과 묶음을 받아 프로그램이 처리하는 순서다.
사람은 작업이 아직 진행 중인지, 다음 묶음이 남았는지, 실제 문서 수가 요청 범위를 충족하는지 확인해야 한다.
출력 코드는 이 값을 표시할 뿐 이 원고에서 관측한 결과가 아니다.
수집한 본문에 필요한 절이 빠지거나 출처 메타데이터가 기대와 다르면 원문과 대조해야 한다.
이 글에서는 API 요청을 보내거나 크레딧을 사용하지 않았다.[1][2]

## 자체 호스팅은 운영 책임까지 포함한다

`SELF_HOST.md`는 소스 버전에 맞는 Compose 구성을 출발점으로 삼고 API·worker·Playwright·캐시·큐·데이터베이스를 설명한다.
처음에는 기본 수집 경로를 확인하고 필요할 때 별도 엔진이나 모델 공급자를 붙이라고 한다.
AI 기반 기능에 모델 공급자가 기본 제공되는 것은 아니라는 경계도 명시한다.[3]

기본 API는 인증되지 않은 상태이므로 신뢰된 네트워크 밖으로 노출하려면 완전한 인증 설계, TLS와 네트워크 정책을 준비해야 한다.
인증 변수 하나만 바꾸는 것이 배포 완성은 아니다.
해당 Compose는 주요 상태 서비스에 영속 볼륨을 정의하지 않는다고 문서가 경고하므로 백업·복구·보관도 운영자가 설계하고 시험할 대상이다.[3]

라이선스는 주로 AGPL-3.0이며 SDK와 일부 UI는 MIT라고 README가 구분한다.
또한 수집 대상의 개인정보 정책과 이용 조건을 지킬 책임을 사용자에게 명시한다.
자료를 읽을 기술적 능력이 있다고 로그인 경계·접근 제한이나 게시자의 정책을 무시할 권한이 생기는 것은 아니다.[1]

## 정리

Firecrawl은 웹 자료의 발견과 추출, 다중 작업 결과 수집을 API로 연결한다.
호출 성공과 전체 수집 완료, 추출된 내용과 사실 검증, 자체 호스팅 시작점과 운영 준비를 각각 나누어 판단해야 한다.
