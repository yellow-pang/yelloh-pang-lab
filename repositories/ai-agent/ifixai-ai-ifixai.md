## 한 줄 요약

iFixAi는 에이전트에 시험 요청을 보내고 그 응답을 심사해 근거와 점수표를 만드는 Python 감사 도구다.
에이전트를 대신 운영하거나 오류를 자동으로 모두 고치는 실행기가 아니라, 의도와 권한에 맞게 행동했는지 점검하는 쪽에 가깝다.[1]

## 정상 답변만으로는 보이지 않는 문제

에이전트가 그럴듯한 답을 해도 허용되지 않은 도구를 쓰거나 요청 범위를 벗어날 수 있다.
iFixAi는 역할과 정책을 담은 시뮬레이션 환경에서 정상 요청과 경계를 밀어보는 요청을 보내고, 무엇을 물었고 어떻게 답했는지 남긴다.[1]

여기서 fixture는 시험 대상의 역할·능력·규칙을 담은 입력 자료이고, judge는 응답을 판정하는 심사 모델이다.
README의 실제 감사 경로는 대상과 다른 제공자의 심사 모델을 선택한다고 설명한다.
API 키 없이 사용하는 mock 예제는 미리 정한 응답과 판정으로 흐름만 보여주므로 실제 감사 성공 사례가 아니다.[1]

## 실행과 채점은 어떻게 연결되는가?

`ifixai/core/runner.py`의 `run_all`은 대상 능력을 확인하고 심사기와 평가 파이프라인을 구성한다.
이후 `_set_aside`로 적용되지 않는 검사를 분리하고, 캐시된 결과와 새 실행 대상을 나눈 뒤 검사를 수행한다.
완료 결과를 합치고 교차 검사의 일관성 경고를 반영해 실행 결과를 만든다.[2]

이 구조에서 중요한 것은 모든 검사를 무조건 실행하거나 미실행 항목을 성공으로 채우지 않는다는 점이다.
교차 일관성 검사 자체가 실패하면 완료된 점수는 유지하지만 일관성을 확인하지 못했다는 경고를 붙인다.[2]

`docs/scoring.md`는 다섯 핵심 범주를 합산하되 필수 최소 조건을 별도로 적용한다고 설명한다.
B01·B08·P01의 최소 조건 실패는 전체 점수에 상한을 두므로 다른 항목의 높은 점수로 중대한 실패를 덮지 못하게 한다.[3]

근거 부족인 INCONCLUSIVE와 적용 대상이 아닌 상태도 구분한다.
전체 통과율과 얼마나 넓게 검사했는지는 서로 다른 수치이며, 문서는 어느 쪽도 규정 준수 인증이 아니라고 명시한다.[3]

## 가상 예시: 공개 자료 안내 에이전트 점검

공개 문서 검색만 허용된 개인용 안내 에이전트가 있다고 가정한다.
역할과 도구 범위를 프로필에 적고 시험 환경을 만든 다음, 권한 밖 행동을 요구하는 요청에 어떻게 반응하는지 살펴본다.
실행 전 dry-run으로 검사 계획과 심사 호출 수를 확인하고, 실제 실행 뒤 JSON·Markdown 보고서에서 요청과 응답 근거를 읽는 흐름이다.[1]

결과가 좋아도 해당 프로필과 시험 요청에 대한 관찰일 뿐 모든 상황에서 안전하다는 보장은 아니다.
문서가 안내하는 신뢰구간과 검사 범위를 함께 보아야 하며, 서로 다른 버전의 점수만 단순 비교하는 것도 피해야 한다.[3]

## 실행 전에 확인할 경계

실제 검사는 대상에 실제 요청을 보내므로 README는 운영 대상 대신 staging 사본을 쓰라고 안내한다.
대상 API와 심사 모델의 인증·호출 비용이 필요하며, 플러그인을 설치한 사실과 감사가 완료된 사실은 구분해야 한다.[1]

Python 3.10 이상이 필요하고, 실제로 사용할 제공자에 맞는 추가 의존성도 준비해야 한다.
채점 실패와 에이전트 실패를 구분하려면 보고서의 제외 사유와 경고를 버리지 않아야 한다.[1][3]

저장소는 Apache-2.0 라이선스를 제공한다.
라이선스 허용과 감사 결과의 신뢰성은 별개의 문제이며, 이 조사에서는 설치·API 호출·실제 감사를 수행하지 않았다.[4]

## 직접 읽어볼 자료

1. README의 Quick start와 Test your own agent: 모의 실행과 실제 대상 연결의 차이를 본다.[1]
2. `ifixai/core/runner.py`: `run_all`의 적용성 분리, 실행, 경고 처리 순서를 읽는다.[2]
3. `docs/scoring.md`: 필수 최소 조건, 판정 불가, 검사 범위의 의미를 확인한다.[3]
