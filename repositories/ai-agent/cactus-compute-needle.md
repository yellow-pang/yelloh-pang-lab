## 한 줄 요약

Needle은 작은 기기에서 자연어를 함수 호출이나 정해진 데이터 형태로 바꾸는 데 초점을 맞춘 모델과 사용 도구다.
현재 README는 Needle 3를 설명하며, 범용 대화 능력을 일부 포기하는 대신 도구 호출·구조화 추출·텍스트 임베딩에 집중한다고 밝힌다.
따라서 긴 대화를 나누는 챗봇이나 기기 전체를 마음대로 조작하는 완성형 비서와는 역할이 다르다.[1]

## 말과 프로그램 사이를 연결하는 작은 모델

앱 안의 기능은 이름과 입력값이 분명한 함수로 작성되지만 사람은 “지금 Lagos 날씨 어때?”처럼 말한다.
프로그램이 이 문장을 처리하려면 날씨 조회 기능을 선택하고 도시 이름을 입력란에 넣어야 한다.
Needle의 도구 호출은 이 변환을 담당한다.
앱이 어떤 함수를 제공했는지 모르면 모델도 그 기능을 실제로 수행할 수 없으며, 실제 날씨 조회나 조명 제어는 등록된 함수의 책임이다.[1]

README는 대응하는 도구가 없는 요청에는 추측한 호출 대신 빈 목록을 반환한다고 설명한다.
여러 요청을 순서 있는 호출로 표현할 수도 있다.
이 동작 계약은 사용자의 문장이 곧 실행 명령이 되는 작은 앱에서 중요하다.
다만 문서에 설명된 정책과 모든 자연어 입력에서의 정확도는 같은 것이 아니므로, 허용 동작과 확인 절차는 앱이 별도로 설계해야 한다.[1]

## 함수 설명이 모델의 선택지를 만든다

Python 예시에서는 함수에 `@needle.tool`을 붙인다.
데코레이터는 함수에 부가 정보를 달아주는 표시라고 생각하면 된다.
모델이 Python 코드를 자유롭게 해석해 실행하는 것이 아니라, 함수 이름·인자 형식·설명문에서 도구의 명세를 만드는 구조다.
명세는 “도시 이름을 문자열로 받는 날씨 조회”처럼 선택할 동작과 필요한 입력을 기계가 읽을 수 있게 표현한다.[1][2]

실제 `needle/agent/tools.py`의 `build_schema`는 함수의 signature와 타입 힌트를 읽고, docstring에서 전체 설명 및 인자 설명을 분리한다.
기본값이 없는 필수 입력과 선택 입력을 구분해 JSON 형태의 parameters를 만든다.
문자열·정수·숫자·불리언·배열·객체를 매핑하며, Literal이나 Enum처럼 정해진 선택지와 Pydantic 모델도 처리하는 분기가 있다.
여기서 JSON은 이름과 값으로 데이터를 주고받는 텍스트 형식이고, schema는 어떤 이름과 값의 종류를 허용하는지 적은 규칙이다.[2]

`Field`는 길이, 범위, 패턴, 선택값 같은 제약을 명세에 반영한다.
예를 들어 입력값의 종류를 분명하게 적는 일은 문장을 예쁘게 꾸미는 것보다 실제 호출의 모양을 정하는 데 직접 연결된다.
반면 이 코드가 만들어준 형식 규칙만으로 사용자의 의도나 반환된 사실이 참인지 보장되는 것은 아니다.
형식 검증과 의미 검토는 구분된다.[2]

## 추출과 임베딩은 다른 결과를 만든다

구조화 추출에서는 어수선한 텍스트에서 송장·예약·알림 같은 정해진 항목을 뽑는다.
README는 스키마에서 만든 디코딩 문법이 출력이 파싱 가능한 형태가 되도록 제한한다고 설명한다.
파싱 가능하다는 것은 프로그램이 문법 오류 없이 읽을 수 있다는 의미이며, 원문에서 날짜나 금액을 항상 정확히 골랐다는 뜻은 아니다.[1]

임베딩은 문장을 숫자 벡터로 바꾸는 별도 활용이다.
문장 검색, 매칭, 라우팅에 사용할 수 있지만 함수 실행 결과나 사용자에게 보여줄 자연어 답변과는 다르다.
Needle를 읽을 때 “한 모델이 여러 용도를 제공한다”와 “한 번의 호출이 모든 일을 끝낸다”를 혼동하지 않는 것이 중요하다.[1]

## 예시로 따라가는 흐름

공식 빠른 시작에는 `get_weather(city: str)`를 등록하고 Lagos의 날씨를 묻는 예가 나온다.
먼저 앱 개발자가 도시 문자열을 받는 함수와 “현재 날씨를 가져온다”는 설명을 제공한다.
도구 명세 생성 코드는 함수 이름과 `city`의 형식, 설명문을 모델이 사용할 데이터로 옮긴다.
이후 `Needle(tools=[get_weather])`에 자연어를 전달하면 적절한 도구와 인자를 선택하고, `run()`이 실제 함수를 호출해 그 반환값을 결과에 담는 흐름이다.[1][2]

중요한 점은 README의 함수가 외부 기상 서비스를 조회하지 않고 고정된 사전 값을 돌려준다는 사실이다.
화면에 예시 온도가 나온다고 해도 Needle가 최신 관측을 알아냈다는 의미는 아니다.
이 예제가 보여주는 것은 자연어의 도시 이름이 함수 입력으로 연결되는 과정이다.
실제 앱이라면 날씨 함수 내부의 데이터 공급원, 실패 처리, 최신성 표시를 따로 구현해야 한다.
사용자는 선택된 함수와 인자가 맞는지, 반환값이 실제 자료인지 확인할 수 있어야 한다.
이 글에서는 예시 코드를 실행하거나 Lagos의 날씨를 조회하지 않았다.[1]

## 작은 배포와 개인정보를 함께 본다

README는 배포할 깊이를 선택할 수 있는 ladder 구조와 기기별 엔진·가중치 배치를 설명한다.
작은 바이너리라는 소개만으로 임의의 마이크로컨트롤러에서 작동한다고 결론 내릴 수는 없다.
대상 플랫폼의 엔진과 모델 깊이, 기기 자원을 확인해야 하며, 비교 성능은 저장소 저자의 벤치마크 주장으로 읽어야 한다.[1]

로컬 미세조정과 플랫폼 미세조정도 구분되어 있다.
전자는 로컬 데이터로 어댑터를 학습시키는 경로이고, 후자는 파일을 업로드해 서비스 측에서 학습·평가하는 경로다.
로컬 미세조정 표에는 confidence가 `None`이라고 명시되어 있으므로 모든 파생 모델이 같은 신뢰도 점수를 제공한다고 보면 안 된다.
confidence는 앱의 확인·거절 정책을 대신하는 보증서가 아니다.[1]

또한 바이너리의 telemetry는 기본으로 켜져 있다고 README에 적혀 있다.
기기 안에서 추론한다는 소개와 네트워크 전송이 전혀 없다는 주장은 같지 않다.
오프라인이나 민감 데이터 환경을 고려한다면 문서의 `NEEDLE_TELEMETRY=0`, `DO_NOT_TRACK=1` 설정과 실제 배포 동작을 별도로 확인해야 한다.[1]

## 직접 읽어볼 자료

1. [README의 Get started](https://github.com/cactus-compute/needle/blob/main/README.md)
   날씨 함수에서 모델이 맡는 부분과 함수 자체가 돌려주는 고정값을 나눠 읽는다. `function_calls`, `reasoning`, `confidence`가 실행 결과와 어떻게 구분되는지도 확인할 지점이다.
2. [도구 명세 생성 코드](https://github.com/cactus-compute/needle/blob/main/needle/agent/tools.py)
   `build_schema`와 `tool`을 순서대로 보면 타입과 설명문이 어떤 데이터로 바뀌는지 추적할 수 있다.
   범위 제한이 명세에 포함된다는 사실과 실제 사용자 의도 검증을 혼동하지 않도록 읽는다.
3. [README의 Customisation과 Deploy](https://github.com/cactus-compute/needle/blob/main/README.md)
   동일 문서의 뒷부분에서는 학습 장소, confidence의 차이, 기기별 엔진, telemetry 조건을 함께 비교한다.
   패키지를 설치할 수 있는지보다 어떤 모델과 실행 환경을 배포하는지를 묻는 순서다.

## 정리

Needle의 중심은 작은 기기에서 말의 의도를 제한된 함수와 데이터 구조로 연결하는 일이다.
모델의 선택, 도구 명세, 실제 함수 구현을 구분하면 무엇을 모델에 맡기고 무엇을 앱이 책임져야 하는지 드러난다.
