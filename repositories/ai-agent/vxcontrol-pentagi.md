## 한 줄 요약

PentAGI는 보안 점검 작업을 여러 AI 에이전트와 도구로 수행하고 기록하는 침투 테스트 플랫폼이다.
침투 테스트는 소유자에게 허가받은 환경에서 방어가 제대로 작동하는지 검증하는 활동이다.
이 프로젝트는 대화만 하는 모델이 아니라 도구 실행, 작업 위임, 기억과 보고서를 연결한다.
이 글은 허가된 실습 환경의 구성과 방어적 검토에 한정하며 외부 시스템을 공격하는 절차를 안내하지 않는다.[1]

## 검사 결과보다 검사 과정을 남기는 플랫폼

보안 점검에는 대상 범위 확인, 관찰, 도구 선택, 결과 해석과 기록이 연결된다.
한 명령의 출력만 저장하면 왜 그 결과를 얻었는지 재검토하기 어렵다.
PentAGI의 README는 연구·개발·인프라 작업을 전문 에이전트에 위임하고 명령과 출력을 PostgreSQL에 저장한다고 설명한다.
모델의 응답 외에 실제 수행 기록을 남긴다는 점이 일반적인 질문 답변과 다르다.[1]

장기 기억과 선택적인 지식 그래프도 소개된다.
지식 그래프는 개별 정보의 관계를 연결해 저장하는 방식으로, Graphiti와 Neo4j를 사용하는 구성이 별도 제공된다.
모든 설치가 이를 반드시 포함하는 것은 아니며 관측 도구와 외부 검색도 별도의 연동이다.
따라서 README에 나열된 기능을 곧바로 기본 설치 하나의 보장된 결과로 읽어서는 안 된다.[1]

## 자율 수행과 감독의 역할

README는 자율형과 보조형 침투 테스트 플랫폼이라는 범위를 명시한다.
미리 정의한 공격 캠페인을 실행하는 BAS 제품과 같지 않으며 에이전트가 작성하는 BAS식 스크립트는 현재 구현 기능으로 취급하지 말라고 한다.
비슷한 보안 용어라도 운영 모델이 다른 제품을 혼동하지 않도록 문서 자체가 선을 긋는다.[1]

결과를 사람이 검토하는 표면도 있다.
보고서는 웹 보기, 클립보드 복사, Markdown과 PDF 다운로드를 지원한다고 설명하지만 JSON 보고서 내보내기는 문서화된 지원 형식이 아니라고 명시한다.
결과를 다른 프로그램에 넣으려는 경우 ‘API가 있으니 보고서도 원하는 JSON으로 나온다’고 추정할 수 없다.
기능의 존재와 특정 출력 계약은 따로 확인해야 한다.[1]

여러 모델 제공자를 선택하거나 자체 모델 서버와 연결할 수 있다는 설명은 추론 경로의 선택권을 뜻한다.
외부 검색 API, 모델 API와 관측 연동은 각기 자격증명과 데이터 전송이 관련된다.
자체 호스팅은 관리 서버를 직접 운영한다는 의미이지 선택한 모든 서비스가 로컬이라는 뜻은 아니다.[1]

## 예시로 따라가는 흐름

대표 자료인 Worker Node Setup은 작업 실행을 별도 서버로 분리하는 공식 예제다.
입력은 특정 취약점 공격 명령이 아니라 관리 노드와 작업 노드의 연결 구조다.
권장 구조에서 PentAGI는 작업 노드의 Docker에 연결해 worker 컨테이너를 만들고, worker가 추가 컨테이너를 필요로 하면 강화된 Docker-in-Docker 데몬에 TLS로 연결한다.
Docker-in-Docker는 작업용 컨테이너 환경 안에서 별도의 컨테이너 실행 영역을 제공하는 방식이다.[2]

이 흐름의 결과는 에이전트가 호스트의 Docker 제어권을 그대로 받는 대신 정책이 적용되는 별도 실행 경로를 사용하는 구성이다.
사람은 인증서가 읽기 전용으로 제공되는지, 연결 대상이 의도한 데몬인지, 관리 노드와 실습 대상의 네트워크 범위가 분리됐는지 확인해야 한다.
가이드는 직접 dind에 worker를 만드는 대안도 설명하지만 그 경우 정책 때문에 호스트 bind mount가 거부되고 중첩 Docker를 사용할 수 없다고 구별한다.
이는 공식 배포 예제를 읽은 설명이며 실제 서버를 구성하거나 보안 테스트를 실행한 결과가 아니다.
어느 모드인지 정하지 않은 채 두 설정을 섞으면 격리 목적과 기능 기대가 동시에 어긋날 수 있다.[2]

## 컨테이너라는 이름만으로 완전 격리를 믿지 않기

README의 기능 목록에는 완전한 격리라는 홍보 표현이 있지만, 구체적인 Docker 안내에는 더 엄격한 주의가 있다.
호스트 Docker 소켓을 worker에 연결하면 자율 에이전트가 호스트 수준에 영향을 줄 수 있다고 경고한다.
따라서 ‘컨테이너 안에서 동작한다’는 문장만으로 위험이 제거됐다고 쓰는 것은 같은 문서의 세부 설명과 충돌한다.[1]

공식 worker 가이드는 소켓 파일 마운트의 시작 순서 문제도 설명한다.
재부팅 후 소켓이 아직 없을 때 연결을 시도하면 파일이어야 할 위치에 디렉터리가 생겨 데몬이 시작하지 못할 수 있다.
TLS 연결은 이런 파일 경로 의존성을 피하고 요청을 정책 검사 경로로 보내려는 선택이다.
보안 설정은 단순히 접근을 막는 문제뿐 아니라 재시작 시 예상한 통로가 유지되는지와도 연결된다.[2]

여러 인스턴스가 외부 자원을 공유하는 경우 README의 `TENANT_ID`는 데이터베이스 스키마, 컨테이너 이름, 그래프 영역과 인증·관측 표식을 나눈다.
하지만 데이터 디렉터리와 포트 같은 호스트 자원은 운영자가 별도로 정해야 하며 공유 디렉터리는 다른 흐름 데이터를 덮어쓸 수 있다고 경고한다.
이름 공간 분리와 실제 저장 공간 분리를 같은 것으로 취급하면 안 된다.[1]

허가된 대상과 중지 조건, 네트워크 범위, 테스트 데이터는 실행 전에 사람이 정해야 한다.
에이전트의 계획이 그럴듯하다는 사실은 승인된 범위를 넓힐 이유가 되지 않는다.
자동 보고서도 관찰 자료와 주장 사이를 검토해야 하며 실제로 재현하지 않은 취약점을 확정된 사실로 배포해서는 안 된다.

## 정리
