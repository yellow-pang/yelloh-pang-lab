## 계정의 공개 흔적을 모으되 사람을 확정하지 않는 도구

User Scanner는 사용자 이름이나 이메일을 입력해 여러 서비스의 계정 존재 여부와 공개 프로필 정보를 확인하는 OSINT 도구다.
OSINT는 공개적으로 얻을 수 있는 자료를 조사하는 방식이라는 뜻이다.
README는 명령행 사용, Python 라이브러리 호출, AI Agent와 연결하는 MCP 서버를 함께 소개한다.
계정 후보를 수집하는 프로그램이지, 같은 이름을 쓰는 모든 계정이 동일인이라는 사실을 보증하는 신원 확인 시스템은 아니다.[1][2]

자신이 오래전에 만든 공개 계정의 노출 범위를 확인하려 해도 서비스마다 검색 방식과 표시 정보가 다르다.
이메일 등록 여부만 알 수 있는 서비스도 있고, 사용자 이름으로 소개 글과 링크를 볼 수 있는 곳도 있다.
User Scanner는 이 차이를 서비스별 모듈로 나누고 결과를 모으는 구조다.
공식 사용 범위는 교육, 허가된 보안 연구와 방어적 조사이며, 다른 사람의 신상을 무단으로 추적하기 위한 안내로 읽어서는 안 된다.[1]

## 결과 수보다 연결의 근거를 구분한다

README의 기본 기능은 이메일·사용자 이름 검사와 프로필 메타데이터 수집이다.
메타데이터는 소개 글, 프로필 링크처럼 계정 주변에 붙은 설명을 뜻한다.
결과는 JSON, CSV, PDF 등으로 내보낼 수 있다.
MCP는 AI 프로그램이 외부 도구를 일정한 형식으로 호출하는 연결 규약이며, 이 저장소는 `scan_username`, `scan_email`, `list_available_modules`를 제공한다고 설명한다.
도구 호출을 자동화한다고 조사 권한이나 결과의 신뢰도가 자동으로 생기지는 않는다.[1]

대표 문서 `docs/CROSS_SCAN.md`는 첫 결과에서 다른 사용자 이름이나 주소를 발견해 다음 조회 대상으로 삼는 교차 탐색을 설명한다.
여기서 피벗은 발견한 단서를 다음 조회의 출발점으로 바꾸는 것이다.
문서는 사이트가 알려준 계정 이름, 소유권 연결 절차를 거친 링크, 사용자가 소개 글에 직접 붙인 링크를 서로 다르게 분류한다.
누군가 다른 사람의 주소를 자기 소개에 적을 수 있기 때문에, 텍스트에 등장했다는 사실만으로 소유 관계가 성립하지 않는다.[2]

조회 방식도 둘로 나뉜다.
공개 프로필이 특정 서비스의 특정 계정을 가리키는 경우와, 같은 사용자 이름을 다른 서비스에 넓게 대입하는 경우다.
전자는 출발 프로필에서 링크가 나왔다는 근거가 있고, 후자는 동일한 문자열이 등록되어 있다는 사실만 보여준다.
문서의 `confirmed`, `likely`, `candidate`, `conflicting` 분류는 이 연결 근거와 메타데이터 비교를 설명하기 위한 내부 등급이다.
이름이 강하게 들려도 법적·현실적 신원의 확정으로 번역하면 안 된다.[2]

이메일에도 별도 함정이 있다.
서비스의 이메일 필드에 주소가 있었다는 사실은 그 서비스가 해당 주소를 게시했다는 뜻이지 소유자의 확인 증명이 아니다.
예를 들어 패키지 작성자 정보에서 다른 공동 관리자의 주소가 섞일 수 있다고 문서가 경고한다.
따라서 계정 결과를 읽을 때에는 어떤 경로에서 나온 주소인지, 직접 입력한 대상인지 다른 프로필에서 파생된 후보인지 함께 남겨야 한다.[2]

## 예시로 따라가는 흐름

자신이 소유한 공개 개발자 계정의 프로필 링크를 점검하는 경우를 생각해 보자.
이해를 위한 가상 예시이며 직접 실행한 결과가 아니다.
먼저 허용된 계정과 서비스 범위를 정하고 그 안에서 사용자 이름 결과를 얻는다.
결과에는 프로필 존재 여부와 서비스가 제공하는 소개·링크 정보가 담길 수 있다.
이 단계의 목적은 해당 계정 주변에 무엇이 공개되어 있는지 확인하는 것이지, 발견한 모든 이름을 다른 사람과 연결하는 것이 아니다.[1]

만약 본인 프로필에 다른 서비스의 계정 링크가 있다면, 교차 탐색 문서에 따라 링크가 인증된 연결인지 단순 소개 글인지 구분해 읽는다.
같은 이름의 별도 계정이 넓은 검사에서 발견되어도 그것은 후보로만 취급한다.
사람은 링크의 출처와 실제 프로필 내용을 대조하고, 자신의 계정 목록과 맞지 않는 항목은 동일인으로 단정하지 않아야 한다.
프로필에 공동 프로젝트의 연락 주소가 적혀 있다면 그 주소를 본인의 개인 이메일로 합치는 것도 잘못이다.[2]

검토 결과는 출처와 불확실성을 남긴 노출 점검 목록으로 정리할 수 있다.
최종적으로 무엇을 지우거나 비공개로 바꿀지는 해당 계정 소유자가 별도로 결정한다.
JSON·CSV 보고서는 근거를 보관하는 형식일 뿐이며, 결과가 파일로 정리되었다고 정확성이 높아지는 것은 아니다.
실제 검사에서 차단이나 오류가 있었다면 계정이 없다는 결론과 분리해야 한다.
이 글은 특정 계정이나 이메일을 조회하지 않았다.[1][2]

## 공개 조회에도 부작용과 동의 문제가 있다

특히 주의할 점은 일부 이메일 모듈이 알림, 비밀번호 재설정 또는 확인 메일을 발생시킬 수 있다는 공식 설명이다.
교차 탐색은 이러한 모듈을 기본적으로 건너뛰도록 설명하지만, 사용자가 별도로 허용하면 동작 범위가 달라진다.
따라서 '공개 자료만 읽으므로 대상에게 아무 영향이 없다'고 보장할 수 없다.
본인 계정이나 명시적으로 허가받은 범위만 다루고, 수신자에게 영향을 주는 기능은 별도 동의 없이 활성화하지 않는 경계가 필요하다.[2]

API 응답, 프로필 형식과 서비스 정책은 변할 수 있다.
README의 지원 플랫폼 수는 조회 시점마다 달라질 수 있는 목록 규모이지, 모든 서비스가 항상 정상 응답하거나 동일한 정보를 제공한다는 뜻이 아니다.
자료 수집에 필요한 네트워크 권한과 서비스 이용 조건, 보고서의 보관·공유 범위를 함께 검토해야 한다.
AI Agent 연결은 반복 조회를 더 쉽게 만들므로 대상과 모듈 범위를 사람의 승인 없이 넓히지 않는 것이 중요하다.[1][2]

## 정리

User Scanner는 여러 서비스의 공개 계정 단서를 모으고 연결 경로를 기록하는 도구다.
유용한 구분은 발견한 계정의 수가 아니라 그 계정이 어떤 근거로 대상과 연결되었는지에 있다.
허가된 노출 점검이라는 목적을 유지하고 후보와 신원 확정을 분리해야 결과를 과장하지 않을 수 있다.
