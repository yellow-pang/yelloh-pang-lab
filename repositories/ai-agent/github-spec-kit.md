## 코드보다 요구사항을 먼저 남기는 도구 모음

Spec Kit은 AI 코딩 Agent가 구조화된 절차, 재사용할 템플릿, 기록된 결과물을 이용하도록 돕는 오픈소스 도구 모음이다.
스스로 코드를 작성하는 별도의 언어 모델은 아니다.
실제 코딩 Agent와 함께 사용하며, 요청을 명세와 계획으로 정리하고 구현 결과를 다시 요구사항에 대조하는 작업 순서를 제공한다.[1]

‘사진 정리 앱을 만들어 달라’는 요청만으로도 코드를 만들 수는 있지만, 앨범은 무엇을 기준으로 묶는지, 이미지는 어디에 저장하는지, 완료 여부를 어떻게 판단하는지는 빠지기 쉽다.
Spec-Driven Development, 즉 명세 중심 개발은 먼저 무엇을 왜 만들지 정하고 그다음 구현 방법을 결정한다.
Spec Kit에서 명세는 나중에 붙이는 설명이 아니라 계획과 작업 목록이 참조하는 입력이다.[1]

## 세 가지 입구와 한 가지 구분

README는 기능 개발, 버그 수정, 아이디어 평가를 독립적인 시작점으로 제시한다.
모든 사용자가 세 과정을 차례로 거쳐야 하는 것은 아니다.
명세 중심 개발은 기본 기능이고, 버그 수정과 아이디어 평가는 필요할 때 추가하는 확장 기능이다.
이미 발생한 오류를 고치는 일에 새 기능 명세 전체를 먼저 작성해야 한다고 해석하면 실제 안내와 어긋난다.[1]

기능 개발에서는 프로젝트 공통 원칙인 Constitution을 정하고, 기능마다 specify → plan → tasks → implement → converge를 진행한다.
명세는 원하는 동작, 계획은 기술 선택, 작업 목록은 실행 단위를 맡는다.
구현 다음에 converge가 있는 것은 코드가 생성되었다는 사실과 명세에 수렴했다는 판단을 분리하기 위해서다.
README는 각 Agent Skill을 하나씩 호출하고 결과를 검토한 뒤 다음으로 넘어가도록 안내한다.[1]

버그 수정은 assess → fix → test로 원인 판단과 수정, 재확인을 나눈다.
결과가 `verified`, `partial`, `failed`로 구분되며 검증이 없으면 성공한 수정이 아니라는 설명도 있다.
아이디어 평가는 intake부터 decide까지 근거를 모아 진행·추가 확인·중단을 결정하고, 소스코드가 없는 프로젝트에서도 사용할 수 있다.
두 확장은 본문의 사진 앱 예시와는 별도의 진입로다.[1]

## 계획을 실제 파일로 나누는 방식

대표 자료인 `templates/commands/plan.md`는 계획 단계의 내부 요구사항을 보여준다.
먼저 기능 명세와 공통 원칙을 읽고 기술적 배경의 모르는 점을 `NEEDS CLARIFICATION`으로 표시한다.
그 뒤 조사 결과를 `research.md`에 결정·이유·검토한 대안으로 정리한다.
‘적당한 기술을 골랐다’는 말만 남기는 대신 선택 근거를 문서화하는 구조다.[2]

설계 단계에서는 데이터의 종류와 관계를 `data-model.md`로 추출한다.
외부 인터페이스가 있으면 다른 코드나 사용자가 따라야 할 약속을 `contracts/`에 적고, 끝으로 `quickstart.md`에 처음부터 끝까지 확인할 시나리오를 정리한다.
이 quickstart는 전체 구현 코드나 테스트 묶음을 넣는 장소가 아니라 전제조건과 실행·검증 방법을 설명하는 안내문이다.
문서마다 맡는 역할을 나눈다는 점이 중요하다.[2]

## 예시로 따라가는 흐름

README의 공식 예시는 날짜별 앨범과 타일 미리보기를 갖춘 사진 정리 앱이다.
첫 입력에서는 이러한 사용자 기능을 specify에 전달한다.
다음 plan 입력에서는 Vite와 기본 JavaScript를 쓰고 이미지는 로컬에, 메타데이터는 SQLite에 보관한다는 기술 조건을 준다.
이렇게 하면 화면에서 원하는 일과 저장 방식에 대한 결정을 같은 문장에 섞지 않고 단계별로 읽을 수 있다.[1]

계획 템플릿을 이 예시에 대입해서 읽으면 먼저 사진과 앨범의 관계를 정의하고, 명세의 검증 조건을 확인하며, 해결되지 않은 기술 질문을 조사하는 흐름이 보인다.
이후 작업 목록을 만들고 Agent가 구현한 뒤 converge 결과를 확인하는 것이 문서상의 순서다.
이 설명은 공식 요청 예시와 계획 지침을 연결한 것이지 실제 앱을 생성한 실행 기록은 아니다.
사람은 ‘날짜’가 촬영일인지 파일 생성일인지 같은 모호한 요구를 명세에서 해소했는지, 데이터 모델이 그 의미를 지키는지, 완성된 화면만 보고 저장 기능까지 완료했다고 판단하지 않았는지를 확인해야 한다.
파일이 여러 개 생겼다고 요구사항이 맞아진 것은 아니다.

## 자동화가 바꾸는 것과 남겨 두는 책임

README가 안내하는 전제조건은 Python 3.11 이상, uv, 지원되는 코딩 Agent다.
터미널의 CLI 초기 설정과 Agent 채팅창의 Skill 호출은 서로 다르다.
예시의 `/speckit-*`를 일반 셸 명령처럼 실행하는 방식이 아니며 Agent 및 통합 모드에 따라 호출 문법도 달라질 수 있다.[1]

계획 템플릿에는 확장 hook, 즉 계획 전후에 연결된 다른 작업을 호출하는 절차도 있다.
활성화된 필수 hook은 출력만 하지 말고 실제 호출을 기다리도록 지시한다.
따라서 Spec Kit을 문서 양식만 복사하는 도구로 생각해서는 안 된다.
선택한 확장과 Agent 권한에 따라 추가 작업이 발생할 수 있으므로 실행할 절차와 파일 변경 범위를 먼저 이해해야 한다.[2]

명세가 잘못되면 그 명세에 맞춘 구현도 잘못될 수 있다.
Spec Kit은 판단 내용을 밖으로 드러내고 확인 단계를 구성하지만, 요구사항의 타당성이나 Agent의 테스트 결과를 독립적으로 보증하는 인증 도구는 아니다.
오류 수정의 `partial`이나 미해결 질문은 완료처럼 숨기지 않고 남기는 것이 이 구조를 제대로 읽는 방법이다.

## 정리

Spec Kit은 코딩을 명세·계획·작업·구현·확인의 문서 흐름으로 연결한다.
핵심은 문서를 많이 만드는 데 있지 않고 단계마다 입력과 판단 기준을 분리하는 데 있으며, 검토 책임까지 Agent에 넘긴다는 뜻은 아니다.
