## 한 줄 요약

Kaneo는 프로젝트와 할 일을 관리하는 자체 호스팅 가능한 웹 애플리케이션이다.
AI가 모든 일을 대신 수행하는 에이전트 자체가 아니라, 사람이 보드로 작업을 정리하고 외부 AI 도구도 같은 작업 데이터에 접근하도록 연결하는 서비스다.
README는 복잡한 관리 도구의 버튼과 알림보다 실제 작업에 집중하는 인터페이스를 지향하며 MIT 라이선스와 자체 호스팅을 제시한다.
이것은 설계 목표이지 사용 속도를 직접 측정한 결과는 아니다.[1]

## 작업 목록을 프로젝트의 상태로 바꾸기

메모에 해야 할 일을 적는 것과 프로젝트를 관리하는 것은 다르다.
어떤 작업이 대기 중인지, 어느 프로젝트에 속하는지, 누가 맡았는지, 기한이 언제인지 함께 볼 수 있어야 하기 때문이다.
Kaneo의 작업 API는 이러한 정보를 프로젝트 단위 보드로 다룬다.
보드는 상태를 나타내는 열과 그 안의 작업으로 구성되며, 보관된 작업과 계획된 작업도 별도 묶음으로 반환한다.[2]

여기서 상태는 단순한 설명 문장이 아니다.
작업을 만들 때 전달한 `status`가 어느 열에 배치할지를 결정한다.
제목만 있는 메모를 추가하는 것과 달리 생성 시점부터 프로젝트 흐름 안에 위치가 생긴다.
조회, 생성, 복제, 담당자 변경, 기한 변경, 우선순위 변경을 나눈 코드 구성도 확인된다.
다만 각 조작의 사용자 화면을 실제 열어본 것은 아니므로 코드에서 드러난 API 역할과 화면의 사용감을 혼동하지 않아야 한다.[2]

## 보드, 접근 권한, AI 연결은 서로 다른 층이다

첫 번째 층은 데이터 조회다. `listTasksRoute`는 필터와 정렬을 먼저 적용한 뒤 여러 페이지로 작업을 나눠 반환한다.
한 응답을 전체 보드로 착각하지 않도록 작업 페이지뿐 아니라 라벨과 링크, 열 정보의 관련 페이지도 따라가도록 설명한다.
긴 설명문은 조회 응답에서 생략될 수 있고 별도 상세 조회가 필요하다.
작업 수가 늘어났을 때 화면이나 연동 프로그램이 빠뜨리지 않고 읽으려면 이 구분이 중요하다.[2]

두 번째 층은 권한이다.
생성 경로에는 프로젝트로부터 워크스페이스 접근을 확인하는 절차와 `task:create` 권한 검사가 있다.
워크스페이스는 같은 접근 범위를 공유하는 작업 공간이라고 이해하면 된다.
일괄 변경은 여러 작업을 받지만 모두 같은 워크스페이스에 속해야 한다.
작업을 많이 선택했다고 해서 서로 다른 공간의 권한 경계가 사라지는 것은 아니다.[2]

세 번째 층은 외부 도구 연결이다.
README는 각 인스턴스의 `/api/mcp` HTTP 엔드포인트와 stdio 방식의 `@kaneo/mcp` 패키지를 안내한다.
MCP는 AI 도구가 외부 기능을 공통된 방식으로 발견하고 호출하도록 하는 연결 규약이다.
Claude나 Cursor 같은 클라이언트에서 작업·프로젝트·라벨을 관리할 수 있다는 설명은 있지만, 그것이 모든 변경을 사용자 승인 없이 맡기라는 의미는 아니다.[1]

## 예시로 따라가는 흐름

개인 웹사이트 개선 프로젝트에 ‘소개 페이지 문구 수정’이라는 작업을 넣는 상황을 생각해 보자.
이해를 위한 가상 예시이며 직접 실행한 결과가 아니다.
입력에는 대상 프로젝트와 작업 제목, 배치할 상태가 필요하다.
서버는 먼저 해당 프로젝트의 워크스페이스에 접근 가능한지 확인하고, 작업 생성 권한과 요청 형식이 맞는지 검사한 다음 상태에 대응하는 열에 작업을 추가한다.
결과로 생성된 작업을 돌려주는 것이 코드에 정의된 흐름이다.[2]

그 뒤 보드를 읽어 작업이 원하는 열에 있는지 확인한다.
작업이 많은 프로젝트라면 첫 응답에 없다는 이유만으로 생성 실패라고 판단하지 않고 페이지와 필터 조건을 함께 확인해야 한다.
상세 설명이 길다면 목록에서 잘린 정보와 실제 저장된 설명도 구분한다.
동일한 작업을 복제할 때는 제목만 복사되는 것으로 생각해서도 안 된다.
코드 설명은 사용자 정의 필드, 라벨, 설명 자산 등을 복사하지만 댓글, 시간 기록, 하위 작업은 복사하지 않는다고 명시한다.
따라서 사람이 마지막으로 확인할 것은 ‘새 작업이 존재하는가’뿐 아니라 소속, 상태, 이어받은 정보와 제외된 정보다.[2]

## 자체 호스팅의 책임과 자동화의 경계

README의 Docker Compose 예시는 Kaneo와 PostgreSQL을 함께 구성한다.
PostgreSQL은 작업 데이터를 지속적으로 저장하는 데이터베이스다.
데이터가 자신의 서버에 있다는 것과 운영 부담이 없다는 것은 다르다.
예시는 데이터 볼륨과 상태 검사를 사용하고 데이터베이스 비밀번호, 인증 비밀값, 클라이언트 주소 설정을 요구한다.
공개 배포라면 인증 설정과 백업, 업데이트를 별도로 관리해야 한다.[1]

기본 Compose 설명에서 데이터베이스는 내부 네트워크로만 접근하며, 호스트에서 개발용 API를 연결할 경우에 한해 루프백 주소로 포트를 명시적으로 노출하도록 안내한다.
외부 접속을 위해 데이터베이스 포트를 무조건 여는 방식과 다르다.
또한 셀프 호스팅, 별도 이미지, 배포 도구별 구성을 섞으면 브라우저가 접근할 API 주소와 서버 내부 주소를 혼동할 수 있다.
README의 배포별 주소 안내를 읽고 자신이 선택한 경로 하나를 기준으로 판단해야 한다.[1]

AI 연결도 작업 저장소의 권한을 사용하는 수단이다.
작업 삭제나 일괄 변경은 읽기와 성격이 다르며, 연결 성공 여부만으로 원하는 대상에 안전하게 적용됐다고 볼 수 없다.
이 글에서 확인한 것은 경로에 선언된 권한 검사와 응답 계약이다.
실제 배포 환경에서 인증·권한 정책이 어떻게 구성됐는지까지 시험한 보안 검증은 아니다.

## 정리

Kaneo의 중심은 프로젝트별 작업 상태를 저장하고 변경하는 관리 서비스다.
MCP는 그 위에 더해진 접근 방식이며, 보드의 페이지 처리와 워크스페이스 권한은 사람 화면과 자동화 모두에서 지켜야 할 경계다.
