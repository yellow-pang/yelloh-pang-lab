## 한 줄 요약

quiche는 QUIC 전송 프로토콜과 HTTP/3를 구현한 저수준 네트워크 라이브러리다.
완성된 웹 서버를 대신 제공하는 것이 아니라, 애플리케이션이 전달한 패킷을 처리하고 연결 상태를 관리하는 부품이다.
실제 소켓 입출력과 시간을 기다리는 이벤트 루프는 사용하는 애플리케이션의 책임이다.[1]

## 프로토콜과 입출력을 나누는 이유

네트워크 프로그램은 데이터를 보내는 규칙만 알아서는 동작하지 않는다.
운영체제에서 패킷을 읽고, 다음 사건이 올 때까지 기다리고, 일정 시간이 지나면 재처리를 시작해야 한다.
quiche는 QUIC의 연결·전송 처리를 맡되 이런 실행 환경의 선택을 외부에 남긴다.
기존 프로그램의 네트워크 구조에 통신 기능을 넣는 상황을 대상으로 이해하기 좋다.[1]

QUIC의 stream은 하나의 연결 안에서 데이터를 주고받는 논리적인 흐름이다.
HTTP/3는 그 전송 기반 위에 웹 요청과 응답을 표현하는 계층이다.
따라서 QUIC stream에 임의의 바이트를 넣는 예제와 HTTP/3 요청 API를 사용하는 예제는 같은 수준의 코드가 아니다.
저장소에 둘 다 있다는 이유로 모든 예제를 HTTP/3 클라이언트라고 부르면 역할을 혼동하게 된다.[1][2]

## 연결 설정부터 송신까지의 책임

`Config`는 프로토콜 버전, 애플리케이션 프로토콜 식별자, 흐름 제어, 혼잡 제어와 유휴 시간 제한 등을 설정한다.
흐름 제어는 상대가 받아들일 수 있는 데이터량을 조절하는 장치다.
README는 일부 stream 개수와 데이터 한도 기본값이 0이라고 설명한다.
사용 사례에 따라 적절한 값을 지정해야 하므로, 객체를 생성했다는 사실만으로 데이터를 보낼 준비가 끝나는 것은 아니다.[1]

클라이언트는 `connect()`, 서버는 `accept()`를 통해 연결을 만든다.
수신한 UDP 데이터를 `recv()`에 넘기면 quiche가 연결 상태에 반영하고, `send()`는 네트워크로 내보낼 패킷을 만든다.
여기서 `send()`라는 이름은 실제 소켓 전송까지 끝냈다는 뜻이 아니다.
반환된 바이트와 목적지 정보를 보고 소켓으로 보내는 코드는 애플리케이션에 남는다.[1]

시간 처리도 같은 경계를 따른다. `timeout()`으로 다음 기한을 확인하고, 기한이 지나면 `on_timeout()`을 호출한 후 새로 보낼 패킷이 있는지 확인한다.
README가 안내하는 pacing은 패킷을 한꺼번에 쏟아내지 않도록 전송 간격을 조절하는 일이다.
라이브러리는 `SendInfo.at`으로 시점 힌트를 주며, 이를 실제 타이머나 운영체제 기능에 반영하는 일 역시 호출 측에서 해야 한다.[1]

Rust 외에 C API도 제공하지만 `ffi` 기능을 켜야 한다.
이는 다른 언어에서 함수를 부르는 접점을 제공한다는 의미이지, 그 언어의 이벤트 루프와 오류 처리를 자동으로 만들어 준다는 의미는 아니다.
HTTP/3 모듈은 이 저수준 기반 위에서 요청·응답을 다루는 별도 API로 소개된다.[1]

## 예시로 따라가는 흐름

공식 `quiche/examples/client.rs`는 URL 하나를 입력으로 받는다.
URL에서 서버 주소를 구하고 주소 체계에 맞는 UDP 소켓을 만든 뒤, `mio` 이벤트 루프에 읽기 관심을 등록한다.
다음으로 연결 설정과 임의의 연결 식별자를 준비하고 `quiche::connect()`를 호출한다.
처음 생성된 패킷도 프로그램이 직접 `socket.send_to()`로 보낸다.
입력 URL이 곧 HTTP/3 API 호출로 연결되는 구조는 아니다.[2]

이후 반복문은 `conn.timeout()`을 기다리는 시간으로 사용한다.
이벤트가 없어서 시간이 만료되면 `on_timeout()`을 호출하고, 데이터가 있으면 소켓에서 읽어 `conn.recv()`로 넘긴다.
연결이 성립하면 URL 경로를 넣은 `GET ...` 문자열을 stream에 한 번 보낸다.
이 파일은 `hq-interop`과 `http/0.9` 등의 프로토콜 식별자를 설정하는 기초 QUIC 예제이며, 별도 HTTP/3 예제와 구분해서 읽어야 한다.[2]

응답은 읽을 수 있는 stream을 순회하며 받아 출력한다.
요청 stream의 종료 표시인 `fin`이 오면 연결 종료를 요청하고, 매 반복에서 quiche가 만든 송신 패킷을 다시 소켓으로 보낸다.
사람은 이 과정에서 소켓 수신, 프로토콜 처리, 애플리케이션 데이터 수신이 서로 다른 단계임을 확인할 수 있다.
이 설명은 코드의 흐름을 따른 것이며 서버 응답이나 소요 시간을 실제 측정한 기록은 아니다.[2]

## 예제의 편의와 운영 조건은 다르다

확인한 클라이언트 예제에는 `config.verify_peer(false)`가 있고, 바로 위에 운영 환경에서는 그렇게 설정하지 말라는 주석이 있다.
간단한 동작 설명을 위해 줄인 검증을 그대로 서비스에 옮기면 안 된다.
README도 예제 클라이언트와 서버의 성능·보안·신뢰성을 보장하지 않으며 운영 목적이 아니라고 명시한다.[1][2]

빌드 안내에는 Rust와 CMake, BoringSSL 관련 조건이 있고 Windows에서는 NASM도 요구된다.
C API 사용 여부나 대상 플랫폼에 따라 준비가 달라진다.
이 글에서는 설치 명령을 실행하지 않았으므로 특정 시스템에서 빌드가 된다고 결론 내리지 않는다.[1]

프로토콜 구현을 채택하는 일과 안정된 네트워크 애플리케이션을 완성하는 일도 다르다.
타이머 누락, 전송 한도 설정, 인증서 검증, 소켓의 일시적인 쓰기 불가 상태 등을 호출 측이 다뤄야 한다는 점은 예제의 반복문에서도 드러난다.
라이브러리 경계를 이해하지 않고 함수 이름만 따라 붙이면 필요한 처리가 빠질 수 있다.[1][2]

  각 단계에서 quiche가 해 주는 일과 애플리케이션이 직접 해야 하는 일을 두 줄로 나누어 정리하면 API 경계가 분명해진다.

  기초 stream 예제의 범위를 과장하지 않고, 예제 코드와 실제 배포 코드 사이에 남는 책임을 확인할 수 있다.

## 정리

quiche는 QUIC·HTTP/3 처리를 다른 프로그램에 통합하기 위한 라이브러리다.
연결 상태 관리는 내부가 맡지만 입출력, 타이머 적용과 운영용 보안 설정은 외부 프로그램이 완성해야 한다.[1][2]
