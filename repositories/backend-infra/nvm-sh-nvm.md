## 한 줄 요약

nvm은 한 사용자 계정에서 여러 Node.js 버전을 설치하고 셸마다 사용할 버전을 선택하는 도구다.
Node.js는 JavaScript 프로그램을 브라우저 밖에서 실행하는 환경이며, nvm은 그 실행 환경 자체가 아니라 버전 선택을 돕는 셸 스크립트다.
공식 설명은 사용자별 설치와 셸별 호출을 명확하게 구분한다.[1]

## 같은 명령이 다른 실행 환경을 가리킬 때

서로 다른 시기에 만든 두 JavaScript 프로젝트가 각각 다른 Node.js 버전을 요구할 수 있다.
컴퓨터에 새 버전을 설치했다고 기존 프로젝트의 실행 조건까지 맞춰지는 것은 아니다.
nvm은 여러 버전을 보관하고 현재 터미널에서 `node`라는 이름이 어느 실행 파일을 가리킬지 바꾸는 방식으로 이 문제를 다룬다.
프로젝트 소스나 라이브러리의 코드를 자동으로 변환해 주는 도구는 아니다.[1][2]

`install`과 `use`의 차이가 출발점이다.
전자는 필요한 버전을 준비하는 동작이고 후자는 준비된 버전을 현재 셸에서 선택하는 동작이다.
README는 설치 가능한 원격 목록, 설치된 버전, 별칭, 실행 파일의 위치를 확인하는 명령을 구분한다.
이미 실행 중인 다른 프로그램의 Node.js가 모두 함께 교체된다고 이해하면 안 된다.
nvm이 바꾸는 범위는 셸 환경과 그 환경에서 실행할 명령이다.[1]

## 버전 파일에서 실행 경로까지

프로젝트의 `.nvmrc`에는 사용할 버전 표현을 적는다. `nvm use`처럼 버전을 생략한 명령은 현재 디렉터리에서 시작해 위쪽 디렉터리로 올라가며 이 파일을 찾는다.
따라서 프로젝트의 하위 폴더에서 작업하더라도 루트에 적힌 버전을 읽을 수 있다.
구현의 `nvm_find_nvmrc`와 `nvm_rc_version`은 파일 탐색과 내용 해석을 분리하고, 파일이 없거나 내용이 비정상인 경우를 처리한다.[1][2]

버전을 골랐으면 실제 실행 파일을 찾는 순서도 바뀌어야 한다. `PATH`는 셸이 명령 이름에 해당하는 프로그램을 탐색할 디렉터리 목록이다. `nvm.sh`의 버전 전환 부분은 선택한 버전의 디렉터리를 계산한 뒤 `PATH`를 변경하고 `NVM_BIN`, `NVM_INC` 같은 환경변수를 설정한다.
그래서 버전 선택을 이해하려면 다운로드 폴더만 볼 것이 아니라 현재 셸의 검색 경로를 함께 봐야 한다.[2]

별칭은 긴 버전 번호 대신 사용할 이름이다.
README의 `node`는 최신 버전을, `lts/*`는 최신 장기 지원 계열을 가리키는 표현으로 소개된다.
이런 이름은 편리하지만 시간에 따라 해석되는 버전이 바뀔 수 있다.
정확한 실행 환경 재현이 필요한 상황에서 특정 버전 번호와 이동하는 별칭은 같은 약속이 아니다.
또한 `current`는 `.nvmrc`가 요구하는 버전이 아니라 현재 셸에서 활성화된 버전을 뜻한다.[1]

## 예시로 따라가는 흐름

README의 `.nvmrc` 예제는 프로젝트에 `5.9`라는 버전 표현이 있을 때 버전을 생략한 `nvm use`가 그 파일을 찾아 사용하는 과정을 보여 준다.
이 번호는 공식 문서의 오래된 설명용 예제이지 지금 새 프로젝트에 권하는 버전이 아니다.
문서에서 중요한 입력은 프로젝트 경로, `.nvmrc`의 내용, 로컬에 이미 설치된 버전이며, 출력으로 제시한 버전 문자열을 이 글에서 재실행한 결과로 취급하지 않는다.[1]

프로젝트 안의 하위 폴더에서 명령을 요청하면 nvm은 상위 경로에서 `.nvmrc`를 찾고 내용을 해석한다.
필요한 버전이 준비돼 있다면 선택한 디렉터리의 실행 파일을 쓰도록 현재 셸의 경로를 전환한다.
아직 설치되지 않았다면 버전 사용과 설치는 구별해야 한다.
README는 `nvm install`도 `.nvmrc`를 읽을 수 있으며, 그 버전이 없다면 설치하고 전환한다고 설명한다.[1][2]

확인 단계에서는 단지 파일이 존재하는지만 보지 않는다. `node -v`는 실제로 호출되는 Node.js 버전을, `nvm which`는 지정한 버전의 실행 파일 위치를 확인하는 경로다.
다른 터미널에서 같은 결과를 원한다면 그 셸에서도 nvm이 로드됐는지와 선택된 버전을 따져야 한다. `.nvmrc`를 만들었다고 디렉터리 이동마다 자동 전환이 생기는 것은 아니며, README의 자동 전환 예제는 별도의 셸 통합 설정이다.[1]

## 버전 전환이 해결하지 않는 문제

nvm은 프로젝트 의존성을 관리하는 npm과 역할이 다르다.
Node.js 버전을 선택해도 프로젝트의 라이브러리가 새 환경에서 호환되는지는 따로 확인해야 한다.
전역으로 설치한 npm 패키지를 다른 Node.js 버전으로 옮기는 작업도 README에서 별도 명령으로 다룬다.
버전 관리가 패키지 호환성 검사를 대신한다는 뜻은 아니다.[1]

지원 셸도 중요하다.
공식 README는 POSIX 호환 셸과 Unix, macOS, Windows WSL을 안내하며 Fish는 직접 지원하지 않는다고 명시한다.
이름이 비슷한 `nvm-windows`는 이 프로젝트가 개발하거나 지원하는 같은 프로그램이 아니다.
또한 `~/.npmrc`의 사용자 지정 `prefix`나 관련 환경변수가 충돌할 수 있고, Homebrew로 설치한 nvm은 공식 지원 설치 경로가 아니라고 안내한다.[1]

자동화 환경에서는 초기화가 또 다른 경계다.
README의 Docker 설명은 비대화형 bash가 일반 프로필 파일을 자동으로 읽지 않는다는 점을 다룬다.
터미널에서 동작한 명령이 자동 실행 환경에서도 바로 보일 것이라고 가정하면 안 된다.
미리 빌드된 Node.js 파일이 없는 환경에서는 소스 컴파일과 개발 도구가 필요할 수도 있다.
이 글은 그런 설치 작업을 수행하지 않았다.[1]

## 직접 읽어볼 자료

- [README의 Intro·About·Usage](https://github.com/nvm-sh/nvm/blob/master/README.md):

  설치와 선택, 단일 명령 실행이 어떻게 구별되는지 먼저 읽는다. `node`, `lts/*`, `current`의 의미를 비교하면 버전 이름을 적는 방식이 결과의 재현성에 어떤 차이를 만드는지 이해할 수 있다.[1]
- [README의 .nvmrc·Deeper Shell Integration](https://github.com/nvm-sh/nvm/blob/master/README.md):

  버전 파일을 찾는 방향과 자동 전환 설정을 나누어 읽는다.
  파일 하나를 추가한 효과와 셸 프로필을 변경한 효과가 왜 다른지 확인하는 순서다.[1]
- [nvm.sh](https://github.com/nvm-sh/nvm/blob/master/nvm.sh):

  `nvm_find_nvmrc`에서 파일 탐색을, `nvm_rc_version`에서 값 해석을, 버전 전환 분기에서 `PATH` 변경을 찾는다.
  전체 셸 문법을 이해하기보다 버전 표현이 실제 실행 경로가 되는 연결을 따라가면 된다.[2]

## 정리

nvm의 핵심은 여러 Node.js를 보관하는 것과 현재 셸에서 하나를 선택하는 것을 분리한 데 있다. `.nvmrc`는 프로젝트의 요구 버전을 전달하지만 자동 전환이나 패키지 호환성을 보장하지 않는다.
셸 초기화, 선택된 버전, 실제 실행 경로를 함께 확인해야 한다.[1][2]
