## 한 줄 요약

Cilium은 Kubernetes 애플리케이션의 통신 연결, 접근 정책, 네트워크 관찰을 함께 다루는 eBPF 기반 프로젝트다.
웹 서비스를 작성하는 프레임워크가 아니라, 이미 실행 중인 서비스 사이에서 패킷이 어디로 가고 어떤 요청이 허용되는지를 담당한다.[1]

## 주소가 바뀌어도 유지해야 하는 통신 규칙

컨테이너는 새로 생성되거나 다른 노드로 옮겨지면서 IP 주소가 바뀔 수 있다.
이때 “이 주소는 허용한다”는 규칙만으로 서비스를 관리하면 주소 변화에 맞춰 정책도 계속 손봐야 한다.
Cilium은 같은 보안 정책을 공유하는 애플리케이션 집단에 보안 식별자를 부여한다.
통신을 허용하는 기준을 일시적인 주소와 분리하는 방식이다.[1]

여기서 eBPF는 Linux 커널의 네트워크 입출력이나 소켓 등에 작은 프로그램을 연결하는 기술이다.
Cilium의 데이터 처리 경로는 이를 이용한다.
다만 eBPF 자체가 사용자의 의도를 이해하는 것은 아니다.
어떤 애플리케이션끼리 연결할지, 포트뿐 아니라 HTTP 요청까지 제한할지는 운영자가 정책으로 표현해야 한다.
네트워크를 제공하는 일과 원하는 보안 경계를 설계하는 일은 구분된다.[1]

## 연결·정책·관찰이 맡는 역할

연결 방식에는 overlay와 native routing이 있다.
overlay는 호스트 사이에 가상 네트워크를 만들며, native routing은 Linux의 일반 경로표를 활용한다.
후자는 기반 네트워크가 컨테이너 IP로 가는 경로를 처리할 수 있어야 한다.
따라서 두 방식은 이름만 다른 선택지가 아니라 주변 네트워크에 요구하는 조건이 다르다.[1]

부하 분산은 하나의 서비스로 들어오는 요청을 실제 처리할 애플리케이션으로 보내는 기능이다.
README는 eBPF를 이용한 분산 부하 분산과 kube-proxy 대체 구성을 설명한다.
여러 클러스터를 연결하는 Cluster Mesh는 서비스 발견과 공통 식별자 기반 정책을 다룬다.
단일 클러스터 연결 문제와 여러 클러스터의 일관된 접근 문제를 같은 것으로 보지 않는 것이 중요하다.[1]

정책은 주소·프로토콜·포트 수준뿐 아니라 HTTP 메서드와 경로 같은 애플리케이션 계층의 조건도 표현할 수 있다.
L3/L4는 네트워크 주소와 전송 규칙, L7은 애플리케이션 요청의 의미에 가까운 계층이라고 이해하면 된다.
“80번 포트에 접속 가능”과 “특정 경로로 POST 요청만 가능”은 서로 다른 허용 범위다.[1][2]

Hubble은 이런 네트워크를 관찰하는 구성 요소다.
서비스 관계, 식별자와 라벨이 붙은 흐름 정보, DNS 관련 단서와 차단 원인을 보여 주는 방향으로 설명되어 있다.
연결이 실패했을 때 단순히 재시도하는 대신 정책 위반인지 이름 조회 문제인지 분리해 조사하도록 돕는다.
관찰 정보가 있다는 사실이 모든 장애의 원인을 자동으로 해결한다는 의미는 아니다.[1]

## 예시로 따라가는 흐름

공식 `sw_l3_l4_l7_policy.yaml`은 이름이 `rule1`인 CiliumNetworkPolicy 예제다.
먼저 `endpointSelector`가 `org: empire`, `class: deathstar` 라벨을 가진 대상을 고른다.
이는 규칙을 적용받는 목적지를 정하는 단계다.
다음 `fromEndpoints`는 들어오는 요청의 출발점이 `org: empire` 라벨을 가졌는지 표현한다.
목적지 선택과 출발지 조건이 별도로 쓰여 있다는 것이 첫 번째 읽을 지점이다.[2]

그 뒤 `toPorts`는 TCP 80번 포트를 지정하고, 그 안의 `rules.http`는 `POST`와 `/v1/request-landing`을 묶는다.
이 예제를 읽으면 같은 서버의 같은 포트에 도달하더라도 HTTP 요청 종류와 경로에 따라 정책의 허용 범위가 달라짐을 알 수 있다.
사람은 먼저 실제 대상 라벨이 선택자와 맞는지, 의도한 호출이 이 메서드·경로인지 확인해야 한다.
포트만 열렸다는 이유로 다른 기능까지 허용되었다고 판단해서는 안 된다.[2]

여기까지는 공식 선언 파일의 해석이며 직접 실행한 결과가 아니다.
실제 클러스터에서는 다른 정책과 배포 구성도 함께 확인해야 한다.
Hubble의 흐름 정보는 그 다음 단계에서 요청이 전달되거나 차단되는 이유를 살펴볼 자료가 된다.
YAML의 조건, 애플리케이션이 보내는 요청, 관찰된 흐름을 서로 대조해야 하며, 이 글은 성공 응답이나 차단 로그를 만들어 제시하지 않는다.[1][2]

## 도입 전에 구분할 경계

Cilium은 Linux 커널의 기능과 네트워크 구성에 의존한다.
기존 연결 경로에 영향을 주는 구성 요소이므로 “라이브러리 하나를 추가한다”는 접근과 다르다.
특히 native routing의 경로 조건과 kube-proxy 대체 여부처럼 기존 통신 체계와 맞닿는 선택은 설치 전에 구분해야 한다.[1]

README는 개발용 snapshot, RC, CI 이미지를 운영용으로 쓰지 말라고 명시한다.
기능 설명이 최신 개발 브랜치에서 보인다는 사실과 안정 배포판에서 같은 조건으로 사용할 수 있다는 사실은 다르다.
성능을 강조하는 소개도 이 글에서 별도로 측정한 결과가 아니다.[1]

라이선스 또한 한 종류로 뭉뚱그리기 어렵다.
사용자 공간 구성 요소는 Apache-2.0이며 BPF 코드 템플릿에는 GPL-2.0-only 또는 BSD-2-Clause의 이중 라이선스가 안내된다.
코드를 가져다 쓰거나 재배포할 때는 실제 사용 부분의 조건을 구분해서 읽어야 한다.[1]

## 정리

Cilium의 중심은 바뀌는 주소와 보안 정책을 분리하면서 연결과 관찰을 함께 제공하는 데 있다.
실제 선택에서는 eBPF라는 기술명보다 필요한 라우팅 조건, 정책의 적용 대상, 결과를 확인할 관찰 경로를 먼저 구분해야 한다.[1][2]
