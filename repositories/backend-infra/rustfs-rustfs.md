## 한 줄 요약

RustFS는 S3 방식의 API로 객체를 저장하고 읽는 Rust 기반 분산 저장소 서버다.
객체는 파일의 내용과 부가 정보를 함께 다루는 단위이고, 버킷은 그런 객체를 담는 묶음이다.
프로그램 안에 추가하는 작은 파일 입출력 라이브러리가 아니라 인증, 저장 공간, 관리 화면과 보호 정책을 갖추어 운영하는 서비스에 가깝다.[1]

## 파일 보관에서 객체 관리로

사진이나 정적 웹 자산을 저장할 때 필요한 것은 업로드와 다운로드만이 아니다.
같은 이름으로 다시 올린 자료를 어떻게 관리할지, 누가 읽을 수 있는지, 오래된 데이터를 언제 없앨지도 정해야 한다.
RustFS의 README는 단일 노드와 분산 배치, 버전 관리, 수명주기 관리, Object Lock, 서버 측 암호화 등을 제공 기능으로 소개한다.
Object Lock은 보존 조건에 따라 객체의 변경·삭제를 제한하는 기능이고, 수명주기는 데이터의 만료나 이동 규칙을 다루는 기능이다.[1]

이때 S3 호환이라는 표현을 정확히 읽어야 한다.
공식 호환성 문서는 지원되는 기능에 대해 폭넓은 S3 API 호환성을 제공한다고 쓰며, 모든 표준·공급자별 동작의 완전한 구현을 주장하지 않는다.
기존 클라이언트가 연결된다는 것과 그 클라이언트가 쓰는 모든 예외 동작이 같다는 것은 별개의 문제다.[2]

## 저장 데이터와 API 계약

첫 번째 축은 객체의 본문과 메타데이터다.
본문은 실제 바이트 내용이고 메타데이터는 내용 유형, 캐시 정책, 언어 같은 설명 정보다.
똑같은 파일 내용이라도 이런 정보가 바뀌면 클라이언트가 해석하는 방식이 달라질 수 있다.
공식 `CopyObject` 회귀 테스트는 객체를 복사하거나 자기 자신에게 다시 복사하면서 메타데이터를 교체하는 경우를 구분한다.[3]

두 번째 축은 보호·운영 기능의 범위다.
README는 암호화, 복제, 무결성 검사와 복구, 관리 콘솔 등을 안내하면서 일부 기능을 Preview로 분리한다.
KMS는 암호화 키를 관리하는 구성 요소이며 Local·Static 백엔드는 개발과 시험용이라고 제한한다.
MinIO 디스크 형식 호환은 선택 기능에 묶여 있고, MinIO가 암호화한 객체는 읽을 수 없다는 주의사항도 있다.
저장 형식이 비슷하다는 이유로 기존 디스크를 바로 교체해 붙일 수 있다고 보아서는 안 된다.[1]

세 번째 축은 호환성의 증거다.
지원표는 구현됐다고 보는 테스트, 아직 통과하지 않는 테스트, 의도적으로 제외한 테스트를 분리해 연결한다.
버킷 접근 로그나 소유권 제어 같은 항목은 별도의 한계가 적혀 있다.
특정 HTTP 요청을 처리하는 코드가 있다는 사실과 요구한 동작이 검증됐다는 주장을 구분하도록 설계된 문서다.[2]

## 예시로 따라가는 흐름

대표 자료는 `copy_object_standard_metadata_copy_replace_and_clear` 테스트다.
테스트는 버킷에 JavaScript 자산을 저장하며 본문 외에 캐시 정책, 내용 유형, 언어와 사용자 메타데이터를 붙인다.
먼저 별도의 키로 기본 복사를 요청한 뒤 HEAD로 부가 정보를 확인하고 GET으로 본문을 읽어 처음의 내용과 같은지 비교한다.
HEAD는 주로 응답의 설명 정보를 확인하는 요청이고 GET은 객체 본문까지 받는 요청이다.
여기서 설명하는 것은 저장소에 작성된 테스트 절차이지 이 글에서 수행한 시험 결과가 아니다.[3]

이후 같은 객체에 `MetadataDirective::Replace`를 적용해 메타데이터를 바꾼다.
테스트는 이전의 `stale` 값이 사라지고 새 캐시 정책과 언어 등이 반영돼야 한다고 검사한다.
그 다음 본문을 다시 내려받아 메타데이터 교체 때문에 실제 데이터가 없어지지 않았는지도 확인한다.
단순히 복사 요청이 성공 응답을 냈는지보다, 설명 정보와 본문이 각각 올바른지를 나누어 검증하는 사례다.[3]

다만 이 자료들에는 확인이 필요한 불일치가 있다.
호환성 문서는 REPLACE에서 `Content-Type`을 생략하면 기존 값도 기본값도 유지하지 않는다고 설명한다.
반면 조회한 테스트는 빈 교체 요청 뒤 `binary/octet-stream`을 기대한다.
따라서 생략했을 때의 최종 응답을 한쪽 자료만 근거로 확정하지 않았다.
사용하려는 버전에서 직접 확인하거나 필요한 유형을 요청에 명시해야 할 지점이다.
문서와 테스트를 함께 읽는 이유가 바로 이런 경계를 드러내는 데 있다.[2][3]

## 배포와 호환성의 주의점

처음 정한 저장 공간 구성은 나중의 확장 방법에도 영향을 준다.
README는 단일 노드·단일 드라이브 배치를 독립적인 로컬 경로로만 지원하며, 기존 구성 그대로 확장하거나 Pool에 추가할 수 없다고 명시한다.
여러 드라이브 구성으로 옮기려면 새 배포를 만들고 S3를 통해 데이터를 이전해야 한다.
Pool은 여러 저장 장치를 묶는 배치 단위이므로, '분산 저장소'라는 소개만 보고 작은 시험 구성을 그대로 키울 수 있다고 가정하면 안 된다.[1]

컨테이너는 기본적으로 비루트 사용자로 동작하며 README는 호스트에서 연결한 데이터·로그·인증서 경로의 권한을 확인하도록 한다.
저장소 서버가 시작되지 않는 문제가 객체 API의 문제가 아니라 파일 경로 접근권한 때문일 수 있다.
초기 구성을 복사할 때는 포트와 볼륨뿐 아니라 실제로 쓰기·읽기가 가능한 계정을 함께 확인해야 한다.[1]

빠른 시작 안내에는 기본 관리 계정이 있으므로 외부에 노출하기 전에 인증 설정을 확인하고 기본값을 변경해야 한다.
웹훅은 저장소의 사건을 외부 주소로 알리는 요청이다.
웹훅의 `RUSTFS_NOTIFY_WEBHOOK_SKIP_TLS_VERIFY_PRIMARY`를 켜면 상대 서버의 TLS 인증서를 검증하지 않아 통신을 가로채는 중간자 공격 위험이 생긴다고 README가 경고한다.
사설 인증서를 사용하는 경우에는 검증을 끄는 대신 `RUSTFS_NOTIFY_WEBHOOK_CLIENT_CA_PRIMARY` 설정을 먼저 확인하도록 안내한다.[1]

호환성 문서는 객체 키도 완전히 불투명한 문자열처럼 취급하지 않는다고 설명한다. `.`이나 `..`, 연속된 구분자로 생기는 빈 경로 조각은 디스크상의 경로 해석을 모호하게 만들기 때문에 제한된다.
또한 사이트 복제는 RustFS 측 관리 API까지 포함한 연결이고, 일반 S3 호환 서비스로의 버킷 복제와 같은 범위가 아니다.
API 호환, 디스크 호환, 관리 기능 호환을 하나의 표현으로 합치지 않아야 한다.[2]

README에는 성능 비교도 있지만 이 글은 이를 재현하지 않았다.
Rust로 작성됐다는 사실이나 제시된 비교 자료만으로 다른 장비·네트워크·파일 크기에서도 우위를 단정할 수 없다.
객체 저장소 선택에서 필요한 것은 사용하는 요청과 보호 정책이 지원되는지, 배포 조건이 맞는지에 대한 개별 확인이다.[1][2]

  이어 컨테이너 안내에서 데이터 경로의 권한과 선택 빌드 기능이 자신의 구성에 어떤 전제가 되는지 확인한다.[1]

  필요한 API가 Supported인지뿐 아니라 Not Yet Passing과 Intentional Deviations에 관련 동작이 있는지 찾는다.
  복제 범위와 객체 키 제약도 이 자료에서 확인할 수 있다.[2]
- [CopyObject 메타데이터 테스트](https://github.com/rustfs/rustfs/blob/main/crates/e2e_test/src/copy_object_metadata_test.rs):

  저장 → 복사 → HEAD → GET의 순서로 기대값을 따라간다.
  특히 REPLACE의 누락 필드 처리와 본문 보존 검사를 나누어 읽고, `Content-Type`의 기대값이 문서 설명과 다른 지점을 확인한다.[3]

## 정리

RustFS는 객체 저장 API와 데이터 보호·운영 기능을 결합한다.
폭넓은 S3 호환은 무조건적인 대체 가능성을 뜻하지 않는다.
기능표와 실제 사용 요청을 대조하고, 문서와 테스트의 불일치는 실행 결과로 추정해 메우지 않는 것이 중요하다.[1][2][3]

## 자료 확인 범위

2026-09-27의 공식 README, S3 호환성 문서, CopyObject 회귀 테스트 코드를 읽었다.
서버를 설치·실행하거나 테스트를 돌리지 않았고 성능도 측정하지 않았다. `Content-Type` 생략 시 처리의 문서·테스트 불일치는 미확정 사항으로 남겼다.
