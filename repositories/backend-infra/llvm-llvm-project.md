## 한 줄 요약

LLVM 프로젝트는 컴파일러와 최적화 도구, 실행 환경을 만드는 재사용 가능한 기술 모음이다.
저장소 전체를 하나의 프로그래밍 언어나 실행 파일로 이해하면 구성 요소들의 역할을 놓치기 쉽다.
핵심 LLVM은 중간 표현을 처리하고 목적 파일로 바꾸는 도구·라이브러리를 제공하며, Clang과 LLD 등은 서로 다른 단계를 맡는다.[1]

## 소스코드에서 실행 가능한 형태로 가는 여러 단계

사람이 작성한 코드는 그대로 CPU가 처리할 수 있는 명령이 아니다.
먼저 언어의 문법과 의미를 읽고, 프로그램을 다른 표현으로 옮기고, 대상 환경에 맞는 코드로 만드는 과정이 필요하다.
LLVM의 중간 표현인 IR은 이 사이에서 사용하는 공통 형태다.
특정 언어의 문법과 대상 기계의 세부사항을 한 단계에 모두 묶지 않는 접점으로 이해할 수 있다.[1][2]

README는 Clang이 C, C++, Objective-C와 Objective-C++를 LLVM bitcode로 바꾸고 LLVM을 통해 목적 파일로 이어간다고 설명한다.
libc++는 C++ 표준 라이브러리이며 LLD는 링크 단계의 도구다.
컴파일러가 코드 조각을 목적 파일로 만드는 일과 여러 조각을 연결하는 일, 프로그램이 사용하는 표준 기능을 제공하는 일은 구분된다.[1]

## 작은 언어 예제로 보는 LLVM의 위치

대표 파일로 확인한 Kaleidoscope Chapter3의 `toy.cpp`는 간단한 언어를 읽고 LLVM IR을 만드는 예제다.
lexer는 문자 입력을 숫자, 이름과 명령 같은 토큰으로 나눈다.
parser는 이 토큰을 읽어 표현식의 구조를 만든다.
AST, 즉 추상 구문 트리는 숫자나 변수, 이항 연산 같은 문법 요소를 나무 모양으로 표현한 자료구조다.[2]

이 앞부분은 LLVM이 임의의 언어를 자동으로 이해하는 마법이 아님을 보여 준다.
예제 작성자는 `def`, `extern`과 숫자·식별자를 읽는 규칙, 연산자의 우선순위 등을 직접 작성한다.
그 결과로 만든 AST의 각 노드가 `codegen()`을 통해 LLVM의 값과 명령을 생성한다.
언어를 읽는 책임과 공통 중간 코드를 만드는 API가 만나는 지점이다.[2]

숫자는 `ConstantFP`로, 더하기·빼기·곱하기는 `IRBuilder`의 부동소수점 연산 생성 함수로 옮겨진다.
IRBuilder는 명령을 직접 문자열로 이어 붙이기보다 LLVM 자료구조로 생성하도록 돕는 도구다.
변수는 이름 표에서 찾고, 함수 호출에서는 대상 함수의 존재와 인자 개수를 확인한다.
소스코드가 문법상 읽힌 뒤에도 이름과 호출 관계를 점검하는 단계가 남는다는 뜻이다.[2]

함수 생성에서는 모듈 안에 함수를 준비하고 시작 basic block을 만든 뒤 반환 명령을 붙인다.
basic block은 제어 흐름이 한 방향으로 이어지는 명령 묶음으로 볼 수 있다.
예제는 생성한 함수에 `verifyFunction`을 호출하고, 실패 경로에서는 잘못 만들어진 함수를 제거한다.
이 검사는 생성 IR의 일관성을 확인하는 과정이며 사용자가 원한 의미까지 증명하는 것은 아니다.[2]

## 예시로 따라가는 흐름

이해를 위한 가상 예시이며 직접 실행한 결과가 아니다.
작은 함수가 두 입력값을 받아 덧셈 표현식을 반환한다고 생각해 보자.
Chapter3 예제의 관점에서는 먼저 lexer가 함수 정의 명령, 이름과 인자, 연산 기호를 구분한다.
parser는 함수 원형과 본문 표현식을 AST로 묶고, 코드 생성은 인자 이름을 `NamedValues`에 등록해 본문의 변수 참조와 연결한다.[2]

이항 덧셈 노드는 왼쪽과 오른쪽 하위 표현식의 코드를 먼저 생성한 뒤 `CreateFAdd`를 호출한다.
함수 본문이 값을 만들어 내면 반환 명령을 추가하고 함수 검증을 호출한다.
반대로 알려지지 않은 변수를 찾거나 함수 인자 개수가 맞지 않으면 오류를 보고하는 경로가 있다.
입력 문장을 받는 단계와 내부 표현이 유효한지 판단하는 단계가 연속해서 존재하는 것이다.[2]

이 장의 실제 드라이버는 생성한 함수 IR을 출력한다.
파일 안의 주석이나 모듈 이름에 JIT라는 단어가 보인다고 이 코드가 최종 기계어 실행 결과까지 반환한다고 결론 내리면 안 된다.
JIT는 실행 중 코드를 컴파일하는 방식이지만, 이번에 읽은 Chapter3에서 확인한 종료점은 IR 생성과 출력이다.
사람은 연산·인자·반환 구조가 의도와 맞는지 IR을 읽고, 실행과 최적화는 해당 단계의 다른 자료로 이어가야 한다.[2]

## 거대한 저장소를 읽는 범위 정하기

루트에는 `llvm`, `clang`, `lld`, `libcxx` 등 여러 구성 요소가 나뉘어 있다.
README가 소개하는 전체 범위와 예제 하나에서 확인할 수 있는 범위는 크게 다르다.
간단한 언어 예제를 읽었다고 Clang의 모든 C++ 처리, 대상 CPU별 코드 생성이나 런타임 지원을 검증했다고 할 수 없다.[1][2]

특히 교육용 lexer와 parser는 이해를 돕는 작은 구현이다.
일반 사용자의 임의 소스 입력을 다루는 완성된 언어 도구로 그대로 간주해서는 안 된다.
예제의 타입 선택이나 오류 복구 방식은 설명 범위에 맞춘 설계이며, 새 언어를 만들려면 문법과 타입 규칙, 진단 및 검증 요구를 별도로 정해야 한다.[2]

LLVM의 구성 요소들은 재사용되는 기술 기반이지만, 이름에 최적화가 들어 있다는 이유만으로 어떤 프로그램에서나 더 빠른 결과를 만든다고 보장할 수는 없다.
어떤 언어의 어떤 입력을 어떤 대상과 옵션으로 처리했는지 없이는 성능 비교가 성립하지 않는다.
이 글은 설치와 빌드 안내의 존재를 확인했을 뿐 직접 빌드 조건이나 결과를 시험하지 않았다.[1]

## 정리

LLVM은 언어와 실행 대상 사이의 공통 기반을 제공하는 프로젝트 집합이다.
Chapter3 예제는 언어별 구문 구조를 LLVM IR로 옮기는 경계를 보여 주며, IR 생성·검증·실행·최적화는 서로 구분해서 살펴야 한다.[1][2]
