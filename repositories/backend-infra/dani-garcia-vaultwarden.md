## 한 줄 요약

Vaultwarden은 공식 Bitwarden 클라이언트와 통신할 수 있도록 Bitwarden Client API를 Rust로 구현한 독립적인 서버다.
비밀번호를 입력하는 앱을 새로 만드는 프로젝트라기보다, 기존 클라이언트에 연결할 자체 운영 서버의 선택지를 제공한다.
공식 Bitwarden 서버 자체와는 구분해야 한다.[1]

## 클라이언트를 유지하면서 서버를 선택하는 구조

비밀번호 관리 도구에는 사용자가 보는 앱과 데이터를 보관하고 동기화하는 서버가 있다.
Vaultwarden의 출발점은 이 둘 사이의 API, 즉 요청과 응답의 약속을 호환되게 구현하는 것이다.
사용자는 모바일·데스크톱·브라우저 클라이언트를 이용하면서 서버를 직접 운영하는 구성을 선택할 수 있다.[1]

README는 공식 서비스보다 작은 자체 호스팅 환경을 염두에 둔 대안으로 소개한다.
다만 여기서 자원 절약의 정도를 수치로 확인한 것은 아니다.
“호환 API를 구현한다”는 설명과 “모든 클라이언트 버전과 모든 기능이 언제나 동일하다”는 보장은 다르다.
문서도 구현 범위를 nearly complete라고 표현하므로 필요한 기능과 사용 버전을 별도로 확인해야 한다.[1]

## 금고, 공유, 추가 인증은 서로 다른 층이다

개인 금고는 비밀번호와 관련 항목을 다루는 기본 기능이며, 첨부파일과 Send 같은 자료 전달 기능도 지원 목록에 들어 있다.
여러 사용자가 함께 쓰는 조직 기능에는 컬렉션, 역할, 그룹, 이벤트 기록과 정책이 포함된다.
개인 항목을 폴더로 정리하는 일과 다른 사람에게 공유 권한을 부여하는 일은 같은 작업이 아니다.[1]

다중 인증은 비밀번호 이외의 추가 증거를 요구하는 방식이다.
README에는 인증 앱, 이메일, FIDO2 WebAuthn, YubiKey와 Duo가 안내된다.
지원 목록이 있다고 모든 수단이 별도 준비 없이 활성화되는 것은 아니다.
어떤 로그인 방식과 복구 경로를 선택할지, 그 수단을 잃었을 때 무엇을 할지는 운영 계획에 포함되어야 한다.[1]

대표 구현으로 확인한 `folders.rs`는 서버의 역할을 작은 범위에서 보여 준다.
폴더 목록은 요청한 사용자의 식별자로 조회한다.
개별 폴더 조회·수정·삭제에서는 폴더 식별자와 사용자 식별자를 함께 확인한다.
객체 주소를 안다는 사실만으로 다른 사람의 폴더를 다룰 수 있도록 작성된 코드가 아니라, 소유 관계를 조회 조건에 포함하는 구조다.[2]

또한 변경은 데이터베이스 저장과 클라이언트 알림으로 이어진다.
생성에는 `SyncFolderCreate`, 수정에는 `SyncFolderUpdate`, 삭제에는 `SyncFolderDelete`가 사용된다.
이 작은 경로만 보더라도 서버가 요청을 받아 저장하는 일과 다른 기기에 변경 사실을 알리는 일을 함께 수행함을 알 수 있다.
다만 이 파일 하나를 읽었다고 금고 전체의 암호 설계나 모든 접근 제어를 감사했다고 말할 수는 없다.[2]

## 예시로 따라가는 흐름

이해를 위한 가상 예시이며 직접 실행한 결과가 아니다.
사용자가 자신의 금고에서 학습용 계정들을 묶을 폴더를 만든다고 가정하자.
확인한 서버 코드에서 입력은 `FolderData` 형태의 이름과 선택적 식별자이며, 요청 헤더로부터 현재 사용자와 기기 정보를 받는다.
생성 함수는 현재 사용자 식별자를 넣어 새 폴더를 만들고 데이터베이스에 저장한 다음 생성 알림을 보내고 JSON 응답을 반환한다.[2]

같은 폴더의 이름을 바꾸면 수정 경로는 먼저 폴더 식별자와 현재 사용자 식별자로 대상을 찾는다.
대상이 없거나 다른 사용자에게 속하면 오류를 반환하는 경로가 있다.
대상이 확인되면 이름을 갱신하고 저장한 뒤 수정 알림을 보낸다.
따라서 “어떤 폴더인가”와 “누가 요청했는가”를 함께 검사한 다음 변경하는 순서로 읽을 수 있다.[2]

사람이 확인해야 할 결과도 나눌 수 있다.
요청한 계정에서 폴더가 보이는지, 다른 기기에 변경이 반영되는지, 의도한 개인 폴더인지 공유 컬렉션인지 구분해야 한다.
이 사례는 서버의 폴더 처리 메커니즘을 설명할 뿐 실제 비밀번호 내용이나 암호화된 이름의 형식을 만들어 보여 주지 않는다.
클라이언트 화면과 알림이 실제로 어떻게 표시되는지는 별도의 실행 확인 대상이다.[1][2]

## 자체 호스팅에서 사라지지 않는 책임

Web Vault는 브라우저의 Web Crypto API를 쓰기 위해 HTTPS와 보안 컨텍스트를 요구한다.
README는 역방향 프록시 사용도 권장한다.
역방향 프록시는 외부 요청을 받아 내부 서버로 전달하는 앞단이며, 컨테이너를 켜는 것과 외부에서 안전하게 접근할 주소를 제공하는 것은 별도 작업이다.[1]

문서의 컨테이너 예제는 데이터를 호스트 저장 공간에 연결하고 포트를 `127.0.0.1`에 바인딩한다.
이는 영구 데이터의 위치와 공개 경계를 함께 생각해야 함을 보여 준다.
컨테이너 이미지가 다시 생성되더라도 보관할 데이터가 어디에 남는지, 프록시가 어느 주소로 전달할지 확인해야 한다.
이 글은 예제를 실제 배포했다는 의미로 다루지 않는다.[1]

비밀번호 서버는 데이터를 잃었을 때의 영향이 크다.
README는 파일과 데이터베이스의 정기 백업을 강하게 권장하며 데이터 손실 책임에 관한 고지도 둔다.
백업 파일이 있다는 사실과 복구 가능성을 확인했다는 사실 역시 다르므로, 중요한 데이터를 맡기기 전에는 복구 절차까지 별도로 검토해야 한다.[1]

지원 창구도 분명히 구분된다.
이 프로젝트에서 생긴 문제는 사용하는 클라이언트 종류와 무관하게 Vaultwarden 쪽에 보고하라고 안내한다.
공식 Bitwarden 지원과 동일한 운영·지원 계약이 제공된다고 보아서는 안 된다.
README의 AGPL 라이선스 표시도 코드 수정과 재배포를 검토할 때 함께 읽을 사항이다.[1]

## 정리

Vaultwarden은 기존 Bitwarden 클라이언트에 연결할 대안 서버 구현이다.
API 호환성과 자체 운영의 자유를 제공하지만 HTTPS, 접근 경계, 데이터 보존과 복구는 서버를 운영하는 쪽에서 준비해야 한다.[1][2]
