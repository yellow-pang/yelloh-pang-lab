## 한 줄 요약

Plane은 해야 할 작업과 일정 단위, 프로젝트의 구성 영역과 문서를 함께 관리하는 프로젝트 관리 도구다.
코드 실행이나 배포를 대신하는 시스템이 아니라, 무엇을 진행하고 있으며 어떤 작업이 서로 관련되는지를 정리하는 애플리케이션이다.
Cloud와 자체 호스팅 경로를 구분해 안내한다.[1]

## 작업 목록만으로 표현하기 어려운 관계

작은 개인 프로젝트에서도 “무엇을 할 것인가”와 “언제 집중할 것인가”는 다른 질문이다.
기능별로 묶은 작업이 있고 특정 기간에 마칠 작업이 있으며, 아직 실행할 항목이 아닌 아이디어 문서도 있다.
Plane은 Work Items, Cycles, Modules, Views와 Pages로 이런 관심사를 나누어 표현한다.[1]

Work Item은 실제 추적할 작업 항목이며 설명, 파일과 관련 항목을 연결할 수 있다.
Cycle은 일정한 실행 주기 안의 진행을 보는 단위이고, Module은 복잡한 프로젝트를 더 작은 영역으로 나누는 단위다.
이름이 비슷한 묶음 기능을 모두 폴더처럼 취급하기보다 시간 기준인지 기능 범위 기준인지 먼저 구분하면 화면 구조를 이해하기 쉽다.[1]

## 원본 작업과 바라보는 방식의 분리

Views는 조건으로 관련 작업만 골라 저장하고 공유하는 기능이다.
예를 들어 현재 살펴볼 작업만 보이게 한다고 원본 작업 자체가 다른 프로젝트로 이동하는 것은 아니다.
Pages는 아이디어와 내용을 문서로 정리하고 작업으로 이어갈 수 있는 영역으로 소개된다.
Analytics는 기록된 데이터의 경향과 진행을 보는 기능이다.
보고서가 정확하려면 그 앞의 상태·일정 입력이 의미 있게 유지되어야 한다.[1]

대표 구현인 `cycle.py`는 Cycle이 단순한 제목 목록이 아님을 보여 준다.
이름과 설명, 시작·종료 시각, 소유자, 시간대, 보관 시각과 진행 snapshot 등의 필드를 가진다.
시간대는 날짜를 해석하는 기준이므로, 같은 시각 정보를 여러 환경에서 볼 때 화면 표시와 기간 판단을 구분할 필요가 있다.
이 파일은 데이터 모델이며 실제 UI와 모든 날짜 계산까지 검증한 것은 아니다.[2]

Cycle과 작업은 `CycleIssue`라는 연결 모델로 묶인다.
작업 본문을 Cycle에 복사하는 대신 작업 객체와 주기 객체 사이의 관계를 기록한다.
코드에는 삭제되지 않은 동일한 Cycle·Issue 조합의 중복을 막는 제약이 있다.
다만 이 제약만으로 하나의 작업이 시스템 전체에서 어느 Cycle들에 들어갈 수 있는지 모든 규칙을 단정할 수는 없다.
확인한 것은 이 조합의 데이터 중복 방지다.[2]

또 다른 모델인 `CycleUserProperties`는 주기와 사용자를 연결하고 필터, 화면 배치와 표시 속성을 저장한다.
기본 필터에는 우선순위·상태·담당자 등이 있고 표시 설정에는 그룹, 정렬과 목록 배치 등이 보인다.
작업 데이터, Cycle 소속과 사용자별 화면 구성이 별개라는 점을 코드 수준에서 확인할 수 있다.[2]

## 예시로 따라가는 흐름

이해를 위한 가상 예시이며 직접 실행한 결과가 아니다.
공개 학습용 웹 프로젝트에서 “소개 페이지 정리”와 “오류 메시지 개선”이라는 작업을 준비한다고 가정하자.
Work Item에는 실제 해야 할 내용을 적고, 기능상 다른 영역은 Module로 나눌 수 있다.
이번 주기에 집중할 대상을 정하면 Cycle에 연결하여 기간 내 진행을 바라본다.
문서 아이디어를 저장하는 Page와 수행할 작업은 구분해서 남기는 흐름이다.[1]

데이터 모델의 관점에서는 Cycle에 이름과 기간, 소유자 및 시간대가 있고 각 작업과의 연결이 별도 객체로 기록된다.
사용자가 상태나 담당자 조건으로 표시 대상을 좁히는 설정은 Cycle 자체의 이름이나 작업 본문과 분리되어 저장될 수 있다.
따라서 화면에서 보이지 않는 항목이 실제 삭제된 것인지 필터로 숨겨진 것인지 먼저 구분해야 한다.[2]

확인할 결과는 카드 개수나 그래프 모양만이 아니다.
작업이 올바른 주기에 연결되어 있는지, 시작·종료 시각의 기준이 맞는지, 상태 변경이 실제 작업 완료를 뜻하는지 사람이 살펴야 한다.
이 글은 특정 기간의 완료율이나 burn-down 차트를 실제로 생성하지 않았다.
README가 소개하는 진행 시각화와 코드에서 확인한 저장 필드를 연결해 설명한 것이며, 모든 집계 로직을 읽은 결과는 아니다.[1][2]

## 서비스 이용과 자체 호스팅의 차이

Cloud는 인프라를 직접 준비하지 않고 접근하는 경로이고, 자체 호스팅은 자신의 서버에 설치하고 운영하는 경로다.
README는 Docker와 Kubernetes 배포 문서, 인스턴스 관리자 설정을 안내한다.
프로젝트 안의 작업 권한과 전체 인스턴스 설정을 바꾸는 관리 권한을 동일하게 취급하면 안 된다.[1]

Pages의 AI 기능 등 README가 소개하는 항목은 설치 방식과 제공 범위를 확인할 출발점이지, 모든 배포에서 같은 조건으로 준비된다는 검증 결과가 아니다.
이 글에서는 외부 AI 연결이나 데이터 처리 경로를 직접 조사·실행하지 않았으므로 관련 비용과 전달 범위를 확정하지 않는다.
필요한 경우 실제 사용할 판본의 공식 안내를 더 확인해야 한다.[1]

라이선스는 README에서 AGPL v3로 안내하고, 확인한 모델 파일에도 `AGPL-3.0-only` 식별자가 있다.
수정·재배포나 네트워크 제공을 계획한다면 구체적인 라이선스 조건을 읽어야 한다.
보안 취약점은 공개 이슈에 바로 올리기보다 별도 신고 경로를 이용하라는 안내도 있으므로 일반 기능 제안과 보안 보고를 구분한다.[1][2]

## 정리

Plane은 작업과 기간, 구성 영역과 문서를 연결해 진행 상황을 정리한다.
Cycle 모델은 원본 작업과 소속 관계, 사용자별 표시 설정을 나누며, 화면의 편리함과 데이터·운영 정책의 정확성은 따로 확인해야 한다.[1][2]
