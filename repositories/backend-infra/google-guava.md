## 한 줄 요약

Guava는 Java 프로그램에서 반복해서 필요한 자료구조와 유틸리티를 모은 라이브러리 집합이다.
서버나 애플리케이션을 대신 실행하는 프레임워크가 아니라, 프로그램 안에서 호출해 사용하는 부품이다.
컬렉션, 그래프, 동시성, 입출력, 문자열과 해시 등의 기능을 제공한다.[1]

## 자료를 담는 규칙도 프로그램의 일부다

여러 값을 모아 다른 코드에 넘길 때는 내용뿐 아니라 누가 그것을 바꿀 수 있는지도 중요하다.
설정 목록을 전달했는데 다른 함수가 항목을 추가하면 이후 동작을 이해하기 어려워진다.
Guava가 제공하는 불변 컬렉션은 이런 경계에서 “이 목록의 구성은 바뀌지 않는다”는 의도를 타입과 API로 표현하는 수단이다.[1][2]

이것이 Guava 전체를 불변 목록 라이브러리로만 보아야 한다는 뜻은 아니다.
README는 한 키에 여러 값을 연결하는 multimap, 원소의 개수까지 다루는 multiset, 그래프와 다양한 유틸리티도 소개한다.
기능 범위가 넓으므로 모든 API를 한꺼번에 외우기보다, 현재 코드에서 필요한 자료의 관계와 변경 규칙부터 정하고 해당 기능을 읽는 접근이 적합하다.[1]

## ImmutableList로 보는 생성과 사용의 분리

확인한 `ImmutableList.java`의 설명은 내용이 바뀌지 않는 `List`라고 정리한다. `of`는 주어진 원소로 목록을 만들고, `copyOf`는 다른 컬렉션이나 배열 등에 담긴 원소로 목록을 구성한다.
컬렉션을 원소 하나로 넣을지 그 안의 원소들을 옮길지는 서로 다른 작업이다.
소스 주석은 `of(list)`와 `copyOf(list)`의 반환 구조 차이를 직접 설명한다.[2]

`copyOf`라는 이름만 보고 언제나 새 배열 전체를 복사한다고 단정해서도 안 된다.
문서는 안전할 때 실제 복사를 피할 수 있으며 정확한 조건은 바뀔 수 있다고 밝힌다.
사용자가 의존해야 할 것은 목록의 계약이지 매번 같은 내부 메모리 배치가 아니다.
이것은 라이브러리의 공개 의미와 구현 최적화를 구분하는 구체적인 사례다.[2]

Builder는 여러 단계에 걸쳐 원소를 모은 뒤 최종 목록을 만드는 도구다.
공식 주석의 색상 목록 예제는 기존 원소들을 추가하고 새 색을 넣은 다음 `build()`를 호출한다.
결과의 순서는 추가한 순서를 따른다.
Builder는 다시 사용할 수 있지만 이미 만든 목록을 직접 수정하는 API와는 다르다.[2]

실제 구현에서 `build()`는 copy-on-write 표시를 설정하고, 이후 원소를 추가할 때 필요하면 내부 배열을 복사한다.
copy-on-write는 먼저 공유하되 변경할 때 복사해 기존 결과가 영향받지 않게 하는 방식이다.
이 파일에서 확인한 것은 목록의 저장 구조에 관한 처리다.
목록 안에 담긴 임의 객체의 모든 내부 상태까지 깊은 복사로 고정한다는 의미로 확대해서는 안 된다.[2]

## 예시로 따라가는 흐름

공식 Builder 예제를 문서상에서 따라가면 입력은 이미 있는 색상 원소 모음과 추가할 색상 객체다. `addAll`로 기존 원소들을 넣고 `add`로 하나를 더 넣은 뒤 `build`로 최종 불변 목록을 얻는다.
생성 중에는 원소를 모으는 Builder가 있고 생성 후에는 그 시점의 목록이 있다는 두 단계가 분명하다.
결과 원소의 순서는 Builder에 넣은 순서라는 계약으로 설명된다.[2]

이후 같은 Builder에 다른 원소를 넣고 다시 `build()`할 수도 있다.
주석은 새 목록이 이전 목록의 원소들을 포함한다고 설명하고, 코드의 copy-on-write 처리는 이미 반환된 목록의 구성을 보존하는 구조를 보여 준다.
사람은 원래 결과와 새 결과를 같은 객체의 수정으로 이해하지 말고, 서로 다른 시점에 만든 목록으로 읽어야 한다.
이 글에서는 실제 색상 목록을 출력하거나 객체 동일성을 시험하지 않았다.[2]

입력에 `null`이 들어가는 경우도 확인해야 한다. `add`는 원소 검사 함수를 호출하고 여러 생성 메서드는 null 원소에 대한 예외를 문서화한다.
따라서 기존 가변 목록을 넘길 때 null을 허용하던 코드의 가정을 그대로 유지할 수는 없다.
목록이 안 바뀐다는 장점만 보는 대신 원소 순서, null 허용 여부와 내부 객체의 변경 가능성을 각각 확인하는 것이 이 예제의 핵심이다.[2]

## 의존성과 호환성의 범위

Guava는 JRE용과 Android용 배포를 구분한다.
README는 Java 실행 환경과 Android 호환 라이브러리에서 어느 flavor를 선택할지 설명하며, Gradle 예제에서도 내부 구현으로만 쓰는 경우와 공개 API에 타입을 노출하는 경우를 나눈다.
내 코드 안에서만 쓰는 의존성과 다른 사용자의 코드가 직접 보게 되는 의존성은 영향 범위가 다르다.[1]

`@Beta`가 붙은 API는 변경되거나 제거될 수 있다.
특히 다른 사람이 의존하는 라이브러리를 작성한다면 beta API를 무심코 공개 계약에 포함하지 말라는 경고가 있다.
반대로 beta가 아닌 API의 바이너리 호환성 정책과 예외 가능성도 README에서 따로 설명한다.
최신 소스의 메서드 존재만으로 모든 이전 배포에 같은 기능이 있다고 말할 수는 없다.[1]

또한 직렬화된 객체 형태를 장기 보관 형식으로 가정하지 말라고 경고한다.
직렬화는 객체를 저장하거나 전송할 표현으로 바꾸는 일인데, 향후 버전이 같은 형태를 읽는다는 보장이 없을 수 있다.
악의적인 호출자로부터 보호하는 보안 경계로 클래스를 사용하지 말라는 안내도 있다.
편리한 자료구조와 안전한 외부 입력 검증은 다른 책임이다.[1]

## 정리

Guava는 Java의 반복적인 자료 처리 작업을 공통 API로 제공한다.
ImmutableList 사례는 변경 가능한 생성 과정과 변경되지 않는 결과를 분리하지만, beta 여부와 입력 제약, 저장 형식의 호환성까지 자동으로 해결하지는 않는다.[1][2]
