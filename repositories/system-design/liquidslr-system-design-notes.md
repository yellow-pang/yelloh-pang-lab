## 한 줄 요약

system-design-notes는 『System Design Interview – An Insider’s Guide』를 바탕으로 작성된 장별 학습 노트다.
저장소 작성자의 요약 자료이며 책의 공식 원문이나 실행 가능한 시스템 구현체와는 다르다.
README는 작성 중인 노트임을 명시하고, 기초 확장 개념에서 요청 제한기·채팅·검색·저장소·결제 시스템 등의 설계 주제로 이어지는 목차를 제공한다.[1]

## 완성된 그림보다 설계 순서를 복습하기

시스템 설계 문제를 받았을 때 바로 데이터베이스와 서버 상자를 그리면 요구 사항과 관계없는 복잡한 구조가 될 수 있다.
이 노트의 설계 프레임워크 장은 먼저 문제와 범위를 이해하고, 큰 구조에 합의하고, 중요한 부분을 깊게 검토한 뒤, 남은 한계와 개선점을 정리하는 순서를 설명한다.
프레임워크는 특정 소프트웨어 패키지가 아니라 문제를 풀어가는 사고의 순서라는 뜻이다.[2]

README는 장별 자료와 추가 읽을거리를 따로 제공한다.
예를 들어 요청 제한, 일관된 해싱, 키-값 저장소 같은 항목 아래에 외부 글이나 논문 링크가 연결된다.
요약을 읽고 모르는 부분을 더 찾아가는 경로는 있지만, 외부 링크 전체가 저장소 안에 보관되거나 항상 같은 내용으로 유지되는 것은 아니다.
이 글에서 확인한 것은 대표 장과 공식 저장소에 기록된 연결 관계다.[1]

자료가 책을 바탕으로 한다는 사실도 범위를 규정한다.
각 장의 축약된 설명은 복습용 노트이지 원저자의 모든 논거와 조건을 담은 완전한 대체물이 아니다.
또한 이 저장소의 README가 1차 자료인 것은 노트의 구성과 목적에 대해서다.
그 안에서 소개하는 모든 알고리즘·서비스의 실제 동작까지 저장소 자체가 권위 있는 명세가 되는 것은 아니다.[1]

## 요청 제한기를 통해 보는 구성 방식

대표로 읽은 Rate Limiter 장은 클라이언트나 서비스가 보내는 요청량을 제한하는 구성 요소를 다룬다.
과도한 호출을 줄여 자원 고갈·비용·과부하 문제를 완화하려는 목적을 설명하고, 서버 쪽 API에서 여러 제한 규칙을 지원하며 제한 사실을 사용자에게 알리는 조건을 나열한다.
요청을 차단한다는 결과만 보지 않고 정확도, 지연, 메모리, 분산 환경, 장애 허용 조건을 함께 고려하도록 구성되어 있다.[3]

배치 위치도 비교한다.
클라이언트 자체에 맡기는 제한은 우회될 수 있으므로, 서버나 API 게이트웨이 같은 중간 계층을 검토한다.
API 게이트웨이는 외부 요청이 여러 서비스로 들어가기 전에 공통 처리를 맡는 입구로 이해할 수 있다.
노트는 현재 기술 구성과 요구를 보고 위치·알고리즘을 선택하도록 안내한다.
게이트웨이를 쓴다는 이름만으로 제한 정책과 장애 처리가 결정되는 것은 아니다.[3]

알고리즘 비교에서는 Token Bucket, Leaking Bucket, 고정 구간 카운터와 두 종류의 이동 구간 방식을 설명한다.
토큰 버킷은 일정한 속도로 허가 표식을 채우고 요청이 올 때 하나를 소비하는 방식이다.
버킷 크기와 보충 속도가 입력 조건이 된다.
고정 구간 카운터는 시간 구간별 요청을 세는 간단한 방식이지만 구간 경계에 호출이 몰릴 수 있고, 이동 구간 로그는 시간 기록을 더 세밀하게 보관하는 대신 메모리 비용이 커진다고 비교한다.[3]

## 예시로 따라가는 흐름

개인 공개 API에서 한 클라이언트의 반복 호출을 제한하려는 상황을 생각해 보자.
이해를 위한 가상 예시이며 직접 실행한 결과가 아니다.
입력은 클라이언트 요청과 사전에 정한 제한 규칙이고, 기대하는 결과는 규칙 안의 요청만 처리하거나 초과 사실을 알려 거절하는 것이다.
먼저 프레임워크 장의 순서에 따라 무엇을 기준으로 요청자를 구별할지, 잠깐 몰리는 호출을 허용할지, 여러 서버가 같은 제한을 공유해야 하는지 정해야 한다.[3][2]

그 다음 Rate Limiter 장의 큰 구조를 따라 요청을 중간 계층으로 보낸다고 가정한다.
문서의 대표 흐름은 중간 계층이 Redis의 카운터를 확인하고 기준에 따라 처리 또는 거절하는 것이다.
Redis는 여기서 빠른 카운터 연산을 위한 메모리 기반 자료 저장소로 등장한다.
토큰 버킷을 선택한다면 버킷 용량과 보충 속도를 정하고, 고정 구간 방식을 선택한다면 구간 경계의 몰림을 추가로 검토해야 한다.
이름만 바꾸는 문제가 아니라 허용하려는 요청 패턴이 선택 기준이 된다.[3]

서버가 여러 대이면 두 요청이 동시에 남은 허용량을 읽는 상황도 생길 수 있다.
노트는 이런 경쟁 상태와 동기화 문제를 별도 고급 항목으로 들고, 잠금·Lua 스크립트·공통 저장소 같은 해결 방향을 소개한다.
사람은 카운터를 읽고 갱신하는 동작이 분리되어 초과 허용되지 않는지, 저장소 장애 때 어떻게 응답할지, 거절된 사용자가 무엇을 알 수 있는지를 추가 확인해야 한다.
이 노트에는 완성된 서버 코드와 검증 결과가 없으므로 “분산 환경에서도 정확히 제한했다”는 실행 결론까지 도출할 수는 없다.[3]

마지막 읽기 결과는 API 앞에 제한기를 넣은 그림 하나가 아니라, 식별 기준·허용 패턴·상태 저장 위치·동시 요청과 장애 질문을 적은 설계 설명이다.
프레임워크 장의 Wrap-Up으로 돌아가 무엇을 확인했고 무엇이 남았는지 정리하면, 대표 사례를 다른 장의 설계 문제와 비교할 기준도 생긴다.[2]

## 요약의 장점과 구현 전 남는 일

Rate Limiter 장은 각 방법의 장단점을 짧게 나열하므로 비교 출발점으로 읽기 쉽다.
그러나 메모리 효율적이라거나 정확하다는 표현은 정해진 요청량과 구현 조건에 따라 따져야 한다.
허용량을 얼마나 자주 보충하는지, 자료가 얼마나 오래 남는지, 지리적으로 나뉜 서버 사이에서 언제 상태가 맞춰지는지 같은 선택이 실제 동작을 바꾼다.
노트의 설명을 운영 요구에 맞춘 검증 대신 사용할 수 없다.[3]

설계 프레임워크의 시간 배분과 면접 조언 역시 예시 안내다.
이를 모든 면접이나 실제 프로젝트에 반드시 맞는 절차로 볼 필요는 없다.
중요한 것은 요구 사항을 묻는 단계와 상세 구현으로 들어가는 단계를 구별하고, 선택의 이유를 설명하는 구조다.
작성 중이라는 README의 상태와 함께 보면 완결된 정답보다 사고 경로를 복습하는 문서라는 역할이 명확하다.[1][2]

조회한 README와 루트 구성에서는 노트 전체의 명시적인 재사용 라이선스를 확인하지 못했다.
책을 바탕으로 한 자료이므로 노트의 텍스트, 책에서 유래한 내용, 이미지의 권리도 구별해야 한다.
개인적으로 읽을 수 있다는 사실을 번역본이나 그림 전체의 공개 재배포 허락으로 해석하지 않아야 한다.
이 원고에서는 장의 개념과 읽기 경로를 설명하며 도표를 복제하지 않았다.
