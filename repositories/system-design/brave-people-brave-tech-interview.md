## 한 줄 요약

Brave Tech Interview는 기술 면접 질문과 예비 답안, 참고 링크를 주제별 Markdown 문서에 모은 한국어 학습 자료다.
실행하는 면접 프로그램이나 자동 채점기가 아니며, 질문을 보고 설명을 시도한 뒤 펼쳐진 답안과 비교하는 읽기 구조를 갖는다.
공식 README는 개념을 정확하게 글로 표현하고 표면적으로만 아는지 점검하는 취지를 설명한다.[1]

## 알고 있는 용어를 설명할 수 있는지 묻기

용어의 정의를 읽을 때 이해했다고 느끼는 것과, 질문을 받고 자기 말로 관계를 설명하는 것은 다르다.
예를 들어 쿠키와 세션이라는 이름은 익숙해도 여러 서버로 요청이 나뉠 때 무엇이 달라지는지는 바로 답하기 어려울 수 있다.
이 자료는 짧은 질문을 앞에 놓고 예비 답안과 심화 질문을 이어 배치해 이러한 차이를 드러내는 방식이다.[1][2]

README 목차는 알고리즘, 프로그래밍 언어, 객체지향, 데이터베이스, 네트워크, 운영체제, 보안, 소프트웨어공학으로 나뉜다.
코딩테스트 후기와 별도 읽을거리도 있지만, 각 범주의 본문은 동일한 깊이로 완성된 교과서가 아니다.
실제 네트워크 파일에는 해설이 있는 항목, 외부 링크만 있는 항목, 답안 준비 중이라고 표시된 항목이 함께 있다.[1][2]

질문 출처도 구분해서 읽어야 한다.
README는 면접 후기와 외부 자료를 참고했고 연습 문제나 변형한 문제가 있다고 밝힌다.
태그가 없으면 실제 면접 문제라는 프로젝트의 안내는 소개할 수 있지만, 이 글이 각 문제의 실제 출제 사실을 독립 확인한 것은 아니다.
질문을 학습 범위로 사용하는 것과 특정 채용 과정에서 다시 나올 것이라고 예측하는 것은 다르다.[1]

## 질문, 예비 답안, 후속 질문의 구성

네트워크 문서는 HTTP 메소드부터 프로토콜 버전, 브라우저 요청 흐름, 쿠키·세션, 인증 방식까지 이동한다.
다수 항목에서 HTML의 `details`와 `summary`로 답을 접어 놓는다.
이는 정답을 자동 판정하는 장치가 아니라 답안을 바로 보지 않고 먼저 생각할 수 있게 하는 문서 표현이다.
텍스트로 내려받으면 질문과 답이 연속해서 나타나므로 읽는 화면에 따라 경험이 다를 수 있다.[2]

세션 관련 항목은 로그인 정보를 유지해야 하는 이유를 소개한 뒤 서버가 여러 대일 때의 심화 질문으로 이어진다.
세션은 여러 요청 사이에서 사용자의 상태를 이어 다루기 위한 정보로 이해할 수 있다.
이어 스티키 세션, 세션 복제, 별도 저장소라는 접근을 비교한다.
스티키 세션은 같은 사용자의 요청을 특정 서버로 이어 보내는 방식이며, 자료는 쏠림과 서버 장애의 문제도 함께 적는다.[2]

데이터베이스 문서에서는 키의 종류를 같은 표를 이용해 비교한다.
키는 행을 구별하거나 다른 표와의 관계를 만드는 기준이다.
고객 ID 하나로 구분되는 상황과 ID에 이름까지 붙이는 상황을 대조하여 유일성과 최소성을 설명한다.
별개의 이름을 암기하는 대신, 무엇을 빼도 여전히 행을 구분할 수 있는지 질문으로 바꿔 읽을 수 있다.
이 예시는 본문이 정의뿐 아니라 비교 대상을 제공하는 경우다.[3]

## 예시로 따라가는 흐름

네트워크 파일의 실제 심화 질문인 “로드 밸런싱을 사용하고 있는 웹서버의 경우에는 세션을 어떻게 관리할까요?”를 대표 읽기 사례로 삼아 보자.
입력은 설치 명령이 아니라 질문 문장과, 요청이 여러 서버에 배분되는 상황이다.
로드 밸런싱은 요청을 여러 처리 서버로 나누는 것을 뜻한다.
이 사례는 문서 읽기 순서를 설명한 것이며 서버를 구성해 시험한 기록이 아니다.[2]

먼저 앞의 쿠키·세션 항목에서 어떤 상태를 이어 기억하려는지 찾는다.
이어 답안을 펼쳐 스티키 세션에서는 사용자를 특정 서버에 연결하고, 클러스터링에서는 세션 자료를 복제하며, 별도 저장소 방식에서는 서버 밖에 공통 상태를 둔다는 비교를 읽는다.
이때 각 방식의 이름만 적는 대신 상태가 어디에 있는지와 다음 요청이 그것을 어떻게 찾는지를 간단한 문장으로 정리하면 답안 사이의 차이가 드러난다.[2]

그 다음 자료에 적힌 단점을 질문으로 되돌린다.
특정 서버로 요청을 모으면 무엇이 쏠리는지, 복제한다면 어떤 갱신 비용이 생기는지, 별도 저장소를 둔다면 그 저장소의 장애 조건은 어디에서 확인해야 하는지를 구분한다.
마지막 항목까지 이 저장소가 완전히 답해 주는 것은 아니므로, 답안에서 찾은 설명과 추가 확인이 필요한 조건을 나누어 남기는 것이 결과물이다.
심화 항목에는 참고 링크도 있으나 이 글에서는 링크 대상의 최신 동작을 검증하지 않았다.[2]

이렇게 읽으면 최종 결과는 특정 방식을 무조건 선택하는 답이 아니라, 상태의 위치와 요청 경로, 장애 시 영향을 구별한 설명이 된다.
바로 아래의 세션 인증과 토큰 인증 비교로 넘어갈 때도 같은 질문을 유지할 수 있다.
다만 자료의 문장을 그대로 복사하는 것과 조건을 이해한 것은 다르므로 설명 속 절대 표현은 별도 검토 대상으로 남겨야 한다.[2]

## 예비 답안을 기술 표준처럼 쓰지 않기

이 저장소는 스스로 답안을 예비 답안이라고 표기한다.
네트워크 문서의 HTTP 특성이나 인증 방식 설명에는 여러 구현 조건을 압축한 문장이 있고, 데이터베이스 문서에는 특정 제품의 트랜잭션 동작을 참고한 항목이 있다.
이를 모든 프로토콜 버전과 데이터베이스에 공통인 규칙으로 옮기면 안 된다.
자료의 대상과 조건이 명확하지 않으면 표준이나 해당 제품 문서를 추가로 확인할 필요가 있다.[2][3]

구체적으로 데이터베이스 파일에는 슈퍼키를 속성 또는 속성 집합으로 설명하는 앞부분과, 뒤에서 두 개 이상의 속성 집합으로 적는 부분이 함께 있다.
이런 차이는 같은 파일 내부에서도 답안 표현을 대조해야 한다는 신호다.
또한 트랜잭션 예제의 DDL 되돌리기 설명은 MySQL 문서를 참조하므로 이를 다른 데이터베이스까지 일반화한 문장으로 받아들이지 않는 것이 안전하다.[3]

문서가 공개되어 있다는 사실도 모든 문장·이미지를 제한 없이 재배포할 수 있다는 허락과 같지 않다.
확인한 루트 구성과 README에서는 명시적인 재사용 라이선스 안내를 찾지 못했다.
개인적으로 읽고 질문을 정리하는 것과 답안을 통째로 출판하는 행위는 구분하고, 인용할 때는 출처와 필요한 이용 조건을 따로 확인해야 한다.

## 정리

Brave Tech Interview는 질문을 통해 개념 설명의 빈틈을 찾게 하는 자료 모음이다.
예비 답안과 후속 질문을 읽는 출발점으로 활용하되, 정답의 완결성·최신성·실제 출제 사실까지 보증하는 자료로 받아들이지 않아야 한다.
