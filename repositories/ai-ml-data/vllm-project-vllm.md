## 한 줄 요약

vLLM은 이미 학습된 언어 모델을 실행하고 여러 요청에 응답하도록 만드는 추론·서빙 엔진이다.
새로운 모델 가중치나 완성된 채팅 제품을 뜻하지 않으며, 모델을 효율적으로 돌리는 실행 계층에 해당한다.[1]

## 한 요청의 답변보다 여러 요청의 처리

언어 모델은 문장을 한 번에 완성하기보다 작은 텍스트 단위인 토큰을 이어 생성한다.
요청마다 입력 길이와 출력 길이가 다르므로, 먼저 들어온 긴 요청이 자원을 오래 점유할 수 있다.
vLLM은 지속적 배치 처리와 KV 캐시 관리, 프리픽스 캐싱 등을 주요 기능으로 소개한다.
KV 캐시는 이전 토큰 처리 중 계산한 정보를 다음 계산에 재사용하기 위한 메모리다.[1]

README의 PagedAttention은 이 메모리 관리를 위한 핵심 기법으로 제시된다.
다만 기능 목록에 있다는 사실만으로 모든 모델·장치·양자화 조합이 같은 성능을 내는 것은 아니다.
OpenAI 호환 API 서버와 스트리밍도 제공하므로 실행 엔진을 기존 클라이언트에 연결할 수 있다.[1]

## 스케줄러가 이번 단계의 일을 고르는 방법

루트는 Python 패키지 `vllm/`, 저수준 구현 `csrc/`, 예제·문서·벤치마크로 나뉜다.
대표 코드 `vllm/v1/core/sched/scheduler.py`의 `schedule`은 요청별 계산 진행량과 토큰 예산을 관리한다.
코드의 설명은 prefill과 decode를 별도 단계 종류로만 나누기보다, 계산한 토큰 수가 필요한 토큰 수를 따라가도록 배정한다고 밝힌다.
prefill은 입력을 처음 처리하는 일, decode는 뒤에 올 출력 토큰을 생성하는 일이다.[2]

실제 루프는 실행 중인 요청부터 살피고 토큰 예산·입력 예산·모델 길이 한도 안에서 새 계산량을 제한한다.
긴 입력이 다른 요청의 예산을 독점하지 않도록 임계값을 적용하는 조건도 있다.
중지 상태에서는 예산을 0으로 만들며, 결과에는 새 요청·재개 요청·계속 실행할 요청 등이 구분된다.
이 파일은 처리량이 모델 연산만이 아니라 요청을 배치하는 정책에도 달렸음을 보여준다.[2]

## 가상 시나리오: 길이가 다른 요약 요청

공개 문서 세 개를 각기 다른 길이로 요약하는 API를 가정한다.
먼저 지원 모델과 장치 구성을 정하고 모델을 로드한 뒤 API 요청을 엔진으로 전달한다.
엔진은 각 요청의 남은 계산량을 관리하고 이번 단계에 처리할 토큰을 예산 내에서 배정한다.[1][2]

출력이 끝난 요청과 아직 진행 중인 요청의 상태는 달라지며, 클라이언트는 스트리밍으로 결과를 받을 수 있다.
여기서 관찰할 항목은 전체 처리량뿐 아니라 첫 응답까지의 지연과 긴 요청이 다른 요청에 미치는 영향이다.
이는 측정 설계의 예시이고 이 조사에서 서버를 띄우거나 성능을 재현한 것은 아니다.[1][2]

## 엔진 선택과 운영 검증은 별개

README는 여러 GPU·CPU와 하드웨어 플러그인을 안내하지만, 원하는 모델이 해당 백엔드에서 지원되는지 별도로 확인해야 한다.
양자화는 메모리를 줄이는 표현 방식이며, 사용 가능 형식과 커널은 장치·모델 조합에 영향을 받는다.[1]
API 호환이라는 표현도 인증·접근 제한·배포 운영이 자동 해결된다는 뜻은 아니다.
처리량 수치를 적용하려면 입력·출력 길이, 동시 요청 수, 정밀도와 하드웨어를 함께 고정한 평가가 필요하다.
저장소 코드는 Apache-2.0이다. 엔진의 라이선스와 별도로 불러올 모델 가중치의 사용·배포 조건을 확인해야 한다.[3]
