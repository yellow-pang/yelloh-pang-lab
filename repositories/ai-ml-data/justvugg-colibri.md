## 한 줄 요약

Colibrì는 이미 학습된 대형 MoE 모델을 로컬에서 계산하는 추론 엔진이자 시스템 연구 프로젝트다.
MoE는 여러 전문가 모듈 가운데 입력에 필요한 일부를 선택하는 모델 구조다.
전문가가 사람을 뜻하는 것은 아니며 각각 학습된 가중치 묶음이다.
이 프로젝트는 필요한 전문가를 RAM·VRAM·저장장치 사이에 배치하고 가져오는 문제를 추론 설계의 중심에 놓는다.[1]

## 모델이 메모리에 전부 들어가야 하는가

일반적으로 큰 모델을 실행하려면 큰 메모리가 필요하다고 생각하기 쉽다.
Colibrì의 접근은 한 순간에 선택되는 가중치와 모델 전체의 가중치를 구분하는 것이다.
README의 설명에서는 계속 필요한 공통 부분은 메모리에 유지하고 선택된 전문가를 디스크에서 읽으며, 자주 쓰는 부분은 캐시에 남긴다.
빠른 메모리가 부족하면 속도가 달라질 수 있지만 모델의 정밀도나 전문가 선택 의미를 몰래 바꾸지 않는다는 설계 원칙을 제시한다.[1]

이는 저장 공간의 필요가 없어졌다는 뜻이 아니다.
큰 모델의 가중치는 여전히 디스크 어딘가에 있어야 한다.
엔진 실행 파일이 작고 C 코드의 의존성이 적다는 소개를 모델 다운로드나 저장 공간까지 작다는 주장으로 확대하면 안 된다.
실제 실행 가능성과 실용적인 응답 속도도 나눠야 한다.
README는 속도에 대한 서비스 수준 보장을 하지 않는다고 명시한다.[1]

## 캐시와 미리 읽기가 맡는 일

캐시는 다시 쓸 가능성이 있는 데이터를 빠른 곳에 보관하는 공간이다.
README는 계층별 LRU, 자주 쓰는 전문가를 고정하는 저장 영역과 다음 계층의 미리 읽기를 소개한다.
LRU는 최근 사용하지 않은 항목부터 내보내는 정책이다.
매번 같은 전문가를 디스크에서 새로 가져오는 비용을 줄이려는 구성이다.[1]

그러나 과거 사용 패턴이 앞으로의 모든 요청을 대표하지는 않는다.
README는 반복 작업에서 유리한 패턴이 특정 프롬프트에 과하게 맞춰질 수 있으며 미리 읽기가 일부 장치에서는 손해가 될 수 있다고 설명한다.
CPU와 GPU를 함께 쓰거나 여러 저장장치를 조합하는 방법도 대역폭·상주 비율·작업에 따라 달라진다.
개별 계산이 빨라졌다는 수치보다 처음부터 끝까지의 응답 시간과 품질을 함께 측정하라는 원칙이 제시된다.[1]

모델별 C 엔진은 공통 전면 명령인 `coli chat`, `coli serve`, `coli web`으로 연결된다.
대화, API 제공과 웹 대시보드는 추론을 사용하고 관찰하는 표면이다.
Brio는 자유로운 문장 생성 대신 허용된 답 후보의 확률과 불확실성을 보여주는 별도 모드로 소개된다.
확률 표시는 모델 내부의 선택 신호이지 현실에서 그 답이 참일 확률을 자동 보증하는 것은 아니다.[1]

엔진과 실행 도구의 준비 조건도 구별해야 한다.
README는 C 엔진 자체와 달리 `coli` 런처와 API gateway가 Python 스크립트이며 Python 3 설치가 필요하다고 안내한다.
엔진의 무의존성 설명을 배포 묶음 전체에 적용하면 실제 실행 준비를 빠뜨릴 수 있다.[1]

## 예시로 따라가는 흐름

대표 파일 `c/expert_store.h`의 전문가 저장소 계약으로 한 번의 가중치 사용을 따라갈 수 있다.
입력은 계층 번호와 전문가 번호로 이루어진 `ColiExpertKey`다.
호출자는 `lookup`으로 필요한 전문가를 요청하고 성공하면 gate·down·up 텐서 뷰와 lease를 받는다.
텐서는 계산에 쓰는 다차원 수치 배열이고 lease는 사용하는 동안 데이터가 유효함을 관리하는 임시 사용권이라고 이해할 수 있다.[2]

계산이 끝나면 같은 저장소와 같은 뷰에 `release`를 정확히 한 번 호출해야 한다.
실패한 조회에서는 뷰가 비워지므로 이를 사용하거나 정상 조회처럼 해제해서는 안 된다.
미리 읽기는 제안일 뿐 lease를 잡지 않으며 사용 중인 항목을 내보내면 안 된다는 규칙도 있다.
이 설명은 코드에 적힌 계약을 읽은 것이며 실제 모델을 실행한 결과가 아니다.
사람이 구현을 확인할 때는 캐시 적중 수뿐 아니라 사용 중인 가중치의 수명과 해제 시점이 맞는지 봐야 한다.
데이터 이동을 줄였더라도 아직 쓰는 메모리를 재사용하면 속도 이전에 계산 정확성이 깨질 수 있기 때문이다.[2]

## 작은 인터페이스에 드러난 검증 기준

전문가 저장소의 통계에는 요청, 적중, 실패, 미리 읽기, 읽은 바이트와 상주·용량 바이트가 있다.
이는 ‘빨라졌다’는 결과를 어느 데이터 이동 변화로 설명할지 보여주는 항목이다.
다만 이 헤더는 인터페이스와 사용 계약을 정의하므로 각 저장소 구현이 어떤 장치에서 어떤 정책을 쓰는지까지 모두 확인한 것은 아니다.[2]

스레드 안전성도 구현마다 다르다고 명시한다.
같은 저장소에서 조회·해제·미리 읽기를 동시에 호출해도 된다고 가정해서는 안 되고 하나의 뷰를 여러 스레드에서 동시에 사용하지 않도록 한다.
따라서 여러 GPU나 병렬 처리 지원이라는 큰 소개와 개별 데이터 구조의 동시 사용 조건을 섞으면 안 된다.[2]

README는 실험 보고에 하드웨어, 모델·형식, 정확한 명령, 입력, 캐시 상태와 품질 검사를 함께 남기도록 한다.
이미 메모리에 올라온 상태의 결과와 처음 읽는 상태의 결과를 같은 조건으로 비교하기 어렵기 때문이다.
공개된 빠른 예시를 자신의 기기에서도 재현할 수 있다고 보장하지 않으며, 모델별 가중치 조건은 엔진 코드의 라이선스와 별도로 살펴야 한다.[1]

## 정리

Colibrì는 대형 모델의 가중치를 계층적으로 이동시키며 계산하는 엔진이다.
핵심은 모델을 바꾸지 않고 필요한 데이터를 제때 준비하는 것이며, 자원 요구와 속도는 모델·하드웨어·작업별 측정이 필요하다.
