## 입력 장치 설정을 로컬에서 다루는 앱

OpenLogi는 지원되는 마우스·키보드·웹캠의 설정을 로컬에서 관리하는 도구다.
README는 Rust와 GPUI 기반 앱, GUI와 CLI, 사람이 읽을 수 있는 TOML 설정 파일을 소개한다.
HID++는 지원 입력 장치의 기능을 제어하는 통신 방식이고, UVC는 웹캠 제어에 사용하는 표준 계열이다.
일반적인 키 매핑만 하는 도구와 달리 장치가 제공하는 DPI·휠 동작·영상 설정까지 연결하지만, 모든 장치가 모든 기능을 제공한다고 말하지 않는다.[1]

마우스의 뒤로 버튼을 편집기에서는 실행 취소로 쓰고 싶거나, 수신기 연결과 유선 연결에서 다른 감도를 쓰고 싶은 상황을 생각할 수 있다.
이런 요구는 버튼 하나에 단축키 하나를 지정하는 것보다 복잡하다.
장치의 정체, 연결 경로, 현재 앱, 누르는 방식이 함께 영향을 준다.
OpenLogi의 공식 설정 예제는 이 층을 별도 항목으로 나누어 표현한다.[2]

## 장치, 연결, 동작의 세 구획

`config.example.toml`에는 앱 전체 설정과 장치별 설정이 분리되어 있다.
앱 전체에는 로그인 시 실행, 업데이트 확인, 마우스 이벤트 포착 등의 선택지가 있고, 장치에는 DPI와 프리셋, 스크롤·휠 관련 값이 들어간다.
예제의 첫 문장은 필요한 절만 복사하라고 안내한다.
모든 값을 그대로 적용하는 권장 운영 설정이 아니라, 표현 가능한 구성의 예라고 읽어야 한다.[2]

버튼 바인딩은 물리 입력을 어떤 동작으로 바꿀지 정하는 연결이다.
예제는 Back과 Forward에 브라우저 이동을, MiddleClick에는 누르는 동안만 유지되는 단축키를 지정한다.
짧게 누르기와 길게 누르기를 분리한 항목도 있으며, 주석은 기준 시간 이전에 놓는 경우와 그 시간에 도달한 경우의 동작을 구별한다.
한 번 눌렀다는 사실만이 아니라 눌림의 지속과 해제까지 모델링하는 구성이다.[2]

앱별 바인딩은 기본값 위에 필요한 차이만 올리는 방식으로 드러난다.
예제에는 특정 편집기의 Back 버튼을 Undo로 바꾸는 항목이 있다.
README는 앱별 프로필의 플랫폼 조건을 따로 적으며, Linux에서는 X11 또는 XWayland 범위로 한정한다.
같은 설정 문법이 보인다고 모든 데스크톱 환경에서 자동 전환까지 동일하게 동작한다고 가정하면 안 된다.[1][2]

장치의 고유 정체와 연결 경로도 분리한다.
예제 주석은 schema 5 이후 장치를 `unit:` 또는 `serial:` 같은 식별자로 묶어, 수신기와 케이블 사이에서 설정이 두 벌로 갈라지지 않도록 한다고 설명한다.
연결별 `capabilities`는 해당 경로에서 노출되는 기능을, `overrides`는 그 연결에서만 달리 적용할 설정을 담는다.
같은 하드웨어라도 전송 방식에 따라 기능이 달라질 수 있다는 사실을 설정 구조에 반영한 것이다.[2]

## 예시로 따라가는 흐름

공식 TOML 예제의 마우스 바인딩을 읽는 것으로 흐름을 따라가 보자.
기본 설정에서는 Back 버튼이 `BrowserBack`으로 연결된다.
같은 장치 아래 특정 앱의 `per_app_bindings`에는 Back을 `Undo`로 덮어쓰는 항목이 있다.
입력은 같은 물리 버튼이지만, 어떤 프로필이 선택되느냐에 따라 요청할 동작이 달라지는 구성이다.
이 설명은 설정 파일의 의미를 읽은 것이며 실제 마우스를 연결해 시험한 결과가 아니다.[2]

그다음 연결 차이를 보자.
예제의 장치 수준 DPI와 별도 연결의 `overrides` DPI는 각각 기본값과 예외값 역할을 한다.
주석에 따르면 연결에 별도 값이 없으면 장치 수준 설정을 따른다.
따라서 사람이 확인할 것은 '현재 숫자가 얼마인가'뿐 아니라 지금 어떤 연결 경로로 장치를 인식하고 있는지다.
수신기를 바꾸거나 케이블을 꽂았을 때 다른 기능 집합이 관찰된다면, 연결별 능력 기록을 먼저 구분해 읽어야 한다.[2]

예상되는 결과는 선택된 프로필과 연결 설정에 따른 입력 동작 요청이다.
하지만 파일에 설정이 있다는 것만으로 운영체제가 해당 동작을 허용했는지, 장치가 기능을 노출했는지까지 증명되지 않는다.
실사용 검토에서는 원래 버튼 동작이 중복으로 남는지, 앱 전환 시 적용 대상이 맞는지, 지원되지 않는 제스처를 지정하지 않았는지를 구별해야 한다.
README가 기본 클릭과 휠 컨트롤에 새 제스처를 임의로 할당할 수 없다고 한 제한도 이 지점에서 중요하다.[1]

## 하드웨어를 제어한다는 말의 조건

README 첫머리는 아직 안정 상태가 아니며 기능과 설정이 바뀔 수 있다고 경고한다.
같은 문서가 macOS·Linux·Windows를 안내하더라도 지원 성숙도와 세부 기능은 구분되어 있다.
Windows의 실기기 검증 설명은 프로젝트가 보고한 범위이지 모든 장치에 대한 이번 조사자의 시험 결과가 아니다.
macOS 최소 버전과 Linux 사전 빌드의 GLIBC 조건도 배포판 선택 전에 확인할 사항이다.[1]

입력 장치 접근은 기존 설정 앱과 충돌할 수 있다.
README는 기존 Options+와 함께 장치 접근을 시도하면 수신기 소유권이 충돌하므로 먼저 종료하라고 안내한다.
Linux의 장치 접근 규칙이나 백그라운드 에이전트 역시 실제 입력을 읽고 생성하는 범위와 연결된다.
여기서 agent는 AI가 아니라 장치 입출력을 맡는 상주 프로세스를 가리킨다.
Windows 안내는 GUI와 agent 실행 파일을 함께 두어야 한다고 명시한다.[1]

코드는 Apache-2.0 또는 MIT 중 선택할 수 있는 이중 라이선스로 소개되지만, 브랜드 자산과 포함된 일부 코드는 별도 조건이다.
특히 로고·아이콘을 코드와 같은 조건으로 재사용할 수 있다고 해석해서는 안 된다.
또한 제조사의 공식 제휴 제품이 아니라는 안내가 있으므로, 이 저장소의 지원 설명과 제조사의 보증 범위도 구별한다.[1]

## 정리

OpenLogi는 하드웨어 기능과 운영체제 입력 동작을 로컬 설정으로 연결한다.
대표 예제의 핵심은 장치 정체·연결·앱별 프로필을 나누는 것이며, 실제 지원 여부는 장치와 플랫폼 조건을 함께 보아야 한다.[1][2]
