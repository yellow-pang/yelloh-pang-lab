## 다른 Apple 기기를 Mac의 추가 화면으로 쓰기

OpenDisplay는 iPhone, iPad 또는 다른 Mac을 송신 Mac의 보조 화면으로 활용하는 앱이다.
현재 화면을 그대로 복제하는 미러링뿐 아니라 창을 옮겨 놓을 수 있는 확장 화면을 제공한다고 설명한다.
송신 앱과 수신 앱을 각각 사용하며, 화면 영상은 케이블이나 로컬 네트워크의 직접 연결로 전달된다.
기기에 HDMI 입력 기능을 새로 만드는 방식은 아니다.[1]

책상에 남는 iPad가 있어도 Mac이 이를 일반 모니터로 자동 인식하는 것은 아니다.
OpenDisplay는 이 간격을 가상 화면과 영상 전송으로 연결한다.
Mac에는 새 모니터가 연결된 것처럼 작업 공간을 만들고, 그 공간의 내용을 압축해 수신 기기의 앱에서 보여준다.
입력도 지원되는 경우 반대 방향으로 전달하므로 단순한 동영상 전송과 화면 제어가 함께 있는 구조다.[1]

중앙 서버를 거치지 않는다는 점은 전송 경로에 관한 설명이다.
이것만으로 네트워크 암호화나 접속자 인증까지 제공한다고 해석해서는 안 된다.
공식 프로토콜 문서가 명시한 보안 제약은 사용 조건의 핵심이므로 기능 소개와 함께 읽어야 한다.[2]

## 가상 화면에서 압축 영상까지

송신 측 흐름은 `CGVirtualDisplay`로 가상 화면을 만들고, ScreenCaptureKit으로 캡처하고, VideoToolbox로 H.264 영상을 만드는 순서다.
가상 화면은 물리적인 패널 없이 운영체제에 등록되는 표시 공간이고, H.264는 영상 데이터를 줄여 전달하는 압축 형식이다.
수신 앱은 받은 영상을 화면에 표시한다.
이 구조에서는 화면 생성, 캡처, 압축, 전송, 표시가 각각 다른 실패 지점이 될 수 있다.[1]

대표 구현인 `Mac/VirtualDisplay.swift`는 비공개 CoreGraphics API를 감싸고 화면 크기와 HiDPI 모드를 설정한다.
HiDPI는 논리적인 화면 크기에 더 많은 픽셀을 대응시켜 글자 등을 선명하게 표시하는 방식이다.
코드에는 화면 식별자와 저장된 배치를 다루는 처리도 있어, 확장 화면을 만드는 일이 영상 크기만 정하는 문제가 아님을 보여준다.[3]

운영체제가 표시 모드를 다시 바꾸는 상황에 대응하여 설정을 재확인하는 코드도 있다.
원하는 HiDPI 모드를 적용하지 못했을 때 반복 요청을 늦추는 처리와, 방향·크기 변경 시 기존 가상 모니터의 정체성을 유지하려는 `resize`가 확인된다.
이는 실제 기기의 성능이나 성공률을 측정한 자료가 아니라, 가상 화면 상태를 유지하기 위해 고려한 조건을 드러내는 구현이다.[3]

## 수신기가 기다리고 송신기가 연결한다

프로토콜은 수신기가 연결을 기다리고 송신기가 접속하도록 정한다.
로컬 네트워크에서는 Bonjour로 기기를 발견하고, iPhone·iPad USB 연결에서는 macOS의 usbmuxd를 통해 수신 포트에 접근한다.
usbmuxd는 USB로 연결된 Apple 기기의 통신을 중계하는 운영체제 구성 요소다.
영상 장치로 직접 연결하는 것이 아니라 같은 바이트 흐름을 다른 전송 경로로 전달하는 셈이다.[2]

연결 뒤 수신기는 화면 크기·배율·프로토콜 버전 등을 담은 `hello`를 먼저 보낸다.
송신기는 이 정보를 바탕으로 표시 공간과 영상 구성을 준비하고 호환성을 응답한다.
실제 영상 크기는 단순히 기기 패널 숫자만으로 결정되는 것이 아니라 수신 능력과 협의되는 조건을 함께 고려한다.
화면 크기, 작업 공간 크기, 전송 영상 크기를 같은 값으로 생각하면 표시 배율과 성능 설명을 오해하기 쉽다.[1][2]

터치와 스크롤은 JSON 제어 메시지로 송신 측에 돌아간다.
JSON은 이름과 값을 가진 구조화된 데이터 형식이다.
프로토콜은 터치 좌표와 스크롤 이동량의 단위도 구분한다.
즉 기기 화면의 손가락 위치를 Mac 화면에 어떻게 대응시킬지까지 두 앱이 약속해야 한다.
영상을 받는 것만 구현했다고 입력 호환성까지 확보되는 것은 아니다.[2]

## 예시로 따라가는 흐름

공식 README의 iPhone 보조 화면 사례와 프로토콜의 세션 순서를 함께 읽어보자.
입력은 송신 Mac의 확장 화면과 수신 기기가 알리는 표시 정보다.
수신 앱이 먼저 연결을 기다리고 Mac이 데이터 통신이 가능한 케이블 또는 신뢰하는 로컬 네트워크로 접속한다.
이 설명은 공식 문서의 흐름을 따라간 것으로, 이번 조사에서 기기를 연결하거나 화면을 전송한 결과가 아니다.[1][2]

연결이 열리면 수신기가 `hello`를 보내고 송신기가 버전·표시 조건을 확인한다.
호환되는 경우 화면을 캡처해 압축 영상으로 전달하고, 수신 측이 이를 표시한다.
사용자가 Mac의 창을 확장 영역으로 옮겼다면 그 영역의 픽셀이 수신 앱에 보이는 구성이 된다.
반면 연결은 되었지만 검은 화면이 나온다면 발견·접속 문제와 캡처 권한 문제를 구분해서 확인해야 한다.
README는 화면 기록 권한이 없을 때 검은 화면이 나타날 수 있다고 안내한다.[1][2]

화면이 보이는데 탭이 반응하지 않는 경우는 또 다른 경로다.
터치 메시지가 Mac 입력으로 연결되려면 손쉬운 사용 권한이 필요하다고 설명한다.
화면을 세로로 돌렸을 때는 새 크기의 `hello`가 전송되고 표시 구성이 조정된다.
프로토콜 설명과 별개로 구현에는 기존 가상 모니터를 유지한 채 크기를 바꾸는 경로도 있으므로, 이를 매번 새 네트워크 연결을 만드는 동작이라고 설명하면 부정확하다.[1][2][3]

사람이 확인할 결과는 화면이 보이는지 하나뿐이 아니다.
창 배치, 글자 크기, 회전 후 비율, 입력 위치, 연결 경로를 각각 점검해야 한다.
수신 Mac의 키보드·마우스 전달은 README에서 후속 과제로 구분하므로, iOS 터치 지원을 모든 수신 환경의 입력 지원으로 확대해서도 안 된다.[1]

## 직접 연결이 보안 보장을 뜻하지는 않는다

프로토콜 버전 3에는 TLS 암호화와 인증이 없으며 신뢰할 수 있는 로컬 네트워크와 직접 케이블을 전제로 한다.
TLS는 통신 내용을 암호화하고 상대를 확인하는 데 쓰이는 표준 보호 계층이다.
화면이 중앙 서버로 전송되지 않는다는 장점과 로컬 통신의 보호 수준은 서로 다른 질문이다.
공용 네트워크나 인터넷에 노출할 원격 접속 서비스처럼 취급하면 안 된다.[2]

송신 앱은 macOS 14 이상, Mac 수신 앱은 macOS 12 이상, iOS·iPadOS 수신 앱은 15 이상으로 안내된다.
WiFi 발견에는 양쪽의 로컬 네트워크 권한이 필요하며 충전 전용 케이블은 USB 통신에 사용할 수 없다.
현재 자료에는 오디오 전달도 범위 밖으로 설명되어 있다.
연결 방식·권한·기능의 조합이 맞는지 먼저 구분해야 한다.[1]

가상 화면 생성은 비공개 `CGVirtualDisplay` API에 의존하므로 OS 업데이트의 영향을 받을 수 있다고 README가 경고한다.
해상도와 작업 공간을 키우면 캡처·압축·네트워크 부담이 달라진다는 설명도 있지만, 문서의 사례 수치를 모든 기기의 보장 성능으로 일반화할 수는 없다.
현재 라이선스는 GPL-3.0이며 예전 MIT 릴리스와 조건이 다름도 구분해야 한다.[1][3]

3. [가상 화면 구현](https://github.com/peetzweg/opendisplay/blob/main/Mac/VirtualDisplay.swift)

## 정리

OpenDisplay는 가상 모니터를 영상으로 전달하고 지원 입력을 되돌려 받아 보조 기기를 확장 화면으로 쓰는 도구다.
화면의 직접 전송과 통신 보안, 영상 표시와 입력 지원은 각각 구분해서 판단해야 한다.
