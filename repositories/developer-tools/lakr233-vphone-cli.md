## 가상 iPhone의 준비와 수명을 관리하는 연구 도구

vphone-cli는 물리 Apple Silicon Mac에서 가상 iPhone을 만들고 실행하는 프로젝트다.
README는 Apple의 Virtualization.framework와 PCC 연구용 VM 기반을 사용한다고 설명한다.
일반적인 모바일 앱 빌드 도구나 모든 실제 iPhone을 원격 제어하는 서비스가 아니라, 호스트 안에 만든 가상 기기의 펌웨어 준비·복원·실행을 다루는 도구다.[1]

가상 머신은 별도의 운영체제가 돌아가는 가상 컴퓨터다.
이를 사용하려면 화면 창만 여는 것으로 끝나지 않고 부팅에 필요한 자료를 준비하고 저장 형식을 맞추며, 호스트와 게스트 사이의 제어 통로도 정해야 한다.
vphone-cli의 2.x는 이 작업을 자체 포함 `VPhone.bundle`로 묶고, Launchpad가 번들 설치와 VM 생성을 안내하는 구조다.
게스트는 가상 머신 안에서 실행되는 시스템, 호스트는 그 바깥의 Mac을 뜻한다.[1]

## 준비, 실행, 게스트 제어의 세 역할

README의 구성 설명에서 `vphone-cli`는 펌웨어와 복원 및 수명 주기를, `vphone-vm`은 실제 게스트 실행과 macOS 창을 맡는다.
게스트 안의 `vphoned`는 창의 제어 기능과 선택적 HTTP·WebSocket API를 제공한다.
따라서 CLI 프로세스, VM 프로세스, 게스트 데몬을 하나의 프로그램처럼 취급하면 어느 쪽에 오류나 권한 문제가 있는지 구별하기 어렵다.[1]

API 문서는 통신 경계를 더 자세히 보여 준다. `vphoned`는 게스트의 VSOCK 통로에서 요청을 받고, VM 프로세스가 선택적으로 호스트 TCP 주소에 그 통로를 노출한다.
VSOCK은 호스트와 가상 머신 사이에 사용하는 소켓 통신 방식이다.
호스트 리스너는 명시적으로 켠 경우에만 생기며, 인증된 연결에 대해 바이트를 양방향 전달한다고 설명한다.
HTTP 요청 내용을 다른 의미로 번역하는 일반 웹 백엔드라기보다 연결을 중계하는 구조다.[2]

HTTP는 요청과 응답을 주고받는 방식이고 WebSocket은 연결을 유지하며 메시지를 주고받는 방식이다.
같은 API 계열이라도 연결 수명과 인증 적용 단위가 다르므로 문서는 이를 구분한다.
이 글은 자신의 연구용 VM 상태 확인과 화면 자료 취득의 구조만 다루며, 게스트의 민감한 저장소를 추출하거나 다른 기기에 접근하는 절차를 안내하지 않는다.[2]

## 화면 캡처를 둘러싼 데이터 흐름

공식 API 문서는 `screen.screenshot`이 게스트 내부의 화면 캡처를 사용해 JPEG를 base64 형태로 반환한다고 설명한다.
base64는 이미지 같은 바이트를 텍스트 형태로 전달하는 표현이다.
응답에는 매체 형식과 가로·세로 정보가 포함되며, 호스트의 저장·복사 메뉴는 그 게스트 이미지를 해석한다.
호스트 창에서 그린 노치나 외곽 장식은 게스트 캡처에 포함되지 않는다고 명시한다.[2]

이 차이는 시각 자료를 비교할 때 중요하다.
Mac의 전체 창을 캡처한 이미지와 게스트 API로 얻은 이미지는 같은 순간을 보여도 범위가 다를 수 있다.
실제 앱 화면을 검토하려는지, 가상 기기를 감싼 호스트 UI까지 기록하려는지에 따라 의미가 달라진다.
문서의 특정 VM 해상도 표시는 그 문서가 설명하는 환경의 값이며 모든 펌웨어 조합의 고정 규격으로 일반화하지 않는다.[2]

## 예시로 따라가는 흐름

이해를 위한 가상 예시이며 직접 실행한 결과가 아니다.
사용자가 이미 준비한 자신의 연구용 VM에서 앱 화면을 기록하고 싶다고 하자.
먼저 VM 창이 담당하는 제어와 게스트에서 제공하는 캡처 기능을 구분한다.
로컬 자동화를 사용한다면 호스트 API가 켜졌는지와 해당 실행의 인증 정보가 있어야 하며, 단지 VM 창이 떠 있다는 이유로 외부 API도 항상 열려 있다고 가정하지 않는다.[1][2]

문서상의 처리 흐름은 인증을 통과한 호스트 연결이 게스트 통로로 전달되고, 게스트 캡처 기능이 JPEG 자료와 크기 정보를 응답하는 것이다.
호스트 쪽 클라이언트는 그 자료를 이미지로 해석해 저장하거나 복사할 수 있다.
이 단계에서 결과는 화면의 표현이며, 앱 내부 상태 전체의 백업이나 실행 중 프로세스의 완전한 복제는 아니다.
README가 따로 제시하는 VM 내보내기·가져오기 기능과도 목적을 나누어야 한다.[1][2]

사람이 검토할 항목은 캡처한 이미지가 의도한 VM과 앱에서 왔는지, 호스트의 장식이 빠진 것이 오류가 아닌지, 화면에 개인 자료나 비밀값이 있는지다.
API 응답을 얻는 데 성공했다고 앱의 기능 동작까지 성공한 것으로 볼 수는 없다.
이 사례는 화면을 가져오는 제어 경로를 설명할 뿐 실제 응답이나 스크린샷을 만들어 낸 기록이 아니다.

## 연구용 호스트와 강한 API 권한

지원 조건은 물리 Apple Silicon Mac과 macOS 15 이상이며, 호환되는 iPhone·cloudOS 펌웨어 조합이 필요하다.
로컬 펌웨어가 있어도 복원 티켓을 위한 네트워크와 상당한 디스크 공간이 필요하다고 안내한다. 2.x는 `schemaVersion=2` 형식의 VM만 시작하고 이전 VM은 다시 만들어야 한다.
기존 폴더가 있다고 그대로 새 실행기에 연결되는 호환성을 기대해서는 안 된다.[1]

추천 호스트 설정은 SIP를 유지하면서 일부 디버깅 제한을 완화하고 권한 있는 helper를 사용한다.
이는 보통의 데스크톱 앱을 설치하는 것과 다른 보안 전제다.
여기서는 보호 설정을 바꾸는 명령이나 펌웨어 수정 절차를 실행·재현하지 않았다.
해당 Mac의 중요 자료와 연구 환경을 어떻게 분리할지는 설치 편의와 별개로 검토할 문제다.[1]

API 문서는 `vphoned`가 root로 실행되고 게스트 파일 읽기·쓰기 등 강한 기능을 가진다고 명시한다.
호스트 토큰 검사와 게스트의 브라우저 요청 검사라는 두 경계가 있지만, 토큰이 있다는 이유로 무심코 외부 네트워크에 공개할 기능은 아니다.
문서도 loopback 이외의 주소로 수신할 때 경고를 출력한다고 설명한다.
접근 토큰과 민감한 API 응답은 공개 예제나 로그에 남기지 않는 방향으로 다루어야 한다.[2]

## 정리

vphone-cli는 가상 기기의 준비·실행과 게스트 제어를 분리한 연구용 도구다.
화면/API 편의 기능보다 먼저 호스트 보안 조건, 펌웨어 호환성, 강한 제어 권한의 노출 범위를 확인해야 한다.[1][2]
