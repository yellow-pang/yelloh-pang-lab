## 작은 입력창에 모은 macOS 작업

Tinycast는 단축키로 검색창을 열고 앱 실행, 파일 열기, 클립보드 재사용 같은 작업을 고르는 macOS 런처다.
런처는 실행할 대상을 찾아 주는 입구라는 뜻이며, Tinycast 자체가 문서 편집기나 운영체제를 대신하는 것은 아니다.
README는 SwiftUI와 AppKit으로 만든 네이티브 앱으로 소개하고, 파일 검색에는 자체 색인이 아니라 Spotlight를 이용한다고 설명한다.[1]

앱을 여는 일, 조금 전 복사한 문장을 다시 붙이는 일, 특정 폴더의 문서를 찾는 일은 목적이 다르지만 모두 찾기와 선택을 반복한다.
Tinycast는 이 작업들을 명령 팔레트라는 공통 입력창에 모은다.
사용자는 전역 단축키를 지정하고 검색어를 입력한 다음 결과를 선택한다. `Tab`으로 앱과 클립보드를 전환하는 사용법도 README에 제시되어 있다.
여러 기능을 모두 켜야 하는 도구라기보다, 필요한 항목을 설정하고 접근 경로를 통일하는 앱으로 이해할 수 있다.[1]

검색창에 나타나는 결과와 그 뒤에서 실행되는 동작은 구별할 필요가 있다.
파일을 찾는 것, 셸 명령을 실행하는 것, 다른 앱에 텍스트를 붙여 넣는 것은 서로 다른 권한과 부작용을 가진다.
하나의 화면으로 묶였다고 해서 모든 기능의 안전 조건까지 같아지지는 않는다.

## 기존 시스템 기능을 연결하는 방식

파일 검색 서비스의 `search`는 사용자의 문자열뿐 아니라 검색 정책과 파일 유형 필터를 받는다.
정책에서 실제 검색할 디렉터리 범위를 정한 뒤, Spotlight 검색식을 만들고 결과 경로를 가져온다.
조회한 구현에는 `MDQuerySetSearchScope`로 범위를 지정하는 호출과 후보 개수 제한이 있다.
전체 디스크를 새로 순회해 독자적인 색인을 만드는 구현으로 설명해서는 안 되는 이유가 여기에 있다.[2]

가져온 경로를 그대로 화면에 내보내는 것도 아니다.
제외된 경로는 먼저 거르고, 이미 본 경로는 집합으로 중복을 제거한다.
이어 파일 정보를 확인하면서 숨김 파일과 앱 유형을 제외하고 결과 객체로 바꾼 뒤 순위를 매긴다.
다만 순위 산정의 세부 규칙은 다른 `FileSearchQuery` 구현에 위임된다.
이번에 읽은 서비스 파일만으로 어떤 검색어가 항상 몇 번째에 나온다고 예측하지는 않았다.[2]

검색어가 비어 있을 때는 별도 흐름을 탄다. `recent`는 사용·변경 관련 날짜 기준의 질의를 모으고 경로별 날짜를 합친 뒤 최신 순으로 제한된 결과를 반환한다.
빈 화면을 곧바로 오류로 보는 대신 최근 항목의 출발점으로 취급하는 설계다.
검색어가 있는 경우와 없는 경우를 구분하므로, 화면에 나타난 파일을 해석할 때에도 왜 선택되었는지 먼저 따져 볼 수 있다.[2]

다른 기능들은 이 검색 서비스와 구분해서 읽어야 한다.
README의 Snippets는 재사용할 텍스트 템플릿과 선택적인 키워드 확장을, Quicklinks는 입력값·클립보드·날짜 등을 URL이나 명령에 넣는 기능을 소개한다.
AI 채팅과 선택 텍스트 처리도 있지만 기본적으로 꺼져 있고, 사용자의 키나 설치된 AI 계정을 이용하는 별도 기능이다.
파일 검색 구현을 확인했다고 AI 기능의 데이터 흐름까지 검증한 것은 아니다.[1]

## 예시로 따라가는 흐름

다음은 이해를 위한 가상 예시이며 직접 실행한 결과가 아니다.
개인 Mac에서 사용자가 검색 대상으로 고른 문서 폴더에 있는 여행 일정 파일을 찾는 상황을 생각해 보자.
사용자는 Tinycast의 단축키로 팔레트를 열고 파일 검색에서 이름 일부를 입력한다.
이때 입력 문자는 파일 내용 전체에 대한 질문이나 AI 요청이 아니라, 검색 정책과 함께 파일 검색 서비스로 전달될 문자열이다.[1][2]

서비스는 허용된 검색 범위를 모으고 이름 검색식과 유형 조건을 적용한다.
Spotlight가 반환한 후보 중 제외 경로와 중복을 제거하고, 접근할 수 있는 파일의 메타데이터를 확인한 다음 순위를 정한다.
따라서 결과가 없다면 파일이 실제로 없는 경우 외에도 선택 폴더, 제외 정책, Spotlight가 제공하는 후보를 구분해 살펴봐야 한다.
이 코드를 읽는 것만으로 사용자의 Mac에서 색인 상태가 정상인지 알 수는 없다.[2]

사용자가 원하는 경로의 파일을 골라 여는 것이 이 상황의 결과다.
같은 이름의 복사본이 있을 수 있으므로 제목뿐 아니라 위치를 확인해야 한다.
검색어를 지우면 서비스는 최근 항목 흐름으로 바뀌므로, 그때 나타나는 목록을 앞선 검색 결과와 동일한 조건으로 해석하지 않아야 한다.
README의 파일 열기 기능과 구현의 후보 선별 과정을 이렇게 연결하면, 검색창 하나가 실제로 무엇을 대신하고 무엇은 사용자가 판단해야 하는지 드러난다.[1][2]

## 편리함과 권한은 별도로 살피기

README의 지원 조건은 macOS 26 이상이며 Apple Silicon과 Intel용 배포 경로가 구분된다.
자체 서명 앱이라는 안내도 있으므로 배포 파일의 출처와 시스템 보안 경고를 이해한 뒤 판단해야 한다.
이 글은 보안 설정을 바꾸거나 검역 속성을 제거하는 절차를 실행하도록 권하는 설치 지침이 아니다.[1]

다른 앱으로 붙여 넣기와 텍스트 확장을 할 때에는 손쉬운 사용 권한이 필요하다.
Snippets는 기본 비활성이며, README는 키 입력 매칭이 로컬에서 이루어지고 저장·전송하지 않는다고 설명한다.
이것은 해당 기능에 대한 작성자의 설명이다.
AI나 확장 기능까지 동일한 네트워크 경계를 가진다는 뜻으로 넓히면 안 된다.
클립보드에는 민감한 텍스트가 들어갈 수 있으므로 기록을 남길 범위와 사용하는 기능을 따로 확인해야 한다.[1]

README에 적힌 메모리 사용량과 의존성 관련 소개는 직접 측정한 결과가 아니다.
또한 Raycast 확장 실행을 지원한다는 소개만으로 모든 확장의 호환성을 보장할 수 없다.
코드 수정·재배포에 관심이 있다면 AGPL-3.0 조건을 따로 읽어야 한다.
사용 가능 기능, 실행 환경, 배포 의무는 서로 다른 판단 항목이다.[1]

## 정리

Tinycast는 macOS의 여러 작업을 한 팔레트로 연결하지만, 대표 파일 검색은 Spotlight의 후보를 정해진 범위와 정책으로 가공하는 방식이다.
검색의 편의성과 텍스트 주입·명령 실행·AI 연결의 권한은 따로 판단해야 한다.[1][2]
