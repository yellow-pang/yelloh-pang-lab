## 한 줄 요약

`n`은 여러 Node.js 버전을 내려받아 보관하고 사용할 버전을 선택하는 도구다.
Node.js는 JavaScript 프로그램을 브라우저 밖에서 실행하는 환경이다.
이 도구는 프로젝트 의존성을 설치하는 npm을 대신하는 패키지 관리자가 아니라, 그 프로그램들을 실행할 Node.js 자체의 버전을 관리한다.[1]

## 설치했는데 다른 버전이 나오는 상황

새 프로젝트에 맞는 Node.js를 설치했는데 터미널에서는 예전 버전이 보일 수 있다.
컴퓨터에 서로 다른 설치 경로가 있고, 명령을 찾는 순서에서 예전 경로가 앞서기 때문이다. `n`의 README와 별도 이전 안내는 이를 installed와 active의 차이로 보여준다.
원하는 버전을 내려받은 일과 현재 `node` 명령이 그 파일을 실행하는 일은 같지 않다.[1][2]

`n`은 미리 빌드된 Node.js 패키지를 받아 하나의 설치 경로에 복사한다.
기본 경로는 `/usr/local`이며 새 활성 버전을 설치하면 이전 활성 버전을 덮어쓴다.
다운로드는 별도의 캐시에 남아 다시 전환할 때 재사용된다.
각 프로젝트 폴더에 Node.js 전체를 자동으로 따로 넣는 방식이라기보다, 보관된 버전과 현재 선택한 설치본을 구분하는 모델이다.[1]

## 캐시·활성 설치·일회성 실행

캐시는 여러 버전의 보관함이고 활성 설치 경로는 보통의 `node` 명령이 찾아야 하는 자리다. `N_PREFIX`는 활성 설치 위치를 바꾸며 `N_CACHE_PREFIX`는 다운로드 보관 위치를 바꾼다.
후자를 바꾼다고 활성 Node.js가 그 위치로 옮겨지는 것은 아니다.
경로 옵션을 읽을 때 무엇의 위치를 바꾸는지 구분하면 불필요한 재설치를 피할 수 있다.[1]

대표 코드인 `bin/n`의 `activate` 함수는 캐시에서 선택한 버전을 찾아 `lib`, `bin`, `include`, `share` 등으로 파일을 복사한다. `lib`를 `bin`보다 먼저 복사하는 이유를 심볼릭 링크의 대상이 존재하도록 하기 위해서라고 주석에 설명한다. `node` 실행 파일은 기존 파일을 지우고 복사하며, npm과 corepack은 보존 옵션을 확인한다.
단순히 버전 문자열을 설정하는 기능이 아니라 실제 설치 파일을 바꾸는 작업이다.[3]

활성 설치를 바꾸지 않고 저장된 버전을 쓰는 방법도 있다.
README는 `n which`로 캐시의 실행 파일 경로를 찾고, `n run`으로 그 Node.js를 실행하며, `n exec`로 PATH를 바꾼 상태에서 명령을 실행하는 방식을 구분한다.
PATH는 실행 파일을 찾을 디렉터리 순서다.
기본적으로 이 명령들은 버전이 이미 캐시에 있어야 하며 필요 시 다운로드하는 별도 옵션이 안내되어 있다.[1]

## 버전 번호 대신 프로젝트 조건 읽기

`lts`는 최신 장기 지원 릴리스, `latest`와 `current`는 최신 공식 릴리스를 가리키는 표기다.
이 이름이 가리키는 실제 번호는 시간이 지나면 달라진다.
재현 가능한 실험을 설명하려면 이름과 실제 선택된 번호를 혼동하지 않아야 한다.
README의 오래된 출력 예시는 동작 형태를 보여주는 자료이지 이번 시점의 최신 버전 안내가 아니다.[1]

`auto`는 현재 또는 상위 폴더의 `.n-node-version`, `.node-version`, `.nvmrc`를 순서대로 찾고 없으면 `engine` 방식으로 넘어간다. `engine`은 `package.json`의 `engines` 조건을 읽으며 `jq` 또는 `node`가 필요하고 복잡한 범위 해석에는 `npx semver`를 사용한다.
프로젝트의 요구 버전을 읽는 기능과 폴더를 이동할 때마다 자동 전환되는 셸 기능은 구분해서 이해해야 한다.[1]

## 예시로 따라가는 흐름

공식 `changing-node-location.md`는 Homebrew로 설치한 Node.js에서 `n` 관리 설치로 옮기는 상황을 보여준다.
아래는 그 문서의 판단 순서를 설명한 것이며 직접 실행한 결과가 아니다.
출발점은 `/opt/homebrew` 아래에 기존 설치와 전역 npm 패키지가 있는 환경이다.
먼저 기존 전역 패키지 목록과 `node`, `npm`의 실제 경로를 기록한다.
이동 대상이 Node.js 한 파일만이 아니기 때문이다.[2]

그 상태에서 `n`으로 `/usr/local`에 버전을 설치해도 기존 경로가 PATH에서 앞서면 활성 버전은 계속 Homebrew 쪽이다.
문서는 두 경로가 동시에 보이는 예시와 `n doctor`의 우선순위 경고를 제시한다. `activate` 구현도 설치한 실행 파일과 `command -v node`로 찾은 파일이 다르면 각각의 버전과 위치를 출력한다.
설치 성공 메시지만 보지 말고 어떤 경로가 실제 선택되는지 확인하게 만드는 부분이다.[3][2]

문서의 이전 절차는 기존 설치를 정리하고 새 경로의 실행 파일을 확인한 뒤 필요한 전역 패키지를 다시 설치하는 방향이다.
다른 대안으로 새 `bin` 경로를 PATH 앞쪽에 두는 방법도 소개한다.
여기서 특정 삭제 명령을 독자의 환경에 바로 적용하라고 권하는 것은 아니다.
자신의 기존 설치를 확인한 후 어느 설치를 유지할지 결정해야 하며, 결과는 `node`뿐 아니라 `npm`, `npx`의 경로까지 함께 맞는지 확인해야 한다.[2]

## 플랫폼과 권한이 정하는 경계

`n`은 Bash 스크립트지만 사용자의 대화형 셸을 Bash로 바꿀 필요는 없다고 설명한다.
macOS·Linux·WSL을 포함한 유닉스 계열을 지원하며, 네이티브 Windows 셸이나 Git for Windows Bash, Cygwin은 지원하지 않는다고 명시한다.
Windows에서 Bash라는 이름이 보인다는 이유만으로 모두 같은 환경이라고 판단할 수 없다.[1]

기본 `/usr/local`에 쓰기 권한이 없을 수 있다.
README는 소유권 조정, 쓰기 가능한 사용자 경로 지정, 관리자 권한 실행을 선택지로 소개하지만, 이 글은 시스템 디렉터리의 소유권을 일괄 변경하라는 설치 안내가 아니다.
기존 패키지 관리 방식과 충돌하지 않는 경로를 먼저 정해야 한다.
npm 보존 설정과 CPU 아키텍처도 전환 결과에 영향을 주므로 단지 Node.js 번호만 확인해서는 부족할 수 있다.[1][3]

## 정리

`n`은 다운로드 보관함에서 Node.js를 골라 공통 설치 경로에 활성화하거나 일회성으로 실행하도록 돕는다.
버전 전환을 이해하는 핵심은 캐시, 설치 경로, PATH의 세 가지 구분이다.
지원 플랫폼과 쓰기 권한을 확인해야 전환 결과도 올바르게 판단할 수 있다.
