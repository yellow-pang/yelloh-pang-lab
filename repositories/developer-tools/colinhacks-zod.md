## 외부 값을 실제로 검사하는 TypeScript 라이브러리

Zod는 데이터의 형태와 조건을 스키마로 정의하고, 실제 입력이 그 조건을 만족하는지 검사하는 라이브러리다.
스키마는 '이 값은 문자열이고 저 값은 숫자여야 한다'처럼 자료가 지킬 규칙을 나타낸다.
README는 검사에 통과한 결과를 강한 타입 정보와 함께 돌려준다고 설명한다.
데이터베이스나 API 서버를 대신하는 도구가 아니라, 프로그램이 외부 값을 받아들이는 경계에 놓는 검사 도구다.[1]

TypeScript 코드에 숫자 타입을 적는 것과 네트워크에서 받은 값이 정말 숫자인지 확인하는 것은 다르다.
예를 들어 경험치가 숫자여야 하는데 문자열 `"100"`이 들어오면, 이름과 겉모양만으로 올바른 데이터라고 판단할 수 없다.
Zod의 README는 `username` 문자열과 `xp` 숫자로 이루어진 Player 스키마를 만들고, 정상 입력과 잘못된 타입의 입력을 비교한다.
규칙을 한 번 정의해 실행 시 검사와 개발 중 타입 추론에 연결하는 구조다.[1]

## 스키마에서 결과 타입까지

`z.object`는 여러 필드를 가진 객체의 규칙을 묶는다.
그 안의 `z.string()`과 `z.number()`는 각각 허용할 값의 종류를 정한다. `z.infer`는 이 스키마에서 TypeScript 타입을 꺼내 쓰는 도구다.
같은 자료 구조를 검사 코드와 별도 타입 선언으로 반복해서 적는 대신, 스키마를 기준으로 타입을 얻을 수 있다.
다만 타입 추론이 있다는 사실이 실제 값을 검사하는 호출을 생략해도 된다는 뜻은 아니다.[1]

`parse`와 `safeParse`는 실패를 다루는 방식이 다르다. `parse`는 검증 실패 시 `ZodError`를 던지고, `safeParse`는 성공 여부와 결과 또는 오류를 담은 객체를 반환한다.
이때 오류에는 어느 필드에서 어떤 종류의 문제가 생겼는지 나타내는 경로와 정보가 들어간다.
화면에 오류를 보여 주거나 잘못된 요청을 거절하려면, 성공한 데이터와 실패 정보를 분리해 처리해야 한다.[1]

변환이 있으면 입력과 출력의 타입도 달라질 수 있다.
README의 문자열 길이 변환은 문자열을 받아 숫자를 내보내며, `z.input`과 `z.output`으로 두 타입을 따로 확인한다.
따라서 통과한 값을 쓸 때는 원래 입력 객체를 계속 사용하는지, 파서가 반환한 결과를 사용하는지 주의해야 한다.
검증과 변환을 통과한 결과가 프로그램 안으로 들어가야 의도한 경계가 만들어진다.[1]

대표 테스트에서는 객체의 추가 필드 정책도 확인할 수 있다. `points`만 정의한 기본 객체 스키마에 `unknown`이라는 항목을 넣으면, 테스트는 결과에서 그 항목이 제거되기를 기대한다.
passthrough 설정은 추가 항목을 보존하고, strict 설정은 같은 입력을 실패로 처리하도록 테스트한다. '정의하지 않은 값은 항상 오류'라는 예상은 기본 객체 동작과 다르므로 명시적으로 구별해야 한다.[2]

## 예시로 따라가는 흐름

공식 README의 Player 예제에서는 입력이 `{ username: "billie", xp: 100 }`이고, 두 필드의 타입이 스키마와 맞으므로 그 형태의 결과를 반환하는 것으로 설명된다.
반대로 `{ username: 42, xp: "100" }`은 이름 자리에 숫자, 경험치 자리에 문자열이 들어온 경우다. `safeParse`를 사용하면 실패 분기로 들어가 필드별 오류를 읽는 흐름을 구성할 수 있다.
여기서 문자열 숫자를 저절로 숫자로 고친다고 설명하지 않는 것이 중요하다.[1]

이 예제를 테스트의 추가 필드 사례와 연결하면 처리 결과를 더 정확히 이해할 수 있다.
필수 필드가 모두 맞더라도 스키마에 없는 항목을 어떻게 다룰지는 별도의 정책이다.
테스트 파일의 `strip by default`는 필요한 `points`만 남은 결과를 기대하고, `strict`는 추가 필드를 가진 입력의 성공 여부가 false이기를 기대한다.
이들은 저장소에 적힌 테스트 기대값이며 이번 조사에서 실행해 얻은 로그가 아니다.[2]

사람이 결정할 부분은 잘못된 타입을 거절할지 변환 규칙을 따로 둘지, 추가 필드를 제거할지 거부할지, 오류 중 어떤 내용을 사용자에게 보여 줄지다.
스키마가 통과했다고 해서 경험치의 의미나 사용 권한까지 검증된 것은 아니다.
예컨대 특정 사용자가 그 값을 바꿀 수 있는지는 인증·권한 규칙의 문제이며, 여기서 본 문자열·숫자 검사는 그 판단을 대신하지 않는다.
데이터 모양의 정확성과 행위의 허용 여부를 분리하는 사례다.

## 비동기 검사와 컴파일의 주의점

README는 비동기 refinement나 transform을 쓰는 스키마에서는 `parseAsync` 또는 `safeParseAsync`를 사용해야 한다고 안내한다.
refinement는 기본 타입 외의 추가 조건을 검사하는 함수다.
외부 조회처럼 즉시 끝나지 않는 조건을 동기 파서로 처리할 수 있다고 가정하면 안 된다.
입력·출력 타입뿐 아니라 검사가 완료되는 시점도 호출 방식에 영향을 준다.[1]

조회한 README에는 `z.compile`을 통한 사전 컴파일 안내도 있다.
유효한 입력은 빠른 경로로 처리하고 실패 입력은 일반 파서로 돌아가 동일한 오류 설명을 유지한다는 구조다.
그러나 `new Function`을 사용하며 비동기 조건이나 일부 구성은 지원하지 않는다고 적는다.
실패 입력에서는 refinement와 transform이 두 번 실행될 수 있다는 경고도 있으므로, 해당 함수에 외부 상태를 바꾸는 동작을 넣었을 때의 영향까지 생각해야 한다.[1]

컴파일 성능 수치는 프로젝트가 특정 벤치마크에서 보고한 결과이지 모든 스키마에 적용되는 보장이 아니다.
README 스스로 단순 문자열 검사는 얻는 이점이 없을 수 있다고 구별한다.
이 글에서는 성능 수치를 재현하지 않았고, 기본 검사와 오류·추가 필드 정책에 초점을 맞췄다.
최적화보다 먼저 실제 입력에 필요한 규칙과 실패 처리가 빠짐없는지 확인해야 한다.[1]

## 정리

Zod는 스키마를 실제 입력 검사와 타입 추론의 공통 기준으로 삼는다.
반환 결과, 추가 필드 정책, 오류 흐름을 구분해야 검사 경계를 올바르게 만들 수 있으며 업무 의미나 접근 권한은 별도로 검증해야 한다.[1][2]
