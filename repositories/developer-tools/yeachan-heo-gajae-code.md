## 한 줄 요약

Gajae-Code(`gjc`)는 저장소나 worktree에서 실행하는 외부 코딩 에이전트 harness다.
Harness는 모델 호출, 도구 사용, 작업 단계와 세션을 둘러싸서 실제 일을 진행하게 하는 실행 틀을 뜻한다.
새 언어 모델 자체도 아니고 Claude Code에 설치하는 확장도 아니다.
README는 계획을 먼저 검토하고 실행 뒤 근거를 남기는 절차를 중심에 둔다.[1]

## 수정하기 전에 요구사항을 드러내기

'이 화면을 편하게 바꿔 달라'는 요청만으로 코드를 고치면 편하다는 말의 의미가 빠질 수 있다.
먼저 사용자에게 필요한 조건을 묻고, 계획을 비판적으로 검토한 다음 파일을 바꾸는 단계가 필요한 이유다.
GJC는 `deep-interview → ralplan → ultragoal` 흐름을 제시한다.
모호한 요구를 구체화하고, 구현 계획을 만들고 검토하며, 실행·수정·검증·증거를 목표 단위로 관리하도록 각 역할을 나눈다.[1]

여기에 연구가 계획의 근거가 되어야 할 때 선택적으로 사용하는 `autoresearch`가 있다.
README는 이 네 가지 워크플로 Skill과 executor·architect·planner·critic 역할을 설명한다.
Skill은 반복 작업의 지침을 담은 문서이며, 역할 에이전트는 그 지침 안에서 구현이나 읽기 전용 검토 같은 책임을 맡는 구성이다.
단계를 나눈다는 설명을 모든 결과가 자동으로 정확하다는 보증으로 읽지는 않아야 한다.[1]

## 구독 연결과 질문 응답의 두 축

README는 기존 코딩 구독을 로그인으로 연결하는 경로와 API 키 제공자·로컬 런타임·게이트웨이 구성을 함께 소개한다.
따라서 '별도 API 과금 없이 사용'이라는 소개 문구는 지원되는 구독 연결의 맥락에서 읽어야 한다.
모든 제공자와 모든 실행 방식이 같은 비용 조건을 갖는다고 단정할 수 없다.
지원 목록은 연결 경로 안내이고 실제 계정의 권한·한도는 따로 확인할 부분이다.[1]

에이전트가 질문할 때 터미널을 지켜보지 않아도 응답할 수 있도록 Telegram·Discord·Slack 전달과 일반 `action_needed`/`reply` 프로토콜도 안내한다.
이를 통해 사람의 결정을 전달받는 통로를 작업 실행과 분리한다.
메시지 앱 연결은 편리한 입력 경로일 뿐 승인 자체를 생략하는 기능으로 설명되어 있지 않다.
어떤 세션의 어떤 질문에 답하는지를 유지하는 것이 중요하다.[1]

## Skill 파일의 소유권을 구분하는 방식

`docs/skills.md`는 Skill의 형식이 Claude Code·Codex와 같아도 다른 도구의 설정 폴더를 그대로 실행하지 않는다고 명시한다.
직접 읽는 표준 위치는 프로젝트의 `.gjc/skills`와 사용자 범위의 `~/.gjc/agent/skills` 등 GJC 경로다.
다른 도구의 Skill은 가져오기 후보로 발견할 수 있지만, 실제 사용하려면 명시적으로 복사해 GJC의 실행 위치에 놓아야 한다.[2]

프로젝트 범위와 사용자 범위의 신뢰 설정도 나뉘며, 같은 이름이 겹치면 우선순위와 진단을 제공한다.
특히 네 가지 내장 워크플로 Skill은 파일 시스템의 같은 이름 Skill로 대체할 수 없다.
이는 모든 텍스트가 동등하게 실행 정책을 바꾸는 구조가 아니라, 내장 절차와 사용자가 추가하는 지침 사이에 경계를 두는 설계다.[2]

외부 제어용 `gjc-sdk-operate` Skill은 허용된 SDK 작업만 호출하고 정확한 세션 식별자를 선택하도록 요구한다.
세션 생성·분기·재개·종료 등의 생명주기 작업 전에는 대상과 입력을 보여주고 일회성 승인을 받아야 한다.
이 Skill은 그 승인 절차가 보안 경계 자체는 아니며 실제 세션 권한은 SDK 코어가 유지한다고도 설명한다.
절차 문서와 기술적 접근 통제를 구분한 대목이다.[3]

## 예시로 따라가는 흐름

이해를 위한 가상 예시이며 직접 실행한 결과가 아니다.
개인 메모 앱의 검색 동작을 바꾸려는 요청을 생각해 보자.
입력은 '검색 개선'에서 시작하더라도 `deep-interview` 단계에서는 무엇을 검색하고 어떤 결과를 원하는지 구체화해야 한다.
그다음 `ralplan`에서 계획을 만들고 비판하며, 승인된 계획을 `ultragoal`의 목표 실행으로 넘기는 것이 README의 안내 흐름이다.
이 사례에서 특정 검색 알고리즘이 자동 선택되었다고 가정하지 않는다.[1]

실행 중 결정을 묻는 질문이 다른 인터페이스로 전달되더라도 응답은 원래 작업의 문맥에 연결되어야 한다.
외부 제어 Skill은 워크플로 승인에 일시적인 알림 ID가 아니라 지속되는 gate ID와 `expectedSessionId`를 사용하도록 한다.
사람은 질문 문장뿐 아니라 대상 세션과 승인할 동작을 확인해야 한다.
승인 입력이 바뀌면 이전 승인을 재사용하지 않는다는 규칙도 있다.[3]

긴 작업에서 대기 시간이 끝났다고 작업이 취소된 것은 아니다.
SDK Skill은 전송 후 결과가 불확실하면 무턱대고 프롬프트를 다시 보내지 말고 저장한 작업 참조로 상태를 맞춰 확인하라고 설명한다.
같은 요청을 재전송해 중복 변경을 만드는 일을 피하려는 구분이다.
최종 확인 대상은 자연어 완료 보고만이 아니라 목표별 실행·검증 증거와 실제 변경이다.
다만 이 글은 그 절차를 읽은 것이며 가상의 코드나 테스트 성공 출력을 만들지 않는다.[1][3]

## 실험 단계와 자동화의 책임

README는 프로젝트를 실험적인 베타 단계로 표시하고 중요한 작업에 의존하기 전에 출력을 검증하라고 경고한다.
컨텍스트 절약을 위해 구조 요약, 큰 출력의 별도 아티팩트 저장, 압축을 설명하지만 실제 절약량을 이 조사에서 측정하지 않았다.
요약된 출력이 원래 자료 전체와 같지 않다는 점도 검토자가 인식해야 한다.[1]

외부 SDK 제어는 터미널 화면을 긁거나 인증 파일을 직접 읽는 방법보다 브로커가 중개하는 JSON 표면을 사용하도록 안내한다. `session.delete`, 임의 작업 이름, 인증·권한 모드 변경 등은 확인한 Skill의 허용 범위 밖이다.
자동화 연결이 가능하다는 이유만으로 모든 세션 조작이나 설정 변경이 승인된 것은 아니다.[3]

## 정리

Gajae-Code는 모델과 도구를 연결하면서 계획·승인·실행·증거를 하나의 코딩 절차로 다루는 실행 환경이다.
외부 봇이나 Skill로 확장할 수 있지만 그 연결에는 경로 신뢰와 작업 허용 범위가 있다.
베타 단계의 도구인 만큼 선언된 절차와 실제 결과를 구분해 검토해야 한다.
