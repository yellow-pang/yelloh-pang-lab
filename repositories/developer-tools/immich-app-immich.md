## 사진을 보관하는 서버와 다시 찾는 화면

Immich는 사진과 동영상을 사용자가 관리하는 서버에 올리고 모바일·웹에서 찾아보는 자체 호스팅 관리 도구다.
README는 업로드, 앨범과 공유, 메타데이터 보기, 얼굴·내용 검색 등을 소개한다.
단순 폴더 동기화 도구도 아니고 저장 장치 자체도 아니다.
파일을 모으는 기능 위에 사진을 분류하고 다시 발견하는 화면을 제공하지만, 그 서버를 안전하게 보존하는 일까지 사라지는 것은 아니다.[1]

휴대전화로 찍은 사진과 컴퓨터에서 모은 사진은 원래 위치와 이름이 제각각이다.
나중에 여행 사진을 찾으려면 촬영 시각이나 위치를 기억할 수도 있고, '바닷가에서 찍은 장면'처럼 내용만 떠올릴 수도 있다.
Immich의 문서는 이 서로 다른 찾기 방식을 메타데이터 검색과 내용 기반 검색으로 구분한다.
메타데이터는 날짜·카메라·경로처럼 파일에 붙은 설명 정보다.[2]

## 업로드와 앨범 동기화는 서로 다른 동작

모바일 백업 문서에 따르면 사용자가 선택한 앨범의 새 사진·영상은 앱을 열거나 다시 활성화할 때, 그리고 주기적인 백그라운드 작업으로 서버에 업로드된다.
앨범을 제외할 수도 있으며 한 사진이 여러 앨범에 속하는 iOS의 경우를 별도로 설명한다.
따라서 '휴대전화 사진 전체가 무조건 올라간다'는 이해보다 선택·제외 규칙이 어떤 파일에 적용되는지 먼저 확인해야 한다.[3]

중복 업로드를 줄이는 기준은 파일 내용의 체크섬이다.
체크섬은 내용을 비교하기 위해 계산하는 식별값이라고 생각하면 된다.
문서는 처음 선택한 앨범의 각 파일에 대해 이를 계산하고, CLI·웹·다른 기기에서 이미 올라온 자산과 일치하면 건너뛴다고 설명한다.
파일명이 같다는 이유만으로 중복을 판정하는 방식과 다르며, 사진이 비슷하게 생겼다는 의미의 유사 이미지 분류와도 구별된다.[3]

앨범 동기화는 별도 선택 기능이다.
이를 켜면 기기의 앨범 구조를 서버 쪽 앨범에 반영하지만, 문서는 기기에서 서버로 가는 단방향 동기화라고 명시한다.
양쪽에서 수정하면 항상 같은 구조로 합쳐지는 일반적인 양방향 동기화로 설명해서는 안 된다.
이미 업로드한 자료를 앨범에 다시 정리하는 작업도 따로 안내한다.[3]

## 파일 이름을 몰라도 찾는 검색

검색 문서는 Postgres를 메타데이터와 CLIP 문맥 검색의 데이터베이스로 사용한다고 설명한다.
CLIP 계열 검색은 이미지와 검색 문장의 의미적 관련성을 이용해, 파일 설명에 같은 단어가 없어도 후보를 찾는 방식이다.
VectorChord 확장이 이 문맥 검색을 뒷받침한다고 안내한다.
반면 파일명·경로·기간·위치·사람·카메라·태그 같은 조건은 보다 명시적인 검색 필터다.[2]

내용 검색 모델은 언어와 자원 사용의 영향을 받는다.
공식 문서는 영어 중심 모델과 다국어 모델을 나누고, 모델 변경 후 기존 자산을 다시 처리하는 작업을 설명한다.
더 큰 모델을 골랐다는 사실만으로 모든 한국어 질문이 정확해지거나 검색 속도가 빨라지는 것은 아니다.
문서는 메모리·시간 값이 추정치이며 하드웨어와 처리 조건에 따라 달라진다고 경고한다.[2]

## 예시로 따라가는 흐름

다음은 이해를 위한 가상 예시이며 직접 실행한 결과가 아니다.
사용자가 휴대전화의 여행 앨범을 백업 대상으로 선택하고, 제외하고 싶은 앨범은 별도로 지정한다고 하자.
앱을 열면 선택 규칙에 해당하는 사진을 검토하고 내용 체크섬으로 서버에 이미 있는 자료와 비교한다.
같은 파일을 앞서 웹에서 올렸다면 문서가 설명하는 중복 확인 대상이 되고, 새로운 파일은 네트워크 설정을 만족할 때 업로드되는 흐름이다.[3]

앨범 동기화를 켠 경우에는 서버에도 기기의 앨범 구조를 반영한다.
이때 파일이 업로드되는 것과 앨범에 소속되는 것은 다른 단계이므로, 웹에서 자료가 보이지만 원하는 앨범에 정리되지 않은 상황을 업로드 실패와 똑같이 보지 않아야 한다.
사람이 확인할 부분은 선택·제외 앨범, 전송 완료 상태, 서버의 원본 보존과 앨범 구성이다.
백업 문서의 일방향 설명 때문에 서버에서 바꾼 구성이 휴대전화에 그대로 내려온다고 기대하지 않는다.[3]

이후 사진을 찾을 때는 기간과 위치 필터로 범위를 좁히거나 내용 검색을 시도할 수 있다.
모델이 비슷한 후보를 제시해도 원하는 장면인지 최종 선택은 사람이 한다.
검색 결과에 나오지 않는다는 사실이 파일이 서버에 없다는 뜻도 아니므로, 파일명이나 촬영 날짜 같은 다른 경로로 확인할 수 있다.
업로드 확인과 의미 검색 품질은 같은 검사가 아니라는 점이 이 사례의 핵심이다.[1][2]

## 모바일 운영체제와 보존 책임

기본 업로드 네트워크는 Wi-Fi이며 백업 설정에서 바꿀 수 있다.
Android는 배터리 최적화 정책 때문에 백그라운드 작업이 제한될 수 있고, iOS는 시스템이 실행 시점을 관리하므로 앱이 원하는 순간에 작업을 시작할 수 없다고 문서에 명시되어 있다.
따라서 '자동 백업'이라는 이름을 촬영 직후의 즉시 전송 보장으로 읽지 않아야 한다.[3]

iCloud에만 있는 자료를 포함한 로컬 앨범을 백업할 때에는 해당 파일을 임시 캐시로 가져온 뒤 체크섬 계산과 업로드를 진행하고 임시 파일을 비우는 흐름이 안내된다.
이 과정은 추가 저장 공간과 네트워크 데이터를 사용할 수 있다.
서버 저장 공간뿐 아니라 휴대전화의 여유 공간도 전송 조건에 포함된다는 뜻이다.[3]

README는 귀중한 사진과 영상에 3-2-1 백업 계획을 따르라고 경고한다.
모바일에서 서버로 올라간 사본이 하나 있다는 사실만으로 서버 손상·오삭제·분실에 대비한 복구 체계가 완성되지는 않는다.
이 글은 서버와 데이터베이스의 전체 복구 절차를 검증한 문서가 아니다.
공개 공유와 다중 사용자 기능을 켤 경우 사진뿐 아니라 위치·얼굴 같은 개인 정보가 어떻게 노출될지도 따로 판단해야 한다.[1]

## 정리

Immich는 사진을 서버에 모으고 앨범·메타데이터·내용 검색으로 다시 찾게 한다.
자동 업로드, 앨범 반영, 검색 품질, 별도 복구용 백업은 서로 다른 책임으로 나누어 관리해야 한다.[1][3][2]
