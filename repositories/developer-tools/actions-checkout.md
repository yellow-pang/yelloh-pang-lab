## 자동화 작업에 소스 파일을 준비하는 단계

`actions/checkout`은 GitHub Actions의 실행 환경에 저장소 파일을 가져와 후속 단계가 읽을 수 있게 하는 Action이다.
Action은 자동화 절차에 끼워 넣는 작업 단위이며, 이 프로젝트 자체가 테스트 실행기나 배포 서비스는 아니다.
README는 저장소를 `$GITHUB_WORKSPACE` 아래에 체크아웃한다고 설명한다.
체크아웃은 선택한 버전의 파일을 실제 작업 디렉터리에 펼치는 과정이다.[1]

자동화 설정에 테스트 명령을 적었다고 해서 테스트할 소스가 저절로 준비되는 것은 아니다.
어느 저장소의 어느 변경분을 가져올지, 과거 이력까지 필요한지, 다른 저장소에 접근할 자격이 있는지를 정해야 한다.
checkout은 이 준비를 표준화하지만, 가져온 코드가 안전한지 또는 테스트가 올바른지는 대신 판단하지 않는다.
특히 외부 기여자가 보낸 코드와 강한 권한을 가진 실행 환경의 결합은 별도의 보안 문제다.[1]

## 가져올 버전과 가져올 범위

README의 기본값은 자동화 이벤트가 가리키는 ref 또는 SHA의 한 커밋만 가져오는 것이다.
ref는 브랜치·태그처럼 버전을 가리키는 이름이고 SHA는 특정 커밋의 식별자다.
현재 파일만 검사할 때와 이전 변경을 비교할 때 필요한 자료가 다르므로, `fetch-depth`는 단순 속도 조절값이 아니라 후속 작업이 볼 수 있는 이력의 경계를 정한다. `0`은 모든 브랜치와 태그의 전체 이력을 가져오는 설정으로 안내된다.[1]

파일 범위와 이력 범위도 별개다. `sparse-checkout`은 필요한 경로나 패턴 중심으로 작업 트리에 파일을 펼치는 기능이며, README에는 루트 파일만 받기, 특정 폴더 선택, 단일 파일 선택 예제가 있다. `path`는 준비된 저장소를 둘 위치를 정한다.
저장소를 둘 이상 가져올 때 같은 실행 환경 안에서도 경로를 분리할 수 있지만, 두 저장소의 권한과 버전 선택이 자동으로 동일해지는 것은 아니다.[1]

추가로 연 소스 공급자 구현은 디렉터리 준비, Git 확인, 인증 설정, 가져오기, 체크아웃을 차례로 연결한다.
전체 이력을 요청한 경우에는 참조가 예상 커밋을 가리키는지 검사하고 필요하면 다시 가져온 뒤에도 일치하지 않으면 오류를 낸다.
이름이 같은 태그라도 실행이 시작된 뒤 가리키는 대상이 바뀔 수 있다는 상황을 코드에서 다룬다.
단순한 다운로드 한 번보다 입력 버전과 실제 결과를 맞추는 절차가 포함된 셈이다.[2]

Git을 사용할 수 없어 REST API 다운로드로 대체하는 경로도 있다.
다만 해당 경로에서는 하위 저장소를 연결하는 submodule과 SSH 키 입력을 지원하지 않는다고 오류 처리한다.
파일을 받을 수 있다는 것과 로컬 Git 저장소가 완전하게 구성된다는 것은 같은 보장이 아니다.
후속 단계가 Git 이력을 사용하는지에 따라 이 차이가 중요해진다.[2]

## 예시로 따라가는 흐름

README의 단일 파일 선택 예제를 따라가 보자.
입력은 `README.md`라는 sparse-checkout 패턴과 `sparse-checkout-cone-mode: false` 설정이다.
cone mode는 디렉터리 중심 선택 방식이며, 공식 예제는 파일 하나를 패턴으로 지정할 때 이를 끈다.
Action 버전과 이 입력은 워크플로 설정에 들어가고, checkout은 이벤트의 기본 버전 선택과 함께 작업 디렉터리를 준비한다.[1]

구현에서는 sparse 설정이 있고 별도 filter가 없으면 가져오기 필터를 설정한 뒤, 지정된 이력 깊이에 맞게 커밋 정보를 가져온다.
이어 체크아웃 정보를 결정하고 non-cone sparse 설정을 적용한 다음 선택한 버전을 펼친다.
여기서 sparse 설정은 필요한 파일을 선택하는 절차이고, 전체 이력을 자동으로 요청하는 절차가 아니라는 점이 중요하다.
결과 파일이 있다는 사실만으로 이전 커밋까지 사용할 수 있다고 생각하면 안 된다.[2]

이후 단계가 README를 검사하는 상황이라면 사람은 실제 체크아웃된 커밋, 선택한 경로, 후속 검사가 요구하는 파일 범위를 확인해야 한다.
README가 다른 파일을 참조하거나 도구가 전체 프로젝트 설정을 요구한다면 파일 하나만으로는 부족할 수 있다.
이 설명은 공식 예제와 소스의 처리 순서를 연결한 것이며, 워크플로를 실행해 성공 로그를 얻은 결과가 아니다.
원하는 범위만 받는 선택과 검사 목적에 충분한 자료를 받는 선택을 함께 판단하는 사례다.[1][2]

## 자격 증명과 외부 코드의 경계

조회한 README에는 여러 주요 버전의 변경 안내가 함께 남아 있다.
v6 설명은 자격 증명을 `.git/config`에 직접 저장하는 대신 `$RUNNER_TEMP` 아래 별도 파일로 옮겼다고 적고, 더 아래 v4 설명에는 이전 저장 방식이 남아 있다.
따라서 문장 하나를 떼어 모든 버전의 동작으로 일반화하면 안 된다.
사용할 Action 버전과 그 버전의 안내를 맞춰 읽어야 한다.[1]

v7 안내는 `pull_request_target` 또는 `workflow_run`으로 시작된 작업에서 fork의 PR 코드를 기본적으로 거부하는 변경을 설명한다.
이 트리거들은 기본 저장소의 토큰·비밀값·실행기 접근 권한과 연결되기 때문에, 외부 코드를 신뢰된 환경에서 실행하는 위험이 있다.
위험을 허용하는 입력이 있다는 사실은 사용을 권장한다는 뜻이 아니다.
여기서는 우회 절차가 아니라 기본 경계의 의미만 설명한다.[1]

README의 권장 토큰 권한은 대체 인증을 따로 제공하지 않는 일반적인 경우 `contents: read`다.
다른 비공개 저장소를 가져올 때는 현재 저장소 범위의 기본 토큰만으로 충분하지 않을 수 있다.
자격 증명을 남길지 결정하는 `persist-credentials`와 작업 종료 후 정리도 함께 읽어야 한다.
프로젝트는 외부 기여 접수 제한을 공지하면서 보안 업데이트와 중대한 호환성 문제 대응은 계속한다고 설명하므로, 기여 제한과 완전한 유지보수 종료를 같은 뜻으로 쓰지 않았다.[1]

## 직접 읽어볼 자료

- [README의 버전별 What's new와 Usage](https://github.com/actions/checkout/blob/main/README.md)
  우선 실제 선택할 주요 버전을 정한 다음 그에 해당하는 인증 방식과 실행기 요구 조건을 읽는다.
  한 페이지 안에 남은 이전 버전 설명이 서로 다른 동작을 가리키는지 구별하는 것이 첫 과제다.
- [git-source-provider.ts](https://github.com/actions/checkout/blob/main/src/git-source-provider.ts)
  `getSource`에서 Git 사용 가능 여부, 이력 깊이, sparse 설정이 각각 어디에서 분기하는지 찾는다.
  특히 ref 검증과 REST 대체 경로의 오류 조건을 보면 정상 예제 밖의 동작을 이해할 수 있다.
- [README의 Scenarios와 Recommended permissions](https://github.com/actions/checkout/blob/main/README.md)
  단일 파일, 여러 저장소, PR 커밋 예제를 목적별로 비교한다.
  경로·버전·권한 중 무엇을 바꾸는 예제인지 표시하면 불필요하게 전체 이력이나 넓은 토큰 권한을 복사하지 않을 수 있다.

## 정리

checkout은 자동화에 사용할 소스를 준비하는 도구다.
정확한 버전과 충분한 파일·이력을 확보하는 일, 외부 코드를 어느 권한으로 실행할지 정하는 일은 연결되어 있지만 서로 다른 판단이다.[1][2]
