## 값을 사람이 읽는 문자열로 바꾸는 C++ 도구

{fmt}는 숫자·문자열·시간 같은 값을 정해진 표시 형식에 맞춰 문자열로 만들거나 출력하는 C++ 라이브러리다.
README는 C stdio와 C++ iostreams의 대안으로 소개하고, 중괄호를 사용하는 형식 문법과 사용자 정의 타입 확장을 설명한다.
문서 자체를 예쁘게 만드는 서식 프로그램이 아니라 C++ 코드 안의 출력 처리에 사용하는 라이브러리다.[1]

프로그램이 가진 숫자와 화면에 표시할 문장은 다른 자료다.
같은 값도 소수점 자릿수, 정렬, 앞자리 채움, 날짜 형식에 따라 표현이 달라진다.
모든 위치에서 직접 문자열을 이어 붙이면 표시 규칙과 데이터가 뒤섞인다. {fmt}는 형식 문자열에 빈자리와 표시 조건을 두고 실제 값을 별도 인자로 전달한다.
README의 `fmt::format("The answer is {}.", 42)`는 이 관계를 가장 작게 보여 준다.[1]

## 문자열 생성과 출력의 차이

`fmt::format`은 완성된 문자열을 돌려주고 `fmt::print`는 출력을 수행한다.
계산한 설명을 다른 함수에 넘길 때와 바로 화면에 보일 때 필요한 동작이 다르므로 두 API를 구별해야 한다.
README의 파일 출력 예제처럼 출력 대상에 따라 별도 기능을 선택할 수도 있다.
표시 규칙은 비슷해 보여도 결과를 저장할지, 어디로 보낼지는 호출부의 책임이다.[1]

중괄호 안의 위치 번호는 값을 넣을 순서를 정한다.
공식 예제의 `{1}`과 `{0}`은 인자를 전달한 순서와 문장 속 배치 순서를 다르게 만든다.
값 자체를 바꾸지 않고 표현 순서를 바꿀 수 있다는 점이 핵심이다.
다만 위치를 바꿀 수 있다는 기능만으로 번역이나 자연어 문법이 자동 처리되는 것은 아니다.
형식 문자열의 의미는 여전히 작성자가 정한다.[1]

콜론 뒤의 형식 지정자는 값의 표시 방법을 정한다.
추가로 읽은 테스트에는 너비, 0 채우기, 정렬, 진법 표기와 잘못된 지정자의 오류 기대가 있다.
예를 들어 0 채우기는 단순히 맨 앞에 글자를 덧붙이는 것이 아니라 부호와 숫자의 관계를 고려한다.
테스트가 음수와 여러 정수 타입을 나누는 이유는 겉보기 문자열의 작은 차이도 출력 규칙에 해당하기 때문이다.[2]

시간과 범위 자료는 해당 헤더를 통해 표현한다.
README는 날짜·시간에 `fmt/chrono.h`, 벡터 같은 여러 값의 묶음에 `fmt/ranges.h`, 색상과 강조에 `fmt/color.h`를 사용하는 예제를 보여 준다.
기본 문자열 출력 하나를 익힌 뒤 필요한 자료형으로 확장하는 읽기 순서가 가능하다.
예제 헤더가 다르다는 사실을 무시하고 코드 한 줄만 복사하면 필요한 인터페이스가 빠질 수 있다.[1]

## 예시로 따라가는 흐름

공식 `zero_flag` 테스트에서 `fmt::format("{0:05}", -42)`를 살펴보자.
입력은 음수 정수와 형식 문자열이다. `0`은 첫 번째 인자를 가리키고, `05`는 0을 채움에 사용한 너비 지정으로 등장한다.
테스트는 결과가 `-0042`가 되기를 기대한다.
이 값은 여기서 새로 계산한 실행 결과가 아니라 소스에 적힌 기대 문자열이다.
부호를 포함한 출력 형태를 검사한다는 점이 중요하다.[2]

바로 뒤의 `zero_flag_and_align` 테스트는 정렬 옵션과 0 문자가 함께 있으면 0이 무시된다는 주석을 두고, 왼쪽·가운데·오른쪽 정렬의 기대 문자열을 비교한다.
따라서 '0을 쓰면 언제나 숫자 앞을 0으로 채운다'는 규칙으로 단순화하면 예외를 놓친다.
형식 옵션은 각자 독립적인 스위치가 아니라 함께 해석되는 문법이다.[2]

다른 입력으로 문자열을 넘기는 오류 사례도 같은 테스트에 있다.
숫자를 요구하는 지정자를 문자열에 적용하면 `format_error`와 설명 메시지를 기대한다.
사람이 확인할 부분은 실제 인자의 타입, 형식 문자열이 컴파일 때 알려지는지 실행 중에 만들어지는지, 잘못된 입력을 받았을 때 예외를 어떻게 처리할지다.
이 파일을 읽었다고 테스트를 실행한 것은 아니며, 실제 프로그램의 출력 대상과 오류 처리 방식은 별도 확인이 필요하다.[2]

이 흐름의 결과는 단지 예쁜 문자열이 아니다.
입력 타입과 표시 규칙이 맞을 때 정해진 표현을 얻고, 맞지 않을 때 조용히 다른 메모리를 읽는 대신 오류를 다룰 경로를 갖는다는 점이 라이브러리 사용의 핵심이다.
다만 출력 문장의 내용이 사실인지, 로그에 민감한 값을 넣어도 되는지까지 형식 검사로 판단할 수는 없다.

## 안전성과 성능 주장을 읽는 기준

README는 C++20에서 문자열에 정수 지정자를 적용하는 예제가 컴파일 오류가 된다고 설명한다.
반면 추가로 읽은 테스트는 `runtime`으로 실행 시 형식 문자열을 전달해 오류를 확인한다.
컴파일 시점에 알 수 있는 형식과 실행 중 만들어지는 형식은 검사 시점이 다르다. '컴파일 타임 검사 지원'을 모든 외부 입력이 실행 전에 검증된다는 의미로 넓히지 않아야 한다.[1][2]

헤더만 포함하는 선택적 구성도 README에 있지만, 이를 모든 프로젝트에서 빌드 비용이 사라지는 방법으로 해석할 수는 없다.
README의 성능 표는 특정 장비, 컴파일러, 최적화 옵션과 측정 범위를 제시한다.
라이브러리 및 모듈 빌드 비용을 제외했다는 설명도 있으므로 숫자 하나만 비교하면 다른 질문에 답하게 된다.
이 조사에서는 표의 결과를 재현하거나 자신의 환경에 적용 가능한 배수로 환산하지 않았다.[1]

Unicode와 색상 출력 역시 환경 조건을 갖는다.
README의 색상 예제는 Unicode를 지원하는 현대적 터미널의 출력으로 소개된다.
라이브러리가 문자열을 만들었다는 사실과 터미널이 같은 글꼴·폭·색상으로 보인다는 사실은 다르다.
파일 출력과 터미널 표시를 나누어 시험해야 할 이유다.
기본 locale 독립성이라는 설명도 지역별 표현이 자동으로 적용된다는 뜻이 아니다.[1]

## 정리

{fmt}는 데이터와 표시 규칙을 분리하고 타입에 맞는 문자열 생성·출력을 제공한다.
형식 지정자의 상호작용과 검사 시점을 이해해야 하며, 성능과 화면 표현은 실제 사용 환경의 별도 확인이 필요하다.[1][2]
