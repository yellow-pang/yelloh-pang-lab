## 한 줄 요약

hey는 하나의 HTTP 요청을 여러 작업자에게 반복하게 하고 응답 시간과 상태 통계를 출력하는 Go 기반 부하 생성 도구다.
부하 테스트는 서버에 요청을 보내 반응을 관찰하는 작업이지, 도구를 켜기만 하면 서비스의 최대 수용량이 증명되는 절차는 아니다.[1][2][3]

## 브라우저 대신 반복 요청을 보내는 도구

사람이 페이지를 한 번 여는 것만으로는 요청이 겹칠 때의 상태를 알기 어렵다.
hey는 요청 수와 동시에 일할 작업자 수를 받아 같은 요청을 반복한다.
명령행에서 HTTP 메서드, 헤더, 본문, 시간 제한, HTTP/2 사용 여부를 지정할 수 있다.
구현은 Go의 HTTP 클라이언트로 요청하므로 화면 렌더링이나 사용자의 클릭 여정을 재현하는 브라우저 자동화 도구로 이해하면 안 된다.[1][2][3]

README의 기본값은 요청 200개와 동시 작업자 50개다.
인자 없이 가볍게 URL을 확인하는 명령처럼 보여도 실제로는 여러 요청을 만들 수 있다.
이름이 작은 도구라고 해서 대상 서버에 주는 영향까지 작다고 판단하지 말고, 허가받은 대상·메서드·요청량을 먼저 정해야 한다.[1]

## 입력, 작업자, 보고서가 나뉜 구조

`hey.go`는 옵션을 읽고 URL과 헤더·본문으로 요청 원형을 만든다.
수량과 동시성 값이 올바른지 확인한 뒤 `requester.Work`에 넘기며, 지정 시간이 끝나거나 인터럽트를 받으면 중단 신호를 보낸다.
`-z`로 시간을 지정한 경우 README가 설명하듯 `-n` 기준 대신 시간 기반으로 동작하도록 구성한다.[2]

`requester/requester.go`는 작업자들을 실행하고 요청을 복제한다.
DNS 조회, 연결, 요청 쓰기, 첫 응답 바이트 도착 등의 시간을 추적하며, 응답 본문은 읽어 버린다.
따라서 응답 JSON의 내용이 맞는지 검사하는 기능 테스트와는 다르다.
중단 신호는 작업 반복 사이에 확인하므로 설정 시간이 지났다는 사실과 모든 진행 중 요청이 즉시 취소됐다는 사실도 같지 않다.[3]

`requester/report.go`는 결과를 모아 요청률, 시간 분포, 상태 코드와 오류 분포를 만든다.
요청률은 오류 결과까지 포함한 결과 수를 총 시간으로 나누지만, 지연 시간 표본에는 전송 오류가 없는 결과가 들어간다.
HTTP 오류 상태가 도착한 경우도 전송 자체가 성공했다면 시간 표본에 들어갈 수 있다.
숫자 하나만 보지 말고 상태 코드와 전송 오류를 함께 읽어야 하는 이유다.[4]

## 예시로 따라가는 흐름

자신이 운영하며 부하 시험 권한이 있는 로컬 테스트 서버가 있고, `http://127.0.0.1:8080/health`가 상태 확인만 하는 경로라고 가정하자.
다음은 확인한 옵션을 이 가정에 맞춰 조합한 설명용 명령이며 실행 기록이 아니다.[1][2]

```sh
hey -n 20 -c 2 -q 1 -t 5 -disable-redirects http://127.0.0.1:8080/health
```

입력은 GET 요청, 전체 요청 수, 동시 작업자 수, 작업자별 속도 제한, 요청별 시간 제한이다.
CLI가 요청을 만들면 작업자들이 각자 제한에 맞춰 순서대로 보낸다.
여기서 `-q`는 프로그램 전체의 초당 요청 수가 아니라 작업자 하나의 제한이다.
응답이 느리면 실제 처리 속도는 더 낮아질 수 있으며, 동시 작업자 수를 곧바로 실제 사용자 수라고 해석해서도 안 된다.[1][2][3]

끝나면 응답 시간 분포와 상태 코드·오류를 확인한다.
예상한 정상 상태가 나왔는지, 시간 초과가 있었는지, 서버 로그에서 같은 요청이 어떻게 처리됐는지 사람이 대조해야 한다.
더 많은 요청을 보내기 전에 허가 범위와 중단 기준부터 정하는 것이 전제다.
이 원고는 임의의 응답 시간이나 요청률을 결과처럼 제시하지 않으며, 위 경로가 현재 실행 환경에 존재한다고 주장하지 않는다.[3][4]

## 옵션과 구현 사이에서 놓치기 쉬운 점

수량 기반 실행에서 구현은 각 작업자에게 `N/C`를 정수 나눗셈으로 배분하며, 나머지를 무시한다는 주석도 있다.
그래서 `-n`이 `-c`로 나누어떨어지지 않으면 요청한 수량보다 적게 보낼 수 있다.
정확한 요청 수가 중요하다면 인자뿐 아니라 실제 결과와 서버 수신 기록을 확인해야 한다.[3]

보고서는 시간·상태 코드 표본을 최대 100만 개까지 저장한다.
그 이후에도 시간 누적은 계속되지만 평균 계산의 분모는 저장된 지연 표본 수를 사용한다.
이 코드 경로에서는 대규모 장시간 실행의 평균이 왜곡될 수 있으므로 모든 통계가 무제한 표본을 대표한다고 전제하면 안 된다.
이는 해당 고정 커밋의 소스를 읽어 확인한 집계 방식이며 재현 실험 결과는 아니다.[4]

연결 재사용과 압축을 끄거나 HTTP/2를 켜는 옵션도 있다.
같은 URL을 시험하더라도 연결을 매번 새로 만드는지, 압축과 프로토콜 조건이 같은지에 따라 측정하는 작업 자체가 달라진다.
비교를 하려면 이런 설정과 실행 머신·네트워크 조건을 함께 기록해야 한다.[1][3]

## 권한, 인증과 비용의 주의점

중요한 보안 조건은 HTTPS 전송 설정의 `InsecureSkipVerify: true`다.
이 코드 경로는 서버 인증서 검증을 건너뛰므로 hey에서 요청이 성공했다는 사실은 인증서가 신뢰할 만하다는 증거가 아니다.
실제 서비스의 TLS 검증이나 보안 점검을 대신할 수 없으며, 인증 토큰을 싣는 경우에는 대상과 경로를 별도로 신뢰할 수 있어야 한다.[3]

README에는 공개 사이트를 대상으로 하는 예제가 있지만 이를 누구에게나 부하를 가해도 된다는 허가로 받아들이면 안 된다.
실제 시험은 소유하거나 명시적으로 허가받은 대상에 한정하고, 리다이렉트가 권한 밖의 대상으로 이어지는지도 확인해야 한다.
POST·PUT·DELETE와 본문 전송이 지원되므로 같은 명령을 반복하면 실제 데이터 변경이 반복될 수 있다.
`-disable-redirects`는 리다이렉트를 따라가지 않도록 하는 옵션이지 잘못 고른 대상의 위험을 모두 제거하는 장치는 아니다.[1][3]

코드는 Apache-2.0으로 제공되고 재배포 조건과 무보증 조항이 있다.[5]
이 코드 라이선스와 테스트 서버·클라우드 요청·전송 자원 비용은 별개다.
읽은 자료에는 운영 대상의 요금이 없으므로 비용 없는 테스트라고 단정하지 않는다.
또 이 조사에서는 요청을 한 번도 보내지 않았다.
