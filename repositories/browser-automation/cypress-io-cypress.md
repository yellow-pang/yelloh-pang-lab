## 한 줄 요약

Cypress는 브라우저에서 동작하는 웹 애플리케이션을 시험하는 도구다.
사람이 화면을 클릭하고 결과를 눈으로 확인하는 일을 테스트 코드의 조작과 검증 조건으로 표현하도록 돕는다.
README는 Mac·Linux·Windows용 설치를 안내하고, 저장소는 브라우저 시험을 위한 구현과 개발 자료를 제공한다.
웹 서비스를 대신 만드는 프레임워크나 실행만 하면 품질을 보증하는 판정기는 아니다.[1]

## 버튼을 누른 다음 언제 확인해야 할까

웹 화면에서는 클릭 직후 결과가 항상 바로 나타나지 않는다.
화면 전환, 비동기 요청, 렌더링 때문에 아주 잠깐 이전 상태가 남을 수 있다.
너무 빨리 확인하면 정상 기능도 실패로 보이고, 고정된 긴 대기 시간을 매번 넣으면 느린 환경에는 부족하고 빠른 환경에는 낭비가 된다.
Cypress의 내부 재시도 구현은 정해진 제한 시간 안에서 조건을 다시 확인하는 작업을 다룬다.[2]

테스트에는 수행할 행동과 확인할 조건이 함께 필요하다.
예를 들어 화면의 특정 영역을 찾는 것과 그 안의 글자가 기대한 값인지는 다른 질문이다.
재시도는 그 질문이 충족될 시간을 주는 장치이지, 기대값을 정하거나 실패를 무조건 성공으로 바꾸는 장치가 아니다.
이 글은 전체 Cypress 기능 목록보다 `packages/driver/src/cy/retries.ts`에 나타난 시간·취소·안정 상태의 경계를 대표 메커니즘으로 살펴본다.[2]

## 기다림을 제한하고 종료 조건을 명시하기

해당 파일의 `retry`는 재시도 시작 시각, 간격, 현재 실행 대상과 제한 시간을 관리한다.
실행 대상은 지금 수행 중인 테스트 단위에 대응하는 상태다.
함수는 이미 기다린 시간과 다음 간격을 계산해 허용 시간을 넘는지 판단하며, 넘으면 오류 정보에 타임아웃 설명을 붙여 검증을 종료하는 경로를 갖는다.
무한히 확인하다 우연히 맞는 순간을 찾는 방식이 아니다.[2]

취소도 별도의 종료 조건이다.
테스트가 취소됐거나 현재 실행 대상이 바뀌면 이전 재시도를 계속하지 않는다.
코드 주석은 비동기 취소가 제때 전파되지 않을 수 있어 이런 확인이 필요하다고 설명한다.
이전 테스트의 기다림이 다음 테스트까지 이어져 서로 영향을 주는 문제를 막으려는 경계다.
재시도는 단지 같은 함수를 반복하는 것보다 실행 수명의 관리에 가깝다.[2]

안정 상태라는 개념도 등장한다. `whenStable(fn)`은 안정 상태에 도달했을 때 전달된 확인 함수를 실행하는 경로이고, 불안정 상태로 표시돼 있으면 시작 시각을 초기화하는 코드가 있다.
여기서 안정은 Cypress 내부 실행 상태이지 서비스 전체에 오류가 없다는 보장이 아니다.
코드가 어떤 상태를 기다리는지와 사람이 시험하려는 기능이 올바른지는 서로 다른 층위다.[2]

## 예시로 따라가는 흐름

다음은 재시도 구현을 설명하기 위한 가상 예시이며 직접 실행한 결과가 아니다.
사용자가 소유한 연습용 페이지에서 버튼을 누르면 잠시 뒤 “저장 완료”라는 문구가 표시된다고 하자.
테스트의 입력은 그 페이지에 대한 조작과 완료 문구를 확인하는 조건이다.
처음 확인할 때 문구가 없다고 곧바로 최종 실패로 결정하기보다, 해당 검사가 재시도 경로에 들어갔다면 허용된 시간 안에서 확인을 이어갈 수 있다.[2]

재시도 함수는 현재 검사와 관련된 로그를 찾고 시작 시각과 제한 시간을 기록한다.
다음 확인을 기다릴 때에도 취소됐는지, 실행 대상이 달라졌는지를 검사한다.
화면이 불안정한 상태라면 안정화 경로를 거쳐 확인 함수를 부른다.
완료 문구가 끝내 나타나지 않으면 제한 시간에 따라 오류 처리로 이어진다.
이 과정은 버튼 클릭 자체를 무제한 반복해야 한다는 뜻이 아니며, 이 파일 하나만으로 모든 Cypress 명령의 재실행 규칙을 일반화하지 않았다.[2]

사람이 확인할 것은 실패 이유다.
문구의 철자가 잘못됐는지, 다른 영역을 검사했는지, 저장 요청이 실패했는지, 허용 시간이 실제 환경에 맞는지는 시험 목적에 따라 다르다.
시간만 늘리면 결함이 해결됐다고 판단할 수 없다.
반대로 테스트가 통과해도 다른 입력이나 브라우저 환경까지 확인한 것은 아니다.
자동화의 결과는 작성한 조작·기대값과 실행 범위 안에서 해석해야 한다.

## 시험 코드도 검토 대상이다

저장소의 `system-tests/projects/todos/tests/test1.js`는 `expect(true).to.be.true`를 검사하는 아주 작은 예다.
이 파일은 테스트 문법을 확인하는 데는 도움이 되지만 실제 할 일 관리 앱의 동작을 검사하는 사례로 소개할 수는 없다.
폴더 이름이나 파일 존재만 보고 로그인·저장·화면 전환 같은 기능이 검증됐다고 추정하지 않는 것이 중요하다.[3]

README에 있는 Cypress Cloud 배지도 구분해서 읽어야 한다.
배지는 테스트 상태나 개수를 보여 주도록 연결하는 수단으로 소개되며, 배지를 붙이는 행위 자체가 검증 범위를 늘리지 않는다.
설치 방법, 저장소의 테스트 구현, 원격 결과 표시를 같은 기능으로 합치지 않아야 한다.
이 글에서는 원격 서비스 가입이나 결과 업로드를 수행하지 않았다.[1]

시험 대상의 부작용도 남는다.
실제 웹 페이지를 대상으로 입력·제출을 수행하면 테스트라는 이름과 관계없이 서버 데이터가 바뀔 수 있다.
읽기용 예시는 개인 연습 페이지와 통제된 데이터로 한정해 이해해야 한다.
또한 확인한 소스의 타임아웃 관리는 오류를 보고하는 메커니즘이지 네트워크 응답이나 테스트 데이터의 일관성을 자동으로 만들어 주는 기능이 아니다.[2]

## 직접 읽어볼 자료

- [공식 README](https://github.com/cypress-io/cypress/blob/develop/README.md):

  설치 안내와 기여 문서 연결, Cloud 배지 항목을 구별해 읽는다.
  도구를 추가하는 작업과 테스트를 작성하는 작업, 결과를 외부에 표시하는 작업이 각각 무엇인지 파악하는 출발점이다.[1]
- [재시도 구현](https://github.com/cypress-io/cypress/blob/develop/packages/driver/src/cy/retries.ts):

  `retry` 안의 제한 시간 계산에서 시작해 `ended`와 `whenStable`로 이동한다.
  얼마 동안 기다리는지뿐 아니라 언제 더 이상 반복하면 안 되는지를 묻고 읽으면 실행 경계가 보인다.[2]
- [작은 시스템 시험 입력](https://github.com/cypress-io/cypress/blob/develop/system-tests/projects/todos/tests/test1.js):

  검사 대상이 실제 화면인지 고정된 참 값인지 확인한다.
  짧은 테스트가 있다는 사실과 사용자 기능이 검증됐다는 주장의 차이를 직접 확인할 수 있는 자료다.[3]

## 정리

Cypress는 브라우저 기능을 반복 가능한 조작과 조건으로 시험하게 한다.
내부 재시도는 비동기 화면의 기다림을 관리하지만 시험 목적이나 정답을 대신 정하지 않는다.
종료 조건과 실패 이유를 읽고, 통과 결과는 실제 작성한 검사 범위 안에서 해석해야 한다.[1][2]

## 자료 확인 범위

2026-09-27 기준 README, 드라이버의 재시도 구현과 작은 시스템 시험 파일을 읽었다.
Cypress를 설치하거나 브라우저 테스트를 실행하지 않았다.
예시의 화면 동작과 테스트 통과 결과를 실제 측정한 것으로 제시하지 않았다.
