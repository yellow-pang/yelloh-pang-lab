## 한 줄 요약

이 저장소는 Douyin의 동영상·사진을 내려받아 로컬 자료로 관리하는 Python CLI와, 별도로 안내하는 데스크톱 앱 Douzy를 함께 소개한다.
CLI는 터미널에서 명령을 입력해 쓰는 프로그램이다.
현재 README는 CLI의 여러 다운로드 경로가 플랫폼 요청 검증에 막혀 있다고 명시하므로, 기능이 구현되어 있다는 설명과 지금 실제로 다운로드된다는 보장을 구분해야 한다.[1]

## 먼저 구분할 것: Python CLI와 Douzy

한 창작자의 게시물을 다시 확인하려고 매번 링크를 찾는 대신, 허락받은 자료를 로컬 폴더에 정리하는 상황을 생각할 수 있다.
여기서 필요한 일은 파일 하나를 받는 것만이 아니다.
대상 게시물을 고르고, 이미 받은 항목은 건너뛰고, 중간 실패를 구분하며, 나중에 원본을 찾을 수 있게 이름을 붙여야 한다.
Python CLI는 이런 반복 작업을 위한 수량·날짜 조건, 다운로드 기록, 재시도와 선택적 부가 기능을 제공한다.[1]

그러나 README의 플랫폼 목록을 CLI의 지원 목록으로 읽으면 범위가 틀어진다.
Douzy는 Douyin·TikTok·YouTube·Telegram·X를 다루는 데스크톱 앱으로 소개되고, Python CLI는 Douyin만 지원한다.
Douzy의 플랫폼별 기능도 활성화된 플러그인이나 로컬 구성요소에 의존하며 일부 일괄·고급 기능은 활성화가 필요하다고 설명한다.
이 글의 구현 분석은 공개 Python 코드와 설정 파일에 한정하며, 데스크톱 앱의 동작을 직접 확인한 것은 아니다.[1]

더 중요한 경계는 현재의 가용성이다.
확인한 README는 개별 영상·사진, 컬렉션, 음악, 좋아요와 즐겨찾기 등의 CLI 다운로드가 요청 검증에 막힌다고 알린다.
창작자 프로필의 게시물은 Playwright라는 브라우저 자동화 도구를 이용한 대체 경로를 시도할 수 있지만 성공을 보장하지 않는다.
쿠키를 새로 받거나 반복 재시도하는 것으로 이 검증 차단이 해결되지 않는다는 설명도 있다.[1]

## 설정은 대상을 고르고 코드는 기록과 파일을 비교한다

`config.example.yml`은 입력 링크와 저장 경로, 다운로드 모드, 수량 제한을 한곳에 모은 예제다.
`mode: post`는 작성자의 게시물을 대상으로 하며, `number.post`가 처리 수량을 제한한다.
README의 빠른 시작 예시는 열 개를 사용하지만 설정 예제 파일에는 한 개로 적혀 있다.
숫자 0은 제한 없음이므로 “아무것도 받지 않음”으로 해석하면 안 된다.
원하는 범위를 명시적으로 바꾸고 확인하는 과정이 필요하다.[1][2]

저장 대상도 구분되어 있다.
예제 설정은 영상 본체만 켜고 음악·표지·아바타·원본 JSON 저장은 끈다.
파일명과 폴더명 템플릿에는 날짜·제목·게시물 ID를 사용하며, 같은 이름으로 덮어쓰는 일을 피하려고 ID를 포함하도록 안내한다.
작성자 폴더를 닉네임으로만 만들면 동명이인이나 이름 변경의 영향을 받을 수 있어, 설정은 고유 ID 또는 닉네임과 ID를 결합하는 선택지도 설명한다.[2]

증분 다운로드는 이미 받은 항목을 건너뛰고 새 항목을 추가하는 방식이다.
`core/downloader_base.py`의 `_should_download`는 먼저 로컬 자료 인덱스를 확인한다.
인덱스를 만들 때 비어 있는 파일과 표지·아바타·음악 같은 부가 파일은 제외하므로, 표지만 있다고 영상 본체까지 받은 것으로 판단하지 않도록 되어 있다.
`redownload_missing_files`가 켜져 있으면 로컬 본체가 없는 항목을 다시 받을 수 있고, 꺼져 있으면 유효한 데이터베이스 기록을 근거로 건너뛸 수 있다.[3]

`core/user_downloader.py`는 게시물 ID인 `aweme_id`로 중복 대상을 제거한 뒤 다운로드 큐에 넘긴다.
결과를 성공·실패·건너뜀으로 나누고, 데이터베이스를 쓰는 경우 기록을 묶어 저장한다.
따라서 최종 숫자에서 “건너뜀”은 실패와 같지 않으며, 목록에 게시물이 존재한다는 사실만으로 파일이 생성되었다고 판단할 수도 없다.[4]

## 예시로 따라가는 흐름

공식 빠른 시작의 프로필 링크 예제를 바탕으로, 자신의 Douyin 게시물 중 제한된 수량을 로컬에 보관하려는 상황을 가정한다.
이해를 위한 가상 예시이며 직접 실행한 결과가 아니다.
입력은 본인이 접근·보관할 권한이 있는 프로필 URL, `post` 모드, 저장 폴더, 수량 제한이다.
설정 파일에는 로그인 후 저장한 쿠키를 사용할 수 있지만, 이 설명에서는 실제 계정이나 인증자료를 입력하지 않았다.[1][2]

프로필 처리 코드가 게시물 정보를 확보하면 `aweme_id`를 기준으로 목록의 중복을 제거하고, `_should_download`로 기존 파일을 확인한다.
이미 비어 있지 않은 본체 파일이 있다면 기본 증분 설정에서는 건너뛰며, 없다면 자산 다운로드 단계로 넘긴다.
파일이 사라졌을 때 다시 받을지, 기록만으로 건너뛸지는 `redownload_missing_files` 설정에 따라 달라진다.
이 단계들을 거쳐 얻으려는 산출물은 선택된 미디어 파일과 다운로드 이력이지, 링크 목록 자체가 아니다.[4][3]

프로필 게시물 목록이 충분하지 않을 때의 브라우저 대체 경로는 브라우저에서 ID를 모으고, 이미 가진 목록과 비교하여 빠진 게시물의 상세 정보를 보완한다.
코드에는 다른 작성자의 ID로 판명된 항목을 제외하는 검사도 있다.
하지만 현재의 요청 검증 제한 때문에 이 경로가 파일 저장까지 성공한다고 가정할 수는 없다.
차단되면 실제 결과는 성공 아카이브가 아니라 실패·누락 기록일 수 있으며, 이를 숨기고 완료로 적으면 안 된다.[1][4]

사람이 확인할 부분은 선택한 프로필과 날짜·수량 범위, 저장된 본체 파일의 존재와 재생 여부, 실패와 건너뜀의 차이다.
`increase.post: false`로 바꾸면 선택 범위의 자료를 다시 내려받아 덮어쓸 수 있으므로, 단순히 “누락만 보충”하는 설정과 구별해야 한다.
이 예시는 출력 폴더나 성공 건수를 만들어 제시하지 않으며, 공식 자료가 설명하는 처리 순서만 따라간 것이다.[1][3]

## 접근 권한·저작권·인증자료는 별개의 조건이다

첫째는 사이트에 접근할 수 있는 권한이다.
로그인 계정으로 볼 수 없는 자료를 이 도구가 허용해 주는 것은 아니며, README도 브라우저의 검증 절차는 사람이 직접 완료하도록 안내한다.
요청 검증 차단을 쿠키 문제로 오해하여 인증자료를 계속 바꾸는 것은 공식 안내와 맞지 않는다.
현재 사용 가능성은 프로그램 설정뿐 아니라 플랫폼의 응답에 달려 있다.[1]

둘째는 자료의 복제·재배포 권한이다.
워터마크 없는 다운로드를 제공한다는 소개는 원저작자의 권리가 사라진다는 의미가 아니다.
저장소는 학습과 개인 자료 관리를 용도로 들면서 저작권·개인정보·플랫폼 규칙을 존중하라고 명시한다.
소프트웨어의 MIT 라이선스와 다운로드한 영상·사진의 이용 허락은 별도로 확인해야 한다.[1]

셋째는 인증자료의 취급이다.
예제에는 `cookies` 항목과 전사 API 키 설정이 있으므로, 실제 값을 넣은 설정은 공개 예제와 다르게 취급해야 한다.
설정 파일이나 오류 보고를 공유할 때 인증값을 빼는 것이 필요하다.
선택적 음성 전사 기능은 기본적으로 꺼져 있지만 외부 전사 API 주소와 키를 지정하는 구조이므로, 켤 경우 미디어의 외부 처리와 해당 서비스 조건을 따로 살펴야 한다.
댓글 수집 역시 기본 비활성화이며, 활성화하면 영상 파일 외의 추가 자료가 저장되는 기능이다.[2]

실행 환경으로는 Python 3.9 이상이 안내되고, 프로필의 브라우저 대체 경로에는 Playwright와 Chromium 준비가 필요하다.
실시간 방송 기능은 실험적이며 HLS 입력에서는 재생 가능한 완성 영상 대신 재생 목록을 저장한다는 제한도 있다.
따라서 “다운로더”라는 이름만으로 모든 콘텐츠 유형을 같은 결과 파일로 만들 것이라 기대해서는 안 된다.[1]

  표지 파일만 남은 상태를 영상 다운로드 완료로 취급하지 않는 이유도 여기서 확인할 수 있다.

## 정리

이 프로젝트의 Python 부분은 Douyin 자료를 선별하고 중복·이력·파일을 관리하는 다운로드 처리 코드다.
현재의 요청 검증 제한을 먼저 이해해야 하며, Douzy의 기능 목록을 CLI의 동작 보장으로 옮겨 적어서는 안 된다.
기술적 접근 가능성, 자료 이용 권한, 인증자료 보호도 각각 따로 판단해야 한다.[1][2]
