## 한 줄 요약

Cua는 AI Agent가 컴퓨터의 앱을 관찰하고 조작하도록 도구와 실행 환경을 제공하는 프로젝트 모음이다.
하나의 AI 모델이나 브라우저 자동화 프로그램만을 뜻하지 않으며, 데스크톱 조작용 Driver, 로컬·클라우드 실행 환경, 평가 도구와 전문 판단 모델을 구분해 제공한다.[1]

## 답을 쓰는 Agent와 앱을 움직이는 도구

“계산 결과를 알려 달라”와 “계산기 앱을 열어 계산하고 화면을 확인해 달라”는 서로 다른 요청이다.
앞의 요청은 답변만으로 끝날 수 있지만, 뒤의 요청에는 대상 앱을 찾고 버튼이나 입력란을 조작한 뒤 바뀐 상태를 읽는 과정이 필요하다.
이처럼 컴퓨터의 그래픽 화면을 포함한 여러 수단으로 작업하는 방식을 computer use라고 부른다.
Cua는 Agent가 코드·API·화면을 오갈 때 사용할 컴퓨터와 조작 도구를 제공하며, 범용 계획과 모델 선택은 사용자가 연결하는 Agent에 남겨 둔다.[1]

이 구분을 놓치면 Driver를 설치한 것만으로 일을 알아서 수행하는 AI가 완성되었다고 오해하기 쉽다.
Driver는 요청받은 관찰·조작을 실행하는 계층이고, 무엇을 할지 정하는 Agent와 그 판단을 만드는 모델은 별도다.
또한 화면을 움직이는 도구가 있다는 사실과 독립된 실행 공간이 있다는 사실도 다르다.
기존 데스크톱을 사용할지, 가상 머신이나 클라우드 데스크톱을 준비할지는 따로 선택해야 한다.[1][2]

## 구성요소를 역할별로 읽기

Cua Driver는 macOS·Windows·Linux의 앱과 브라우저를 살피고 조작한다.
Agent는 명령줄 CLI나 외부 도구 연결 규약인 MCP로 접근할 수 있고, 개발자는 Python·TypeScript용 개발 라이브러리인 SDK를 사용할 수 있다.
SDK는 같은 네이티브 실행 기반을 프로그램 내부에서 부르며, 직접 사용에는 별도 백그라운드 서비스인 daemon이 필수가 아니다.[1][2]

실행 환경 쪽에는 Cua Fleets와 Lume이 있다.
Fleets는 클라우드 데스크톱 용량을 풀로 유지하고, 프로그램이 그중 데스크톱을 확보해 명령 실행·화면 캡처·앱 조작에 사용하는 구조다.
Lume은 Apple Silicon에서 macOS·Linux 가상 머신을 만들고 관리한다.
가상 머신은 호스트 안에서 별도 운영체제를 실행하는 환경이며, 여기서는 Agent 작업을 위한 컴퓨터를 준비하는 역할이다.
로컬 환경과 Fleets가 Sandbox SDK를 공유해도 인증자료·이미지·지원 작업·실행 요건까지 같지는 않다.[1]

Cua Bench는 과제를 만들고 Agent를 평가하며 행동 기록을 내보내는 도구다.
CUA-S1은 입력란에 어떤 값을 넣을지 같은 제한된 결정을 연구하는 전문 모델 계열이다.
범용 Agent의 계획·추론을 대체하지 않으며, 소스와 모델 가중치는 별도 배포물이다.
Driver를 쓴다고 CUA-S1을 자동으로 쓰는 것도 아니다.[1]

## 관찰한 대상에만 행동하고 결과를 다시 본다

Driver의 Skill은 정확한 앱과 창을 고르고, 현재 상태를 읽고, 행동한 뒤 사용자 목표가 충족되었는지 확인하는 순서를 요구한다.
`get_window_state`는 지정한 창의 상태를 읽는 도구이고, 접근성 트리는 버튼·입력란처럼 운영체제가 알려주는 조작 요소의 구조다.
Agent는 여기서 얻은 최신 `element_token`으로 대상을 지정한다.
새 상태를 읽으면 이전 요소 참조가 더 이상 유효하지 않을 수 있으므로, 다른 실행에서 나온 번호를 복사해 쓰는 방식이 아니다.[3]

화면의 의미 구조만으로 닿지 않는 대상에는 스크린샷과 좌표가 필요할 수 있다.
이때도 다른 창의 이미지나 보지 못한 화면을 근거로 좌표를 추측하지 말라는 규칙이 있다.
성공 종료 코드만 받는 것으로 끝내지 않고 `verify_state`나 새 관찰로 결과를 확인한다.
실행 결과가 불확실한 행동을 그대로 반복하지 않는다는 점은 저장·입력 같은 작업에서 특히 중요한 경계다.[3]

## 예시로 따라가는 흐름

공식 첫 앱 튜토리얼은 계산기를 열어 `6 × 7`을 입력하고 표시 결과를 다시 읽는 과제를 사용한다.
다음은 공식 문서의 절차를 설명한 것이며 직접 실행한 결과가 아니다.
입력은 숫자식 하나가 아니라 “설치된 계산기 앱을 조작하고 새 상태에서 표시값을 확인하라”는 요청이다.
전제 조건은 Agent, 실제 데스크톱 세션, 사용 가능한 계산기, Driver의 연결과 운영체제 권한이다.[4]

Agent는 앱 목록과 창 목록에서 대상을 찾고, 정확한 프로세스와 창에 대해 상태를 읽는다.
이후 현재 화면에 존재하는 요소 토큰으로 계산기 버튼이나 입력 대상을 조작한다.
앱마다 이름과 버튼 구조가 다르므로 다른 운영체제의 고정된 요소 번호를 재사용할 수 없다.
조작이 끝나면 새 창 상태를 읽어 표시값을 확인하며, 공식 튜토리얼은 `42`가 보이는지와 Agent의 마지막 관찰이 그 값을 보고하는지를 확인하도록 한다.[3][4]

이 흐름에서 산출물은 숫자 답변만이 아니라, 실제 앱을 조작한 뒤 관찰한 결과에 근거한 완료 보고다.
정답을 알고 말하는 것만으로 계산기를 조작했다는 증거가 되지 않는다.
사람은 표시값 외에도 자신의 활성 앱·키보드 초점·마우스 포인터가 유지되었는지 관찰해야 한다.
백그라운드 동작은 가능한 경우에 제공되는 기능이지 모든 앱에서 방해가 없다는 보장이 아니며, 앱을 여는 행위 자체가 창을 앞으로 가져올 수도 있다.[4]

확인이 끝나면 해당 실행을 종료하되 공유 Driver 서비스 전체를 끄는 것과 구분한다.
Skill은 목표를 증명한 뒤 멈추고 그 실행의 `end_session`을 사용하도록 안내한다.
이 글에서는 계산기 화면이나 로그를 생성하지 않았으므로 실제 성공 보고나 성능 수치로 제시하지 않는다.[3]

## 권한은 설치와 별도로 확인한다

macOS에서는 접근성 권한과 화면 기록 권한을 실제 실행 주체에 부여해야 한다.
Driver 문서는 앱 번들로 실행하는 방식, 직접 MCP 프로세스가 실행 기반을 소유하는 방식, 다른 앱 안에 내장하는 방식을 구분한다.
튜토리얼도 설정 창을 여는 것만으로 권한이 허용되지 않으며 해당 항목을 켜야 한다고 설명한다.
`doctor`가 종료 코드 0을 반환해도 데스크톱 준비가 증명되지 않으므로, 권한 상태와 실제 GUI 앱 접근 여부까지 확인하도록 한다.[2][4]

Driver 자체 권한 모드의 기본값 `standard`는 일반 자동화에서 매번 묻지 않는 방식이다.
`bounded`는 검토된 manifest, 즉 허용할 도구·자원 목록으로 범위를 제한한다.
기존 로그인 Chromium 프로필에 붙는 작업은 별도 명시적 허가 대상이며, Driver가 자체 승인 팝업을 항상 띄워 준다고 기대하면 안 된다.
Skill 또한 페이지나 앱의 내용이 행동 권한을 줄 수 없으며 보안 설정을 숨은 준비 작업으로 바꾸지 말라고 규정한다.[2][3]

화면 캡처와 앱 상태에는 열린 문서나 로그인된 화면이 포함될 수 있다.
관찰 결과를 외부 모델로 넘기는 통합을 선택한다면 어떤 화면과 값을 전달할지 먼저 정해야 하며, 토큰·비밀번호를 화면 자료나 로그에 섞지 않는 별도 관리가 필요하다.
여러 세션을 만든다고 하나의 데스크톱에서 초점·키보드·앱 상태가 격리되는 것도 아니다.
공식 Skill은 공유 데스크톱의 제어 주체를 하나로 유지하고, 전경 조작이 필요해져도 기존 허가를 자동으로 확대하지 않도록 한다.[3]

## 원격 자원·비용·라이선스의 별도 경계

Fleets는 로컬 Driver 연결과 다른 클라우드 인증자료와 자원 관리 절차를 요구한다.
데스크톱 사용을 마쳤어도 풀에 유료 용량이 남을 수 있으므로, 작업 종료와 클라우드 자원 삭제를 같은 것으로 보면 안 된다.
Lume 역시 가상 머신 관리 도구라는 이름만으로 원격 접속 설정까지 모두 안전하게 완료된 것으로 판단할 수 없다.
루트 README가 안내하는 첫 Lume 절차에는 SSH 접속과 무인 설정 기본값 확인이 포함되어 있다.[1]

기본 프로젝트와 Driver는 MIT이지만 모든 선택 구성요소가 MIT인 것은 아니다.
`cua-som`에는 AGPL-3.0-or-later 조건이 있고, 별도 `cua-perception` 확장은 AGPL-3.0-only 탐지 모델 등을 조합한다.
Driver 자체는 이 모델 없이도 사용할 수 있다.
확장의 재배포나 네트워크 서비스 제공에는 소스 제공 의무가 생길 수 있으므로, 선택한 모델·확장·의존성의 정확한 배포 조건을 따로 확인해야 한다.[1][2]

## 정리

Cua를 이해하는 출발점은 Agent의 판단, Driver의 조작, 컴퓨터 실행 환경, 평가 도구를 나누는 것이다.
화면을 읽고 행동할 수 있어도 목표 달성은 새 상태로 확인해야 하며, 로컬 권한과 원격 자원·비용·선택 구성요소의 라이선스는 각각 따로 관리해야 한다.[1][2][3]
